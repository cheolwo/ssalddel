# 오행 업무 규칙 Engine 공통 조립 결과

## 결과

주문·음식점·배차·배송·창고의 변하지 않는 업무 의미와 기존 상태 전이 규칙을 `I오행업무규칙Engine`으로 조립했다. 배차는 토(간괘, `GAN`), 배송·운송은 수(감괘, `GAM`)로 분리했다.

엔진 전체의 설명 메타데이터는 토(간괘, `GAN`)를 주축, 수(감괘, `GAM`)를 보조로 고정했다. 간괘는 모듈·전이 경계를 유지하고 감괘는 서버·로컬·Unity 사이의 요청과 상태 사본 흐름을 보조한다. 이 분류는 실행 권위나 자동 명령 라우팅이 아니다.

기존 `업무상태전이Policy`가 새 엔진을 통과하므로 운영 서버와 Simulation Domain의 기존 호출 계약·상태 코드·허용 전이는 유지된다. 엔진은 규칙 판정만 수행하고 DB 저장, 실제 배차, 결제, 알림, Event·Outbox, Unity 객체를 소유하지 않는다.

## 구현 범위

### 공통 규칙

- `오행업무규칙Contracts.cs`: 다섯 모듈 코드, 괘 코드, Descriptor, 판정 요청·결과, Engine·Module 인터페이스
- `오행업무규칙Engine.cs`: 기본 다섯 모듈 조립, 간괘 주축·감괘 보조 Engine Descriptor의 방어적 조회, 업무 흐름·목표 상태 기반 결정적 모듈 선택, 명시 모듈 불일치 차단, 기존 전이 판정 위임
- `업무규칙Policies.cs`: 기존 공개 호환 판정 API를 새 Engine 경유로 변경
- `음식배달업무상태전이Guard.cs`: 운영 서버 Guard가 같은 Engine을 사용하고 시험·조립 시 대체 Engine을 받을 수 있게 보완

### 로컬·원격 Simulation 조립

- `ISimulationFoodOrderRuntime`에 음식점 응답, 배달 미리보기·확정, 수령 미리보기·확정의 다섯 포트를 완성했다.
- `LocalSimulationRuntime`은 기존 Session Aggregate 메서드를 직접 호출한다.
- `RemoteSimulationFoodOrderRuntime`은 같은 포트를 Simulation Server HTTP 경로로 전달한다. 인증과 `HttpClient` 수명은 외부 조립자가 소유한다.
- Simulation Server에 누락됐던 음식점 응답 확정 HTTP 경로를 추가했다.

이는 운영 서버와 Hosted Simulation의 계약을 같게 만든 것이며, 운영 주문 DB를 Simulation으로 복제하거나 Unity가 운영 상태 권위를 갖게 한 것이 아니다.

### Unity의 첫 GameObject 소비

- `음식배달ActorPresentationProjector`가 같은 Session의 최신 Revision, 배달기사 안정 ID, 현재 주문의 단일 상태 사본, 유한 좌표를 검사해 표시 전용 모델을 만든다.
- 주문 상태 이력이 있으면 최신 확정 전이를 같은 `I오행업무규칙Engine`으로 다시 판정해 Engine·Module·괘·의미 판본·규칙 판본을 표시 모델에 싣는다. 이 재판정은 읽기 검증이며 주문 상태를 전이시키지 않는다.
- 기존 `가상배달관찰Controller`는 이 모델이 성공한 경우에만 기사·차량·화물 GameObject 위치와 표시를 갱신한다.
- 오래된 Revision, 같은 Session에서 바뀐 기사 ID, 활동 중 주문 ID 누락, 주문 상태 사본 누락·중복이면 재생을 중지하고 마지막으로 검증된 위치를 보존한다.
- 합성 배달 한 기사 프로필은 기본적으로 첫 주문을 추적하고, 수령 확인 뒤 기사가 거점의 `Idle`로 돌아오면 다음 Tick 전에 재생을 멈춘다. 다음 주문은 상태를 바꾸지 않은 채 대기 상태로 남는다.
- GameObject와 `MonoBehaviour`는 표현 소비자일 뿐 오행 Engine, 주문 원장 또는 배차·배송 권위를 소유하지 않는다.

현재 결속은 `SimulationWorldLocalRuntimeScope`를 사용하는 기존 합성 배달기사 한 명의 최소 slice다. 여러 기사 생성·해제 관리자나 Unity 제품의 Remote Adapter 선택 등록까지 구현한 것은 아니다.

## 검증

- Workflow Rules Contracts·Rules 빌드: 경고 0, 오류 0
- Simulation 솔루션 빌드: 경고 0, 오류 0
- 오행 Engine Descriptor + 기존 Workflow parity: 27/27 통과
- Local·Remote 음식 주문 포트 + 음식 배달 회귀 + HTTP manifest: 31/31 통과
- Simulation HTTP boundary 전체: 11/11 통과
- 괘 분류 관리 Write·Check 및 전용 검사: 133개 기준 통과
- 한 기사 첫 주문의 배차→픽업→전달→수령→복귀, 행위 기록 순서와 Save/Replay 결정성: 1/1 통과
- Unity `가상배달관찰Tests` EditMode: 18/18 통과. 여섯 상태 전이의 Module·괘 의미, 규칙 판본·상태 이력 불일치 차단, 표현 차단 메시지 보존, 한 건 완료 뒤 중단까지 포함한다.
- Unity 생성 시험 프로젝트 빌드: 오류 0. 전체 프로젝트에 이미 존재하는 경고를 포함해 경고 2,064개가 출력됐으며 이번 결과를 무경고 빌드로 확대하지 않는다.
- `git diff --check`: 통과
- 이번 추가 변경 3경로 범위 `Fast`: `git diff --check` 통과 뒤 기존 Simulation Unity 코드 지도 신선도 불일치에서 중단

대상 EditMode 배치 실행 뒤 live Editor 연결 조회는 연결 인스턴스 0개로 반환됐다. 따라서 현재 Game View를 관찰하거나 실제 입력을 재생하지 않았고, 이를 EditMode 성공으로 대신하지 않는다. Editor를 새로 띄우거나 Scene을 열어 이 범위를 넓히지도 않았다.

배치 시험 직후의 별도 `dotnet build --no-restore`는 Unity가 `Temp/obj`의 NuGet 자산 파일을 정리한 상태라 선행조건에서 중단됐다. 복원을 허용한 동일 생성 시험 프로젝트 빌드는 오류 0으로 통과했으므로 이를 소스 컴파일 실패로 세지 않는다.

범위 `Fast`는 빌드·시험 전에 기존 `simulation-unity-code-map` 신선도 불일치에서 중단됐다. 새 Engine·Adapter에는 코드 지도 대상 메타데이터를 추가하지 않았고, 현재 작업 트리에 다른 스레드의 광범위한 메타데이터·생성 지도 변경이 함께 존재하므로 생성 지도를 이 작업에서 강제로 다시 쓰지 않았다. 직접 빌드와 대상 회귀는 위와 같이 별도로 통과했다.

## 남은 실제 연결

- 실제 운영 서버나 Hosted Simulation에 `RemoteSimulationFoodOrderRuntime`을 DI로 선택하는 Unity 제품 조립
- 다수 기사·주문을 안정 ID별 Prefab 수명에 연결하는 생성·해제 관리자
- Unity Play Mode·Game View에서 주문자·음식점·기사 객체가 같은 주문 상태를 연속 표현하는 검증
- 인증·재시도·서버 장애 시 사용자 피드백 정책

이번 작업에서는 운영 DB·MongoDB·MySQL·Event·Outbox를 실행하거나 변경하지 않았고, 실제 기사 배차·배송, Unity Scene·Prefab·Save, Play Mode·Game View를 수행하지 않았다. Unity Editor의 대상 EditMode 컴파일·시험만 실행했다. commit·push도 수행하지 않았다.
