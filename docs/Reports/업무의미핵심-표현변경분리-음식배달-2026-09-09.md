# 업무 의미 핵심과 변경 가능한 표현 분리 — 음식 배달 첫 결속 결과

## 결론

음식 배달의 오래 유지되는 상태 의미와, 정책·화면·Unity 표현처럼 교체될 수 있는 부분을 실제 서버 상태 변경 경로에서 구분했다.

- 음식 배달 서버의 실제 상태 변경 경로는 공통 `업무흐름규칙Catalog`를 반드시 통과하도록 한 내부 Guard로 결속했다.
- 실제 서버 흐름에 존재하지만 공통 규칙에 없던 `조리중 → 기사배정`을 추가하고 음식 배달 규칙 판본을 `food-delivery.v2`로 올렸다.
- HTTP route, 공개 DTO, DB schema, Event/Outbox 계약, 상태 코드, Unity Scene·Prefab·화면은 바꾸지 않았다.

여기서 “변하지 않는 부분”은 소스가 영원히 수정되지 않는다는 뜻이 아니다. 안정 ID·상태 의미·허용 전이·권위 경계를 판본화해, 바꿀 때 영향과 호환성을 명시적으로 검증한다는 뜻이다.

괘나 오행처럼 사람이 업무를 설명하는 분류는 실행 권위가 아니다. 이번 커밋은 그런 설명 메타데이터를 상태 전이 router로 사용하지 않고, 실제 허용 전이는 기존 공통 규칙과 서버 Guard가 판정하도록 한 범위만 소유한다. 같은 작업 트리에 준비된 괘 분류 확장은 이전 미완료 분류 개편과 파일이 겹치므로 이 결과 커밋에 포함하지 않았다.

## 안정 핵심과 변경 가능 부분

| 구분 | 이번에 고정·검증한 것 | 이후 독립적으로 바꿀 수 있는 것 |
| --- | --- | --- |
| 업무 정체성 | 업무 코드, 원천 capability, 계약·규칙 revision | 표시 이름, 설명 문구 |
| 상태 흐름 | 주문대기·조리중·기사배정·픽업완료·전달완료·수령확인과 허용 전이 | 조리 예상 시간, 배차 점수, 위치 감사 임계값 |
| 권위 | 서버 UseCase/Service/Store가 검증 후 상태를 저장 | Unity Prefab, 애니메이션, 카메라, UI 배치 |
| 이관 | Simulation은 공통 규칙·읽기 상태 사본을 재사용 | 표현 보간, 이동 연출, 모델 교체 |
| 운영 효과 | 실제 DB·배차·개인 주소·알림은 Simulation 제외 효과로 명시 | 알림 모양, 화면 갱신 방식 |

정책 역시 아무 제약 없이 바꾸는 영역은 아니다. 허용 전이와 다른 결과를 만들면 새 규칙 판본과 회귀 검증이 필요하다. 반대로 색상·Prefab·애니메이션 변경이 업무 상태를 직접 만들거나 수정해서는 안 된다.

## 음식 배달 첫 결속

### 발견한 중복과 차이

운영 서버는 음식점 수락 후 기사 추천·배정을 먼저 끝내고, 그 뒤 음식점이 픽업 준비를 기록할 수 있다. 이 경우 주문 상태는 `기사배정`을 유지하고 준비 완료는 별도 이력으로 남는다.

기존 공통 규칙에는 `조리중 → 기사배정`이 없었고, 서버의 여러 저장·진행 경로가 자체 조건문으로 상태를 바꿨다. 따라서 “공통 규칙을 Simulation과 서버가 공유한다”는 설명과 실제 서버 전이가 완전히 결속되지 않았다.

### 적용한 구조

1. [공통 업무 규칙](../../Ssalddel.WorkflowRules/UnityPackage/Runtime/업무흐름규칙Catalog.cs)의 음식 배달 판본을 `food-delivery.v2`로 올리고 `조리중 → 기사배정`을 추가했다.
2. 서버 내부 전용 [음식 배달 상태 전이 Guard](../../Ssalddel/Services/Food/음식배달업무상태전이Guard.cs)를 추가했다.
3. Guard는 입력 상태를 기존 코드로 정규화한 뒤 공통 `업무상태전이Policy`만 호출한다. 거부 시 현재·목표 상태, 규칙 판본, 차단 사유를 포함해 닫힌 상태로 실패한다.
4. 다음 실제 변경 지점이 Guard를 통과하도록 결속했다.
   - [음식점 주문 진행 정책](../../Ssalddel/Services/Food/음식점주문진행Policy.cs)
   - [EF 음식 주문 저장소](../../Ssalddel/Services/Food/EfSsalddelFoodOrderStore.cs)
   - [메모리 음식 주문 저장소](../../Ssalddel/Services/Food/InMemorySsalddelFoodOrderStore.cs)
   - [음식 배달 기사 업무 서비스](../../Ssalddel/Services/Dispatch/Recommendation/FoodDeliveryDriverWorkService.cs)
5. 공통 규칙과 서버 Guard를 모든 음식 주문 상태 쌍으로 비교하고, 허용되지 않은 `주문대기 → 기사배정` 건너뛰기를 명시적으로 거부하는 시험을 추가했다.

이 Guard는 새 Workflow 엔진이나 괘 기반 router가 아니다. 기존 서버 저장과 트랜잭션 경계를 대체하지 않고, 그 경계가 공유 상태 규칙에서 벗어나지 못하게 하는 얇은 검증층이다.

이 결과는 합성 계정·메뉴·좌표를 사용하는 로컬 검증이다. 실제 음식점 영업, 결제, 기사 배달이나 Unity 화면 증거가 아니다.

| --- | --- | --- |
| 음식 배달 집중 시험 | 40/40 통과 | 서버·공통 규칙 단위/통합 시험 |

| 범위 Fast·Task | 두 실행 모두 Simulation/Unity 코드 지도까지 통과 후 기존 E 책임 코드 지도 stale에서 중단 | 전체 Fast·Task 통과 아님 |

Fast와 Task의 첫 차단은 현재 작업 트리의 다른 변경까지 포함된 공유 `evidence-responsibility-code-map` 불일치다. 이번 범위를 이유로 그 공유 생성물을 재작성하지 않았다. Task는 이 선행 관문에서 멈춰 뒤의 전체 solution build/test를 다시 실행하지 않았으며, 별도로 완료한 집중·관련 회귀 결과와 구분한다. 시험·빌드에서 관찰된 nullable 및 xUnit 경고는 기존 경로의 경고이며 이번 상태 전이 결속 오류는 없었다.

상세 시험 결과는 `artifacts/local/validation/stable-workflow-food-20260909/`, Docker 결과는 `artifacts/local/verification/food-observer/result.json`에 있다.

## 남은 범위

1. 창고·화물 배차·화물 운송도 같은 원칙으로 감사할 수 있지만, 이번에는 대표 의미 프로필만 등록했고 실행 경로를 새 Guard로 일괄 교체하지 않았다.
2. 배차 점수·거리·재시도·조리 시간처럼 실제로 변하는 정책에는 각각 별도 판본과 근거가 필요하다.
3. Unity는 서버 상태 사본을 읽어 같은 View 컴포넌트의 여러 인스턴스를 표시하는 경계를 유지한다. 실제 Prefab·Actor·경로 이동은 별도 Editor/Play Mode/Game View 검증 대상이다.
4. 취소·환불·재배차·재고 차감·정산은 현재 음식 배달 정상 폐루프와 다른 업무 규칙이다.
5. 이후 설명 메타데이터를 확장할 때도 실제 도메인 결정을 대신하지 않는다는 검사를 유지해야 한다.
