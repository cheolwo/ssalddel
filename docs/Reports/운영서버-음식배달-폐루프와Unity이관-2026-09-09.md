# 운영 서버 음식 배달 폐루프와 Unity 이관 구현 결과

## 결론

운영 서버의 음식 주문을 기준으로 `메뉴 등록 → 주문 → 음식점 수락 → 영속 배차 요청 → 기사 추천·배정 → 픽업 준비 → 픽업 → 전달 → 주문자 수령 확인`을 한 격리 실행에서 끝까지 확인했다.

- 실제 격리 주문 `FOOD-20260909004800418`은 최종 `수령확인 / 배달완료`가 됐다.
- 음식점 수락과 배차 요청은 같은 RDB 트랜잭션에 기록되며, 배차 생성 실패는 기존 Outbox에서 재시도된다.
- 픽업은 기사 배정만으로 진행할 수 없고 음식점의 픽업 준비 기록을 요구한다.
- 기사 위치와 픽업·전달 위치 차이는 감사 증거로 남기되 이번 판본에서는 경고만 하며 업무를 차단하지 않는다.
- 운영 서버와 Simulation Core가 같은 읽기 전용 수명주기 상태 사본을 만들고 Unity가 그 사본만 소비할 수 있는 공통 계약을 추가했다.
- Unity 샘플은 Mongo 문서나 기사 한 명마다 새 `MonoBehaviour` 타입을 만들지 않는다. 같은 `음식배달ActorView` 컴포넌트의 여러 인스턴스가 서로 다른 `actorStableId`와 주문 상태 사본을 표시한다.

이는 실제 음식점 영업·외부 결제·실제 배달이나 Unity Play Mode 화면의 성공 증거는 아니다.

## 구현 범위

### 1. 음식점 메뉴와 주문 입력

- [음식점메뉴관리Controller.cs](../../Ssalddel/Controllers/Food/음식점메뉴관리Controller.cs)는 인증된 음식점 범위에서 메뉴 조회·등록·수정을 제공한다.
- [음식점메뉴관리UseCase.cs](../../Ssalddel/Application/Food/음식점메뉴관리UseCase.cs)는 메뉴 이름 중복과 수정 판본을 검사한다.
- 주문 접수의 기존 메뉴 검증은 공개 음식점·공개 메뉴·품절 여부를 다시 읽고, 클라이언트가 보낸 이름과 가격을 서버 값으로 대체한다.
- 격리 관찰기는 더 이상 DB에 메뉴를 직접 삽입하지 않고 위 API로 세 메뉴를 등록한 뒤 다시 조회한다.

메뉴 삭제와 실제 재고 차감은 이번 범위가 아니다.

### 2. 음식점 수락과 배차 요청의 단절 보완

기존 흐름은 음식점 수락이 먼저 저장되고 후속 Event Handler가 배차대기를 생성했다. 후속 처리 실패 시 수락된 주문과 배차대기 사이에 단절이 생길 수 있었다.

이번에는 다음처럼 바꿨다.

1. [음식점주문수락CommandHandler.cs](../../Ssalddel/Application/Food/Handlers/음식점주문수락CommandHandler.cs)가 음식점 수락과 `FoodDispatchRequest` Outbox 추가를 같은 트랜잭션으로 커밋한다.
2. [음식배차요청OutboxService.cs](../../Ssalddel/Services/Food/음식배차요청OutboxService.cs)가 기존 `음식마트원장동기화_Outbox` 테이블을 별도 처리 유형으로 재사용한다.
3. 즉시 처리가 실패해도 항목은 `Pending`으로 남고 기존 배경 작업이 재시도한다.
4. 기존 음식·마트 원장 투영 처리기는 `FoodDispatchRequest`를 소비하지 않도록 처리 유형을 명확히 제한한다.
5. 배차대기 생성은 기존 멱등 서비스와 원장 투영·실시간 재조회 신호를 그대로 사용한다.

DB schema와 migration은 추가하지 않았다.

### 3. 픽업 준비, 판본, 위치 감사

- 주문 진행 요청에 선택적 `예상Revision`을 추가했다. 오래된 화면의 진행 요청은 현재 상태이력 수와 다르면 거부한다.
- 주문 응답에는 `Revision`과 `픽업준비시각Utc`가 포함된다.
- 기사 픽업 API는 해당 주문의 픽업 준비 이력이 없으면 거부한다.
- [FoodDeliveryLocationAudit.cs](../../Ssalddel/Services/Dispatch/Recommendation/FoodDeliveryLocationAudit.cs)는 위치 없음, 오래됨, 대상 없음, 범위 안, 범위 밖을 결정적으로 분류한다.
- [FoodDeliveryDriverWorkService.cs](../../Ssalddel/Services/Dispatch/Recommendation/FoodDeliveryDriverWorkService.cs)는 픽업·전달 때 위치 감사 결과를 `운송이벤트`에 `AdvisoryEvidenceOnly` 정책으로 기록한다.

좌표 이상은 이번 승인에 따라 경고·증거 우선이다. 실제 차단 반경, GPS 신뢰 정책, 우회 경로는 후속 규칙이다.

### 4. 운영 서버 중심 Unity 이관

- [음식배달수명주기Contracts.cs](../../Ssalddel.WorkflowRules.Contracts/UnityPackage/Runtime/음식배달수명주기Contracts.cs)는 운영 서버와 Simulation Core가 함께 쓰는 읽기 전용 계약이다.
- [음식배달수명주기조회UseCase.cs](../../Ssalddel/Application/Food/음식배달수명주기조회UseCase.cs)와 [음식배달수명주기Controller.cs](../../Ssalddel/Controllers/Food/음식배달수명주기Controller.cs)는 주문자 소유 범위의 서버 상태 사본을 제공한다.
- [Simulation음식배달수명주기Adapter.cs](../../Ssalddel.Simulation.Contracts/UnityPackage/Runtime/Simulation음식배달수명주기Adapter.cs)는 Simulation 상태를 같은 계약으로 옮긴다.
- [음식배달수명주기표현.cs](../../Ssalddel.Unity/Presentation/음식배달수명주기표현.cs)는 상태 사본을 Unity 표시 단계로 바꾼다.
- [음식배달ActorView.cs](../../Ssalddel.Unity/Samples~/FoodDelivery/Runtime/음식배달ActorView.cs)는 오래된 판본을 거부하고 정해진 경로 지점으로 표현 객체를 이동시키는 비권위 샘플이다.

Unity는 주문·배차·배송 상태를 만들거나 수정하지 않는다. 경로 탐색, Prefab 생성, 서버 polling/streaming, Actor 수명 관리도 제품 Scene에 아직 연결하지 않았다.

## 실제 격리 실행

실행 조건은 외부 HTTP를 차단한 전용 Docker MySQL·MongoDB·ASP.NET Core 호스트와 합성 계정·좌표였다. 관찰 Runner가 배차 큐 단계를 직접 변경하던 호출은 제거했고, 관찰 전용 작업자가 기존 운영 배차 전환 서비스를 호출했다.

관찰 결과:

| 항목 | 결과 |
| --- | --- |
| Run ID | `dc756056f03c4aefbcc026896d961c6f` |
| 주문 | `FOOD-20260909004800418` |
| 관찰 시간 | 299.419757초 / 설정 300초 |
| 주문 상태 | `수령확인` |
| 배차 상태 | `배달완료` |
| 메뉴 | 된장국 1개, 합성 판매가 5,000원 |
| 음식 배차 Outbox | `Succeeded`, 시도 1회 |
| 픽업 위치 감사 | `WithinRange`, 0km |
| 전달 위치 감사 | `WithinRange`, 0km |
| Mongo 음식 주문 원장 | `완료`, revision 8 |
| Mongo 운송 원장 | `완료 / 인수완료`, revision 4 |

상태 이력은 `주문대기 → 조리중 → 기사배정 → 픽업 준비 완료 기록 → 픽업완료 → 전달완료 → 수령확인` 순서로 남았다. 픽업 준비 때 이미 기사 배정 상태였으므로 주문 상태는 `기사배정`을 보존하고 별도 이력과 `픽업준비시각Utc`로 준비 완료를 표현한다.

첫 수정판 Docker 기동에서는 관찰 배차 작업자가 전용 schema 생성보다 먼저 조회해 `운송실행투영` 테이블 없음 로그가 발생했다. 실제 주문 시작 전의 일시 기동 문제였으며 폐루프는 완료됐지만, 최종 코드에서는 작업자가 관찰 Runner의 DB 준비 완료를 기다린 뒤 조회하도록 보완했다. 최종 이미지를 다시 빌드해 보존된 완료 DB로 기동했을 때 해당 오류 없이 `Completed` 상태를 재조회했고 컨테이너를 다시 종료했다.

## 남은 실제 연결

1. Unity Editor에서 실제 Prefab 하나에 `음식배달ActorView`를 붙이고 서버 상태 사본 수신과 경로 이동을 Play Mode·Game View로 검증해야 한다.
2. 제품용 Unity client transport는 인증·취소·재연결·중복 메시지·판본 역행을 포함해 별도 결속해야 한다.
3. 픽업·전달 위치 감사의 차단 여부와 허용 반경은 운영 규칙 승인 뒤 정해야 한다.
4. 메뉴 재고·가격·영업시간, 결제·환불·정산, 주문 취소와 기사 재배차는 별도 폐루프다.
5. 격리 관찰 작업자는 운영 Quartz 전체를 켜지 않기 위한 검증 전용 조립이다. 제품 운영은 기존 Operational 배경 작업을 사용한다.
