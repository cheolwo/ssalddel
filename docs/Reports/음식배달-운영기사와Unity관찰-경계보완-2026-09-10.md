## 구현 결과

FDriver는 실제 기사가 인증된 운영 API를 통해 운행 시작·종료, 제안 수락·거절, 픽업·전달을 수행하는 도구로 유지했다. FDriver 조립에는 `IBusinessWorkflowRuntime`이나 `LocalSimulationRuntime`을 추가하지 않았고 기존 `IFoodDeliveryDriverApiService` 경로만 사용한다.

음식 배달 기사 업무공간 응답에 `MaxActiveDeliveries`를 추가했다. 서버의 단일 정책은 최대 진행 중 음식 배달을 3건으로 정하고, 수락 시 이미 확정된 미완료 건수와 새 단건·묶음 요청 수를 합산한다. 기사별 프로세스 관문과 DB `Serializable` 트랜잭션 안에서 다시 계산하며, 초과 요청은 상태를 바꾸기 전에 HTTP 409와 안정 오류 코드 `FoodDeliveryActiveWorkLimitExceeded`로 거부한다. FDriver 화면은 숫자 3을 자체 보유하지 않고 서버 응답을 사용한다.

공통 `BusinessWorkflowRuntimeDescriptor`에는 다음 읽기 전용 경계를 추가했다.

- `AuthorityScopeCode=SimulationSession`
- `ExperienceRoleCode=AutonomousNpcWorld`
- `AllowsOperationalDriverActions=false`
- `ObservationPresentationOnly=true`

Local과 Remote factory 모두 이 계약을 만든다. 여기서 Remote는 운영 음식 배달 서버가 아니라 원격 Simulation Host다. 계약을 벗어난 Runtime은 조립 단계에서 거부한다.

Unity 프로필5는 로컬 자율 NPC 생활 관찰로 유지했다. 프로필6의 격리 검증 서버 관찰은 Editor 또는 Development Build에서만 허용하며 일반 배포 빌드 설정은 거부한다. 휴대폰 화면에는 `가상 NPC 관찰 · 실제 기사 배차 없음`을 표시한다. 새 Scene, Map Manager, Simulation 권위는 만들지 않았다.

## 발견해 보완한 연결 문제

Unity 실제 import에서 EditMode 시험 assembly가 새 `Ssalddel.BusinessWorkflow` assembly를 참조하지 않아 컴파일이 차단되는 문제를 발견해 참조를 추가했다. 이어 음식점 관찰 시험 세 곳이 변경된 주문 업무 포트 대신 상위 Runtime을 넘기던 문제를 현재 `scope.BusinessWorkflow.Orders` 계약으로 맞췄다. 수정 뒤 Unity Editor 컴파일과 집중 시험이 통과했다.

Unity가 연결 package를 import하며 생성한 새 `.meta` 파일은 asset GUID의 반복 생성 방지를 위해 보존했다. 기존에 추적되던 과거 `.meta` 파일은 삭제 상태로 남기지 않고 원래 내용을 유지했다.
