## 2. 범위와 구성

- 기사 수 1~4 및 안정 ID 접두사 변경을 명시 준비 인수로 지원한다. 역할/능력/권한 누락, 중복 ID, 잘못된 표시 키, 범위를 넘는 기사 수는 시작 전에 거부한다.
- 기존 합성 동네 `placement-map-profile:synthetic-neighborhood.v1`의 도형 9개·기준점 44개·통로 14개를 고정 검사한다. 임의 지형·경로 탐색·실제 면목동이 아니다.
- 원본 4개는 합성 배치 맵·Graph Map·승인 부록·대표 작업 명세다. 시작 해시·필드·배치 참조를 검증한 뒤 자기 전용 저장 슬롯을 사용한다. 과거 null 구성의 기존 시나리오/Save·Replay는 보존한다.
- 현재 화면은 큐브·캡슐 기반의 명시 대체 표현이다. Synty NPC/건물, 걷기/운전 애니메이션, 실제 Collider 이동을 구현·검증한 결과가 아니다.
- 개별 건물과 NPC는 분리된 GameObject이나 업무 상태는 C# 세션 객체다. Mongo의 문서가 MonoBehaviour 자체를 저장하거나 그대로 역직렬화하는 방식이 아니다.

Core 전용 도구는 1800 Tick을 빠르게 진행한 것이며 Unity를 30분 재생한 것이 아니다. 보고의 행위 원장은 `ExistingLedgerTailWithCheckpoint_NotEntireSessionAudit`: 기존 최근 기록과 누적 점검점을 사용하며 전 시간대의 완전 감사 로그라는 주장은 하지 않는다.

## 4. 사용하는 순서

현재 내보낸 파일은 다음 위치다. 원시 Mongo 문서를 수동 편집해 ID와 hash를 맞지 않게 만들지 않는다.

`C:/Users/user/source/repos/Hongdal/artifacts/local/offline-life-r1/export/30dab4885d97ed0d1e5ffe4b741955191d8fc67ccbe381b6138b640e38c57a35/bundle.json`

Unity가 정지해 있을 때 `Ssalddel > 오프라인 생활 > 시작 JSON 선택·검사`로 위 파일을 선택한 후, 기존 `SimulationWorldShell`에서 Play한다. 이는 재현 안내이며 이번에 메뉴/Play를 실제 실행했다는 뜻이 아니다. 다른 명시 서버 관찰 프로필이 설정되어 있으면 혼합하지 않고 차단한다. 기존 Scene·Prefab 저장은 필요하지 않다. 프로필 선택은 해당 Editor 프로세스에만 유지된다.

동일 묶음은 같은 저장 슬롯을 이어간다. 이전 슬롯을 지우거나 다른 세션으로 조용히 대체하지 않는다. 새 실험을 분리하려면 시작 전 `SSALDDEL_LOCAL_SAVE_ROOT`를 **새 전용 폴더**로 명시한다. 기본 저장 루트는 Unity `Application.persistentDataPath/Saves`; 보고는 그 아래 `offline-life-reports/<bundleHash>/<reportHash>.json`이다. GUI의 저장·보고 버튼과 별도 반입 도구를 사용한다.

새로운 구성 준비·보관은 기존 도구로만 수행한다(아래 실행 시 로컬 Mongo 접근은 apply/export/report-apply에만 발생).

```powershell
$taskRoot = 'C:/Users/user/source/repos/Hongdal'
$tool = "$taskRoot/eng/Ssalddel.PublicDataPortalImport/bin/Debug/net10.0/Ssalddel.PublicDataPortalImport.dll"
# 선행 build: dotnet build eng/Ssalddel.PublicDataPortalImport/Ssalddel.PublicDataPortalImport.csproj
dotnet $tool local-life-prepare $taskRoot           # 기본 기사 3명
dotnet $tool local-life-prepare $taskRoot 4 demo-   # 별도 ID, 기사 4명 (새 묶음)
# 위 반환의 실제 경로/hash를 사용한다. 임의 예시 hash로 실행하지 않는다.
dotnet $tool local-life-apply $taskRoot $bundlePath $bundleHash
dotnet $tool local-life-export $taskRoot $bundleHash
# Unity 실행 또는 명시적인 Core 전용 시험 중 하나를 선택한다.
dotnet $tool local-life-run $taskRoot $exportPath $bundleHash
dotnet $tool local-life-report-apply $taskRoot $reportPath
```

기사 4명·`audit-` ID의 준비 도구도 실제 실행했고 `40de28ed…704a2abf` 새 파일을 생성했다. 이 두 번째 구성은 Mongo 반입·Unity Play 결과로 세지 않는다. 기존 기본 묶음과 별도 보존했다.

## 5. 다음 단계와 미완료

1. 준비된 파일을 사용하는 실제 Play/Game View: 공간 담당의 단독 실행에서 자동 설치·상태/화면 판독·재진입·Console·종료 보존을 확인한다. 기존 Scene/미소유 변경을 일괄 저장하지 않는다.
2. 표현 개선: 적합한 NPC·식당·창고·차량 후보와 걷기/주행/픽업 동작을 별도 결속한다. 원형 대장에 항목이 있다는 이유로 적합성과 실제 배치를 확정하지 않는다.
3. 범위 확장: 현재 고정 동네 밖 지형, 무제한 NPC, 새로운 창고 정책·일과·경로 탐색은 이후 좁은 규칙/배치 검토다. 5분야의 모든 운영 API를 이관 완료했다고 판정하지 않는다.
4. 완전한 감사 기록/장기 운용: 현재 보고는 최근 기록·누적 점검점이며 전체 이벤트 스트림이나 장기 보관 정책은 별도다. 동일 입력 중복 방지는 확인했으나 Mongo 장애 주입 시험은 하지 않았다. 실행 경로에 Mongo 의존이 없다는 코드 경계와 장애 실험 증거를 구분한다.

운영 서버 요청·실제 주문 생성·기존 동결 현실 UI 입력 교체·Scene/Prefab 저장·새 DB·외부 게시·commit/push 없음. 이번 결과는 **준비/보관/오프라인 Core/Unity EditMode까지 구현·검증, 실제 생활 화면은 미검증**이다.
