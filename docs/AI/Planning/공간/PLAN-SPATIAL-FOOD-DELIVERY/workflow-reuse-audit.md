# 기존 업무 재사용 조사와 구현 관문

2026-09-06 작업 트리 기준. [승인 공간 기획 r1](README.md)의 후속 조사다. 사용자 요청은 창고·주문·음식점 처리·가상 배차를 E4까지 연결하는 것이지만, **이 문서는 권위 WI의 승인 작업 명세나 E4 완료 증거가 아니다.**

## 이번에 추가한 구현 기반 시험

`Ssalddel.Simulation.Tests/Simulation음식배달Tests.cs`에 기존 접수/수령 서비스의 회귀 시험 6건을 추가했다.

- 수량 0과 음수 거부 시 주문·Task·세션 개정이 바뀌지 않는다(2건).
- 같은 CommandId의 수량 변경은 충돌이며 첫 주문을 보존한다.
- 전달 전 수령 Confirm은 실패하고 수령 Task를 만들지 않는다.
- 현재 세션 개정으로 요청해도 오래된 주문 개정의 수령은 차단된다.
- 관찰용 주문 사본·출처 배열·상태 전이 객체 수정이 권위 원장에 반영되지 않는다.

이 시험은 새 주문 생성기나 새 관찰 진행 프로필의 구현 증거가 아니다. 기존 서비스 호출 경계의 회귀 기준선이다. 음식배달 12건과 NPC/공간 관련 15건, 공급망 기존 회귀 25건을 포함한 52건이 통과했다. 공급망 시험에는 기존 영역 간 회귀도 포함되며 새 개발의 필수 선행으로 채택한 것은 아니다. 운영 음식점 수락·진행 및 배차 정책 관련 단위 시험도 15건 통과했다. 실제 운영 API·DB·Unity Editor·Play Mode·Game View는 실행하지 않았다.

Simulation 시험 로그: `artifacts/local/validation/observer-workflow-baseline/simulation-baseline.trx`.

## 구현 전 결속이 필요한 항목

`world-interactions.json`에서 Hub의 기존 WI를 확인했으나, 음식배달 명칭/`FoodDelivery`로 조회한 기존 권위 WI와 현재 Goal·준비 주체 결속은 찾지 못했다. 명칭 검색만으로 다른 의미 ID가 없다고 단정하지 않는다. 기존 ID를 의미별로 재대조한 뒤 연결하고 신규 ID를 임의 발급하지 않는다.

현재 `implementation.md`의 승인 쓰기 범위는 비권위 표현 지원이다. 다음 권위 변경을 그 문서의 승인으로 포괄하지 않는다.

1. 고객 접수와 음식점 수락을 구분할 주문 WI: 메뉴·수량·목적지 검증, 주문자/처리자 역할, 직접 결과, 거절·취소·회복 규칙.
2. 기존 자동 진행과 공존할 명시적 관찰 프로필: 구형 저장의 기본값·해시 유지, 새 프로필의 명령/개정·Save/Replay 결속. 기존 모의 Actor를 기사로 간주하지 않는다.
3. 가상 배정 WI: 준비된 기사·오토바이, 한 주문 점유, 후보와 확정 분리, 차단 시 작업 중단, 취소 시 예약 반환, 수령과 복귀 분리.
4. 각 WI의 승인 기획 revision/hash와 E7 작업 명세, 필요한 전문 연구 기준선. Logic/Presentation E4 증거와 실제 E5 결속을 분리한다.

사용자는 후속 문답에서 **기존 엔진 이관 우선, 식재료 모델 제외**를 선택했다. 앞서 제기한 식재료 예약 반환 질문은 현재 이관의 선행 조건이 아니다. 기존 음식배달 코드에서 확인되지 않은 식재료 예약·소비를 전제해 새 규칙을 추가하지 않는다.

## 우선순위와 완료 기준

1. 기존 엔진의 순수 규칙과 운영 조회를 분리하고, 역할·기존 WI 결속 및 고객 접수→음식점 수락 한 WI의 승인 작업 명세를 만든다. 사용자 입력과 자체 생성 데이터는 같은 Simulation 명령 경계를 통과한다.
2. 기존 Hub 독립 출고 루틴의 재고 수량·예약·취소 회귀와 H 후보를 결속한다. 기존 피킹/포장 자동 전이를 독립 Confirm으로 재작성하지 않는다.
3. 음식점 준비→가상 기사 배정→도로 이동/차단·회복→별도 수령→복귀를 작은 WI로 진행한다. 운영 서비스 호출, 실제 주소/주문/결제/알림은 금지한다.
4. H1 작업점·정차점과 H2 독립 업무 공간의 실제 후보/판본/차폭·진입·시야·대체 표현을 검토한다. 후보 누락은 차단으로 남긴다.

전체 E4 구현은 미완료다. 권위 상태 전이·저장 형식·공개 API·실제 Scene·Goal/E 승격은 변경하지 않았다.

## 승인 후 1차 구현 — 공통 계산 규칙

- `Ssalddel.WorkflowRules/UnityPackage/Runtime/창고출고배분Policy.cs`로 단일 창고 우선·분할 배분·공유 재고 최소 가용량 계산을 추출했다. 운영 `OutboundBatchEngine.CreatePlan`이 이 규칙을 실제 호출한다. 후보 조회·창고 점수·예약 저장은 기존 운영 경계에 남는다. 입력 후보 사전의 순서에 따른 기존 동점 선택도 보존한다.
- 같은 공통 프로젝트의 `음식배달픽업평가Policy.cs`로 조리 예상 시각 대비 조기/적정/지연 판정, 거리·대기 점수와 후보 정렬을 추출했다. 운영 `음식배달배차업무정책`이 이를 실제 호출한다. 배달권 확장·적격성/위치 신선도·후보 조회·배정 확정까지 이관한 것은 아니다.
- 공통 모듈은 DB·외부 경로·현재 시각을 직접 조회하지 않으며 Simulation에서 사용하는 netstandard2.1로 컴파일된다. 시각·거리·후보는 호출자가 제공한다. 기존 서버 API/DTO·운영 저장 동작은 유지했다.
- `운영엔진공통규칙이관Tests`는 독립 모의 입력으로 공통 규칙을 호출한다. 기존 음식배달 회귀 포함 20건 통과. `기존창고배분참조`는 이관 전 HEAD의 순수 계산을 동결한 시험 전용 비교 기준이며 프로덕션에서 사용하지 않는다.
- **아직 미연결:** Simulation 세션의 모의 창고 후보 공급, 음식점 수락→전용 기사 후보 조회→배정, 사용자/생성기 공통 접수, 기사/차량 점유 및 경로 차단·복귀. 공통 계산 시험이 통과해도 이 업무 연결이나 전체 이관 완료를 주장하지 않는다.
- 실제 Unity 자산/Scene 변경은 없다. 시험 로그는 `artifacts/local/validation/observer-engine-transfer/`에 남긴다.
