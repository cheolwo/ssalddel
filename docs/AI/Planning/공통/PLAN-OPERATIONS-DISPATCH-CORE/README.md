## 이 기획이 소유하는 범위

이 기획은 특정 동네나 Unity 장면이 아니라 주문자·음식점·기사·플랫폼이 함께 사용하는 운영 배차 의미를 소유한다. 음식 배달을 첫 사례로 삼되 다른 배차 업무에서 재사용할 수 있는 계약과 판정 경계를 검토한다.

- 기사 신규 배차 수신 의사와 서버의 실제 배차 가능 상태
- 역할별 유효 제안과 수락·거절·무응답
- 수락 뒤 완료·중단·취소와 책임 귀속
- 거절률·수락 후 완료율·시간당 균형 건수
- 영속 원장과 재구성 가능한 Redis 판정 투영의 경계
- 배차 후보의 거리·예상 도착시간·기회 균형 원칙

다음은 다른 기획이 소유한다.

- 실제 앱과 Unity NPC의 권위 분리: `PLAN-ARCH-OPERATIONS-UNITY-TRANSFER-001`
- 같은 장면의 자율 NPC 생활과 카메라 관찰: `PLAN-SYSTEM-OBSERVER-WORLD`
- Simulation의 게임 전용 실패·회복·귀환: 각 PlayableLoop 기획과 Simulation 공통 계약

## 확정

주문자·음식점·배달 기사에게 수락·거절·중단 사유를 허용한다. 거절률은 역할별 `유효 제안`만 분모로 사용한다. 근무·영업시간 밖, 서비스 범위·차량·용량·재고·안전 조건 불일치, 중복·전달 실패와 시스템 오류는 당사자 거절률에 넣지 않는다.

기사 배차 지표는 운영 시장 `Asia/Seoul`의 달력 날짜 기준 `오늘·어제·그제`로 투영한다. 오늘을 주 판단으로 사용하고 어제·그제는 짧은 보조 이력으로 둔다. 정확한 최소 표본·가중치·감점 구간은 아직 정하지 않았다.

기사의 `신규 배차 받기 ON/OFF`는 기사 의사 상태다. ON 구간만 배차 활동시간 후보가 되고 OFF는 신규 제안과 타이머를 멈추지만 이미 수락한 배달은 완료한다. 연결 오류가 기사 의사 ON을 OFF로 바꾸지 않으며, 실제 배차 가능 여부는 별도 서버 상태로 판정한다. 오류·연결 불가 시간은 거절이나 무응답으로 귀속하지 않는다.

배차 판단은 음식점까지 예상 도착시간을 기본 효율로 보고, 유효 후보였으나 선택되지 않은 기사의 기회와 최근 시간당 편중을 보조로 고려한다. 운영자가 설정하는 시간당 약 3~5건은 소프트 균형 목표이고, 동시 수행 안전 상한과 다른 정책이다. 다른 유효 기사가 없으면 6~7건 같은 예외 배차를 허용할 수 있다.

시간당 균형 건수는 기사가 배차를 수락한 순간 주문 1건을 점유한다. 주문자·음식점·플랫폼 책임으로 취소되면 반환하고 기사 책임 중단이면 유지한다. 안전사고·질병·차량 고장처럼 보호가 필요한 중단은 기사 책임으로 자동 확정하지 않는다. 균형 건수, 수락 후 완료율, 동시 수행 안전 상한은 서로 다른 지표다.

운영 완료율과 Simulation 회복은 섞지 않는다. 회복은 이후 Simulation·Unity 공통 계약에서 별도로 다룬다.

화물 기사가 배차를 수락한 뒤 화주가 화물 중량·부피·품목·위험성, 필요한 차량·장비, 상하차 방식·인력, 장소·시간창, 운임·대기료·통행료처럼 운송 부담을 바꾸는 핵심 조건을 변경하면 기존 수락을 그대로 유지하지 않는다. 플랫폼은 변경 전후와 변경 주체·시각을 원장에 남기고 기사에게 차이를 명확히 제시한 뒤 재동의를 받아야 한다. 기사가 변경 조건을 거절하면 이를 기사 거절률·수락 후 미완료율·기사 책임 중단에 넣지 않고 운송은 재배차 대상으로 돌린다. 기사가 이미 이동하거나 대기했다면 실제 발생한 이동·대기에 대한 보전 대상으로 분리하며, 연락처나 현장 안내처럼 운송 부담을 바꾸지 않는 정정만 재동의 없는 수정 후보로 둔다.

플랫폼은 기사에게 휴식·주유·식사·개인 용무 사유를 입력받거나 위치 정지 패턴만으로 이를 추측하지 않는다. 대신 서버가 기사가 현재 책임지는 화물과 한 건의 보유 제안을 `운송 약속 그래프`로 파생한다. 노드는 현재 수행 지점·상차·하차·보유 제안이고, 간선은 순서가 있는 이동 구간이며, 잠긴 목표·최종 도착 한계, 예상·보수 소요시간, 상하차 서비스 시간, 적재량·혼적·차량 제약을 함께 평가한다. 마지막으로 확인된 위치·교통·운송 상태의 관측 시각과 품질을 근거로 남기며 근거가 없거나 오래됐으면 위험을 확정하지 않고 `근거 부족`으로 판정한다.

서버는 이 파생 그래프를 주기적으로 다시 만들고 순회해 모든 수락 화물이 최종 도착 한계 안에 남는지 확인한다. 판정 엔진은 `정상·주의·위험·근거 부족`과 근거만 반환하고 상태를 직접 변경하지 않는다. 권한 있는 UseCase가 최신 원장과 판정 revision을 다시 확인한 뒤 알림·추가 제안 중단·미픽업 보유 제안 반환 같은 효과를 적용한다. 기사의 휴식 여부나 정차 사유 자체는 문제 판정과 불이익의 근거가 아니며, 같은 운송 약속을 지킬 수 있는지가 기준이다.

운송 약속 그래프의 `주의·위험·근거 부족` 판정과 기사에게 보내는 경로 조정 안내는 화주에게 공개하지 않는다. 기사에게는 운행 중 조작을 줄이는 음성 중심 알림을 사용하고 운영자에게는 근거와 판정 revision을 내부 관측으로 남긴다. 화주 화면이나 메시지에는 기사 정차·내부 경로·위험 점수·그래프 순회 결과를 표시하지 않는다.

화주에게는 예측이나 가능성이 아니라 실제 운송 업무 결과가 달라진 경우만 알린다. 도착 약속 범위의 확정 변경, 현재 기사 운송의 중단과 재배차 시작, 운송 불능·취소처럼 화주가 수령 준비나 대체 결정을 바꿔야 하는 상태 전이가 이에 해당한다. 알림에는 내부 위험 단계나 기사 행동 사유를 넣지 않고 `변경된 도착 범위·재배차 진행·운송 불능` 같은 최소 결과와 필요한 다음 행동만 전달한다.

화주에게 지연·재배차 같은 변경 결과를 알린 뒤 새 기사 배차나 경로 회복으로 다시 약속 범위 안에서 진행할 수 있게 되면 `현재 정상 진행 중`이라는 회복 결과도 한 번 알린다. 같은 상태 revision의 회복 알림은 멱등 키로 한 번만 발송하며, 내부 그래프 상태가 반복 순회될 때마다 같은 메시지를 다시 보내지 않는다.

## 기존 코드와의 경계

- 기존 `기사운행시작요청/응답`의 `ShiftId`와 시작 시각을 재사용 후보로 둔다.
- 기존 Redis 기사 상태의 위치·Aging·후보 없음 자료는 입력 후보지만 영속 통계 원장으로 승격하지 않는다.
- `RedisDriverRejectedRequestStore`의 요청 ID 집합은 재추천 방지 자료이지 날짜·사유·유효성·책임을 가진 비율 원장이 아니다.
- `음식배달기사활성업무Policy.MaxActiveDeliveries=3`은 동시 책임 상한이며 시간당 소프트 균형 목표로 대체하지 않는다.
- 첫 구현 후보에서도 기존 공개 DTO·FDriver 화면·실제 추천 점수·Controller·운영 DB·Unity를 자동 변경하지 않는다.
- 2026-09-11 화물 연속 배차의 계약·기사 의사 원장·다음 콜 단일 예약·시간 약속·현재 위치 기반 위험 조회·UseCase·Controller·Memory/Redis 투영과 DriverApp reservation/revision 연결을 구현했다. 기능은 `FreightContinuity:Enabled=false`, `ShadowMode=true`, 운임 정책 비활성으로 시작하며 실제 추천 순위나 운영 배차를 자동 변경하지 않는다. 조건 변경 재동의·보전 원장, 여러 화물의 완전한 약속 그래프 순회와 화주 결과/회복 알림은 후속 수직 구현이다.

## 공통 코어 1차 구현과 후속 범위

사용자의 현 스레드 구현 요청에 따라 다음 중 공통 의미와 비활성 경계만 1차로 구현했다.

1. 기사 의사 ON/OFF와 서버의 실제 배차 가능 상태를 분리한 공유 계약
2. 운영 시장 날짜·Shift·제안·주문·주체·사유를 가진 배차 활동 사건
3. 유효·부적합·전달 실패·보호 사유를 설명하는 유효 제안 판정 결과
4. 수락·거절·무응답·완료·책임별 중단·인계 결과 코드
5. 오늘·어제·그제 일별 집계와 분모 0을 안전하게 처리하는 순수 계산
6. 영속 원장 포트와 재구성 가능한 판정 투영 포트
7. 날짜 경계·유효 분모·책임 제외·중복 사건·자정 이후 완료 귀속 집중 시험

구현 경로는 `Ssalddel.Contracts/Common/Dispatch`, `Ssalddel.Domain/배차`, `Ssalddel/Services/Dispatch/Common`이다. 후속 요청에 따라 MySQL 활동 사건 원장과 한정 마이그레이션, Memory/Redis 판정 투영, 원장 우선 재구성 UseCase, 기사 본인의 수신 상태·명시적 ON/OFF·단기 지표 API를 2차로 연결했다. Redis 오류는 경고를 남기고 원장 응답을 계속하며 범용 활동 사건 쓰기는 외부 API에 노출하지 않는다.

기사 API는 `GET api/v1/driver/operational-dispatch/availability`, `PUT api/v1/driver/operational-dispatch/availability/intent`, `GET api/v1/driver/operational-dispatch/short-metrics`이다. 3차 백엔드 묶음에서는 공통 배차 추천 라운드 시작을 유효 제안으로, 기사 추천 거절을 허용된 공통 사유 코드와 기사 책임으로 같은 DB 저장에 기록한다. 음식 배달 수락과 고객 전달 완료도 각각 해당 상태 변경 트랜잭션에 주문별 사건으로 결속했다. 음식 배달 거절 API는 빈 본문 호환을 유지하면서 선택형 `ReasonCode`를 받을 수 있다. 단기 지표는 같은 유효 제안 분모의 수락률과 거절률을 제공하며, 조회 시 영속 원장을 우선해 당일의 오래된 Redis 투영을 다시 만든다.

4차 백엔드 묶음은 서버 검증을 통과한 음식 주문 등록을 음식점의 유효 제안으로 기록하고, 음식점 수락·거절을 주문 상태 변경과 같은 DB 트랜잭션에 결속한다. 재고 부족·영업시간 외·조리 용량 부족은 뒤늦게 확인돼도 음식점 거절률의 분모와 분자에서 제외하고, 서비스 장애는 보호 사유로 둔다. 음식점은 `GET api/v1/food-orders/restaurant/operational-activity/short-metrics`에서 자신의 오늘·어제·그제 수락·거절 지표를 조회할 수 있다. 역할이 다른 사건은 같은 주문 ID를 사용해도 서로 다른 cohort로 계산하며 기사에게만 수락 후 완료율과 균형 점유를 적용한다.

주문자는 `POST api/v1/food-orders/{orderNo}/cancellation`으로 음식점 수락 전 `주문대기` 단계만 직접 취소할 수 있다. 클라이언트 요청 ID와 예상 revision으로 멱등·동시성 검사를 하며, 주문자 책임 취소와 음식점의 보호된 제안 철회를 주문 변경과 같은 DB 트랜잭션에 남긴다. 공통 음식 배달 상태 규칙은 중단 뒤 조리·픽업대기로 돌아가는 회복 전이까지 포함한 `food-delivery.v4`다. 음식점 수락 이후 취소는 조리비·환불·기사 보상 정책이 정해지기 전까지 자동 허용하지 않는다.

음식점이 이미 조리를 시작했거나 완료했더라도 악천후·기사 부족 등으로 플랫폼 배차가 성립하지 않아 배달 지연 취소가 발생하면, 주문자에게 환불하고 플랫폼이 음식점의 재료·조리 노동 손실 일부를 보상하는 것을 원칙으로 한다. 이를 특정 기사가 제안을 수락하지 않았다는 이유만으로 개인 기사 책임으로 자동 귀속하지 않는다. 음식점 보상액은 전액을 자동 보장하지 않으며 조리 단계·상한·증빙·이의 제기 기준은 후속 문답에서 정한다.

배달 중단 사유는 사고에 한정하지 않고 `음식점 조리 지연·배터리 부족·배달 수단 고장·날씨 문제·개인 긴급 사유·기타`를 포함한다. 음식점이 주문 접수 때 확정한 조리 완료 예정 시각을 10분 넘겨도 픽업 준비가 되지 않으면 기사는 조리 지연으로 현재 배차를 중단할 수 있다. 이 중단은 기사 수락 후 완료율의 분모·미완료 건·거절률·책임 불이익에 산입하지 않고 시간당 균형 점유도 반환한다. 음식점이 확정 예정 시각을 주지 않은 주문의 기준은 후속에서 정한다.

갑작스러운 용변 등 개인 긴급 사유는 운영 시장 `Asia/Seoul` 달력 날짜 기준 하루 1회까지 기사 지표와 불이익에서 제외한다. 두 번째 이후 신고도 곧바로 악용으로 확정하지 않고 일반 책임 판정과 관리자 검토 대상으로 보낸다. 이 보호 횟수와 신규 배차 ON/OFF는 독립적이므로 개인 긴급 중단 뒤 계속 일할지 쉴지는 기사가 직접 결정한다.

조리 지연으로 첫 기사가 배달을 중단한 주문도 보류하지 않고 즉시 새 배차 대기열에 등록한다. 새 기사에게는 일반 주문과 구별되는 `조리 지연 재배차`임을 보여 주고 최신 조리 완료 예정 시각을 함께 제공한다. 새 기사가 수락하면 `수락 시각 + 최소 10분`과 음식점이 갱신한 완료 예정 시각 중 더 늦은 시각을 2차 준비 예상 시각으로 고정해 표시한다. 이 시각은 음식점의 확정 완료를 보장하는 값이 아니라 재배차 기사가 이동·대기 판단에 사용하는 갱신 예상값이며 원래 예정 시각과 변경 이력을 원장에 보존한다.

두 번째 이후 기사도 자신에게 표시된 준비 예상 시각을 10분 넘겨 기다리면 같은 조리 지연 사유로 불이익 없이 중단할 수 있고 주문은 관리자 수동 확인을 기다리지 않고 다시 배차 대기열로 간다. 전국 단위 운영에서 관리자가 모든 반복 지연을 직접 배차하지 않으며 시스템이 재배차 횟수·기사별 대기시간·예정 시각 변경을 누적한다. 반복 지연 사실은 주문자 본인의 주문자 앱 주문 상세에서 보여 주고 주문자는 계속 기다리거나 조리 지연 사유로 주문을 취소할 수 있다.

첫 번째와 두 번째 조리 지연 중단은 주문자 앱 주문 상세의 현재 배차 상태만 조용히 갱신하고 별도 알림·팝업이나 취소 유도를 하지 않는다. 같은 주문에서 세 번째 조리 지연 중단이 발생하면 주문자 앱 내부 알림을 한 번 만들고 `음식 준비가 늦어져 새 기사 배차 중`이라는 최소 상태와 `계속 기다리기·주문 취소` 선택만 보여 준다. 주문자 앱에는 총 지연시간·재배차 횟수·기사별 중단 사유와 내부 판정 이력을 표시하지 않고 외부 문자·카카오톡도 기본 발송하지 않는다.

세 번째 조리 지연 중단에서 주문자 앱 내부 알림을 한 번 보낸 뒤 네 번째 이후 중단마다 알림을 반복하지 않는다. 재배차와 준비 예상 시각은 주문 상세에서 계속 갱신하되 새 알림이나 취소 유도를 누적하지 않는다. 알림 발송 기준은 같은 주문의 조리 지연 중단 횟수로 계산하고 다른 주문의 이력과 합산하지 않는다.

세 번째 알림 뒤 주문자가 아무 선택을 하지 않아도 주문을 자동 취소하지 않고 계속 유효하게 유지해 재배차한다. 주문자가 앱을 계속 보고 있지 않아도 플랫폼이 주문 진행을 이어 가며 배달이 완료되면 정상적인 배달 완료 알림을 보낸다. 주문자 미응답 자체는 취소 동의나 배달 포기로 해석하지 않는다. 주문자가 직접 취소하거나 음식점이 조리 불가능을 확정하거나 배달 자체가 불가능해진 경우에만 별도 취소·환불 규칙으로 종결한다.

총 지연시간·재배차 횟수·기사별 대기시간·중단 사유·음식점 예정 시각 변경과 책임 판정은 권한 있는 운영자만 확인한다. 주문 완료 뒤에도 주문자 앱에는 이 내부 이력을 추가하지 않고 일반 주문·배달 완료 기록만 남긴다. 운영자 조회 권한과 열람 기록은 별도로 관리하며 상세 이력을 주문자나 다른 음식점·기사에게 공개하지 않는다.

운영자는 개별 주문 상세와 함께 음식점별 `오늘·어제·그제 조리 지연 건수·평균 초과시간·재배차 횟수`를 시간대별로 분석한다. 특정 점심·저녁 피크 시간대의 지연이 지속되면 음식점 앱 메시지로 관찰된 시간대와 현재 조리시간 설정을 알려 주고, 예를 들어 15분 설정을 30분으로 넓히는 방안을 권고할 수 있다. 이 메시지는 제재나 자동 설정 변경이 아니며 음식점이 실제 사정에 맞춰 수락·수정·유지할 수 있다. 메시지에는 개별 기사 식별정보를 넣지 않고 사용한 집계 기간·근거·권고값·발송 운영자를 기록한다.

음식점은 기본 조리시간 하나만 두지 않고 `상품 × 시간대`별 조리 예상시간을 설정할 수 있다. 같은 음식도 평상시·점심·저녁 피크에 서로 다른 값을 둘 수 있고 운영자 권고를 수락할 때도 지연이 관찰된 상품과 시간대만 조정한다. 음식점이 설정을 수락·수정·유지한 주체·시각·적용 기간과 이전 값을 이력으로 보존하며 플랫폼이 권고만으로 값을 자동 변경하지 않는다.

플랫폼은 주문 상품·수량·시간대·현재 관찰된 대기 정보를 이용해 `이 시간대에는 보통 약 몇 분 걸렸습니다`라는 평균 조리시간 참고 알림을 음식점에 제공한다. 이 값은 미리 선택되는 기본값이나 확정 권고가 아니며 음식점이 현재 조리 중인 주문과 곧 들어올 업무를 보고 최종 예상시간을 직접 선택한다. 주문 수락 화면에는 `20분·30분` 같은 간단한 시간 버튼을 두고, 음식점이 시간을 선택한 뒤 `수락`을 누르면 그 값이 해당 주문의 조리 완료 예정 시각 기준이 된다. 별도 확인 단계를 하나 더 요구하지 않고 복잡한 상품별 합산이나 긴 숫자 입력도 요구하지 않는다. 플랫폼은 참고 평균·음식점 선택값·수락 시각을 함께 보존한다.

배달기사는 배차 수락 뒤 음식점에 실제로 도착하면 `가게 도착`을 누르고, 서버는 현재 배차·주문 상태를 확인해 서버 수신 시각을 도착 사건으로 기록한다. 이후 `픽업 완료` 사건까지의 시간을 `현장 조리 대기시간`으로 계산해 음식점·상품·시간대 분석에 사용한다. 이 구간은 주문 접수부터의 전체 조리시간이 아니라 기사가 현장에서 기다린 부분이므로 실제 조리시간과 동일시하지 않으며, 단일 측정값만으로 음식점이나 기사를 자동 제재하지 않는다.

주문자가 반복 조리 지연 때문에 취소하면 주문자에게 환불하고 원인을 음식점 조리 지연 책임으로 기록한다. 음식점이 재료를 이미 투입했거나 조리를 상당 부분 마쳤더라도 플랫폼은 해당 취소에 대한 음식점 보상이나 재조리 비용을 지급하지 않는다. 이 사건은 기사 책임과 음식점의 주문 거절률에는 섞지 않고 별도의 조리 지연·주문 취소 사건으로 남긴다.

추천 만료를 기사 무응답으로 자동 기록하는 것은 아직 포함하지 않았다. 기사 수신 의사 ON, 서버 실효 상태, 실제 전달 가능성을 같은 시점에 확인하지 않은 채 만료만으로 기사 책임을 만들지 않기 위해서다. 음식점 수락 이후 주문 취소·환불·보상, 세 번째 조리 지연 주문자 알림·취소 선택, 음식점별 분석·권고 메시지, 화물 완료 자동 사건, 실제 배차 점수 적용, 주문자·음식점 화면, 운영 DB 마이그레이션의 실제 환경 적용, 운영 활성화, Simulation·Unity 투영은 후속이다. DriverApp 화물 작업공간과 FDriver 동시 수행 상한은 서버 계약에 연결했지만 실제 모바일 조작은 검증하지 않았다. `Ssalddel.BusinessWorkflow`와 Simulation 공통 Runtime은 Unity가 가상 세션을 관찰·표현하기 위한 Simulation facade로 유지하며 운영 배차 코어의 쓰기 권위로 합치지 않는다.

## 미정

- 시간당 계산 구간: 시계 기준 한 시간, 운행 시작 기준 구간 또는 다른 구간
- 묶음 배차를 묶음 1건과 주문별 여러 건 중 어느 방식으로 셀지
- 오늘·어제·그제의 최소 표본·가중치와 감점 상한
- 기사 배달 중단의 사후 증빙·통지·이의 제기 절차와 운영자 재정정 횟수
- 음식점이 확정 조리 완료 예정 시각을 여러 번 변경한 경우의 지연 기준
- 장기 조리 지연에서 주문자 앱 밖의 푸시 알림을 예외적으로 보낼 조건
- 음식점별 시간대 집계의 최소 표본·권고 발송 기준과 운영자 조회 보존 기간
- 음식점이 권고를 수락·수정·유지한 결과와 이후 개선 여부를 확인할 기간
- 플랫폼이 여러 상품·수량·피크 혼잡을 조리시간 선택 후보로 계산하는 내부 규칙
- `가게 도착` 누락·지연·오입력의 운영자 정정 절차
- 개인 긴급 중단 하루 1회 이후의 지표 반영과 관리자 판정 기준
- 배달 사고 손실 대응 재원의 적립 기준·지급 한도·회계 및 법률 검토
- 관리자 악용 판정 뒤 기사 통지·소명·이의 제기와 조치 단계
- 조리 시작 전·조리 중·픽업 준비 완료 단계별 내부 보상 비율·상한의 정확한 값과 예외 증빙
- 기본 채널 미확인 뒤 대체 문자로 전환할 정확한 대기시간과 필수 운영 알림의 수신 동의 범위
- 상세 링크의 유효기간·재발급과 기존 링크 무효화 기준
- 중복 송금·고의적 부정 청구 조사에서 사용할 증거·통지·환수 절차의 운영 세부값
- 악천후·기사 부족·배달 지연을 플랫폼 배차 실패로 판정하는 시점과 운영자 이의 제기
- 자동 수락 옵션과 예외 배차 동의 방식
- 기사·음식점·주문자·운영자에게 공개할 지표 범위
- 화물 상차 준비 지연의 무상 대기시간, 대기료 시작 시점·단가·상한과 기사 무불이익 중단 기준
- 수락 뒤 핵심 조건 변경으로 이미 발생한 빈차 이동·현장 대기를 보전할 산정 기준과 지급 주체
- 운송 약속 그래프의 같은 단계 재알림 기준과 기사 음성 알림의 최소 반복 간격
- 그래프 판정이 정상과 주의를 짧게 오갈 때 회복으로 확정할 안정화 기준

## 다음 질문 하나

새 기사가 실제로 배정된 것처럼 영속 업무 상태가 회복되면 즉시 회복 알림을 보내되, 교통 ETA만 좋아진 경우에는 운송 약속 그래프가 연속 두 번 정상으로 판정한 뒤 회복으로 확정할까? 추천은 권위 상태 변화는 즉시 알리고 흔들리는 예측값은 잠시 안정화해 알림 번복을 줄이는 방식이다. 대가는 주기 간격만큼 회복 안내가 늦어질 수 있다는 점이다.
