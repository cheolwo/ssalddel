# 가상 동네 직업 생활 — 구현 결과 r1

[승인 범위](neighborhood-life.r1.md) · [이전 주문 r4](order-ledger-result.r4.md)

후속 화면과 실행·저장 분리는 [관찰·운영 휴대폰 r1](observer-phone-result.r1.md)이 현행이다. 아래 검증은 생활 기반 구현 시점의 기록이다.

## 실행

Unity에서 `Ssalddel → 실행 프로필 → NPC 직업 생활 · 30분`을 선택한 뒤 기존 `SimulationWorldShell`에서 Play, 오른쪽 아래 `휴대폰 → 동네 → 재생`을 누른다. 전용 슬롯은 `synthetic-neighborhood-life-r1-primary`이며 r1~r4 슬롯을 교체하지 않는다. 새 프로필만 1초당 한 Tick, 최대 1,800 Tick이다. 종료 시 미완료 업무를 그대로 저장·정지하며 앱을 닫은 시간은 따라잡지 않는다.

이번 결과는 주민·음식점·마트·보충창고·기사의 **직업 중심 합성 생활 표본**이다. 실제 면목동 GIS, 실제 운영 DB, 실제 주문·요금·정산이나 서버 업무 전체 이관은 아니다.

## 모듈과 책임

| 모듈 | 하는 일 / 인계 |
| --- | --- |
| `가상배달관찰표본.CreateNeighborhoodLife` | 주민 2명·음식점 주인·창고 작업자 2명·배달기사 3명·화물기사 1명, 권한·유한 재고·30분 초기값 |
| `가상동네생활` | 근무 → 수락 업무 마무리 → 휴식점 이동 → 휴식 → 복귀. 기존 업무 원장 식별자를 참조하며 결과를 대신 만들지 않음 |
| 기존 `가상주문흐름`·음식점 응답/조리 | 주민의 음식/마트 교대 주문, 수신함, 실제 음식점 수락 다음 Tick 배차, 조리·준비 완료 |
| 기존 `가상배달대기` | 가까운 가능 기사 선정, 구간·교차점·정차점·출입구 점유, 픽업·주민 수령·복귀 |
| `가상동네보충` | 합성 입고 검수·적치 → 출고 예약·피킹·포장 → 화물 상차·운송·하차 → 마트 검수·재입고 |
| 기존 `SimulationNpcPolicyChangeRequest` | 신규 접수 중단/재개, 조리 시간, 우선순위, 보충 기준, 다음 근무·휴식 주기. 명령·Revision·저장·재생 유지 |
| `가상동네생활해시`·기존 Save/Replay | 생활·물품·예약·점유·정책의 깊은 복제와 결정적 해시 |
| Unity `가상동네생활View` | 같은 Session 상태 사본의 위치·역할색·물품·대기 사유·개별 따라보기·정책 카드 표현 |

업무 상태는 공통 Simulation Core가 확정하며 Unity Transform은 조회 결과만 표시한다. 운영 서버의 `OutboundBatchEngine`과 같은 순수 출고 배분 Policy, 기존 배달 후보·이동 자원 점유 Policy를 재사용한다. 물품은 SKU별 초기 42개(창고 40+마트 2)만 존재한다. 보충 한 건은 4+4개, 화물차 적재 한도 12개이며 이는 단순 수량 적합성이다. 전체 차량 규격·배송권·실제 운임 엔진을 이관했다고 보지 않는다.

## 관찰 규칙

- 기본 근무 420초·휴식 120초. 마감 후 신규 업무는 받지 않고 수락한 업무와 귀환을 마친다. 정책 변경은 진행 중 업무를 취소하지 않는다.
- 주민은 60초 차례마다 음식·마트를 교대로 요청하되 한 사람의 미완료 주문은 합쳐서 최대 한 건이다. 마지막 180초에는 신규 주문/보충을 만들지 않는다.
- 재고 부족은 대기 사유로 남고 창고 → 화물 → 마트 인계 후 기존 주문을 재개한다. 재고 초기화나 무한 보충은 없다.
- 서로 다른 통로는 동시에 사용한다. 이동 구간과 목적 정차점을 함께 얻고, 도보 접근 중에는 도로를 해제하되 정차점과 출입구를 보호한다. 물리 차선·신호등·일반 교착/기아 해결은 미구현이다.
- 차량 정차는 도로 밖 별도 점으로 분리했다. 창고 작업자는 물품 인계 후 포장대로 복귀해 하역 접근점을 비운다.
- 새 프로필에서는 다른 Scene 모듈 세 개의 서버 초기화를 시작 순서와 무관하게 차단한다. 운영 프로필·r1~r4의 분기는 바꾸지 않았다.

## 검증과 남은 관문

- .NET 집중 시험 20/20: 1,800 Tick 전체, 수량 보존, 복수 기사 이동, 준비 전 픽업 금지, 휴식과 배정, 정책 중단 후 기존 업무 완료, 저장·재생·동일 해시, 사본 격리, 과거 프로필 기간 제한, 이전 파일의 선택 필드 누락 호환·변조 차단.
- 최종 Task `20260907-114057`: Simulation·Unity 솔루션 build, Simulation 전체 1,846/1,846, Unity 공용 라이브러리 720/720, 코드·E 책임 지도 검사 통과. 로그는 `artifacts/local/validation/neighborhood-life-*`와 해당 실행 폴더에 있다.
- Unity 최종 컴파일 오류 0, 관련 EditMode 8/8. 새 프로필/슬롯 분리·사본 표현·종료 후 Tick 차단, Runtime 설치 전 무관한 서버 초기화 차단, 과거 선택 필드 없는 파일 복원·변조 차단을 검사했다. `neighborhood-life-editmode.json` 참조.
- 기존 WorldScope 저장·복원·손상 차단 회귀 3/3도 통과했다(`neighborhood-life-save-regression.json`). 첫 시도는 종료된 Play의 메모리 Scope가 남아 프로필 충돌 1건이 있었고, 저장 파일을 건드리지 않고 시험 전 Scope를 해제한 뒤 재검증했다.
- 저장 호환 점검 중 기존 r4 파일을 새 계약으로 재직렬화하면 추가된 null 필드 때문에 checksum이 달라지는 문제를 발견했다. Unity 저장소와 .NET `FileSimulationLocalSaveSlotStore`에서 저장 당시 Package JSON 원문의 checksum을 확인한 뒤 기존 Replay 검증을 유지하도록 수정했다. 파일 checksum을 새로 쓰거나 검증을 생략하지 않았다. 실제 r4·새 생활 슬롯 모두 `VerifySlotAsync` 성공(`neighborhood-life-slot-verification.json`).
- 새 WI 11개, 기존 WI 재사용을 포함한 개별 작업 명세 23개, 주체/기획 hash 결속 검사 통과. 기존 공간 모판은 입력 원장 판본만 갱신했으며 포함 WI 32개와 배치 의미를 늘리지 않았다. E0/승격 비활성 상태를 자동 시험 성공으로 올리지 않았다.
- Unity 실제 r4 기준선은 244 Tick, 음식 수령 4·마트 수령 2, 저장 완료를 관찰했다. 새 생활 프로필은 실제 Play에서 0→126 Tick 진행·저장 후 재진입했고 126 Tick·화물 하차 후 차량 복귀 상태를 복원했다. `RestoredFromSlot=true`, `RecoveredFromBackup=false`(`neighborhood-life-play-resume.json`). 재진입 대기 시간은 진행 Tick에 더해지지 않았다.
- 재진입 후 실제 249 Tick까지 진행해 음식 수령 4·마트 수령 2·보충 입고 1건, 마트 재고 4/4·창고 재고 36/36, 저장 완료·busy=false를 확인하고 Play를 종료했다(`neighborhood-life-play-final.json`). 마지막 Play 구간의 새 Console 오류는 0건이다(`neighborhood-life-console-final.json`). 자동화로 재생 상태를 설정한 Runtime 관찰이며 마우스 버튼 입력이나 Game View 캡처는 아니다. 다음 Play에서는 선택된 30분 프로필의 저장부터 재개한다.

30분 실시간 연속 관찰, 실제 버튼 입력·Game View 문자/카메라 판독, 새 공간의 시각 수용, Hosted/RemoteHost 연결은 별도 미검증이다. 화면 캡처가 필요하면 월드·공간·배치 담당에게 이 프로필·Scene·판본과 음식 픽업/마트 피킹/화물 하차/휴식 시점을 인계한다. Scene 저장·커밋·푸시 없음.
