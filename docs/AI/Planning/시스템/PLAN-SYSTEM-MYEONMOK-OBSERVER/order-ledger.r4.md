# 로컬 주문 원장·음식점 수락·배차 — r4

Approved: 사용자가 서버 주문 저장·수락·배차 후속 처리와 유사하게 Unity에 적용하는 계획을 승인하고 `Implement the proposed plan.`을 요청했다. 기존 r1~r3 저장·명세는 보존한다.

## 서버 대응과 구현 범위

서버 음식주문등록CommandHandler의 멱등 저장→음식점 알림, 음식점주문수락CommandHandler의 멱등 수락→음식점수락후배차대기생성EventHandler, 기존 배차 후보 Policy를 기준으로 한다. 로컬은 기존 Runtime 직렬 명령 경계와 Session의 음식 주문 원장·자동 응답을 재사용한다. EF/DB/SignalR/외부 지오코딩은 추가하지 않는다. NPC 자동 명령은 기존 Core Tick 안에서 실행하며, 수신함은 원장의 조회 결과이지 중복 주문 저장소가 아니다.

음식 주문의 접수 시각 AcceptedTick은 호환 유지한다. r4 연결 기록은 실제 음식점 응답 코드·시각과 배차 큐 등록·기사 배정 정보를 별도로 저장한다. 응답 후 다음 Tick에서 수락된 미등록 주문을 멱등 등록하고 저장 재생 시 같은 후속 처리를 복원한다. 거절은 배차 제외, 담당 NPC 부재는 수신함 대기, 기사 부재는 재탐색 대기다. 배정 직전 주문·기사 상태를 재검사한다. 조리와 배차는 병행하고 도착·조리 완료 모두 충족한 뒤 픽업한다.

주문자 A/B의 첫 시각은1/31 Tick, 간격60 Tick이다. 미완료 음식 주문이 있으면 그 차례를 건너뛴다. 365 Tick 표본에서 남은 시간이180 Tick 미만이면 새 음식 주문을 생성하지 않는다. 마트는 기존 초기 주문3건·재고2개씩·포장 후 배차를 독립 유지한다. 마트 부족 재고는 음식 주문 생성을 차단하지 않는다.

## 주체·WI·공간 결속

기존 주문자 `participant:synthetic:a/b`, 음식점과 조리 NPC, 음식 주문·기사·마트 주체를 유지한다. 기존 음식 주문 등록·음식점 응답·조리·합성 ASSIGN/MOVE/PICKUP/DELIVER/RECEIVE/RETURN의 명령 의미를 재사용하며 중간 전달 기록을 새 플레이 WI로 늘리지 않는다. 승인 r3 공간 기준은 Required/Accepted로 계승한다. 새 건물·경로·역할색은 없고 주문자 상태/음식점 수신함/배차 대기 판독만 추가한다.

## WI별 E7 수직 작업 명세

등록: NPC→주문 원장, 고유 주문번호·접수 시각 확정. 응답: 음식점 NPC→주문, 수락/거절과 시각 확정. 배정: 배차 규칙→가용 기사/주문, 같은 주문에 기사1명 결속. 직접 결과를 먼저 검증하며 플레이어 성장과 외부 효과는 NotApplicable이다. 개별 기존 WI 관문을 새 판본과 재결속하며 E 자동 승격하지 않는다.

Logic E7→E1: 재진입→수락 전/거절/기사부재→공통 LocalProcess/RemoteHost Core→기존 공간→Save/Replay/멱등→접수·수락·배차 분리→주문자/기사 ID. Presentation E7→E1: 실제 화면 판독→알림/대기 표시→기존 Scene→기존 도형→사본 시험→원장 조회→역할색. E1→E7 조립: 연결 계약→주문 발생/응답 기록→배차 후속 처리→저장·해시→UI→회귀. 실제 입력·Game View·Hosted·운영 검증은 별도다.

현 작업실 소유: 합성 주문/배송 partial, 응답의 r4 전용 기록 hook, 사본·해시, 표본·프로필·관찰 Controller, 전용 시험. 신규 r4 저장 슬롯만 사용한다. 저장 실패 시 관찰 재생을 멈추고 저장 성공 전 추가 진행을 차단하며 재시도는 동일 메모리 상태를 저장한다. 상태를 숨겨 성공한 것처럼 표시하지 않는다. 검증: 수락 전 배차 금지, 거절, 미처리 수락 복원, 명령 중복, 담당자/기사 부재, 조리 전 도착, 독립 주문 주기, 저장 실패·재시도, r1~r3 회귀.
