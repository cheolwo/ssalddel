# 주문 원장·수락 후 배차 — 구현 결과 r4

[승인 기획·작업 명세](order-ledger.r4.md) · [이전 마트 r3](mart-center-result.r3.md)

## 실행

Unity의 **Ssalddel → 실행 프로필 → NPC 주문·음식점 수락·배차**를 선택하고 기존 `SimulationWorldShell`에서 Play 후 재생한다. 현재 Editor에는 이 프로필을 선택해 두었으며 Play는 실행하지 않았다. 전용 슬롯은 `synthetic-delivery-r4-primary`다. r1~r3 저장은 보존한다.

## 서버 흐름을 로컬에 대응한 부분

| 서버 | 로컬 구현 |
| --- | --- |
| 음식주문등록CommandHandler → Store 저장 | 기존 음식 주문 Command/Core로 등록하고 Session 원장을 저장·재생 |
| 음식점 신규 주문 SignalR 알림 | 주문 원장을 참조하는 수신함·미확인 건수·주문자 상태 표시 |
| 음식점주문수락CommandHandler | 기존 응답 Command의 성공 시 r4 응답 결과·시각 연결 |
| 음식점수락후배차대기생성EventHandler | 다음 Tick에 수락된 미등록 주문을 찾아 멱등 배차 등록 |
| 후보 선정·배정 서비스 | 공통 Policy 후보 계산 후 Session에서 주문·기사 상태 재검사와 배정 |

`가상주문흐름Snapshot`은 주문 본문을 복제하지 않고 주문 식별자·접수/응답/배차 시각·배정 기사·대기 사유를 보관한다. 기존 `AcceptedTick`은 접수 시각 호환값으로 유지하며 음식점 수락의 근거로 사용하지 않는다. 중간 연결은 별도 메시지 서버가 아니라 저장 가능한 원장 참조 상태와 결정적 후속 처리다. 실제 DB·HTTP·SignalR·외부 지오코딩 호출은 추가하지 않았다.

주문자 A/B는1/31 Tick부터60 Tick 간격으로 음식 주문을 만들며 본인의 미완료 주문이 있으면 건너뛴다. 남은 시간이180 Tick 미만이면 신규 음식 주문을 만들지 않는다. 마트의 포장 후 배차와 재고 부족 대기는 기존대로 유지하되 음식 주문의 다음 차례를 차단하지 않는다. 수락 후 조리·배차를 병행하고 먼저 도착한 기사는 조리 완료까지 기다린다.

## 검증

- Fast `20260907-101736`, Task `20260907-101851` 통과. Simulation·Unity 솔루션 build, 전체 Simulation1837/1837·Unity 라이브러리720/720, 코드 지도·E 책임 지도 strict 검사 통과.
- r4 전용11개 시험: 수락 전 배차 금지, 실제 응답 다음 Tick 등록, 중복 명령/배차 방지, 미완료 주문 제한, 마트 부족과 별개인 음식 주문, 여러 단계 저장·재생/동일 해시, 담당자 부재, 거절, 기사 재탐색, 조리 완료 대기, 저장 실패 전파·동일 상태 재저장. 이전 r1~r3 배송 회귀 통과.
- Unity 컴파일·EditMode5/5 통과. 추가 시험은 r4 프로필/저장 슬롯, 음식점 수신함 표시와 저장 복구 전 Tick 차단을 검사한다. `artifacts/local/validation/order-r4-editmode.json`에 결과 보존.
- 저장 실패 시 관찰 Controller가 재생을 멈추고 재생·단계 진행·새 표본 시작을 차단한다. 수동 저장 재시도 성공 후 해제한다. 이는 관찰 UI의 진행 차단이며 운영 DB 트랜잭션이나 모든 Runtime 호출자의 전역 차단을 의미하지 않는다.
- 수락·배정의 r4 개별 E7 명세 및 주체 결속 검사 통과. 기존 기획 hash와 저장은 보존하며 E 상태는 자동 승격하지 않았다.

**코드·시험 검증 완료 / r4 실제 Play Mode·Game View·Hosted 미검증.** Scene 저장·커밋·푸시·운영 효과 없음. 남은 사항은 기존 한 대 통행 제한, 타 모듈 UI/서버 초기화 격리, 실제 화면의 문자 판독과 입력 확인이다.
