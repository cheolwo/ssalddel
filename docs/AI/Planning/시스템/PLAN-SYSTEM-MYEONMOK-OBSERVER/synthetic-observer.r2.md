## 확정

음식점 1곳·주택 2곳·기사 1명이 있는 합성 City 표본을 먼저 만든다. 관찰자는 재생·일시정지·전체 보기·기사 따라가기를 사용한다. 음식점 NPC는 유효한 모의 주문을 수락하고 조리 자리 1개·2 Tick으로 준비한다. 기사 1명은 주문 하나만 담당한다. 준비와 기사 도착이 모두 충족된 뒤 픽업하며 전달·주문자 수령·복귀는 별도 결과다.

두 주택의 주문 묶음이 수령되고 기사가 복귀한 뒤 다음 묶음을 새 식별자로 생성한다. 차단 중에는 주문을 계속 늘리지 않는다. 1초당 1 Tick으로 재생하고 일시정지·종료 시간은 따라잡지 않는다. 별도 프로필·저장 슬롯으로 재진입하며 기존 수동 음식점 표본과 100 Tick 제한을 조용히 변경하지 않는다.

`Simulation Core → 상태 사본 → Presenter → Unity 표현`을 유지한다. 정산·금액·우천 효과·운영 DB/API·GIS 반입·실내·Blender 고도화는 제외한다. 공식 Scene은 `SimulationWorldShell`이며 다른 영역의 상태를 요구하지 않는다.

## 현재 코드 대조와 순서

- `음식점관찰표본.Create`와 `주문`은 기존 자동 수락·조리 입력으로 재사용한다. 기존 표본은 수동 Tick이며 `RestaurantPreparationOnly=true`다.
- `AdvanceFoodDeliveryForTask`는 `FoodPreparationOnly`일 때 픽업 대기 이후를 실행하지 않는다. 다른 기존 Task의 경과 시간 기반 배송 전이는 새 경로 기반 표본에 재사용하지 않는다.
- `음식배달관찰경로`·`음식배달관찰동선`은 상대 좌표와 보간을 제공하지만 기사 권위 상태를 소유하지 않는다. 경로 끝 좌표가 계산됐다는 사실로 픽업·전달·수령을 확정하지 않는다.
- 등록된 음식점 WI는 `WI-CITY-RESTAURANT-ACCEPT`와 `WI-CITY-RESTAURANT-COOK`다. 기존 `WI-CITY-01~04`는 일반 도심 서비스 의미이므로 배차·픽업·복귀로 전용하지 않는다.
- 다음 구현 순서는 필수 연구 승인 → 기사·차량·주문자·시설의 구체 주체/배송 WI 등록 → WI별 E7 명세 및 파일 소유 결속 → Core 경로·도달·인계/반복/저장 → Unity 표현이다. 연구나 WI를 문서만으로 `Accepted`·`Ready`·E7로 승격하지 않는다.

## 필수 연구와 현재 제한

[합성 공간·표현 기준](synthetic-spatial-study.r1.md)은 `Accepted`이며 차량·도보 속도, 건물/도로/출입구 치수와 가상 배치를 소유한다. 건물·공간·배치·동작 판독 분야를 한 적용 연구로 묶되 각 분야의 조건과 근거를 구분한다. 실내 구조·건설·실제 지형 및 Humanoid Clip 연구는 이번 기본 도형 표본에 포함하지 않는다.

공간 기준 승인 보류는 해제했다. 현재 새 배송 Goal/WI를 자동 등록·활성화하지 않았으며 개별 명세를 결속한 범위만 실제 권위 상태에 연결한다. 독립 지원 모듈의 구현 범위·검증은 [첫 이동 모듈 작업 명세](movement-support.r1.md)로 분리한다. 이 문서는 후속 기획이며 완성된 E7 작업 명세 자체가 아니다.
