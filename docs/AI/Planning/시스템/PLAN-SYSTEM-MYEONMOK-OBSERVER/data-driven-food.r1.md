# 기존 음식 자료로 선택하고 배달하는 동네 r1

기획 ID: `PLAN-SYSTEM-MYEONMOK-OBSERVER` / 판본: `data-driven-food.r1`

상태: Approved / DataSelectionImplemented / IsolatedHttpVerified / GameViewBlocked. 승인: 2026-09-08 `Implement the proposed plan`.

## 목적과 범위

괘상 분류나 추가 수집보다 기존 자료가 NPC의 일로 드러나는 것을 먼저 완성한다. 같은 도형 동네의 주문자·음식점·기사, 공식 `SimulationWorldShell`, 모드·슬롯·마트 내부를 보존한다. 마트 업무와 음식 주문을 같은 원장으로 합치지 않는다.

지금: 명시적 검증 시작과 한 끼 필요. 여기: 기존 음식점·주택·배송 경로. 나: 관찰자. 너: 합성 주문자·음식점·기사와 기존 공개 음식 자료. 이렇게: 자료에서 메뉴를 고르고 기존 역할 API로 주문·조리·픽업·배송·수령을 확인한다.

## 주체와 단일 상호작용 작업 명세

- 준비된 주체: 기존 customer, restaurant, driver-near/far 및 격리 음식점. 대표 상호작용은 `자료 기반 메뉴 선택 → 기존 음식 주문 등록`이다. 기존 배달 검증 흐름을 회귀·통합 묶음으로 재사용한다. 새 Goal/WI/H/공식 Scene은 만들지 않는다.
- 선택 입력: 식사 필요, 선호 메뉴, 검증용 예산, 음식점의 현재 공개·판매 가능 메뉴. 세 후보 이하, 한 개 수량. 동일 입력의 선택은 결정적이다. 다른 후보·불가 사유도 보존한다.
- 직접 결과: 선택한 자료 ID와 실제 메뉴 ID가 동일 주문번호에 결속된다. 원장 수령 확인이 완료를 판정하며 화면 이동이 완료를 만들지 않는다.
- 가격: 기존 5,000원은 검증용 합성 판매가다. KAMIS는 양파 재료의 과거 관측 참고값이며 요리 판매가·원가·실시간 재고가 아니다. 재료 매핑의 자동 매칭 상태도 표시한다. 날짜·지역·단위·출처를 남기고 오래된 자료를 최신으로 표시하지 않는다.
- 공공 자료: 기존 `hongdal_dev`는 읽기 전용 트랜잭션으로만 조회한다. 식약처 이름·자료 ID·체크섬·재료 연결과 KAMIS 참고값만 작은 동결 파일로 내보낸다. 원문 조리법·이미지·개인정보·API 키는 포함하지 않는다. 내부 비공개 검증만 승인하며 공개 게시 권리 검토는 별개다.
- 실패/회복/귀환: 메뉴 자료 없음·손상·예산 초과·판매 불가면 주문을 만들지 않고 이유를 표시한다. 원본 수정이나 대체 도시락 자동 주문 없음. 명시적 재준비·재시작으로 복구하며 자동 반복 주문은 하지 않는다. HTTP 실패는 기존 오류 경계를 따른다.
- Logic E1~E4: 이 명세, 동결 계약, 선택 정책·결속·오류 시험. E5~E7: 격리 MySQL/Mongo/정상 역할 API의 동일 주문·중복 요청·배송 재조회 검증을 분리 기록한다. 운영 실행 승인이 아니다.
- Presentation E1~E4: 기존 도형·Actor ID·휴대폰 카드 재사용. 외부 모델/애니메이션 연구 NotApplicable. 선택 메뉴/이유/출처/기준일을 부가 표시한다. E5 실제 서버 사본 결속, E6 상태 전이·오류 유지, E7 실제 Game View는 개별 증거가 필요하다.
- 쓰기: FoodObserver 실행기·선택 정책·설정·시험, 검증용 내보내기·Compose, Unity 기존 관찰 사본/매핑/휴대폰·시험, 이 문서·PLANNING·CURRENT_WORK. 실제 재조회에서 발견한 기존 주문자 조회의 메뉴 ID 누락을 같은 계약 필드에 결속하고 관련 회귀시험을 보강한다. Graph Map 원본 변경 없음; 기존 노드·경로 재사용.
- 상한: 한 주문의 격리 검증. 실주문·결제·추가 수집·스케줄러·새 공간·마트 자동 입고·commit/push 제외. Save/Replay·Hosted·E8 이상 주장 없음.

## 검증 기록

### 구현

`export-food-observer-menus.ps1`은 기존 로컬 MySQL에서 읽기 전용 트랜잭션으로 자료 3·5·7(방울토마토 소박이·사과 새우 북엇국·된장국)을 추린다. 실제 재료 연결/검토 표식과 활성 가격 매핑을 확인하고 이름·식별자·체크섬·출처·수집일만 내보낸다. 조리법·이미지는 포함하지 않는다. 사본은 `artifacts/local/verification/food-observer/menus.json` 및 `menu-snapshots/{SHA256}.json`에 남긴다. 실행 중 사본 교체는 거부하고 검증 컨테이너에 읽기 전용으로 마운트한다.

`음식자료선택Policy`는 동결 사본 검증과 결정적 후보 선택을 담당한다. 기존 Runner는 현재 격리 음식점 메뉴와 결속해 공개/품절/가격/주문 가능 여부를 확인한다. 기본 선호는 자료7, 메뉴 예산5,000원(배달비를 포함한 총예산 판정은 아님), 필요=true이다. 조건을 충족하지 못하면 `Waiting`으로 주문 없이 종료한다. 같은 실행의 중복 시작을 거부하며 무한 재주문은 하지 않는다. 식약처 메뉴명은 음식점이 실제로 판매한다는 공공 자료가 아니라 **격리 음식점의 합성 판매 후보**다.

기존 음식 주문 API에 메뉴 ID·수량1을 전달하고 중복 요청의 동일 주문번호, 세 역할/원장 재조회에서 메뉴·이름·수량·단가가 같은지 확인한다. Unity r1 계약에는 선택 결과만 선택적 필드로 추가했고 구 r1은 자료를 발명하지 않는다. 기존 휴대폰에 선택 이유·후보·출처·날짜·가격 구분을 추가했다. 공간·모드·Actor/마트는 유지했다.

### 재현

1. 관찰 서버가 정지된 상태에서 `pwsh -NoProfile -File eng/verification/export-food-observer-menus.ps1` 실행. 추가 수집이나 원본 DB 쓰기 없음.
2. `food-observer.ps1 -Action Prepare`, `Build`, `Up` 순으로 전용 호스트 준비. 비밀값은 비추적 기존 연결 파일에만 보존한다.
3. `Status`로 준비 확인 후 `Start`를 명시적으로 한 번 실행. `Result`로 같은 주문 결과를 저장한다. 기존 완료 결과는 호스트 재기동 시 재조회만 하고 자동 실행하지 않는다.
4. Unity 기존 서버 관찰 프로필6에서 기존 `connection.json` 연결을 사용한다. 실제 Game View는 별도 검증하며 메뉴 표시를 위해 새 Scene을 만들지 않는다.
