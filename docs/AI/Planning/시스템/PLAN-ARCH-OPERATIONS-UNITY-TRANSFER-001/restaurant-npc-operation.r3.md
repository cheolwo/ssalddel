# 음식점 NPC 운영과 도로 거리 배차 — 승인 기준선 r3

- 상위 기획: `PLAN-ARCH-OPERATIONS-UNITY-TRANSFER-001`.
- 판본: `restaurant-npc-operation.r3`.
- 기획 상태: `Approved`. 개발 결속 상태: `PendingInteractionBinding`.
- 승인 근거: 2026-09-06 사용자가 조리 자리 수 설정과 가까운 기사 우선을 선택하고, 제시된 NPC 음식점 운영·거리 기반 배달 계획에 `Implement the proposed plan.`으로 구현을 요청했다.
- 이 문서는 종전 수동 대기함 우선 제안을 대체한다. 사용자가 각 주문을 수락하는 것을 기본 흐름으로 삼지 않는다.

## 승인된 행동

1. 유효한 모의 주문은 음식점 NPC가 다음 Simulation Tick에 수락한다. 조리 자리 부족은 거절 이유가 아니다.
2. 조리 자리가 없으면 접수 순서로 기다린다. 동시에 접수한 주문은 안정 주문 식별자로 순서를 결정한다.
3. 설정은 동시 조리 가능 수와 주문당 조리 시간이다. 기본 조리 자리 수는 1, 표본 조리 시간은 기존 2 Tick을 사용한다. 시간 변경은 아직 시작하지 않은 조리부터 적용하며, 자리 수 축소는 진행 중 작업을 취소하지 않는다.
4. 수락한 주문은 배차 대기열에도 등록한다. 음식 준비와 기사 이동은 병행하며 조리 상태와 배송 상태를 서로 덮어쓰지 않는다.
5. 수락 순서대로 배정하며, 배정 가능한 기사 중 음식점까지 통행 가능한 도로 최단 거리가 가장 짧은 기사를 선정한다. 거리 동률은 기사 안정 식별자로 결정한다. 기사 한 명은 주문 하나만 담당한다.
6. 기사 부족·경로 단절이면 사유를 보존하고 대기한다. 배정 뒤 더 가까운 기사가 생겼다는 이유로 자동 교체하지 않는다.
7. 음식 준비와 기사 도착이 모두 충족돼야 픽업한다. 기사 전달과 주문자 NPC의 별도 수령 확인을 분리한다.
8. 전달 후 기사는 대기 지점으로 복귀한다. 경로 폐쇄 시 마지막 유효 위치에 정지하며 순간이동·자동 전달하지 않는다.

## 사용자 경험과 경계

- 지금: 주문이 들어오고 음식점과 기사 업무가 진행된다.
- 여기: Farm·Hub 공급 없이도 실행되는 독립 가상 동네다.
- 나: 관찰하고 음식점 운영 설정을 바꾸는 사용자다.
- 너: 주문자 NPC, 음식점 NPC, 기사 NPC와 각 시설이다.
- 이렇게: NPC가 권위 Core 규칙으로 수락·대기·조리·이동·인계한다. 사용자는 상태와 지연 이유를 읽는다.
- 결과: 음식 준비·픽업·전달·수령이 각각의 조건과 기록으로 확인된다.
- 다음 선택: 혼잡과 대기 이유를 보고 조리 설정을 조정하거나 다른 주문·기사를 관찰한다.
- 대가: 조리 자리 및 기사 점유에 따른 대기 시간이다. 식재료·결제·경험치·개인 자원 비용을 새로 만들지 않는다.
- 실패·회복: 권한 미충족, 기사 부족, 경로 단절을 구별한다. 실패를 모의 성공으로 바꾸지 않고 유효 상태에서 재평가한다.

## 그래프와 배치

- 기존 그래프맵 업무 레이어에 음식점·주문자·기사와 주문·수락·조리·픽업·전달 관계를 결속한다. 업무 관계는 주문 식별자로 추적한다.
- 공간 레이어는 도로 연결점·방향·폐쇄·정차·인계·현관 접근을 구분한다. 업무 노드와 공간 노드는 안정 식별자로 연결한다.
- 배치맵은 Unity 배치의 입력이다. 그래프 위치나 Unity Transform을 별도 업무 권위로 사용하지 않는다.
- Simulation이 기사 경로 판본·위치·진행을 소유하고 Unity는 같은 상태 사본을 표현한다. 기존 경로 표현 코드는 권위 경로 탐색기가 아니다.
- 새 공식 Scene, 실제 GIS·운영 주문·운영 DB·유료 서비스·Blender 작업은 자동으로 포함하지 않는다.

## 구현 전 확인된 실제 차이

- `ConfirmRestaurantResponse`는 현재 수락 즉시 `FoodPreparationOnly` 작업을 예약한다. 수락과 조리 시작을 분리해야 한다.
- 기존 NPC 정책 변경은 자동 처리·우선순위·선호 실행자 등을 다루며 조리 자리 수·조리 시간 변경 계약은 없다. 우선순위 값을 자리 수로 전용하지 않는다.
- 기존 음식배달 상태는 단일 흐름이다. 수락 직후 배정과 조리 병행을 위해 별도 배송 진행 상태가 필요하다.
- 기존 픽업 평가 정렬은 도착 시간대를 거리보다 먼저 고려한다. 이번 가까운 기사 우선 모의 규칙을 운영 정렬에 덮어쓰지 않는다.
- 기존 E4 공간 표본은 기사 1명·주문 1건이다. 기사 2명·주문 3건·주택 2곳으로 논리 검증 표본을 확장해야 한다.

## 증거 상한

승인된 기획과 실제 구현은 별개다. WI/주체·판본/hash·필수 연구·E7 명세를 결속한 뒤 코드 작업을 시작한다. E1~E3 자동시험, E4 후보, 실제 World 결속, Play Mode·Game View, Hosted 연결을 각각 보고한다. 과거 41/41·712/712는 r2 회귀이며 이 r3의 자동 운영 증거가 아니다.
