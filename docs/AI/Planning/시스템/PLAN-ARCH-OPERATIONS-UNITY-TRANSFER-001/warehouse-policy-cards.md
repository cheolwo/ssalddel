# 창고 입고 관찰과 정책 카드 — r1

- 승인 근거: 사용자가 창고 입고부터 순차 구현하고 카드는 기존 설정 화면으로만 제공하는 계획을 선택한 뒤 구현을 요청했다.
- 기준: [이관 기획](README.md), [기존 Hub 입고·검수·적치](../../../../Architecture/PlayableLoops/Hub입고검수적치.md).
- 기존 Hub 기획 파일 SHA-256: `60D069E785FA57AB7FCA3F5DC7C1CF9A4264CA70B415DCA2CA64592E380ADCD3`.
- 범위: 기존 WI-001/002, 기존 R2 NPC 루틴, LocalProcess 정책 입력·재조회와 엔진 독립 카드 표현 로직. 새 상태 전이·식재료·카드 소모 규칙은 만들지 않는다.
- 이 문서는 이번 구현 범위와 E4 후보 인계 기록이다. 기존 Goal·WI 단계나 실제 Unity 배치 승인을 자동 변경하지 않는다.

## 실제 연결

`창고입고관찰표본.Create`는 기존 Hub 모의 입고 300 KGM 표본과 공간 Fixture를 재사용하고 정책을 검수·적치 두 개로 제한한다. 기존 R2 루틴이 검수→적치를 자동 실행하며 출고 정책이 없어 출고로 진행하지 않는다. Farm 생산이나 영역 간 운송 명령 없이 실행한다. 기존 공간 Fixture의 다른 영역 정의가 포함돼 있다는 사실과 업무의 선행 의존성이 없다는 사실을 구별한다.

`창고정책카드Presenter → ISimulationNpcPolicyRuntime → LocalSimulationRuntime → 기존 UpdateNpcPolicy → 권위 세션 재조회`를 연결했다. LocalRuntime의 기존 명령 직렬화 경계를 사용한다. 요청/저장 형식은 기존 `SimulationNpcPolicyChangeRequest`와 Save/Replay를 유지한다. 새 포트는 Unity가 Application/Domain을 직접 참조하지 않도록 Contracts에 둔다.

## 카드 동작과 표현 후보

| 항목 | 동작 |
| --- | --- |
| 카드 두 개 | 입고 검수, 창고 적치. 해당 시설의 기존 정책만 표시 |
| 설정 | 자동 처리, 기존 우선순위, 선호 담당자, 자동 위임. 새 프리셋·비용·덱 없음 |
| 편집·적용 | 편집은 초안. 명시적 적용에서 편집 당시 세션 개정으로 기존 Command 호출 |
| 충돌·실패 | 자동 재시도/덮어쓰기 없이 재조회하고 다시 선택하도록 안내. 재조회 실패는 이전 화면을 성공 결과로 남기지 않음 |
| 작업 정보 | 담당자·작업 단계·차단 코드, 재고별 수량·단위·상태. 다른 단위의 재고를 합산하지 않음 |
| 진행 중 작업 | 자동 처리를 꺼도 기존 진행 규칙을 유지하며 취소·재고 반환으로 해석하지 않음 |

H1은 기존 `h1-stock:hub-receiving-storage`, H2는 `h2-candidate:hub-inbound-storage` 후보를 재사용한다. 정책 카드는 해당 창고 선택 시 여는 보조 설정으로 두고, 건물·NPC마다 새 정책 원장을 만들지 않는다. 카드 VisualKey 후보는 `warehouse.policy.inspection`, `warehouse.policy.putaway`다. E4에는 제목·설정·작업 상태·적용 결과 판독을 준비하고, E5 실제 UI/World 결속은 별도다.

창고 Core/카드 연결 집중 시험 11건과 카드 Presenter 시험 2건 통과. 직접 검수/적치 Confirm 없이 표본이 두 WI만 자동 실행하고 300 KGM을 보존하는 시험을 포함한다. 별도 명령 경로의 차단·재개·Save/Replay도 검증했다. 로그는 `artifacts/local/validation/warehouse-policy-cards/`에 있다. 이는 .NET 시험이며 Unity Editor/Play Mode/Game View 증거가 아니다.

## 남은 작업

## 후속 구현 범위 — 독립 출고 관찰 r1

사용자의 우선순위별 계속 구현 요청에 따라 다음 표본은 기존 보관 완료 재고 300 KGM에서 출고 요청→피킹→포장·출고 대기까지다. `WI-HUB-03/04/05`와 기존 NPC 출고 정책을 재사용하며 별도 상태 전이 엔진을 추가하지 않는다. 첫 입고 표본은 변경하지 않는다. 출고 정책 카드는 명시적으로 선택한 출고 화면에서만 표시한다.

- 논리: 기존 R2/출고 Fixture·정책 변경·자동 Task·Save/Replay 재사용. 초기 자동 처리 해제 시 출고하지 않으며 재개 후 한 번만 실행한다. 진행 중 해제는 기존 작업을 취소하지 않는다.
- 표현: 출고 요청·피킹·출고 준비 상태의 한국어 표시, 카드 입력/재조회. 실제 적재 차량·운송·배송 완료로 표현하지 않는다.
- E4 후보: 기존 출고/임시 대기 H1과 `h2-candidate:hub-fulfillment`를 검토 대상으로 유지한다. 이번 범위는 코드 연결·시험과 표현 준비이며 실제 World 배치는 아니다.
- Blender 방향: 후속 시각 고도화에서 기존 Synty 후보와 대체 자산을 먼저 검토한 뒤 필요한 파생 자산을 제작한다. 동일 객체·접촉·중단/복구·귀환 판독을 함께 검토한다. Blender 파일만으로 실제 Unity 배치·동작 증거를 대체하지 않는다. 지금은 Blender 실행·자산 가공·구매·E 승격을 하지 않는다.

구현: `창고출고관찰표본`이 기존 보관 완료 Fixture와 출고 정책만 선택한다. 입고 표본에 없던 피킹 작업 공간을 기존 정의에서 가져오되 Farm·마트·회랑 정의는 추가하지 않는다. 정책 카드의 `includeOutbound`를 명시한 화면에서만 출고 설정을 노출하고, 기존 기본 입고 화면은 유지한다. 신규 회귀 두 경우는 초기 중단→재개, 진행 중 자동 처리 해제 후 기존 작업 완주, 출고 상태 계보·300 KGM 보존·작업 중복 없음·Save/Replay를 검증한다. 외부 운송 Task는 만들지 않는다.

### 이전 표본의 남은 작업

확장 회귀는 Simulation 31/31, .NET Unity 라이브러리 712/712 통과했다. 문서 링크 2곳과 diff 공백 검사도 통과했다. 공통 Fast·Task는 기존 Simulation/Unity 코드 지도 불일치에서 중단됐으며 전체 통합 검증 성공으로 표현하지 않는다.

- 실제 카드 UI와 창고 배치의 자산 후보 동결·결속, 담당자 표시명과 차단 이유의 상세 한국어 해석.
- RemoteHost는 기존 `npc-policies` 서버 API가 있으나 새 카드 포트의 HTTP 구현은 이번에 추가하지 않았다. LocalProcess 성공을 Hosted 카드 연결 증거로 사용하지 않는다.
- 표본은 초기 모의 입고 한 건이며 지속 주문 생성기·미접속 서버 Tick은 포함하지 않는다.
- 전체 E4/E5 완료·Goal 활성화·Unity 실행·커밋·푸시는 선언하지 않는다.
