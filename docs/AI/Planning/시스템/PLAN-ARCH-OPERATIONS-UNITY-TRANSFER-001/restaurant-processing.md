# 음식점 내부 주문 처리 — 주문 제출·응답 분리 r2

> 현행 후속 기획은 [NPC 자동 운영 승인 기준선 r3](restaurant-npc-operation.r3.md)다. 아래 수동 대기함 우선 제안은 대체됐다. r2 코드·시험 기록은 이력이며 r3 자동 운영 완료 증거가 아니다.

## r3 첫 구현 — NPC 자동 수락

### P0 보완 — 시간 규칙·저장 호환·설정 표시

> 아래 P0 당시 공통 검증 실패는 [후속 검증 복구](../../../../Reports/공통검증복구-2026-09-06.md)에서 해소했다. 최신 Fast·Task와 전체 시험 결과, 별도 남은 작업 명세 불일치는 해당 보고서를 따른다.

- 새 세션의 합산 Tick 요청은 내부에서 한 단계씩 처리한다. 주문 수락·조리 시작/완료·다음 자리 배정이 한 번에 진행한 시간의 끝으로 밀리지 않는다. 외부 명령은 한 번 기록하므로 여러 개의 Tick 명령과 주문 결과·일정은 같아도 세션 개정/명령 원장 전체가 같다는 뜻은 아니다.
- 새 저장에는 `TickRuleRevision=world-tick-step.r1`를 기록하고 hash·저장 복제·재생에 포함한다. 필드가 없거나 빈 값인 기존 저장은 기존 합산 진행을 유지하며 자동 이관하지 않는다. 알 수 없는 판본과 hash를 갱신하지 않은 판본 변조는 거부한다. 저장 봉투의 기존 `SchemaVersion`은 유지하며, 구형 읽기 구현은 새 hash를 호환 검증하지 못하므로 새 저장을 구형 규칙으로 조용히 재생할 수 없다.
- 새 규칙의 턴 마감은 일반 Tick과 음식점 자동 수락→기존 작업 진행→새 자리 배정 순서를 공유한다. 다른 분야의 전체 Tick 처리를 턴 마감에 추가하지 않는다. 구형 저장의 턴 마감에는 음식점 자동 수락·자리 배정을 새로 넣지 않는다.
- 자리 수 `null`은 `미설정·조리 대기`다. 기본값 1은 새 설정 입력용일 뿐 실제 적용된 정책으로 표시하지 않는다. 정책 없음·중복·조회 실패 시 편집을 차단한다. 적용 실패 뒤 재조회하고 명령을 자동 재시도하지 않으며, 재조회도 실패하면 원래 명령 오류를 보존하고 낡은 표시를 지운다.
- [수락 E7 명세](../../../../../eng/execution-ledgers/work-orders/restaurant-auto-accept.e7-work-order.json)와 [조리 E7 명세](../../../../../eng/execution-ledgers/work-orders/restaurant-cooking.e7-work-order.json)는 `interactionGoalStableId`로 주체 기반 원장에 연결한다. 반복 상태·논리/표현 궤적·표현 준비·통합 관문을 E7 v2 양식으로 정리했으며 승인 r3 hash와 E0·승격 비활성을 유지한다. 등록 검사 통과를 실제 E 완료로 바꾸지 않는다.

검증(2026-09-06): 집중 Simulation 78/78, .NET Unity 719/719 통과. 기존 Loop 양식 1건·음식점 명세 2건과 잘못된 Goal/WI/주체/승인/hash/명세/상한/궤적 등 11종 거부 시험이 통과했다. `artifacts/local/validation/restaurant-p0/p0-targeted.trx`, `unity.trx`, `e7-native.log`가 근거다. 합산 진행 1·2·5·7·20 Tick, 구형 필드 없는 저장과 재저장, 턴 마감 재생, FIFO·진행 중 정책 유지·오류 회복을 포함한다.

전체 검증은 미통과다. Simulation 1697개 중 1685개 통과·12개 실패: WI 개수 기대값 108/실제 112, 행위 개수 68/70, 공간 모판의 WI 판본 불일치, Application 코드의 E 책임 누락이다. Fast·Task는 생성 지도 동기화 이후에도 14개 기존 후보의 `EVIDENCE001`에서 중단된다(`20260906-163358`, `20260906-163410` 검증 폴더). 이번 Presenter와 시험의 책임 표기는 보완했지만 다른 후보를 임의 제외하지 않았다.

기존 Loop 작업 명세 8개 중 열원·개인 계획 2개는 `LogicStageDiffersFromPlayableUnit`로 실패한다. 표현 모듈 통합 시험은 생성 문서 불일치로 중단됐다. 생성 검사와 분리해 실행한 내부 연결·증거 계약 시험 42건은 통과했다(`presentation-binding-fixtures.log`, 모의 증거만 사용). 다른 자료의 단계나 생성 상태를 음식점 완료를 위해 임의 수정하지 않았다. 실제 Unity UI/Scene·Play Mode·Game View·Hosted·기사 배정은 이번 결과에 포함하지 않는다.

### 후속 구현 — 조리 자리와 설정 연결

[조리 명세](restaurant-cooking-work.md)에 따라 `WI-CITY-RESTAURANT-COOK`를 등록했다. 음식점 정책의 `CookingSlots`를 명시적으로 설정한 표본에서만 FIFO 자리 배정을 활성화한다. 작업 시간은 기존 `WorkDurationTicks`, 변경 요청은 선택형 `CookingDurationTicks`를 사용하며 미설정 과거 데이터의 해시 입력은 유지한다.

자리를 배정하면 다음 Tick 시작/완료 일정을 고정한다. 설정 변경은 아직 자리를 받지 않은 주문부터 적용하며, 자동 처리 중지는 새 자리 배정만 막는다. 음식 준비 뒤 배차·전달을 자동 실행하지 않는다. 권위 재조회 기반 설정 카드 Presenter를 추가했지만 실제 카드 화면은 아직 없다.

검증: Simulation 45/45, .NET Unity 713/713, WI·주체 등록 검사 통과. 공통 Fast·Task는 기존 코드 지도 불일치로 중단됐다. 실제 Unity·Hosted·E 승격은 미검증이다.

`WI-CITY-RESTAURANT-ACCEPT`와 주체 기반 Goal을 승인 hash에 결속했다. `NpcAutoAccept=true`는 제출 대기 방식에서만 허용한다. 다음 Tick에 해당 음식점의 권한 NPC가 한 번 수락하고 `FoodOrderCookingQueued` 작업으로 조리 대기를 나타낸다. 미응답과 구별할 때 기존 응답 결정 ID와 작업 종류를 함께 읽는다. 조리 자리 배정과 배차를 이 작업에서 실행하지 않는다.

43개 관련 회귀가 통과했다. 무권한이면 주문을 보존하고, 수락 후 여러 Tick이 지나도 조리·배차하지 않으며 저장 재생에서 자동 결정을 중복 생성하지 않는다. 이번 단위는 조리 대기 **진입**까지다. FIFO 자리 배정·설정·기사 이동·화면은 후속이며 r3 전체 구현 완료가 아니다.

- 사용자 요청: 우선순위에 따라 음식점 주문 처리 시작.
- 이번 범위: 기존 모의 주문 접수 Confirm→조리→픽업 대기를 LocalRuntime에서 실행하고 그 뒤 자동 배정/전달을 하지 않는 선택형 처리 방식. 기존 배송 방식은 기본값으로 보존한다.
- 후속 사용자 승인 “진행”에 따라 `AwaitRestaurantResponse=true`와 조리 전용 옵션을 함께 사용하면 주문자 제출 후 대기한다. 해당 음식점의 조리 권한을 가진 모의 NPC만 별도 수락·거절할 수 있다. 실제 운영 사용자 인증을 구현한 것은 아니다.
- 재사용: `Simulation음식배달.cs`, 기존 음식배달 상태 전이 규칙, Decision/Task 및 Save/Replay. 새로운 식재료·운영 주문·실제 기사·결제·알림은 추가하지 않는다.
- 주체: 요청의 기존 주문자·음식점 실행자·시설 고유 식별자를 유지한다. 실행자를 배달 기사로 해석하지 않는다.

## 작업 명세와 증거 상한

| 단계 | 책임 |
| --- | --- |
| E1 | 음식점 접수/조리와 실제 배송 완료를 분리한다. 기존 승인 대화의 음식점 내부 처리 범위만 사용한다. |
| E2 | 기존 Request의 선택형 플래그, 음식점 전용 Task 종류와 LocalRuntime 포트를 연결한다. |
| E3 | 픽업 대기 이후 Tick 불변, 기존 배송 회귀, 요청 재시도·내용 충돌, Save/Replay를 검증한다. |
| E4 | 주문 수량·조리 중·픽업 대기·후속 배정 미연결의 판독 요구를 남긴다. 자산 채택은 하지 않는다. |
| E5~E7 | 실제 음식점 World/UI·입력·동작·Game View 결속은 별도이며 이번에 승격하지 않는다. |

호환: 기본 플래그 false에서는 기존 Task 종류·기간·예상 결과와 요청 멱등 키를 유지한다. 별도 응답 식별자·거절 사유를 스냅샷에 추가했으며 응답이 없는 과거 스냅샷은 기존 해시 순서를 유지한다. 기존 DecisionConfirm 재생 경로를 재사용한다.

남은 기능은 주문 대기함 Unity 화면, 음식점 전용 정책 카드, Hosted 연결·실제 운영 사용자 인증, 기사 배정 인계다. 음식점 전체 이관 완료로 보고하지 않는다.

## r2 구현과 검증

### 다음 단계 사전 확인 — 구현 관문 미결속

- 다음 우선순위 요청에 따라 현재 Goal·주체 원장·작업 명세를 확인했으나 음식점 주문 대기함·정책 카드의 WI, 승인 기획 판본/hash, E7 작업 명세 결속은 확인되지 않았다. 상위 이관 기획의 `ApprovedForHandoff`를 이 화면이나 자동 수락 규칙의 개발 승인으로 확대하지 않는다.
- 제안하는 첫 단위는 **수동 주문 대기함**이다. 음식점별 주문·수량·대기/조리/픽업대기/거절·거절 사유를 읽고, 사용자가 수락 또는 사유를 넣은 거절을 확인하면 기존 응답 명령을 보낸 뒤 권위 상태를 다시 조회한다. 조회 실패·오래된 판본에서는 조작을 막고 새로고침으로 회복한다.
- 자동 수락 정책 카드는 후속 단위로 분리한다. 수락 대상, 동시 조리 제한, 진행 중 정책 변경의 처리 방식은 아직 확정하지 않았으며 클라이언트 자동 클릭이나 새 상태 원장으로 대신하지 않는다.
- 이번 확인은 코드 변경·시험·Scene 작업이 아니다. 첫 단위의 범위를 확정하고 기존 안정 WI 후보와 주체·기획 판본·작업 명세를 결속한 뒤 구현한다.

- 제출 작업은 접수 기록만 남기며 시간이 지나도 조리하지 않는다. 수락하면 기존 조리 전용 작업으로 연결하고 픽업 대기에서 멈춘다. 거절하면 사유를 보존하고 조리·배송을 시작하지 않는다.
- 별도 원장 없이 기존 음식 주문 상태 사본과 Decision/Task를 사용한다. 대기 목록은 음식점 식별자, 미응답, `FoodOrderInboxSubmission` 작업을 기준으로 기존 상태 사본에서 조회할 수 있다. 화면용 조회 모델은 후속 작업이다.
- `AcceptedTick`은 기존 시스템 접수 시각 의미를 유지한다. 음식점 응답 시각은 `RestaurantResponseDecisionStableId`가 연결하는 결정의 `ConfirmedTick`으로 읽는다.
- Application 서비스와 LocalRuntime 응답 포트를 연결했다. 동일 명령 재시도, 이중 응답, 권한, 오래된 세션·주문 판본, 거절 사유와 저장 재생을 시험한다. 모의 NPC 권한 확인은 실제 로그인 권한 확인과 다르다.
- 관련 회귀 41개 통과 기록: `artifacts/local/validation/restaurant-processing/restaurant-inbox.trx`. 실제 Unity 실행·화면 검증·E 승격은 하지 않았다.
- .NET Unity 라이브러리 시험 712/712와 diff 공백 검사 통과. 공통 Fast·Task는 기존 생성 코드 지도 불일치에서 중단되어 전체 통과로 보고하지 않는다. Fast 로그: `artifacts/local/validation/20260906-134534/code-map-check.log`. 다른 작업이 섞인 생성 지도를 일괄 갱신하지 않았다.

## r1 구현과 검증 이력

- `RestaurantPreparationOnly=true`일 때 기존 접수 요청을 `FoodPreparationOnly` Task로 연결하며 기간과 예상 결과를 조리·픽업 대기로 제한했다. 기존 false 값은 배송 생애주기를 유지한다. 음식배달 스냅샷의 기존 배송 기간 필드는 호환 자료이며 이 방식에서 배송을 실행한다는 의미가 아니다.
- `ISimulationFoodOrderRuntime`과 LocalSimulationRuntime의 Preview/Confirm을 연결했다. 기존 명령 직렬화·권위 Core를 재사용하며 운영 API나 DB를 직접 호출하지 않는다.
- 관련 시험 39/39 통과. 픽업 대기 후 추가 Tick 불변, 동일 요청 재시도, 같은 CommandId의 처리 방식 변경 충돌, 수령 차단, Save/Replay와 실제 LocalRuntime 포트 호출을 확인했다. 기존 창고·LocalRuntime 회귀도 포함한다.
- 로그: `artifacts/local/validation/restaurant-processing/restaurant-preparation.trx`. 초기 LocalRuntime 시험의 필수 출처 ID 누락을 보완했으며 유효성 검증 규칙은 완화하지 않았다.
- 실제 Unity UI/Scene·Play Mode·Game View, Hosted 클라이언트 포트 구현, E 승격·커밋·푸시는 수행하지 않았다.
