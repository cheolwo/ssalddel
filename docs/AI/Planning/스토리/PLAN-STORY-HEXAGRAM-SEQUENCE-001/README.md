## 목적

현행 기획 순서는 **괘의 원문·괘상 의미 → 주인공이 겪는 큰 이야기 → 효사 원문 대조 → 구체 사건 각색 → 주체 확립 → WI·직접 결과 → 필요한 H·공간·개발 인계**다. 넓은 이야기를 검토할 때는 효사 칸을 먼저 채우지 않는다. 사용자가 선택한 큰 줄기를 바탕으로 효사의 상황·관계·경계가 어떤 사건으로 드러날지 한 번에 하나씩 문답한다.

Mirror의 메인 스토리를 **역경(易經)의 64괘를 읽고 게임의 상황·주체·변화로 번역하는 기획 과정**으로 제작한다. 괘 하나는 고유한 캠페인이고, 여섯 효는 그 캠페인 안에서 차례로 변하는 여섯 개의 구체 이야기다. 각 괘 내부의 육효는 캠페인 순서를 이루지만, 괘와 괘 사이에는 무기한 자유 생활 구간을 두어 플레이어를 384개의 일직선 퀘스트에 가두지 않는다.

문서도 384효 전체를 미리 만들거나 질문마다 새 파일을 늘리지 않는다. 실제 원문 공부와 문답을 시작한 **괘 하나당 캠페인 `README.md` 하나**만 정본으로 열고, 괘 전체 약속과 육효 상세 절을 같은 판본에서 관리한다. 기존 `LINE-001..006` ID와 경로는 링크·자동 검사·과거 인계를 위한 호환 안내로 보존하지만 별도 본문 정본으로 계속 편집하지 않는다. 별도 동결 명세나 기계 대장은 독립 소비자가 있을 때만 유지한다.

64개 캠페인은 모두 같은 진행·저장·실패 골격을 재사용한다. 개성은 새 시스템을 64개 만드는 방식이 아니라 `핵심 상황·갈등·주체 관계·압박·판정 규칙·완주 변화`의 조합으로 보장한다. 이 조합은 괘마다 하나의 고유 fingerprint를 가지며, 완전히 같은 조합은 검증에서 거부한다.

캠페인 장면의 기본 표현은 관찰이다. 사용자는 개입 가능 순간에 간편 미니게임 또는 현장 직접 조작을 선택할 수 있고, 무입력 시 이안의 자율 행동과 이야기가 계속된다. 연출을 빠르게 넘기는 것과 아직 판정되지 않은 대응을 맡기는 것, 진행 중 캠페인을 포기하는 것은 서로 다른 행위다. 한 괘를 완주한 뒤 다음 괘 진입을 미루고 자유 생활을 계속하는 것은 손실 없는 정상 경로다.

턴 마감에는 최근 핵심 변화, 괘 캠페인 마감에는 진입 전후의 전체 성장·손실·관계, 다음 캠페인 시작에는 이어받는 변화와 미해결 위협을 알린다. 이데아 맵·인벤토리·능력·회복·위협·관계·세계 상태의 실제 기록을 읽으며, 알림 열람이나 스킵만으로 값을 다시 만들지 않는다.

### 효 턴과 자유 생활 구간

이야기의 `효 턴`과 시간 운영의 `절기 턴`을 구분한다. 효사 원문은 해석 근거이고, 효 턴은 그 효에 대응하는 이야기 사건과 이어지는 자유 생활을 묶는 게임 진행 단위다.

```text
현재 효 이야기 시작
  → 핵심 사건·선택·결과
  → 자유 생활 구간
  → 사용자가 효 턴 마감 선택
  → 진행 중 작업·위험 확인
  → 효 턴 변화 결산
  → 다음 효 이야기 시작
```

- 사용자는 핵심 사건 뒤 곧바로 효 턴을 마감하거나, 현재까지 익힌 WI로 농사·벌목·훈련·거래·관찰 같은 자유 생활을 계속할 수 있다.
- 자유 생활은 다음 효를 자동 시작하지 않는다. 사용자가 `다음 효로 진행`을 선택하면 자유 생활 진입을 닫고 안전하게 중단 가능한 작업을 정리한 뒤 효 턴을 마감한다.
- 진행 중 위험·예약 작업·돌이킬 수 없는 손실 가능성이 있으면 마감 전에 보여 주며, 단순히 오래 자유 생활했다는 이유로 캠페인을 실패시키지 않는다.
- 효 턴 결산은 해당 효 이야기 시작부터 자유 생활 종료까지 발생한 실제 변화를 포함한다. 다음 효 시작 알림은 직전 결산의 핵심과 새 이야기 상황만 이어받는다.
- 상효 턴을 마감하면 괘 캠페인 전체 결산 뒤 괘 사이 자유 생활로 들어간다. 다음 괘는 사용자가 별도로 시작한다.
- 효 턴 마감은 절기나 WorldTick을 자동으로 넘기지 않는다. 두 시간축의 정확한 동기화가 필요하면 해당 캠페인 시간 Profile에서 별도로 선언한다.

### 다음 효의 장소 진입 방식

다음 효마다 이동을 강제하거나 항상 순간 이동시키지 않는다. 해당 효 기획이 이동의 의미를 보고 다음 세 방식 중 하나를 선언한다.

- `CurrentLocationContinuation`: 사건이 이안의 현재 장소에서 이어지거나 필요한 인물이 이안에게 온다.
- `StagedRelocation`: 현재의 짧은 행동을 마친 뒤 이동 요약·암전·시간 경과 같은 전환을 거쳐 다음 이야기 장소에서 시작한다. 이동 자체가 핵심 플레이가 아닐 때 사용한다.
- `RequiredArrival`: 길·거리·위험·지리 학습·호송이 이야기의 일부이므로 사용자가 직접 이동하거나 관찰형 자동 이동이 실제 경로를 통과해 목적지에 도착해야 시작한다.

`StagedRelocation`은 근거 없는 순간 이동이 아니다. 출발지·목적지·경과 시간과 알려진 경로를 기록하고, 해결되지 않은 위협이나 이동 비용을 조용히 건너뛰지 않는다. 이동 중 위험이 현재 효의 의미를 바꾸는 경우 `RequiredArrival`로 전환한다. 사용자는 다음 효 시작 전에 진입 방식과 목적지를 확인할 수 있다.

### 효·캠페인 진행 관문

다음 효 또는 다음 괘 캠페인의 시작은 `진행 가능 조건`과 `발동 방식`을 분리한다. 콜라이더에 들어갔다는 화면 사건만으로 이야기를 해금하지 않고, 권위 상태 사본이 조건 충족을 먼저 판정한 뒤 공간 발동이 이야기를 시작한다.

- `StoryStateGate`: 직전 효 완료, 필수 보고·약속·관계 상태처럼 이야기 인과가 끊기지 않았는지 판정한다.
- `WorldStateGate`: 필요한 재고, 건설된 H1~H4, 권한, 동행 주체, 회복되지 않은 핵심 손실처럼 세계의 실제 준비 상태를 판정한다.
- `SpatialActivationTrigger`: `AreaSet` 입구, H 객체 앞, 또는 안정 공간 ID에 결속된 진입 영역을 실제로 통과할 때 준비된 이야기를 발동한다.

공간에서 발동하는 표준 관문은 `AreaSet + 눈에 보이는 H1` 이중 결속이다. AreaSet은 현재 영역과 스트리밍·공간 소유 범위를 확인하고, H1은 플레이어가 찾아가거나 상호작용할 수 있는 구체 대상을 제공한다. 둘 중 하나만 충족해서는 발동하지 않는다. 공간이 필요 없는 내면·대화 전환은 사유를 기록하고 이중 결속을 `NotApplicable`로 둘 수 있다.

관문은 필요한 조건을 `모두 충족`하거나 승인된 대체 조건 가운데 `하나 이상 충족`하는 조합으로 선언할 수 있다. 충족하지 못하면 자유 생활과 이동은 계속되며, 화면에는 부족한 조건과 가능한 해결 방법을 숨기지 않고 보여 준다. 관찰 모드의 이안도 실제 경로·자원·권한 안에서 관문을 충족할 수 있지만, 존재하지 않는 물건이나 건물을 자동 생성하지 않는다.

재고·건설 조건은 플레이 시간을 늘리기 위한 임의 과제로 두지 않는다. 해당 효가 준비·정착·보호·생산 같은 의미를 실제로 요구할 때만 사용하고, 손상·부상·화물 감소처럼 이야기 변형으로 흡수할 수 있는 값은 막힘보다 다음 장면의 상태 차이로 우선 처리한다. `RequiredArrival`은 공간 도착이 의미 있는 경우의 기본 조합이며, 도착 위치는 Graph Map의 안정 노드·엣지와 배치 맵의 발동 영역을 함께 참조하되 어느 쪽도 Simulation 진행 권위를 대신하지 않는다.

첫 표본은 산수몽 육삼에서 육사로 넘어가는 `타운 입구 도착`이다. 육삼의 핵심 호송 사건을 해결하고 이안 또는 관찰형 이동 중인 호송대가 타운 `AreaSet` 앞 진입 영역에 실제 도착하면 육사 시작이 가능해진다. 마차 손상·지연·부상은 육사가 시작될 때 반영할 장면 변화로 남기며, 캠페인의 핵심 목적을 잃은 경우에만 별도 실패·복원 규칙을 따른다. 정확한 타운 입구 안정 ID와 H 결속은 공간 기획 승인 전까지 미정이다.

### 지금·여기·나·너·이렇게 조건 프로필

효·캠페인 진행 관문은 먼저 사람이 이해할 수 있는 다음 문장으로 작성한다.

> 지금, 여기서, 나는 너를 대하며 이렇게 한다. 그 결과가 확인되면 다음 효 또는 캠페인이 열린다.

- `지금`: 현재 효 완료, 절기·WorldTick 구간, 기다린 시간, 기한과 같은 시간·진행 조건
- `여기`: AreaSet과 H1~H4, 경로·경계·도착·귀환과 같은 공간 조건
- `나`: 이안의 회복·위협·역량·권한·장비·개인 인벤토리와 같은 행위 주체 조건
- `너`: 한스·적·작물·건물·마차·창고의 상태와 그 대상이 가진 재고·수락 가능성 같은 대상 조건
- `이렇게`: 요구 WI·ActionRecord·상호작용·비용·도구·관찰·위임·직접 조작 같은 수행 조건

`결과`는 현재 효 완료 사실이고 `다음 선택`은 다음 효·캠페인 또는 자유 생활의 해금이다. 조건마다 `Required / AnyOf / Optional / NotApplicable`을 명시해 모든 효에 시간·건설·재고를 억지로 요구하지 않는다. 사람용 다섯 칸은 개발 인계에서 기존 `StoryStateGate / WorldStateGate / SpatialActivationTrigger`와 실제 행동 기록 검사로 투영한다.

#### 당분간은 효 순서대로 한 줄씩 닫는다

현재 스토리 정밀화는 한 괘 안에서 `초효 → 2효 → 3효 → 4효 → 5효 → 상효`를 선형 기준으로 삼는다. 다음 효를 먼저 세부 제작하지 않고 현재 효를 아래 한 줄로 완결한 뒤 넘어간다.

```text
직전 효 결과
→ 지금(시간·진행 조건)
→ 여기(AreaSet·H1~H4·경로 조건)
→ 나(이안의 상태·권한·장비·인벤토리)
→ 너(NPC·사물·공간·적의 상태)
→ 이렇게(WI·행동 종류·횟수·품질·완료 행동)
→ 결과(권위 상태와 보이는 변화)
→ 다음 효 진입 조건
```

- 효 안에서 관찰·직접 개입·위임과 자유 생활은 허용하되, 캠페인의 주 이야기 순서는 바꾸지 않는다.
- 선택은 손실·관계·숙련·장면 변형을 만들 수 있지만, 별도 승인이 없으면 효를 건너뛰거나 순서를 재배열하지 않는다.
- 다음 효의 조건이 미충족이면 현재 효 이후의 자유 생활을 유지하며 부족한 조건을 보여 준다. 다음 효 사건을 앞당겨 생성하지 않는다.
- 모델링·Blender·배치 필요는 별도 줄거리로 확장하지 않는다. 해당 효의 `여기·너·이렇게·결과`에서 읽혀야 할 H 상태가 있을 때만 표현 요구 카드를 부착한다.
- 표현 요구 카드는 기존 후보를 먼저 연결하고, 부족한 상태 변화·접점·배치 단서만 기록한다. 카드 작성이 제작·배치 또는 E 승격을 자동 실행하지 않는다.
- 자유롭게 떠오른 미래 이야기는 `StorySeed`로 보존할 수 있지만 현재 효의 완료를 방해하거나 정식 제작 커서를 옮기지 않는다.

#### `지금`의 시간 권위와 Sky 판독

`지금`이 오전·오후·일출·일몰·밤처럼 시간대를 요구하면 시간의 판정과 하늘의 표현을 분리한다.

- `TimeAuthorityCondition`: 현재 `WorldTick`, 절기·계절, Nature 권위 시계와 캠페인 상태가 시작 가능 시간과 남은 안전 시간을 판정한다. 실제 시계의 고정 시각이나 Unity 프레임 시간을 권위로 사용하지 않는다.
- `SkyReadabilityCue`: 기존 `월드시간대Presenter`와 `SkyEnginePresenter`가 태양 고도, 직사광 색, 환경광, 그림자 길이, 하늘색과 날씨를 조합해 현재 시간대를 관찰 가능하게 보여 준다.
- `AlternateReadabilityCue`: 흐림·비·실내·색각 접근성처럼 하늘만으로 판독하기 어려운 경우 시간대 이름, 남은 시간, 일몰 임박 경고를 함께 제공한다.
- Sky Engine은 카메라 전역 표현 계층이며 진행 권위나 H1~H4가 아니다. 하늘이 일몰처럼 보여도 권위 상태가 조건을 충족하지 않으면 효를 시작하거나 완료하지 않는다.
- 일몰 기준은 계절과 권위 시계에서 파생한다. 효사 기획에 별도 Sky 모델·외부 플러그인·공식 Scene·Blender 자산을 자동 요구하지 않는다.

효사 문서에는 필요한 경우 `지금` 아래에 위 세 필드를 기록한다. 실제 Sky 결속과 Game View 판독은 해당 구현·표현 단계의 별도 증거로 검증한다.

#### 384효의 대표 `지금·여기·나·너·이렇게` 카드

각 효는 이야기 문장만이 아니라 그 효를 다른 효와 구별하는 대표 상황 카드 하나를 가진다. 카드는 다음 다섯 질문에 답하며, 한 칸에 여러 보조 조건이 있더라도 플레이어가 기억할 대표값 하나를 먼저 적는다.

| 칸 | 대표 질문 | 연결할 기존 체계 |
| --- | --- | --- |
| 지금 | 언제 이 효가 성립하며 어떤 시간 압박이 보이는가? | Simulation 시간·캠페인 상태, 필요 시 Sky Engine 판독 |
| 여기 | 어떤 영역과 H를 어떤 관계·순서로 통과하는가? | AreaSet, Graph Map, 배치 맵, H1~H4, LH 공간 실행계층 |
| 나 | 이 순간 행동하는 주체는 어떤 상태·역량·권한을 가졌는가? | 주체 대장, 이데아 맵, 회복·위협, 장비·개인 인벤토리 |
| 너 | 직접 대하는 사람·사물·시설·위협은 어떤 상태인가? | 상대 주체·대상 상태, 관계, 대상 보유 재고, H 상태 |
| 이렇게 | 무엇을 어떤 방식과 품질로 수행해야 하는가? | WI, Interaction, ActionRecord, 관찰·위임·직접 조작, 필요 시 E6 동작 표현 |

다섯 칸은 새 엔진 다섯 개를 만들라는 뜻이 아니다. 각 효가 기존 체계 중 무엇을 재사용하고 무엇이 비어 있는지 알려 주는 기획 색인이다. 해당 없는 연결은 사유와 함께 `NotApplicable`로 두며, 대표 카드가 완성되어도 Graph Map·배치 맵·Unity·Evidence가 자동 구현되거나 승격되지 않는다.

일반 게임 기획 용어로는 `지금·여기 = 상황 선행조건`, `나·너 = 참여자 선행조건`, `이렇게 = 행동 계약`, `결과 = 사후 상태`에 대응한다. Unity Scene에서 관계와 배치가 자연스러운지는 이 기획 조건을 바탕으로 Graph Map·배치 맵·실제 Scene을 만든 뒤 검증하며, 현재 효사 문답에서 그 결과를 미리 성립한 것으로 간주하지 않는다.

#### `나·너·이렇게` 구분 기준

- `나`: 행동을 시작하기 **전부터** 이안에게 존재하는 사실이다. 역할, 체류·지휘 권한, 회복·부상 상태, 참여 가능한 이동 능력, 장비 보유, 개인 인벤토리가 해당한다.
- `너`: 행동을 시작하기 전부터 직접 대상에게 존재하는 사실이다. 한스의 동행 수락·현재 가용성, 울타리의 손상 상태, 작물의 성숙 상태, 대상 재고와 관계 응답이 해당한다.
- `이렇게`: 준비된 나와 너가 실제로 수행하는 동사와 절차다. 함께 출발하기, 확인점을 순서대로 통과하기, 도구를 사용하기, 비용을 소비하기, 일몰 전에 귀환하기와 그 횟수·품질·완료 기록이 해당한다.

빠른 판정 질문은 다음과 같다.

1. 아무 행동도 하지 않은 현재 순간에도 참인가? 이안의 사실이면 `나`, 대상의 사실이면 `너`다.
2. 선택·입력·위임 뒤 시작되고 진행·완료가 생기는가? `이렇게`다.
3. 도구를 가지고 있는가는 `나`, 그 도구를 특정 대상에 사용한 것은 `이렇게`다.
4. 걸을 수 있는 상태는 `나`, 실제 경로를 걸어 모든 확인점을 통과한 것은 `이렇게`다.
5. 한스와의 기존 신뢰·수락 상태는 `너` 또는 관계 상태이고, 한스와 함께 순찰한 공동 행동은 `이렇게`다.

같은 사실을 여러 칸에 중복 저장하지 않는다. 예를 들어 체류권은 이안에게 부여된 현재 권한이므로 `나`, 한스가 오늘 순찰할 수 있는지는 `너`, 둘이 실제로 함께 귀환했는지는 `이렇게`의 완료 기록과 `결과`가 소유한다.

#### 효사 문답의 구체 질문 카드

기획 담당은 사용자에게 다음 결정을 물을 때 `지금·여기·나·너·이렇게`를 먼저 완성하고, 그 선택이 요구할 제작 범위를 같은 카드에 표시한다. 최소 표시는 `재사용 H1`, `신규 H1 필요`, `상위 H 후보`, `필요 WI`, `Graph Map 영향`, `배치 맵 영향`, `구현 경계`다.

- `재사용 H1`은 현행 안정 ID와 이 장면에서 맡을 의미를 함께 적는다.
- `신규 H1 필요`는 기존 H1로 장면을 읽을 수 없을 때만 제안하며, 불필요하면 명시적으로 `없음`이라 적는다.
- `필요 WI`는 주체가 실제로 수행할 직접 행위별로 나누고 기존 WI 재사용과 신규 후보를 구분한다.
- Graph Map은 노드·엣지 관계 변화만, 배치 맵은 발견 순서·시야·통행·상대 위치 변화만 적는다.
- 아직 사용자가 선택하지 않은 H·WI는 후보이며, 질문 카드만으로 ID 생성·Graph 반영·Unity 배치·E 승격을 수행하지 않는다.
- 마지막에는 추천·이유·대가를 제시하고 사용자가 이번에 결정할 질문 하나만 남긴다.

질문을 시작할 때는 현재 효만 떼어 보여 주지 않고 `괘 전체 흐름 6칸`을 먼저 제시한 뒤 현재 효를 강조한다. 답변은 괘 정본의 해당 효 절만 갱신하지만, 직전 효의 결과·다음 효 인계·괘 완주 변화가 함께 맞는지 검사한다. 효 절마다 명시적 `line-section` 시작·종료 표식과 안정 앵커를 두어 기계 대장이 같은 괘 문서 안에서도 효별 판본 지문을 독립적으로 계산할 수 있게 한다.

`여기`의 공간 연결은 아래 책임을 섞지 않는다.

1. `AreaSet`: 효 사건이 속한 공간 범위와 세계상 영역을 식별한다.
2. `Graph Map`: 출발·경유·도착·귀환 노드와 이동·관찰·작업 관계를 정의한다.
3. `배치 맵`: 같은 노드가 화면에서 발견되는 순서, 상대 위치·방향, 통행 폭, 가림과 시야를 정한다.
4. `H1~H4`: 재사용 가능한 공간 의미와 상향 조립 조건을 나타낸다. 상위 H가 미정이면 기존 H1만으로 효 공간을 기획할 수 있다.
5. `LH 공간 실행계층`: 승인된 공간 의미를 새로 만들지 않고, 현재 관찰·이동에 필요한 셀과 H 내용을 거리·시간·메모리 예산에 맞춰 준비한다.

따라서 효사 문서는 `SpatialScope / RequiredSpatialNodes / RouteIntent / PlacementReadability / LhRuntimeNeed / OpenSpatialGap`을 기록한다. 정확 좌표·Prefab·Collider·셀 크기는 해당 단계가 준비되기 전 기획에서 임의 확정하지 않는다.

#### `이렇게`의 수행량·품질과 예상 성장

`이렇게`는 행동 유무만 기록하지 않고 다음 다섯 값을 필요 범위에서 가진다.

1. `ActionKind`: 벌목·정밀 타격·수리·순찰·몬스터 처치처럼 무엇을 했는가
2. `ValidActionCount`: 승인 대상과 상황에서 몇 회가 유효했는가
3. `QualityMetric`: 타격 정확도·타이밍·피해 억제·도구 효율처럼 얼마나 잘했는가
4. `ContextDifficulty`: 대상 수준·위험·날씨·부상·도움 유무처럼 어떤 조건에서 했는가
5. `OutcomeRecord`: 나무 벌목·시설 수리·적 격퇴처럼 실제 결과가 남았는가

도끼 50회 휘두르기, 유효 타격점에 일정 비율 이상 명중하기, 몬스터 50마리 처치하기는 서로 다른 기획 조건이다. 단순 입력 반복은 결과 없는 숙련으로 과대 계산하지 않으며, 관찰 모드에서 이안이 자율 수행한 행동도 같은 유효성·품질 규칙을 통과하면 동일하게 기록한다.

각 정량 조건에는 진행 역할을 붙인다.

- `StoryRequired`: 효의 인과를 성립시키는 최소 수행이며 미충족 시 다음 효를 열지 않는다.
- `ReadinessRecommended`: 다음 효의 예상 난이도에 맞춘 권장 숙련이다. 미달이어도 진입할 수 있지만 경고·NPC 도움·높은 위험으로 드러난다.
- `OptionalMastery`: 추가 성장·보상·대안 해결을 여는 선택 조건이며 본편을 막지 않는다.

기획 단계에서는 행동별 성장량을 이용해 다음 효 진입 시점의 `Minimum / Expected / Mastery` 예상 수준 구간을 계산한다. 정확 레벨 하나를 강제하지 않으며, 자유 생활·직접 조작·관찰형 진행의 서로 다른 성장 경로를 함께 비교한다. 예상 구간은 밸런스 자료이고 실제 경험치·숙련·레벨의 권위는 ActionRecord를 소비한 성장 시스템에 남는다.

기획 유입은 제작 순서와 별도로 열어 둔다. 사용자가 떠오르는 이야기를 먼저 말하면 그 내용을 `StorySeed`로 보존하고, Codex가 괘 전체의 강한 상황·변화 의미를 기준으로 주괘 하나와 보조 후보를 제안한다. 사용자가 인정하기 전에는 확정하지 않으며, 처음부터 효사 칸에 억지로 넣지 않는다.

사람이 보는 응답과 상태판에서는 기계용 ID만 앞세우지 않고 다음 형식을 사용한다.

```text
[기획 · 역경 64괘 스토리 · PLAN-STORY-HEXAGRAM-SEQUENCE-001 · 제05괘 수천수/초구 · r18]
```

기계용 `PLAN-*`, `HEX-*`, 효 안정 ID는 링크·자동 검사·과거 기록의 호환을 위해 유지한다.

각 효는 정식 순서 전체에서 `PLAN-STORY-HEX##-LINE-###` 형식의 안정 기획 ID를 가진다. 64괘 384효의 ID는 기계 대장에 전부 등록하되, 아직 연구하지 않는 효마다 빈 문서를 384개 만들지는 않는다. 원문 대조·스토리 문답 또는 요구사항 검토를 시작하면 해당 괘 정본을 열고, 효는 정본 안의 안정 절 앵커로 관리한다.

```text
Mirror 메인 스토리
├─ 제1괘 건·제2괘 곤: 각각 여섯 개의 짧은 실제 플레이 비트를 가진 서막 캠페인
└─ 제3괘 수뢰둔 이후: 본격 캠페인
   └─ 효사 기획(Line Plan): 인물·장소·사건으로 드러나는 번호 있는 여섯 변화 후보
      └─ 사건 마디(Story Beat): 플레이어가 알아차리고 선택하는 한 인과
         ├─ 하위 기획: 지금·여기·나·너·이렇게·결과·다음 선택
         ├─ 준비된 주체 → WI 하나·직접 결과 → 선택적 PlayableLoop
         ├─ H·Graph Map·배치 맵
         └─ Logic·Presentation·Evidence
```

기존 `Act→Chapter`는 삭제하지 않는다. 장과 장면은 탐색·출판·과거 링크를 위한 호환 묶음으로 유지하며, 새 스토리 제작 권위는 `괘→효`가 가진다.

- 효사에서 참조하는 H는 [역경 효사 기획 H 통합 참조 색인](../../../generated/hexagram-h-reference-index.md)으로 모은다. 이 색인은 새 H 채택이나 배치를 수행하지 않는다.
- 기존 기획 중 스토리·규칙·플레이어가 보는 공간·사건처럼 플레이어 경험에 해당하는 27개만 우선 후보 분류했다. 기술·운영·자료 조사·순수 개발 절차는 괘 분류 대상에서 제외한다.
- 후보 분류는 주괘 하나와 순위가 있는 보조 후보 최대 두 개를 가진다. `Candidate`는 Codex의 제안이고, 사용자가 확인한 한스 농장 표본만 `Confirmed`다.

## 64괘 캠페인 정체성 대장

[역경 64괘 캠페인 정체성 대장](../../../generated/hexagram-campaign-identities.md)은 육효를 세밀하게 쓰기 전에 64개 전체의 차이를 비교하는 기준선이다.

- 기존 대장은 괘별 차이를 비교하는 기계 정본이다. [괘 의미별 큰 이야기 제안](괘의미별-플레이스토리-큰줄기.md)은 같은 기획 ID 아래에서 인물의 욕망·사건·전후 인과를 연결하는 사람용 `Proposed` 본문이다. 두 자료가 다르면 기존 승인 이야기를 먼저 보존하고 재검토 항목으로 기록한다.
- 먼저 64개 전체의 큰 흐름을 얕게 검토하고, 선택한 괘의 줄거리에 합의한 뒤 정식 제작 순서에 따라 효사 문답을 깊게 진행한다. 제안서의 8개 이야기 묶음은 읽기용 구분이며 새로운 캠페인·해금·개발 관문이 아니다.
- 캠페인 하나는 `핵심 상황`, `대표 갈등`, `주체 관계`, `압박`, `고유 판정 조합`, `완주 변화`를 반드시 가진다.
- WI·H·Graph Map·배치 맵과 공통 시스템은 재사용할 수 있다. 다만 이들을 묶는 목표·압박·관계·판정 조합은 다른 캠페인과 완전히 같을 수 없다.
- 정체성 `Seeded`는 비교 가능한 초안이며 효사 승인이나 개발 준비를 뜻하지 않는다. 수뢰둔·산수몽은 기존 문답을 반영한 `Reviewed` 표본이다.
- 정본은 [hexagram-campaign-identities.json](../../../../../eng/execution-ledgers/hexagram-campaign-identities.json)이며 자동 생성 색인을 사람이 검토한다.

## 제1·2괘 서막과 제3괘 본격 캠페인 경계

- 제1괘 중천건: 빙의한 나무꾼 안에서 잠재된 가능성과 행위 의지가 깨어나는 여섯 개의 짧은 실제 플레이 비트다.
- 제2괘 중지곤: 몸·도구·땅·날씨의 조건을 받아들이며 세계에 머물 자리를 찾는 여섯 개의 짧은 실제 플레이 비트다.
- 건·곤은 UI 설명만 넘기는 장이 아니다. 실제 이동·관찰·자원·위험 선택을 사용하지만, 큰 공간이나 다수의 신규 WI를 요구하지 않는 짧은 서막으로 제한한다.
- 제3괘 수뢰둔 이후: 건·곤에서 익힌 능동과 수용이 한스·농장·위험·관계라는 구체 주체 사이에서 작동하는 본격 캠페인을 시작한다.
- 하위 사건: 벌목·농사·거래·훈련 같은 생활 사건은 제3괘 이후의 효 이야기와 기존 기획에서 소유하며, 건·곤은 그 사건을 전부 흡수하지 않는다.
- 개발 인계: 건·곤도 효 이야기와 주체·WI·H 요구사항이 승인되면 작은 개발 Goal로 넘길 수 있다. `StorySeeded` 상태만으로는 인계하지 않는다.
- 소가주 경로: 삭제하지 않는다. 중천건의 일차 시점 주체는 모험가로 유지하되 별도 시작 경로와 교차 이야기의 기존 기획을 보존한다.

이 결정은 건·곤의 정확한 거시 국면과 제3괘 이후의 개별 WI를 자동 확정하지 않는다. 실제 괘 캠페인 진행·실패·복원 규칙은 [괘 캠페인 실패·초효 복귀](../PLAN-STORY-HEXAGRAM-CAMPAIGN-RESET-001/README.md)가 소유한다.

## 정식 순서와 출처

- 괘 번호와 육효 괘상은 Unicode Consortium의 [Yijing Hexagram Symbols](https://www.unicode.org/charts/PDF/U4DC0.pdf) `U+4DC0..U+4DFF` 순서를 사용한다.
- 고전 원문 대조는 [《周易》 원문](https://zh.wikisource.org/zh-hant/%E5%91%A8%E6%98%93)을 출발점으로 사용한다.
- 고전 한문 원문과 Mirror가 작성한 한국어 의미 요약을 별도 칸에 기록한다.
- 현대 번역·해설은 권리와 판본을 확인하지 않은 채 복제하지 않는다. 하나의 해설을 게임의 유일한 정답으로 사용하지 않는다.
- 이번 판본은 64괘 순서·괘상·상하괘·효 음양과 정식 효 이름의 뼈대만 검증한다. 괘사·효사 원문과 Mirror 해석은 해당 괘를 제작할 때 별도로 검증한다.

정본 기계 대장은 [hexagram-story-production.json](../../../../../eng/execution-ledgers/hexagram-story-production.json), 사람이 읽는 생성 색인은 [64괘 스토리 제작 색인](../../../generated/hexagram-story-production.md)이다.

## 정식 제작과 자유 기획의 이중 흐름

```text
넓은 기획: 64괘 의미 → 전체 플레이 스토리 제안 → 선택한 괘의 큰 줄기 합의
정식 배열: 01 중천건 → 02 중지곤 → ... → 64 화수미제
현재 정밀화: 기존 기획 대조 → 이미 다룬 범위 보존·건너뜀 → 첫 미완성 괘 안에서 효사 순차 대조
자유 기획 유입: StorySeed → 주괘+보조 후보 → 사용자 확인 → 필요할 때 효 후보 → 효 확정
```

### 큰 이야기에서 효사로 내려가는 문답

1. 괘 이름·육효 괘상, 괘사·단전·상전 중 읽은 근거와 프로젝트 의미 요약을 제시한다.
2. 플레이어의 바람, 현재 주체와 장소, 중심 갈등, 실제 플레이, 끝에 남는 변화, 다음 괘와의 연결을 굵게 제안한다.
3. 큰 줄기의 새 내용은 `Proposed`로 두고 사용자와 합의한다. 기존 승인 기획을 다시 승인받을 필요는 없으며 바뀌는 대목만 묻는다.
4. 효사 원문을 그대로 보존하고, 평이한 뜻·상황 관계·Mirror 각색·각색으로 달라진 뜻을 나란히 적는다.
5. 원문과 줄거리가 어긋나면 줄거리를 조정하거나 부분 각색으로 명시한다. 모든 효를 발단·시험·성공이라는 동일한 여섯 단계로 환원하지 않는다.
6. 효의 사건과 실제 선택이 승인된 뒤에만 기존 주체·WI·H를 찾아 요구사항을 결속한다. 제목만으로 신규 기능을 생성하지 않는다.

초효부터 상효까지의 진행은 게임이 선택한 캠페인 구성이다. 여섯 효를 반드시 한 인물의 연속 시간으로 읽어야 한다는 고전 해석을 주장하지 않는다. 산수몽의 캠페인 이야기와 이미 구현된 독립 학습 맥락 카드·순서 없는 효 공명도 별개로 유지한다. 캠페인 육효로 새로 결속할 때 그 대응은 해당 효 기획에서 결정한다.

- `StorySeed`: 재미와 직관을 우선해 말한 기획 원문을 먼저 보존한다.
- `HexagramCandidate`: Codex가 주괘 하나와 순위가 있는 보조 후보를 이유와 함께 제안한다.
- `HexagramConfirmed`: 사용자가 주괘를 인정한 상태다. 이때도 효사 세분화는 필수가 아니다.
- `LineCandidate`: 주체·상황·변화·결과 또는 다음 상태가 충분히 구체화됐을 때만 효 후보를 연다.
- `LineConfirmed`: 원문과 대조하고 사용자와 문답한 뒤 효사를 확정한다.

재분류 이력은 덮어쓰지 않는다. 자유 기획 분류는 현재 `Active` 괘, 정식 제작 순서, runtime 해금, WI, Graph Map 또는 Evidence를 자동 변경하지 않는다. 정본 씨앗 대장은 [hexagram-story-seeds.json](../../../../../eng/execution-ledgers/hexagram-story-seeds.json), 사람이 읽는 색인은 [역경 자유 기획 씨앗 분류](../../../generated/hexagram-story-seeds.md)다. 새 씨앗은 [역경 자유 기획 씨앗 템플릿](../../../../ProjectOverview/templates/역경자유기획씨앗템플릿.md)을 따른다.

## 한 괘의 제작 절차

1. 64괘 정체성 대장에서 현재 괘의 핵심 상황·갈등·주체·압박·판정·완주 변화를 확인한다.
2. 현재 `Active` 괘의 괘상·괘사·육효·앞뒤 괘 관계를 검증된 원문에서 확인한다.
3. 원문과 프로젝트 자체 한국어 요약을 분리하고, 불확실한 해석은 가설로 표시한다.
4. 제3괘 이후에는 괘상·상괘·하괘·육효 방향을 한 화면에서 읽을 수 있는 시각 자료를 먼저 병기한다.
5. 초효부터 상효까지 한 번에 질문 하나만 열어 `상황 → 주체 → 상호작용 → 직접 결과 → 다음 변화`를 정한다.
6. 기존 Mirror 인물·지역·WI·H를 먼저 대조하고 공통 부품은 재사용하며, 캠페인의 조합만 고유하게 유지한다.
7. 효마다 필요한 주체·WI·H·Graph Map·배치 맵을 선언하되 자동 생성하거나 Evidence를 승격하지 않는다.
8. 모험가와 소가주는 같은 괘와 세계 변화를 공유한다. 효 내부에서 접근 권한·행동 규모·역할만 경로별로 달리 기록한다.
9. 여섯 효의 이야기와 캠페인 정체성의 일치, 전체 인과, 다음 괘 전환을 함께 검토한다.
10. 여섯 효와 괘 전체가 승인되면 현재 괘를 `PlanningApproved`로 바꾸고 다음 괘 하나만 `Active`로 연다.

이 절차는 정식 공부·제작 흐름이다. 자유 기획 씨앗은 어느 괘에든 후보로 들어올 수 있으며, 해당 괘가 `Active`가 아니어도 분류·보존할 수 있다. 다만 정식 괘 승인이나 다음 괘 해금에는 영향을 주지 않는다.

한 효의 이야기가 먼저 승인되면 괘 전체의 개발 완료를 기다리지 않고 `주체 확립 → WI 하나의 개발 Goal → 직접 결과 → 필요한 H·Graph Map·배치 맵·표현`으로 내려갈 수 있다. 여러 WI를 함께 닫아야 할 때만 PlayableLoop를 선택적 검증 묶음으로 둔다. 반대로 개발 완료는 다음 괘의 기획을 여는 조건이 아니다.

## 효사 기획의 요구사항 계약

효사 기획은 이야기 번호만 붙이는 문서가 아니라, 그 이야기를 게임에서 성립시키는 데 필요한 항목을 선언한다.

- 주체: 플레이어 Actor, NPC, 사물·공간·규칙 주체와 현재 재사용 가능 여부
- WI: 플레이어가 실제로 하는 핵심 상호작용 후보와 신규 정의 공백
- H: 필요한 H1과 그 조합으로 성립할 H2·H3·H4, 또는 사유 있는 해당 없음
- 공간 영향: Graph Map 갱신 필요와 배치 맵 필요 여부
- 표현 결속: 공간 영향이 `Required`이면 다섯 조건을 표현 요구 카드로 투영하고 기존 H·Synty·Blender 후보의 재사용·상태 변형 결손·E4 준비 여부를 기록
- 인계 상태: 이야기 승인과 요구사항 해소 여부를 함께 만족했는지

선언은 자동 생성 명령이 아니다. `StoryApproved`와 `ReadyForDevelopment`를 구분하고, 필수 주체·WI·H의 공백이 남아 있으면 개발 인계를 차단한다. H2 이상은 이름만 요구하지 않고 하위 H의 조합 근거를 함께 적는다. 실제 개발 Goal 하나는 WI 하나만 소유한다.

정본 요구사항은 [hexagram-line-planning-requirements.json](../../../../../eng/execution-ledgers/hexagram-line-planning-requirements.json), 사람이 읽는 생성 색인은 [효사별 기획·WI·H 요구사항 색인](../../../generated/hexagram-line-planning-requirements.md), 새 괘 정본과 효 절 형식은 [역경 괘·효사 기획서 템플릿](../../../../ProjectOverview/templates/역경효사기획서템플릿.md)을 따른다.

## 효사에서 모델링·배치로 내려가는 보존형 인계

효 이야기의 공간 영향이 `Required`이면 `지금·여기·나·너·이렇게 → 결과·다음 선택`을 한 장의 표현 요구 카드로 내린다. `지금`은 필요한 전·중·후 상태, `여기`는 AreaSet·H·배치 인스턴스, `나`는 행위 주체와 장비·도달 범위, `너`는 대상 모델과 상태 변형, `이렇게`는 상호작용 접점·접촉점·작업 영역·판독 신호를 설명한다.

이 카드는 기존 모델이나 배치 결과를 대체하는 목록이 아니다. 기존 Synty Prefab·Blender 파생형·PNG·배치 시안은 후보 이력으로 보존하고 현재 요구와의 적합성만 연결한다. 새 모델이 필요하면 원천 후보·파생 이유·상태 변형·판본을 기록한다. Graph Map은 관계, 배치 맵은 특정 AreaSet의 상대 배치, Blender는 외형 후보, Unity E5는 실제 World 결속을 소유한다. 애니메이션·Rig·전이 검증은 E5 뒤 E6에서 다룬다.

괘 정본의 효 절이 표현 요구 카드를 작성했다는 사실은 모델 제작·Scene 변경·E4/E5 승격 승인이나 자동 실행을 뜻하지 않는다. 필수 H 안정 ID나 상태 계약이 미정이면 `ImplementationRebindRequired` 또는 `Blocked`로 남긴다.

## 상태와 관문

| 상태 | 의미 |
| --- | --- |
| `Locked` | 순서 뼈대만 존재하며 정식 이야기 제작을 시작하지 않음 |
| `Active` | 현재 원문 연구와 육효 이야기 제작을 수행하는 단 하나의 괘 |
| `PlanningApproved` | 여섯 효·전체 인과·참조·공백·다음 전환이 기획 승인을 통과함 |

효 이야기는 `Unmapped`, `Draft`, `Reviewed`, `Approved`, `PrototypeReference`로 구분한다. 요구사항 대장에서는 이를 `Seeded`, `ActiveStudy`, `StoryApproved`, `Superseded`로 추적하고 개발 인계 상태를 별도로 판정한다. `PrototypeReference`와 `ActiveStudy`는 학습용 선행 사례이며 정식 제작 순서 관문을 열지 않는다.

건괘의 `用九`와 곤괘의 `用六`은 `SupplementaryInterpretation`으로만 기록한다. 일곱 번째 효 이야기, 보너스 퀘스트 또는 다음 괘의 필수 관문으로 자동 해석하지 않는다.

## 한스·수뢰둔의 처분

[한스 농장 첫 벌목·울타리 수리](../../../한스농장-첫벌목과울타리수리-기획-2026-09-02.md)는 제3괘 수뢰둔의 육효에 이야기를 놓아 본 `PrototypeReference`로 보존한다.

- 기존 한스 기획과 안정 ID를 삭제하거나 재번호화하지 않는다.
- 제3괘를 `Active` 또는 `PlanningApproved`로 승격하지 않는다.
- 한스 배정은 제1괘와 제2괘를 건너뛰는 제작 근거가 아니다.
- 제3괘가 실제 제작 차례가 되었을 때 원문과 당시 현행 Mirror 기획을 다시 대조해 `Accepted`, `Alternative`, `Unmapped`를 새로 판정한다.

수뢰둔의 여섯 표본은 독학 이데아 맵의 기초를 다룬다. 산수몽의 여섯 표본은 멘토 교정과 실제 재현 학습을 읽는다. 승인된 runtime 캠페인에서는 한 괘의 초효부터 상효까지 순서대로 진행하되, 각 효 안의 행동 방식과 괘 사이 자유 생활은 열어 둔다. 산수몽은 `Locked / PrototypeReference`를 유지하며 제1괘의 정식 제작 관문을 건너뛰지 않는다. 상세 학습 전환은 [수뢰둔→산수몽 이데아 맵 학습](../PLAN-STORY-IDEA-MAP-LEARNING-001/README.md)이 소유한다.

## 플레이어 표시 계약

우측 상단의 기본 표시는 다음 형식이다.

```text
┌──────────────────────────────┐
│ ䷀ 乾 · 중천건 · 초구 · 1/6 │
└──────────────────────────────┘
```

- 64개를 고유하게 구분하는 육효 괘상 `䷀`을 기본으로 쓴다.
- 상괘·하괘의 삼효 괘상은 상세 화면에서만 보여 준다.
- 현재 괘·효는 HUD에, 완료된 괘·효는 이야기 기록에 보여 준다. 미래 괘·효는 노출하지 않는다.
- 표시 상태는 `Hidden`, `Current`, `Completed` 세 가지다. 괘에 결속된 메인 이야기가 활성화되지 않았으면 `Hidden`이다.
- 글꼴이 `U+4DC0..U+4DFF`를 지원하지 않으면 동일 괘상의 프로젝트 내장 Sprite로 대체한다.

이번 판본은 데이터 필드·상태·와이어프레임을 위한 Presentation E4 준비 입력이다. 실제 Unity HUD, 입력, 저장, Game View 또는 Presentation E4/E5 승격을 성립시키지 않는다.

## 제3괘 이후 기획 문답의 시각 동반 형식

제3괘 수뢰둔부터 각 괘의 구체 서사를 함께 설계할 때 다음 순서를 고정한다.

1. 육효 괘상과 괘 이름
2. 상괘·하괘와 자연상
3. 효의 표시 방향: 화면은 위에서 아래로 그리되 효 번호와 변화 순서는 아래에서 위로 읽음
4. 검증된 고전 원문과 Mirror의 한국어 의미 요약
5. 게임의 현재 상황·주체·가능한 변화
6. 확정·미정과 다음 설계 질문 하나

시각 자료는 해석과 문답을 돕는 `PlanningVisualCompanion`이다. 이미지 자체가 효 이야기, WI, Graph Map, Unity 배치 또는 Evidence를 승인하거나 승격하지 않는다. 제1·2괘는 거시 기반을 정하는 동안 같은 형식을 선택적으로 사용할 수 있으나, 제3괘 이후에는 반드시 병기한다.

### 괘상 시각 카드

사용자에게 효사 질문을 보여 줄 때는 Unicode 괘상 한 글자만 제시하지 않고, 여섯 효를 실제 괘상처럼 쌓은 고정폭 텍스트 그림을 먼저 제시한다.

```text
                 ䷃ 山水蒙
상괘 ☶ 艮(산)
상구  ━━━━━━━━━━━  양 · 3사건
육오  ━━━━━  ━━━━━  음 · 2사건
육사  ━━━━━  ━━━━━  음 · 2사건
────────────────────────────
하괘 ☵ 坎(물)
육삼  ━━━━━  ━━━━━  음 · 2사건  ◀ 현재 효
구이  ━━━━━━━━━━━  양 · 3사건
초육  ━━━━━  ━━━━━  음 · 2사건
                 ↑ 초효부터 상효로 읽음
```

- 양효는 끊기지 않은 한 줄 `━━━━━━━━━━━`, 음효는 가운데가 끊긴 두 줄 `━━━━━  ━━━━━`로 그린다.
- 화면 배치는 실제 괘상처럼 상효를 맨 위, 초효를 맨 아래에 둔다. 공부·스토리 진행 순서는 아래의 초효에서 위의 상효로 읽는다.
- 상괘와 하괘의 경계, 이름, 자연상을 함께 적어 여섯 줄이 어떤 두 삼괘로 이루어졌는지 보이게 한다.
- 현재 문답 중인 효에는 `◀ 현재 효`를 붙인다. 아직 사건 수를 정하지 않은 괘는 사건 수 표기를 생략한다.
- 괘상 문자 `䷃`은 빠른 식별용 보조 표지다. 글꼴 차이와 무관하게 음양·위치·현재 효를 읽을 수 있는 위 여섯 줄 그림을 기획 문답의 기준 표현으로 삼는다.
- 색상·이미지·게임 HUD는 후속 표현 후보이며, 이 텍스트 카드는 기획 대화와 문서에서 항상 사용할 수 있는 대체 표현이다.
