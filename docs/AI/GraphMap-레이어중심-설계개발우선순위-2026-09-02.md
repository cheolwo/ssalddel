## 방향

당분간 게임 기획은 새로운 기능과 이야기를 계속 넓히는 것보다, 현행 Graph Map의 안정 노드·엣지와 레이어를 중심으로 정밀화한다. 기획 하나는 최소한 `어느 레이어에서`, `어떤 노드·엣지의`, `어떤 입력·비용·상태·선택·결과가 달라지는가`를 설명해야 Graph Map 인계 후보가 된다.

Graph Map은 기획을 줄이는 도구가 아니라 구현 가능한 구조로 바꾸는 중간 기준이다. 모든 기획을 즉시 코드로 만들지는 않지만, Graph Map에서 닫힌 작은 부분 그래프는 기존 Goal·WI·E7 작업 명세와 결속해 개발 후보로 넘길 수 있다.

## 주체 노드와 오행 상호작용 엣지

당분간 기획 문답의 기본 화면은 긴 이야기 문단이 아니라 `주체 노드 → 상호작용 엣지 → 대상 노드 → 직접 결과`다. 플레이어·NPC·부대·차량·시설·자연물·환경처럼 권위 상태를 소유하거나 행동을 일으키는 역할 객체는 주체 노드가 될 수 있다. 장소·자원도 독립 상태와 선택 지점이 있으면 노드로 두고, 단순 배경은 억지로 주체화하지 않는다.

엣지는 두 노드가 가깝다는 사실이 아니라 기존 WI 또는 명시된 후보 행동이다. 각 행동 엣지는 `actionGwae`를 필수 탐색 메타데이터로 갖고, 실제 의미가 있을 때만 `operationGwae`, `targetGwae`, `supportGwae`를 함께 참조한다. 오행은 행위와 관계를 읽는 메타데이터이며 엣지의 권위 조건·비용·성공·실패·귀환이나 Evidence를 대신하지 않는다.

Graph Map의 주목적은 플레이어가 따라야 할 정답 순서를 작성하는 것이 아니라, **노드 사이에 어떤 관계가 존재하고 무엇이 가능·불가능·조건부인가를 판독 가능하게 만드는 것**이다. 엣지가 존재해도 플레이어가 반드시 선택할 필요는 없고, 여러 엣지가 동시에 열려 있어도 시스템이 하나를 추천하거나 자동 실행하지 않는다. 기획이 명시적으로 요구한 튜토리얼·자동 방어 정책·권위 규칙만 별도 근거를 갖고 기본 행동이 될 수 있다.

각 관계 엣지는 필요에 따라 다음 상태를 구분한다.

| 관계 상태 | 의미 |
| --- | --- |
| `Available` | 현재 노드·권한·상태에서 선택할 수 있음 |
| `Conditional` | 자원·권한·거리·정보·시간·관계 같은 조건을 만족하면 열림 |
| `Blocked` | 현재 상태에서는 불가능하며 차단 원인을 보여 줌 |
| `NotApplicable` | 이 노드 관계에는 적용하지 않으며 가짜 엣지를 만들지 않음 |

Graph Map은 이 상태와 조건을 보존하고, 실제 플레이어 선택·조작·우선순위·전술은 Runtime과 플레이어의 영역으로 남긴다. `Blocked`는 영구 금지를 뜻하지 않으며 원인이 해소되면 새 권위 revision에서 다시 계산할 수 있다.

```text
[주체 노드]
  -- WI·주행위 오행·입력·대가 --> [직접 대상 노드]
  -- 완료/실패 결과 ------------> [변경된 상태 또는 다음 선택 노드]
  -- 명시된 경우만 --------------> [1-hop 파생 대상]
```

Graph Map 레벨은 이 단위를 다음처럼 확장한다.

- 레벨 1: 주체·대상 노드와 WI 행동 엣지, 선택·실패·귀환을 표현한다.
- 레벨 2: 해당 엣지가 성립하려면 필요한 거리·통행·시야·점유·H·배치 맵 제약을 연결한다.
- 레벨 3: 같은 노드·엣지를 구현하는 기존 계약·상태·Command·컴포넌트·시험을 결속한다.

앞으로의 질문은 현재 부분 그래프에서 하나의 관계 결손만 고른다. `노드 정체가 불명확함`, `직접 관계가 없음`, `엣지 방향이 미정`, `가능·불가능·조건부 경계가 없음`, `조건 해소 뒤 전환이 없음`, `1-hop 영향이 미정`, `L2 공간 제약 부재`, `L3 구현 결속 부재` 순으로 확인한다. 이미 닫힌 이야기나 플레이 방식을 표현만 바꿔 다시 묻지 않으며, 답변이 확정되면 해당 노드·엣지 판본과 인접 1-hop 영향만 갱신한다. 명시된 인과가 있을 때만 2-hop 후보를 열어 기획이 무한히 늘어나는 것을 막는다.

Graph Map 중심 문답에서는 `무엇을 먼저 할 것인가`, `어떤 전술을 고를 것인가`, `플레이어가 어떻게 조작할 것인가`를 기본 질문으로 삼지 않는다. 대신 `A와 B 사이의 관계가 존재하는가`, `방향은 단방향인가 양방향인가`, `어떤 조건에서 열리거나 막히는가`, `상태가 바뀌면 어느 인접 관계가 함께 달라지는가`만 묻는다. 플레이 순서가 별도 기획에서 이미 확정된 경우에만 그 순서를 엣지 선행조건으로 참조한다.

### 첫 두 전투 부분 그래프

| 시작 | 주체 노드 | 직접 상호작용 엣지 | 직접 대상·결과 | 현재 결손 |
| --- | --- | --- | --- | --- |
| 모험가 | 모험가, 한스 | 협력 방어, 역할 분담, 추적·차단 | 울타리·농장 생활 거점, 접근 마수 무리, 방어·피해·귀환 | 기본 목표 경로 확정. 예외 침투 능력과 방어 중 우선 대응 규칙은 후속 |
| 소가주 | 소가주, 지휘관, 부대 | 명령·수용·조정, 방어 배치, 제한 공세 | 초소·성벽·보급 거점, 적 정찰대·전초, 전황 합류 | 명령 충돌 때 권한·거절·조정 엣지 |

두 부분 그래프는 같은 요동성 전황 오버레이를 참조하지만 서로의 행동을 자동 완료하지 않는다. 먼저 작은 그래프의 결손을 질문으로 닫고, 닫힌 엣지만 Graph Map 담당과 개발 인계 후보로 보낸다.

모험가 첫 방어의 기본 적대 경로는 다음과 같이 확정한다.

```text
[마수 무리]
  → [농장 외곽 접근]
  → [울타리 공격·돌파 판정]
  → [씨앗·식량 창고 공격]
  → [약탈·파손 또는 방어 성공]
  → [마수 후퇴/추적 또는 농장 수리·생활 귀환]
```

울타리가 유효한 동안 일반 지상 마수는 창고나 주민 노드로 직접 건너뛰지 못한다. 울타리가 파손되거나 열린 출입구·확인된 우회 경로가 있을 때만 내부 목표 엣지를 연다. 비행·굴착·도약·잠입처럼 울타리를 무시할 수 있는 예외는 해당 마수의 능력과 감지·대응 관계를 별도 판본으로 확인한 경우에만 허용한다. 창고 피해와 주민 피해는 같은 결과로 합치지 않으며, 실제 도달 대상과 방어 대응에 따라 독립 결과로 남긴다.

첫 울타리 돌파가 발생하면 모험가와 한스는 역할을 `전투 지원`과 `울타리 수리`로 갈라 동시에 처리하지 않는다. 두 주체가 같은 침입 마수 무리를 함께 막는 공동 방어 엣지에 들어가고, 위협을 제거하거나 후퇴시킨 뒤에만 파손 구간 봉쇄·창고 피해 확인·부상 회복·생활 복귀를 연다. 이는 첫 전투의 판단량을 줄이고 직접 전투와 한스의 협력을 한 장면에서 배우게 하기 위한 기본 흐름이다.

```text
[울타리 돌파]
  → [모험가·한스 공동 방어]
  → 성공: [위협 제거/후퇴]
       → [파손 울타리 수리]
       → [창고·주민 피해 확인]
       → [농장 생활 복귀]
  → 실패·중단: [창고 또는 주민 쪽 침입 진행]
       → [후퇴·구조·피해 제한]
```

전투 중 수리는 첫 표본의 동시 선택에서 제외한다. 후속 시설·분대·소가주 규모에서는 별도 수리 인력을 배정할 수 있지만, 그 규칙을 모험가와 한스의 첫 소규모 방어에 소급하지 않는다.

### 공통 능동 방어 기반과 H1·H2

모험가와 소가주 시작은 규모와 초기 권한이 달라도 같은 **능동 방어 기반**을 사용한다. 방어는 타워가 적을 자동으로 지우는 관전형 구조가 아니라, 접근로와 병목을 읽고 H1 조립 단위를 마련한 뒤 플레이어가 3인칭으로 지점 사이를 직접 이동하며 전투·활성화·응급 대응을 수행하는 구조다. H1·H2는 이 직접 행동을 대신하지 않고 가능한 방어 관계와 보호 범위를 만든다.

```text
[위협 발생 영역]
  -- 접근 가능 --> [접근로·병목]
  -- 방어 판정 --> [H1 방어 지점들]
  -- H1 연결·방호 조건 충족 --> [H2 방어 블록]
  -- 방어선 돌파 때만 --> [보호 대상: 주민·창고·생산 시설]

[플레이어 주체]
  -- 통행 가능 --> [H1/H2 내부 대응 지점]
  -- 해당 WI·권한·자원 성립 --> [직접 전투·활성화·수리·구조]
```

H1은 울타리 구간·바리케이드·관측점·보급점처럼 실제로 조립·배치·상태 판정하는 최소 공간 단위다. H2는 H1을 단순히 많이 놓았다는 이유로 생기지 않고, 같은 접근로와 보호 대상을 향한 연결성·통행·작동·방호 조건을 충족한 H1 묶음에서 파생되는 상위 방어 블록이다. UI에서 H2 청사진을 한 번에 미리 보거나 배치 후보로 고를 수는 있지만, 권위 있는 H2 성립은 포함 H1과 Simulation 규칙이 판정한다.

Graph Map은 `어느 H1이 어느 접근로·보호 대상·인접 H1과 관계를 맺는가`, `그 관계가 Available·Conditional·Blocked 중 무엇인가`를 기록한다. 정확 좌표·회전·간격·충돌·시야·미관과 실제 Prefab 선택은 배치 맵과 Presentation E4~E5가 소유한다. 따라서 Graph Map의 연결선만으로 H1/H2가 실제 World에 놓였거나 E5가 성립했다고 보지 않는다.

소가주는 자신에게 맡겨진 영지·부대·물자 범위의 지휘 엣지를 처음부터 `Available`로 가진다. 다른 영주의 구역, 가주 직할군, 권한이 위임되지 않은 재산과 인력은 `Conditional` 또는 `Blocked`이며 직함만으로 자동 개방하지 않는다. 모험가는 개인·동행자·소유하거나 사용 허가를 받은 H1에 직접 대응할 수 있고, 공동 행동·약속·공적을 통해 특정 구역의 임시 지휘·배치 엣지를 얻는다. 두 시작의 차이는 방어 물리 법칙이 아니라 처음 열려 있는 지휘·배치 관계의 범위다.

적은 확인된 접근 엣지와 예외 능력만 사용한다. H1의 요격·지연·관측 효과, H2의 방호 범위, 플레이어의 직접 개입은 같은 권위 revision에서 계산하되 각각 독립 상태로 기록한다. 방어 지점이 존재한다는 이유로 플레이어 행동을 강제하지 않고, 직접 개입하지 않았을 때의 NPC·시설 자율 대응도 실제 역량·정책·자원 엣지가 있을 때만 성립한다.

### H2·H3 선행 청사진과 점진 성립

플레이어는 현재 가진 H1만 임기응변으로 늘어놓는 데서 끝나지 않고, 제한된 거점 안에서 `어떤 생활·생산·방어·공세 기반을 장차 만들 것인가`를 H2·H3 청사진으로 먼저 설계할 수 있다. 청사진은 미래 공간의 역할 슬롯·연결·우선순위·예상 자원·단계별 완성 조건을 예약하는 계획이며, 아직 존재하지 않는 건물·통행·방호 효과를 현재 능력으로 제공하지 않는다.

```text
[H3 거점 청사진]
  ├─ [H2 생활·생산 블록 청사진]
  ├─ [H2 방어 블록 청사진]
  └─ [H2 출동·공세 지원 블록 청사진]
          ↓ 역할 슬롯·연결·건설 순서 후보
       [필수/선택 H1 청사진]
          ↓ 자원·인력·시간·권한을 실제 투입
       [H1 준비/건설/가동]
          ↓ 연결·통행·용량·방호 조건 재판정
       [H2 부분 기능 → H2 성립]
          ↓ 필수 H2와 거점 공통 조건 충족
       [H3 거점 성립]
```

H2·H3 청사진을 선택해도 하위 H1이 자동 생성되거나 일괄 완성되지 않는다. 각 H1이 마련될 때마다 해당 H1이 제공하는 실제 기능과 그 H1에 연결된 플레이만 열린다. 예를 들어 관측점 H1이 먼저 가동되면 접근 위협 판독이 열리고, 울타리·문 H1이 이어지면 지연·차단이 열리며, 보급·치료 H1이 준비되면 방어 지속과 회복 엣지가 추가된다. H2는 자신의 필수 H1 및 연결 조건이 모두 성립한 시점에만 상위 블록으로 판정한다.

청사진은 한정된 자원을 두고 다음 요구가 경쟁한다는 사실을 숨기지 않는다.

| 요구 | 대표 관계 | 부족할 때 드러나는 결과 |
| --- | --- | --- |
| 생활·내정 | 휴식, 식량·물·생산, 저장, 주민 통행 | 회복·생산·지속 방어 능력 저하 |
| 방어 | 관측, 병목, 울타리·문, 주둔·수리·치료 | 침입 지연·피해 제한·복구 능력 저하 |
| 공세 지원 | 출동구, 장비·보급 적재, 정찰·귀환 경로 | 추적·선제 차단·원정 지속 능력 저하 |

플레이어는 동일 부지·자재·인력·건설 시간·유지 용량을 중복 소비할 수 없다. 청사진 화면은 `필수`, `선택`, `후속 확장`, `현재 충족`, `부족`, `충돌`을 구분하고, 한 블록을 앞당겼을 때 인접 블록과 보호 대상에 생기는 1-hop 변화를 보여 준다. 다만 시스템은 방어·내정·공세의 정답 비율을 대신 결정하지 않으며, 성립 불가능한 연결이나 동일 자원 중복만 차단한다.

H3 청사진은 거점 전체의 역할과 H2 사이의 큰 연결을, H2 청사진은 한정된 블록 안에서 H1 역할 슬롯과 연결을 소유한다. Graph Map은 청사진 노드·요구 관계·선행/충돌 엣지를 관리하고, 배치 맵은 선택한 청사진을 실제 부지의 좌표·회전·간격·통로·시야·Prefab 후보로 구체화한다. 청사진 승인, 배치 맵 준비, 실제 H1 건설, H2/H3 성립과 Presentation E5는 각각 별도 상태다.

#### 플레이어 전용 투명 청사진

건설 확정 전 청사진은 플레이어의 설계 보조 표현일 뿐 World의 건축물이나 공간 권위가 아니다. 반투명 외형·윤곽·연결선·예상 통로를 플레이어 화면에만 표시하고, NPC·적·Simulation은 이를 실제 장애물·시설·보호 범위·목표·재고·수용량으로 읽지 않는다.

| 상태 | 플레이어에게 보이는 것 | World에 미치는 효과 |
| --- | --- | --- |
| `DraftGhost` | 자유롭게 이동·회전·교체하는 투명 H1/H2/H3 설계, 예상 연결과 부족·충돌 안내 | 없음. 충돌·통행·방어·생산·AI 목표·H 성립 없음 |
| `SavedBlueprint` | 이름과 판본을 붙여 다시 불러올 수 있는 H2/H3 구성안 | 없음. 저장·수정·교체해도 자재·인력·부지·권한을 예약하거나 소비하지 않음 |
| `ConstructionPreflight` | 선택한 H1의 현재 부지·권한·통행·자원·선행 H·중복 점유 검사와 차단 사유 | 아직 없음. 검사만으로 자원이나 공간을 변경하지 않음 |
| `H1ConstructionCommitted` | 실제로 착공할 H1, 시공 순서, 투입 자재·인력·시간 | 이 시점부터 해당 H1의 부지와 필요한 자원을 예약하고 실제 건설 상태를 생성함 |

`DraftGhost`와 `SavedBlueprint`에서는 성립하지 않는 배치도 자유롭게 그려 볼 수 있다. 겹침·막힌 통로·부족 자원·권한 밖 부지는 편집을 막지 않고 경고로 보여 주며, 실제 H1 착공 확정 때만 해당 오류가 남아 있으면 차단한다. 따라서 최소 생존선은 청사진 작성 조건이 아니라 필요할 경우 방어 거점 착공의 검사 규칙이 된다.

청사진의 예상 비용은 정보일 뿐 지불이나 예약이 아니다. H2·H3 전체 예상량과 현재 부족량을 보여 주되, 실제 자재·인력·시간과 부지 점유는 플레이어가 특정 H1의 착공을 확정한 순간부터만 발생한다. 아직 착공하지 않은 나머지 H1 슬롯은 계속 자유롭게 수정·삭제·교체할 수 있고, 다른 청사진이 같은 자원을 예상한다는 이유로 현재 재고를 잠그지 않는다.

투명 청사진을 보았다는 사실, 청사진을 저장했다는 사실, 사전 검사가 통과했다는 사실을 실제 건설·Collider·Nav 경로·Renderer·H1 가동 또는 E5 증거로 사용하지 않는다. 다른 플레이어와 공유하거나 NPC에게 시공을 위임하는 기능도 별도 공유·권한·건설 Command가 있을 때만 연다.

#### 건축가 NPC와 배치 엔진의 청사진 제안

정식 H2·H3 청사진 기능은 시작부터 무조건 제공하지 않는다. 플레이어가 건축가 역할을 가진 NPC를 발견한 것만으로는 부족하며, 실제 협력·영입·고용·공식 위임 가운데 하나가 성립하고 그 NPC가 현재 설계 업무를 수행할 수 있을 때 열린다. 건축가가 없어도 플레이어는 허용된 기존 H1을 직접 수리하거나 단순 배치할 수 있지만, H2·H3 전체 구성의 자동 분석·후보 생성·비교·저장은 제한한다.

건축가 NPC는 청사진 UI를 여는 이야기·권한 주체이고, 배치 엔진은 그 요청을 계산하는 후보 생성기다. 배치 엔진은 다음 입력을 사용한다.

- 현재 Graph Map의 접근로·병목·보호 대상·위협 방향
- 배치 맵의 실제 부지·고저·경계·기존 H1·통행·점유 후보
- 플레이어가 사용할 수 있는 권한·기술·건설법과 건축가의 지식·숙련
- 현재 재고·인력·예상 공기·유지 용량과 아직 확보하지 못한 자원
- 생활·생산, 방어, 공세 지원 가운데 플레이어가 지정한 목적과 우선순위

배치 엔진은 하나의 정답을 강요하지 않고 목적과 제약이 다른 복수 후보를 반환할 수 있다. 각 후보는 예상 H1 구성, H2/H3 성립 가능성, 부족 자원, 통행·시야·방호 공백, 인접 1-hop 영향과 계산 근거를 보여 준다. 건축가의 지식에 없는 공법, 조사되지 않은 지형, 판독할 수 없는 위협은 임의로 메우지 않고 `Unverified` 또는 `Blocked`로 남긴다.

플레이어는 제안받은 후보를 그대로 저장하거나, 투명 청사진에서 수정하거나, 다른 목적을 지정해 다시 요청하거나, 아무것도 채택하지 않을 수 있다. 건축가와 배치 엔진은 `Candidate`만 만들며 청사진 채택·H1 착공·자원 예약·World 상태 변경을 확정하지 않는다. 실제 착공은 플레이어의 별도 확인과 현재 권위 상태의 재검사를 거친다.

```text
[건축가 협력·영입 성립]
  → [청사진 제안 기능 개방]
  → [Graph Map + 배치 맵 + 현재 상태 입력]
  → [배치 엔진의 복수 Candidate]
  → [건축가 설명: 근거·부족·위험·대안]
  → [플레이어 저장/수정/재요청/보류]
  → 별도 선택: [특정 H1 착공 사전 검사]
```

건축가 NPC의 존재를 배치 엔진 권위로 바꾸지 않는다. NPC 관계와 숙련은 사용할 수 있는 설계 지식과 설명 품질을 제한하고, 배치 엔진은 후보의 공간 적합성을 계산하며, Simulation은 착공·건설·H 성립을 판정한다. Presentation은 투명 외형과 비교 정보를 표시할 뿐이다.

건축가와의 협력·고용·위임 관계가 끝나거나 해당 NPC가 일시적으로 설계 업무를 수행할 수 없게 되어도, 이미 저장된 청사진은 플레이어의 설계 기록으로 남는다. 플레이어는 이를 열람하고 투명하게 표시하며, 현재 조건이 허용하면 기존 설계 그대로 개별 H1 착공을 요청할 수 있다. 청사진에는 작성 건축가, 사용한 설계 지식 판본, 기준 Graph Map·배치 맵·World revision을 남겨 출처와 오래됨을 판독할 수 있게 한다.

건축가가 없는 동안에는 새 자동 후보 생성, H2/H3 구조를 바꾸는 전문 수정, 건축 지식 판본에 따른 재설계를 잠근다. 단순 열람·표시·개별 H1 착공 요청은 유지한다. 실제 착공 사전 검사는 건축가의 재설계와 별개이므로 항상 현재 부지·권한·통행·자원·점유 상태로 다시 수행한다. 저장 당시에는 유효했더라도 지형·도로·기존 건물·권한이 바뀌어 현재 조건을 충족하지 못하면 착공을 `Blocked`로 남기고 원인을 표시하며, 오래된 청사진이 현재 World를 덮어쓰게 하지 않는다.

## 당분간 우선하는 레이어

1. 기준 공간 topology
2. 기상·시간
3. 운송
4. 위협·경비
5. 물류·보급
6. 플레이어 선택·조회

새 레이어는 기존 레이어로 책임을 표현할 수 없는 경우에만 제안한다. 화면 탭이나 색상을 늘리기 위해 업무 레이어를 새로 만들지 않는다.

## 기획 한 건의 최소 산출물

| 항목 | 필요한 내용 |
| --- | --- |
| 기획 근거 | 현재 승인 문서·판본·SHA-256 |
| 대상 레이어 | 한 개의 주 레이어와 필요한 보조 레이어 |
| 기준 topology | 재사용할 안정 노드·엣지·하위 맵·port |
| 입력 | 권위 상태, 관측, 자료 출처, 신선도 |
| 파생값 | 비용, 용량, 위험, 상태, 후보와 계산 근거 |
| 플레이어 선택 | 보고 비교하며 Confirm·중단·우회·귀환하는 지점 |
| 결과 | 권위 결과, ActionRecord, 다음 선택과 복구 |
| 미정 | 임의로 채우지 않을 수치·자산·코드·실행 증거 |

이 표를 채우지 못한 아이디어는 폐기하지 않고 `PlanningReference`로 보존하되 Graph Map 개발 인계는 하지 않는다.

## 설계에서 개발까지의 순환

```text
기획 질문·승인
  → 주 레이어와 영향 노드·엣지 지정
  → 기존 Graph Map 안정 ID 대조
  → 레벨 1 플레이 관계 반영
  → 레벨 2 비용·배치·통행·회복 제약 반영
  → 레벨 3 기존 코드·계약·시험 결속 조사
  → Integrated / Blocked / NoImpact
  → 닫힌 작은 부분 그래프 추출
  → 기존 Goal·WI·E7 재사용 또는 새 관문 필요 판정
  → ReadyForDevelopment
  → 개발의 AcceptedByDevelopment / Blocked / Deferred
  → 코드·시험·Runtime·Game View 증거를 분리해 반환
  → Graph Map과 기획 판본 재결속
```

기획 스레드는 Graph Map 원본이나 생성물을 직접 수정하지 않고 승인 판본과 영향만 인계한다. Graph Map 담당은 중간 진행을 반복 보고하지 않고 최종 상태를 반환한다. 개발은 `ReadyForDevelopment`만으로 자동 시작하지 않으며 현재 파일 소유와 검증 상한을 다시 확인한다.

## 확장 억제 규칙

- 새 아이디어가 기존 노드·엣지·레이어에 미치는 영향이 없다면 현재 Graph Map 개발 범위로 확대하지 않는다.
- 한 번에 전체 World를 구현하지 않고 진입·결과·복구가 닫힌 부분 그래프 하나만 고른다.
- 기상·운송·위협·물류가 같은 비용을 중복 계산하지 않도록 원인 계보를 유지한다.
- 수치·자산·Scene·실제 입력이 미정이면 문서 후보와 실행 증거를 구분한다.
- 알고리즘 선택보다 입력 의미·비용 단위·차단·복구·플레이어 Confirm을 먼저 안정화한다.
- 영역 간 경로를 다루더라도 Farm·Hub·Town·City의 독립 플레이 폐루프를 시작 선행 조건으로 바꾸지 않는다.

## 첫 개발 후보 묶음

### 후보 A — 레이어 대장과 구조 검사

- 기존 `graph-map-overlays.v1.json`을 단일 기준으로 재사용한다.
- 기상·시간뿐 아니라 운송·위협·물류·선택 레이어의 공통 필드와 대상 안정 엣지 참조를 표현할 수 있는지 검토한다.
- topology 변경 금지, 권위 변경 금지, 판본·근거·신선도·비용 중복 금지 검사를 기존 Graph Map 도구에 추가할 수 있는지 평가한다.
- 이것은 문서·구조 검사이며 실제 게임 경로 계산이나 E5가 아니다.

### 후보 B — 작은 다중 경로 Fixture

- 실제 World 배치 전에 거점 3개와 병렬 경로 3~4개인 결정적 Fixture를 사용한다.
- 기상 보정 전후, 한 엣지 `Degraded`·`Blocked`, 대체 경로, 용량 부족을 구분한다.
- 빠름·안전·저렴·대량 후보의 구성 요소와 선택 이유를 사본으로 반환한다.
- Dijkstra·Yen·Pareto·최대 유량 가운데 필요한 최소 조합은 정확 입력 계약과 E7 관문 뒤 개발이 결정한다.

### 후보 C — 실제 PlayableLoop 결속

- 후보 A·B가 통과하고 승인된 Goal·WI·E7이 있을 때만 실제 운송·보급 부분 그래프 하나를 고른다.
- Simulation 상태, ActionRecord, 중단·우회·복구와 Unity 조회 표현을 같은 revision으로 검증한다.
- 실제 Scene·입력·Game View는 월드·공간·배치 담당이 반환하고 개발이 통합한다.

## 현재 완료 의미

이 문서로 레이어 중심 우선순위와 설계·개발 순환을 정했다. 아직 Graph Map 레이어 대장 확장, 알고리즘 구현, 실제 운송, 보급로 차단, Unity 표현, E 승격은 완료되지 않았다.
