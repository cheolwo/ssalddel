## 2. 프로젝트를 한 문장으로 설명하면

Mirror는 현실의 커뮤니티·공공데이터·생산·창고·운송·도시 물류를 서버 권위의 원장과 게임 Simulation으로 다루고, Unity에서 사람이 공간을 돌아다니며 그 관계와 변화를 체험하게 만드는 프로젝트다.

## 5. 현재 게임 기획의 중심

### 5.1 주체를 먼저 세운다

현재 개발 원칙은 `Ready 주체 → WI 하나 → 직접 결과 → 제한된 파생 작용 → 선택적 PlayableLoop 검증 묶음`이다.

- 주체는 자신의 상태, 역할, 권한, 오행 분포와 행위 가능성을 가진다.
- 구현 첫 우선순위는 오행을 포함하는 주체의 확립이다.
- 두 번째는 준비된 주체 사이의 상호작용이다.
- 세 번째는 그 상호작용에서 0~2 hop으로 발생하는 파생 작용이다.
- PlayableLoop는 모든 구현의 선행 의무가 아니라 여러 WI의 성공·실패·회복·귀환을 함께 검증해야 할 때 쓰는 선택적 묶음이다.

현행 기계 대장에는 주체 10건, WI 110건이 있다. 숫자는 현재 미커밋 작업 트리에서 읽은 값이며 이후 바뀔 수 있다.

### 5.2 오행은 행위와 변화의 메타데이터다

- 목: 시작, 성장, 발아, 새로운 업무의 입구
- 화: 드러남, 가공, 활성, 판독 가능한 변화
- 토: 유지, 운영, 수용, 안정된 기반
- 금: 구분, 수확, 절단, 배치와 출고 준비
- 수: 흐름, 운송, 연결, 다음 순환으로의 이동

한 행위에는 주 오행과 보조 오행이 있을 수 있다. 상생·상극은 자연스러운 변화와 제한을 설명하는 규칙으로 사용한다. 오행은 게임 행위를 대신하는 추상 점수가 아니며, 실제 주체·상태·Command·결과가 먼저 있어야 한다.

모든 WI는 집중과 명상으로 되돌아볼 수 있다. 실행 기록인 `ActionRecord`가 있을 때만 이해·숙련·회복 또는 위협 변화의 근거가 생긴다.

### 5.3 상위 이야기 구조

역경 64괘를 각기 특징 있는 캠페인 원형으로 사용한다.

- 64괘 전체 캠페인 정체성 초안이 있다.
- 384효 전체에 안정 앵커와 기획 위치가 있다.
- 중천건·중지곤은 큰 흐름을 여는 짧은 실제 플레이 서막이다.
- 수뢰둔은 처음 자리와 관계와 생활 질서를 만드는 첫 구체 캠페인이다.
- 산수몽은 배움이 유리해지는 맥락이지만, 육효를 강제 순서의 튜토리얼 퀘스트로 만들지 않는다.
- 정식 공부·제작 순서는 1괘에서 64괘 방향을 유지한다.
- 자유 기획은 먼저 `StorySeed`로 보존하고, 사용자 확인 뒤에만 특정 괘로 확정한다.
- 한 괘의 초효부터 상효까지 캠페인 흐름은 이어지되, 괘가 끝난 뒤에는 다음 캠페인으로 진행하거나 기존 WI로 자유 생활을 계속할 수 있다.

## 7. 공간 설계 파이프라인

공간이 플레이 선택이나 결과에 영향을 줄 때만 다음 순서를 사용한다.

```text
기획 정본
→ 주체와 WI
→ Graph Map
→ 배치 맵
→ Presentation E4 자산 후보
→ 필요한 경우 Synty 조사와 Blender 파생형
→ Unity 실제 결속(E5)
→ Animation·전이·중단·귀환(E6)
→ 실제 입력과 Game View 완주(E7)
```

- Graph Map L1: 플레이 관계와 가능·불가능
- Graph Map L2: 공간·통행·거리·위험·배치 제약
- Graph Map L3: 코드·Controller·Component·계약 결속
- 배치 맵: 좌표, 회전, 높이, 접촉, 간격, 통행 폭과 실제 H 조합
- H1: 플레이어가 이해·배치·상호작용할 수 있는 최소 공간 객체 또는 기능 단위
- H2 이상: 여러 H1의 상태와 관계가 조건을 만족할 때 Simulation이 성립시키는 상위 공간

플레이어는 H1 조립을 선택할 수 있지만 H2·H3 성립을 임의로 선언할 수 없다.

2. `graph-map-planning-handoffs`의 저장된 기획 hash는 현행 기획과 어긋나 있다. 최신 Graph Map 재검토 뒤 새 판본으로 결속해야 한다.
3. `CURRENT_WORK.md`의 일부 숫자와 stale 설명은 생성 대장 재작성 이전 상태를 포함한다. 이 파일의 기계 대장 숫자와 실제 검사 결과를 우선 대조해야 한다.
4. 변경된 검사 전체 실행은 2026-09-05에 시작했지만 사용자 중단으로 완주하지 못했다.
5. 개별 E1·Presentation E4 기대값 정합 검사는 현행 `59 plans / 23 playable units` 기준으로 통과했지만, 전체 저장소 Fast·Task 검증을 대신하지 않는다.
6. 이번 snapshot에서는 Unity Editor, Play Mode, Game View, 원격 서버, 운영 DB를 실행하지 않았다.

## 11. GPT와 이어갈 때의 권장 우선순위

### 우선순위 1 — 기획 대화

수뢰둔 정본을 더 늘리기보다 현재 여섯 효 각각에서 필요한 주체·WI·직접 결과·실패·회복·다음 선택의 빈칸만 닫는다. 질문은 한 번에 하나만 한다.

### 우선순위 2 — 공간 재결속

최신 기획 59건 중 실제 공간 영향이 있는 기획만 선별해 Graph Map 평가 범위를 보충한다. 수뢰둔은 승인된 H1 세 건만 사용하고 H2·H3는 미정으로 유지한다.

### 우선순위 3 — E5 최소 slice

개발을 재개할 때는 수뢰둔 전체가 아니라 WI 하나를 고른다. 가장 작은 후보는 `부러진 도끼 발견 → 벌목 → 목재 획득 → 울타리 수리 → 권위 결과 재조회`다. Animation은 E6로 미룬 채 정적 자세·상태 교체·진행 표시 fallback으로 E5를 먼저 검증할 수 있다.

### 우선순위 4 — 통합 검증과 Git 정리

현재 변경은 여러 맥락이 섞여 있다. 전체 검사 완주, `CURRENT_WORK.md` 현행화, diff·민감정보·대용량 파일 확인 뒤에만 커밋과 푸시를 다시 판단한다.

## 12. GPT가 답변할 때 지켜야 할 형식

게임 기획 응답은 다음처럼 시작한다.

```text
[기획 · 분야 · PLAN-* · 판본]
```

그 아래에서 다음을 구분한다.

- 지금·여기·나·너·이렇게
- 확정
- 미정
- 추천과 대가
- 다음 질문 하나

`이렇게`는 플레이어의 구체적인 행동과 수행 방법을 기록하는 항목이다. 괘상·오행 메타데이터는 내부 분류에 사용하되, 사용자가 요구하지 않으면 답변 전면에 과도하게 드러내지 않는다.
