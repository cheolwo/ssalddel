## 자율 음식 배달 첫 기준·현행화 구현 승인 — r12

2026-09-07 사용자가 개별 업무 개입 없는 주문→조리→배달→수령→다음 주문 반복을 첫 세계 기준으로 승인하고 개발 스레드에 이관하지 말고 현행화에서 구현하도록 지정했다. 기존에 구현된 생활 엔진의 반복을 재사용하며 [자율 음식 배달 r6](Planning/시스템/PLAN-SYSTEM-MYEONMOK-OBSERVER/autonomous-food-world.r6.md)의 정확 범위·검증으로 결속한다.

한 번 재생을 시작한 이후 업무를 NPC가 수행한다. 기존 정지·실패·표본 종료·앱 종료 시간 미추적 정책을 유지하며 무한 재시작이나 기존 저장 교체는 하지 않는다. 이야기 진입·구체 개입 규칙은 여전히 미정이다. 이번 음식 배달 범위의 현행화 직접 담당 지정이지 모든 업무의 소유권 이동이나 기존 개발 조사 취소는 아니다.

## 업무에 뿌리 둔 세계 먼저, 몰입을 더하는 이야기 다음 — r11

2026-09-07 사용자 답변: 현실 업무와 맞아떨어지는 가상 세계를 사용자가 관찰하다 마음이 가면 기존 수뢰둔·산수몽 등의 이야기를 통해 직접 플레이에도 참여할 수 있기를 원한다. 지금 개발 우선순위는 스토리 구현보다 현실 업무와 크게 동떨어지지 않은 게임 세계의 구축이며, 그 위에 스토리를 구현해 몰입을 높이는 방향이다.

- 확정: NPC의 주문·접수·조리·배차·픽업·운송·인계·대기와 역할 관계가 일관되게 작동하는 세계를 먼저 구축한다. 사용자가 이야기를 시작하지 않아도 관찰할 가치가 있어야 한다. 현재 도형·판타지 통신 방향은 유지한다.
- 확정: 스토리와 직접 플레이는 사용자가 원할 때 세계에 더 깊게 참여하는 경로다. 관찰만 하는 이용도 독립적으로 성립하며 스토리 완주를 업무 시뮬레이션 이용 조건으로 만들지 않는다.
- 보존: [역경에서 영감을 얻는 스토리 기획 r16](Planning/스토리/PLAN-STORY-HEXAGRAM-SEQUENCE-001/README.md)의 기존 이야기·안정 ID·승인된 구체 사건은 버리지 않는다. 수뢰둔·산수몽과 괘·효는 영감 자료이며 새 세계 기능의 필수 순서·고정 미션 수로 강제하지 않는다. 이 판본은 개별 이야기의 승인·해금·명세 hash를 변경하지 않는다.
- 권위 경계: 현실과의 대응은 역할·절차·재고/상태·시간·거리·대기·실패/회복의 인과가 설명되는 것이다. Simulation과 실제 운영 원장은 분리하고 화면을 실제 영업 가능·허가·정산 준비의 증거로 보지 않는다. 마법 통신이 순간 조리·순간 배송의 근거가 되지 않는다.
- 구현 제안: 세계 전체 완성까지 이야기를 무기한 미루지 않고, 독립된 작은 업무 흐름을 먼저 자율 반복·관찰 가능하게 닫은 뒤 그 흐름의 NPC·사건·선택에 이야기를 결속한다. 기존 엔진과 상태 전이를 재사용하고 스토리 전용 주문/재고 원장을 따로 만들지 않는다. 새 갈등·개입 규칙은 별도 문답/명세로 정한다.
- 미정: 첫 독립 업무 범위와 예외 상한, 스토리 진입 계기, 첫 직접 체험 역할, NPC와의 관계 형성 조건. '마음이 통함'을 자동 친밀도·가입·연락처 공개·업무 참여 동의로 바꾸지 않는다.
- 다음 질문 하나: 첫 세계 완결 기준은 사용자가 개입하지 않아도 음식 주문→조리→배달→수령→다음 주문이 반복되고 그 과정을 관찰할 수 있는 것으로 잡으면 좋을까?

이번은 개발 우선순위의 기획 기록이다. 특정 업무 구현 착수·기존 작업 중단·새 Goal 활성화·Graph Map 수정·E 승격·commit/push를 포함하지 않는다. 현재 현행화의 표현 담당과 개발의 읽기 조사 역할을 유지한다.

## 비스듬한 관찰 구도·현행화 직접 구현 — r10

2026-09-07 사용자가 위에서 비스듬히 내려다보는 구도를 승인했다. 개발 스레드에 모두 이관하지 않고 이번 3D 표현은 현재 현행화 스레드에서 진행하도록 지정했다. 이 지정은 이번 표현 범위의 역할 예외이며 서버·Simulation 업무까지 가져오는 전사 역할 변경이 아니다.

## 기본 도형으로 보는 입체 동네 — r9

2026-09-07 사용자 답변: r8에서 제안한 마법 주문·연락과 시간 소요 조리·직접 이동 배송 방식에 동의했다. 지금은 Synty 프리팹을 억지로 적용할 필요 없이 기존 도형 표현을 유지하되, 평면적으로 느껴지는 화면을 간단한 삼차원 도형과 오가는 움직임으로 표현하기를 원한다.

- 확정: 초기 마법은 주문·연락의 표현에 사용한다. 조리 시간·물리적 픽업·이동·인계는 남긴다. r8의 해당 미승인 추천은 이 답변으로 승인되며 순간이동·즉시 조리를 추가하지 않는다.
- 확정: 당장은 기본 입체 도형으로 공간과 NPC 이동을 읽을 수 있게 하는 것이 우선이다. Synty 신규 적용·Blender 모델링·정교한 건물/인물 제작을 선행 조건으로 삼지 않는다. 기존 자산 삭제나 다른 승인 작업 중지는 포함하지 않는다.
- 표현 후보: 건물은 높이가 있는 상자, NPC는 캡슐/원기둥, 통신구는 작은 구체로 표현한다. 바닥·출입구·도로와 높이/명암을 구분하고 기존 역할 색과 맵 범위·업무 위치를 보존한다. 이는 구체 모양의 추천이며 새 공식 Scene이나 새 업무 상태를 만들지 않는다.
- 검토 경계: 현재 화면이 평면적으로 느껴진다는 사용자 평가를 기록한다. 실제 소스가 2D인지, 카메라 각도·높이·조명 중 무엇이 원인인지는 아직 확인하지 않았다. 이동은 기존 권위 위치·상태를 표현하며 보기 좋게 임의 배차·주문·완료를 발생시키지 않는다.
- 미정: 카메라 구도, 도형별 정확 높이·크기, 통신구 알림 표현. 첫 직접 체험 역할·배포 조건도 미정이다.
- 다음 질문 하나: 처음에는 위에서 비스듬히 내려다보며 동네와 배달원 이동을 함께 보는 구도로 잡으면 좋을까?

이번은 기획 판본과 개발 전달 방향만 갱신한다. 구체 작업 명세·소유 경로·검증 범위를 결속하기 전에는 코드/Scene 변경을 시작하지 않는다. 실제 입체 화면·Runtime·Game View 검증은 아직 수행하지 않았다.

## 판타지 세계의 주문·연락 — r8

2026-09-07 사용자 답변: 게임 속 세계에는 판타지적인 느낌이 있으면 좋겠다. 주문자가 음식점에 주문할 때 마법 통신구 같은 것을 활용하는 모습을 예로 들었다.

- 확정한 방향: 현실 업무를 그대로 복제한 외형에 한정하지 않고, NPC의 주문·연락을 마법 통신구처럼 세계관에 어울리는 도구로 표현한다. 무료 관찰·선택적 역할 체험·희망자의 현실 업무 도구 이용이라는 r7 목적은 유지한다.
- 표현 제안(미승인): 주민의 통신구에 메뉴가 빛으로 나타나고, 음식점의 탁상 통신구가 주문을 알리며, 배달원의 휴대 도구에 픽업 요청이 전달된다. 기존 휴대폰 UI의 정보·상태 연결을 재사용하고 게임에서는 마법 도구로 재해석하는 방안을 검토한다. 구체 자산·UI·조작·장치 형태는 아직 정하지 않는다.
- 규칙 제안(미승인): 우선 통신을 마법적으로 표현하되 조리 시간, 물리적 픽업, 도로 이동, 인계는 관찰 가능한 과정으로 남긴다. 판타지 분위기와 NPC 생활·업무 학습을 함께 보존하기 위한 초기 추천이지, 향후 마법 규칙을 금지하는 결정은 아니다.
- 권위 경계: 통신구의 빛·알림·화면은 실제 Simulation 상태를 읽어 표현한다. 표현만으로 주문 수락·조리 완료·배송 완료를 확정하지 않으며 현실 앱/운영 원장과 자동 연결하지 않는다.
- 미정: 마법의 범위·비용·실패 조건, 순간이동·즉시 조리 같은 업무 규칙 변화, 구체 장치와 시각 스타일. r7의 첫 직접 체험 역할과 배포 조건도 계속 미정이다.
- 다음 질문 하나: 우선 마법은 주문·연락에 쓰고, 음식은 조리 시간이 들며 배달원은 직접 길을 이동하는 방식으로 잡으면 좋을까?

이번 판본은 기획 방향 기록뿐이다. 코드·UI·자산·Graph Map·기존 명세 hash·Goal/E를 변경하거나 개발 조사 범위를 확대하지 않는다. 아래 r7의 역할 질문은 보류하고 위 마법 경계를 먼저 묻는다.

## 무료 Unity 체험에서 역할별 업무 앱으로 — r7

2026-09-07 사용자 답변: 먼저 무료로 이용할 수 있게 하는 것을 우선한다. GitHub 소스는 공개할 의향이며, 접근하기 쉬운 Unity 프로그램에서 NPC를 관찰하고 게임 속 역할을 직접 체험한 뒤 원하는 사람이 기존 .NET MAUI 기반 앱을 설치해 현실 업무·협업으로 이어갈 수 있게 단계적으로 마련한다. 이미 작성된 앱과 자체 서버의 주문 관리·음식점·음식/화물 배달·창고 기능을 재사용하며 게임과 업무 제품을 별도로 처음부터 다시 만들지 않는다.

| 사용자 여정 | 목적과 책임 |
| --- | --- |
| 무료 Unity 관찰 | NPC가 어떤 절차·역할 인계·대기를 거쳐 업무를 수행하는지 부담 없이 살펴본다 |
| 가상 역할 직접 체험 | 원하면 게임 안에서 주문·접수·배송 등의 역할을 맡아 선택과 결과를 배운다. 실제 거래는 발생하지 않는다 |
| 역할별 업무 앱 선택·설치 | 현실 참여를 원하는 사람에게 기존 MAUI/Web 업무 도구와 필요한 준비를 안내한다. 플랫폼·역할별 제공 가능 여부는 실제 검증으로 판단한다 |
| 현실 협업 준비·운영 | 참여 의사·역할·서버 연결·권한과 운영 준비를 별도로 확인하고, 실제 업무는 운영 서버의 원장과 절차로 수행한다 |

이는 쉬운 진입을 위한 권장 여정이며 게임 완주나 등급을 현실 앱 이용 자격으로 만드는 기획은 아니다. 관찰만 즐기거나 가상 체험에 머무를 수 있다. 기존 업무 도구를 이미 쓰는 사람에게 게임 선행을 강제하지 않는다. 가상 계정·재고·주문·보상·저장은 실제 업무 원장으로 자동 전환하지 않는다. 공통 업무 의미·규칙·역할 설명은 재사용하되 Simulation 상태, 운영 권한/저장, Unity 표현의 경계는 유지한다.

- 확정: 우선 무료 이용 접근성, 관찰에서 선택적 직접 체험으로의 진입, 희망자의 기존 업무 도구 사용·현실 협업 준비, 현재 사용자와 후속 제작자를 위한 기존 자산 재사용.
- 공개 의향: GitHub 소스 공개. 현재 원격 저장소 공개 여부를 검증하거나 변경한 것은 아니며, 이 답변을 라이선스 선택·외부 자산/자료 재배포·게시/배포 실행 승인으로 확대하지 않는다.
- 현재 코드 확인: `OrdererApp`·`RestaurantDeskApp`은 MAUI Windows 대상, `DriverApp`·`FDriverApp`·`WarehouseManagerApp`과 통합 `SsalddelApp`에는 Android 등 대상이 선언돼 있다. 프로젝트 설정 확인이지 플랫폼별 빌드·설치·배포·실제 업무 완주 증거가 아니다. 다운로드 경로/플랫폼·앱 조합은 별도 검증과 기획이 필요하다.
- 미정: 첫 직접 체험 역할, 초보자 안내 방식, 앱 배포 플랫폼·설치/연결 절차, 중앙 서버/자체 운영의 초기 제공 방식, 무료 제공의 운영 비용 부담, 구체 라이선스/재배포 범위. 사용자에게 현실 참여나 자체 서버 운영을 자동 요구하지 않는다.
- 다음 질문 하나: 음식 배달의 첫 직접 체험은 주문자가 되어 주문을 넣고 인계를 지켜보는 것부터 시작하면 좋을까?

이번은 목적과 사용자 여정의 개정이다. 기존 승인 WI/작업 명세 hash를 자동 변경하지 않으며 코드·로그인·과금·공개 설정·앱 배포·서버 운영·E 승격은 수행하지 않는다. 아래 r6의 무료 범위 질문은 이 r7 답변으로 대체되며 구체 배포·비용·권리 조건은 계속 미정이다.

## 열린 업무 학습에서 자발적 현실 협업으로 — r6

2026-09-07 사용자 문답: 이미 정리된 주문·접수·배차·음식/화물 배달·창고 절차를 접근하기 쉬운 게임적 공간에서 공개하고, NPC가 움직이고 운영하는 모습을 보며 사람들이 자연스럽게 배울 수 있게 한다. 이후 마음을 모은 사람들이 현실에서도 유사한 협업을 준비할 수 있는 플랫폼을 지향한다. 현재 사람에게 유용하면서 다음 사람이 이해하고 이어받을 수 있다는 앞선 목적과 연결한다.

- 확정한 방향: 업무를 관찰하고 배우는 접근성을 무료 공개 방향으로 검토한다. 화면만 흉내 내는 것이 아니라 기존 업무 규칙·처리 상태·역할 인계를 바탕으로 학습할 수 있게 한다.
- 확정한 방향: 가상 학습 참여와 현실 협업 참여는 별개다. 사람들이 자발적으로 모여 실제 역할·책임·비용과 참여 범위를 합의하도록 돕고, 가상 성공을 현실 실행 준비 완료로 간주하지 않는다. [공동행동 철학](../Architecture/NeighborCenteredDevelopmentPhilosophy.md)·[기존 커뮤니티 경계](../Architecture/CommunityFoundationV0Policy.md)를 유지한다.
- 기획 추천: NPC의 현재 업무뿐 아니라 이전 인계, 다음 처리, 대기 이유, 예외와 회복을 같은 상태 기록에서 볼 수 있게 한다. 이는 관찰을 학습으로 연결하는 후보이며 아직 새 UI/시나리오 구현 승인이 아니다.
- 기획 추천: 다음 담당자를 위해 결정 근거·재현 가능한 가상 표본·실행법·시험과 한계를 남긴다. 접근성을 위해 모든 역할 화면을 처음부터 노출할지는 후속 문답으로 정한다.
- 미정: 무료 이용의 정확 범위, 소스코드 공개·라이선스·자체 운영 배포, 호스팅 비용 부담, 외부 자산/자료 재배포 범위. 무료 공개 방향을 기존 공개 설정이나 외부 자산의 재배포 허락으로 해석하지 않는다.
- 다음 질문 하나: 무료 공개는 누구나 서비스와 학습 기능을 무료로 이용하는 범위인가, 소스코드를 받아 직접 운영하고 고치는 범위까지 포함하는가?

이번 r6은 목적 문답을 추가하며 아래 r5의 오행·회복 목적과 구체 승인 이력을 삭제하지 않는다. 기존 작업 명세에 결속된 r5 hash를 자동 갱신하거나 Goal·WI·Graph Map·공개 설정·가격·실제 운영을 변경하지 않는다. 무료화/배포 구현은 위 미정을 정한 뒤 별도 범위로 인계한다.

## 목적

게임의 상위 목적은 플레이어인 나와 내가 대하는 상대의 필요한 오행 관계가 실제 행동·결과·회복·귀환으로 이어지게 하고, 그 순환 개선이 권위 결과로 확인될 때 관련 회복을 높여 개인과 공동체가 광복기 가능성을 넓히는 것이다.

기능을 많이 갖추는 것 자체는 목적이 아니다. 플레이어는 먼저 자신의 오행이 막힌 원인을 알아차리고 생활·탐험·작업·관계·명상을 통해 순환을 회복한다. 이렇게 확보한 안정·지식·기술·물자·관계와 회복역량으로 자신이 대하는 사람·사물·환경의 막힌 순환을 도울 수 있다. 상대의 실제 회복은 다시 안전한 관계, 이용 가능한 길과 시설, 풍부한 생태, 신뢰와 협력, 새로운 배움과 선택으로 돌아와 나의 다음 회복을 돕는다.

```text
나의 막힌 오행을 관찰
→ 작은 행동으로 나의 순환과 회복을 안정
→ 확보한 역량·지식·물자·관계를 상대에게 적용
→ 상대의 실제 상태가 개선되거나 피해가 예방됨
→ 변화된 사람·사물·환경이 새로운 선택과 도움을 돌려줌
→ 나와 공동체의 다음 회복 순환
```

나의 회복이 높다고 상대의 회복을 버튼 하나로 직접 올리지는 않는다. 높은 회복은 더 어려운 상황에서도 침착하게 관찰하고, 더 복잡한 행동을 지속하며, 실패 뒤 다시 시도하고, 더 넓은 대상과 협력할 수 있는 **기여 조건**이 된다. 상대의 회복은 상대에게 실제로 필요한 행동과 자원, 동의, 권위 결과가 성립했을 때만 오른다.

상대 또는 `너`는 NPC·동행자·주민·조직·적대자 같은 사람과 집단뿐 아니라 손도끼·나무·약초·밭·집·창고·도로 같은 사물·자원·시설, 숲·물길·기상·서식지 같은 환경·공간·생태도 포함한다. 사람의 주체성·동의·거절은 보존하고 사물·환경에 의도나 감정을 부여하지 않는다.

## 회복과 회복역량

- `회복`은 실제 상태 개선 또는 확인된 피해 예방과 그 기여다.
- `회복역량`은 손상·실패·위기 뒤에 회복할 수 있는 능력과 여지다.
- 플레이어의 명상 역량 성장은 개인 회복역량을 높이는 대표 경로지만 현재 회복을 즉시 채우지는 않는다.
- 회복 결과 하나만으로 회복역량을 자동 성장시키지 않는다. 숙련·시설·관계·지식·비축 등 별도 근거와 Profile이 필요하다.
- 정확 변환식·상한·해금·감쇠·반복 방지는 각 하위 기획에서 정한다.

사람의 회복은 개인·공동체 상태, 사물·시설의 회복은 내구·기능·운영 상태, 환경의 회복은 생태·경로·안전·생산 상태처럼 기존 권위 상태로 구체화한다. 모든 대상을 하나의 공통 회복 수치로 합치지 않는다.

## 회복 기여 판독 경계

회복 기여 후보는 같은 WI·ActionRecord·Actor·대상·Session·Revision에 연결된 권위 결과, 전후 상태 차이 또는 확인된 피해 예방, 판본화된 기여 Profile이 있을 때만 남긴다.

한 결과에서는 다음을 분리한다.

- 관점 플레이어
- 실제 실행 Actor
- 직접 대상
- 간접 영향 범위
- 회복 판정 대상
- 대상별 `개선 / 유지 / 손실 / 미확인`

위임한 플레이어와 수행 NPC를 합치지 않으며, 개별 나무의 소모를 숲의 회복으로, 적대 개체의 제압을 그 개체의 회복으로, 재료 소모를 수혜자의 회복으로 자동 치환하지 않는다. 화면 열람·Preview·취소·중복 Confirm·Save 재조회도 기여 원인이 아니다.

## 하위 기획의 목적 관문

새 기능이나 장면은 다음 질문을 통과해야 한다. 모든 칸에서 수치를 만들 필요는 없지만, 상위 목적과 어떤 관계인지 설명할 수 없는 기능을 핵심 진행으로 승격하지 않는다.

1. **나의 현재 막힘:** 플레이어의 어떤 오행 관계·생활 상태·선택 여지가 막혀 있는가?
2. **나의 회복 행동:** 플레이어가 무엇을 관찰하고 어떤 WI를 선택하며 어떤 대가를 치르는가?
3. **기여 자원:** 회복으로 얻은 안정·기술·지식·물자·관계 가운데 무엇을 상대에게 쓸 수 있는가?
4. **상대의 실제 필요:** 사람·사물·환경의 어떤 상태를 개선하거나 어떤 피해를 예방하는가?
5. **권위 결과:** 누구의 어떤 상태가 실제로 개선·유지·손실·미확인됐는가?
6. **환류:** 상대의 변화가 나와 주변 공동체에 어떤 새 선택·안전·관계·자원을 돌려주는가?
7. **비기여 경계:** 단순 관찰·장식·설명·Preview처럼 회복을 직접 만들지 않는 부분은 무엇인가?

이 관문은 [기획 문서 독립 관리 체계](../Architecture/기획문서독립관리체계.md)의 문답 영향 묶음, [Graph Map 기획 인계 순환 체계](../Architecture/GraphMap기획인계순환체계.md)의 레벨 1 목적 연결, [Graph Map 개발 인계 체계](../Architecture/GraphMap개발인계체계.md)의 작은 slice 수용·반환 관문에 반영한다. 기획은 확정과 미정을 구분하고, Graph Map은 확인된 관계만 연결하며, 개발은 그 slice에서 실제로 닫힌 권위 결과와 환류 범위만 반환한다. 이 공통 적용은 Graph Map 원장·게임 코드·Unity Scene을 자동 변경하거나 E를 승격하는 권한이 아니다.

최근 수평 기획은 다음처럼 이 관문 안에서 역할을 가진다.

| 기획 요소 | 상위 목적에서의 역할 | 직접 회복으로 세지 않는 것 |
| --- | --- | --- |
| 절기별 복장·식생 | 현재 세계 상태와 상대의 필요를 관찰하게 하는 신호 | 옷이나 색이 바뀐 사실 자체 |
| 절기별 농사·운송·수리 | 식량·물류·시설의 막힌 순환에 참여할 행동 후보 | NPC 애니메이션만 재생된 상태 |
| Town의 계절 가격 | 공급·재고·수요의 막힘을 읽고 조달·대체·기다림을 선택하게 하는 정보 | 가격표 열람이나 현실 자료 조회 |
| 일반 주민 말풍선 | 상대의 관측 가능한 필요와 생활 맥락을 선택적으로 이해하는 접점 | 클릭·대화 열람 자체 |
| 퀘스트 대화창 | 실제 필요·대가·선택을 명시하고 WI로 진입하는 관문 | 대화창을 연 상태나 자동 수락 |

이 표는 각 하위 기획의 독립 목적을 없애거나 모든 콘텐츠를 회복 수치 보상으로 바꾸지 않는다. 경관·음악·유머·탐색처럼 직접 회복을 만들지 않는 콘텐츠도 세계를 이해하고 머물 이유를 제공하는 보조 층으로 유지할 수 있다. 다만 핵심 진행·성장·광복기 기여로 연결할 때는 위 사슬의 실제 결과를 요구한다.

## Mirror의 첫 대표 세계 표현 — 현실 물류의 거울

상위 목적을 플레이어가 세계에서 구체적으로 체감하는 첫 대표 구현 목표는 **현실의 창고·상하차·분류·배달·인수·반품이 사람과 이동 수단의 생활로 보이는 세계**다. 사용자가 실제로 접해 온 배달·물류 경험과 기존 운영 서버의 기능을 활용해, 표와 상태값으로만 존재하던 흐름을 Unity 안의 공간·사람·차량·행동으로 번역한다.

```text
운영 서버의 권위 있는 물류 상태와 이력
→ 플레이어가 이해할 수 있는 창고·작업 지점·경로로 번역
→ 창고 작업자·운송 기사·배달원이 실제 일을 하는 환경 표현
→ 플레이어의 관찰·직접 참여·위임 가운데 하나를 선택
→ 입고·적치·출고·배송·인수·반품 결과를 같은 판본으로 재조회
→ 물자와 사람의 막힌 흐름이 풀리며 다음 생활·관계·회복 선택이 열림
```

첫 표현 범위에는 다음 풍경을 포함한다.

- 창고에서 화물을 내리고 등록·검수·분류·적치하는 작업자
- 출고 지시에 따라 피킹·포장·상차하고 출발을 확인하는 작업자와 기사
- 도심 물류 창고나 소규모 배송 거점에서 오토바이·차량으로 출발하고 돌아오는 배달원
- 배송 성공뿐 아니라 지연·수취 실패·회수·반품·재배송으로 이어지는 생활 흐름
- 플레이어가 현장을 관찰하거나 직접 일부를 수행하고, 권한과 관계가 있으면 NPC에게 맡길 수 있는 선택

`Mirror`는 Web 화면이나 DB 행을 3D로 일대일 복제한다는 뜻이 아니다. 실제 업무의 원인·역할·대가·결과를 알아볼 수 있게 비추되, 개인정보·민감 정보·정밀 입력은 Web 또는 제한된 상세 패널에 남기고 Unity에는 플레이에 필요한 상태 사본만 보인다. 실제 운영 자료는 맥락과 근거가 될 수 있지만, 게임 Simulation 상태와 운영 상태를 합치거나 Unity 장면만으로 운영 업무가 완료됐다고 판정하지 않는다.

이 물류 표현은 게임 전체를 직업 체험 하나로 제한하지 않는다. 농장·Town·City·Nature의 생산과 생활이 창고와 운송을 통해 서로 영향을 주는 모습을 보여 주고, 플레이어는 모험·제작·운영·관계 중심 성향에 따라 물류에 직접 참여하거나 주변 생활로 경험할 수 있다. 물류 처리량 자체를 도덕 점수나 회복으로 환산하지 않고, 필요한 물자가 제때 도착하고 과로·사고·단절을 줄인 실제 결과만 사람·시설·공동체 회복 기여 후보가 된다.

## 광복기 경계

개인 광복기와 공동체 광복기는 독립적으로 판정한다. 사물·시설·환경 자체를 심리적 광복기에 넣지 않는다. 이들의 회복 결과가 실제 공동체 문제 완화로 이어졌을 때만 참여자·대상·영향 범위가 명시된 공동체 회복 기여 후보가 된다.

현재 구현된 플레이어별 `NatureMind`·개인 기간 전이와 일부 전체 플레이어 사건 배분은 보존한다. 이는 사람·사물·환경 전반의 공통 회복 기여, 공동체 집계 또는 별도 회복역량 구현을 뜻하지 않는다.

## 문답·기록 원칙

이 기획의 후속 답변은 새 `D-###`를 만들지 않는다. 답변마다 이 문서의 `기획 판본`과 상태·확정 내용·미정·다음 질문을 갱신하고 [기획 목차](PLANNING.md)에 현재 판본만 반영한다. 둘 이상의 독립 기획에 적용되는 권위·안전·호환 규칙이 별도로 확정될 때만 그 규칙을 결정 원장에 요약할 수 있다.

- 명상 역량에서 회복역량으로 이어지는 정확한 변환식과 해금
- 공동체 회복 집계 Profile
- UI·Audio·Graph Map의 정확 표현
- WI·Save/Replay·Unity 결속

이 문서는 기획 기준선이며 코드 구현, Scene 배치, 실제 입력, Unity 실행 또는 E 승격의 증거가 아니다.
