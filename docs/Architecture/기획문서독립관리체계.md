# 기획 문서 독립 관리 체계

## 목적

게임 기획의 본문과 전역 결정을 분리한다. 플레이어 상황·선택·대가·실패·회복·귀환, 이야기 분기, 미정 질문과 Graph Map 영향은 기획 문서가 소유한다. `DECISIONS.md`는 여러 기획에 장기간 공통 적용되는 원칙·권위 경계·호환 규칙만 소유한다.

이 분리는 기존 `D-###` 이력을 삭제하거나 다시 번호 매기기 위한 것이 아니다. 과거 결정은 당시 기획 근거를 찾는 링크로 보존하고, 앞으로 기획 답변 하나마다 새 D를 만드는 관행을 중단하기 위한 것이다.

## 문서별 책임

| 문서 | 소유하는 것 | 소유하지 않는 것 |
| --- | --- | --- |
| 기획 문서 | 지금·여기·나·너·이렇게, 결과·다음 선택, 사건 순서, 분기, 대가·실패·회복·귀환, 미정 질문, 판본·상태, Graph Map 영향 | 코드·Scene·Runtime 결과, 전역 호환 정책 |
| [기획 목차](../AI/PLANNING.md) | 안정 기획 ID, 상·하위 기획, 현재 판본·상태, 기준 문서, 다음 질문, 인계 상태 | 각 기획 본문 복제 |
| [결정 원장](../AI/DECISIONS.md) | 여러 기획에 공통인 장기 원칙, 권위·안전·호환·명명·증거 경계, 대체 관계 | 개별 장면의 세부 대사·순서·후보·미정 수치 누적 |
| [현재 작업](../AI/CURRENT_WORK.md) | 지금 활성인 기획·개발·검증 상태와 차단 | 완료 이력과 장기 기획 본문 |
| Graph Map | 승인된 기획 판본의 레벨 1·2·3 구조와 미결속 | 기획 선택의 임의 창작 |

## 안정 기획 ID

### 기획 표시명과 호환 식별자

2026-09-05 사용자 승인으로 일반 기획의 표시명에서 관행적 `-001` 접미사를 생략한다. 개정은 별도 판본 `r1·r2·r3`로 표시한다. 기존 내부 식별자·폴더·링크·JSON·개발 명세·승인 hash는 유지하며 기획 목차의 숨김 호환 주석은 기계 참조용이다. 기존 문서의 `기획 ID` 머리말은 내부 식별자이므로 일괄 수정하지 않는다. 제목·링크 이름·응답에는 한국어 이름 또는 접미사를 뺀 표시명을 쓴다.

새 일반 기획은 `PLAN-{분야}-{주제}`로 만든다. 의미가 다른 기획은 구체적인 주제명으로 구별하며 단순 `001`을 붙이지 않는다. 생성 전 접미사를 제거한 기존 표시명과도 중복을 확인하고 기존 기획이면 재사용한다. `HEX03`, `LINE-001`, WI/H 번호와 실제 구분에 사용되는 `002·003`은 이번 생략 대상이 아니다. 기존 ID를 실제로 변경하려면 별도 호환 이관을 검증한다.

아래 순번형 예시는 과거 식별자 형식과 호환 해석을 설명하며 신규 일반 기획의 명명 기준이 아니다.


기획 문서는 전역 D 번호 대신 다음 안정 ID를 사용한다.

```text
PLAN-{분야}-{주제}-{순번}
```

예:

```text
PLAN-STORY-MIRROR-MAIN-001
PLAN-STORY-YODONG-DEFENSE-001
PLAN-GRAPH-NORTHERN-LIFE-001
PLAN-GAMEPLAY-FIRST-PERSON-FOCUS-001
```

기획 ID는 문서의 정체성을 나타내고 판본은 별도로 증가한다. 파일명을 바꾸거나 내용을 개정해도 같은 기획이면 ID를 유지한다. 전혀 다른 플레이 약속을 독립적으로 검토할 때만 새 기획 ID를 만든다.

### 역경 효사 기획의 하이브리드 경로

역경 64괘의 구체 효사는 `PLAN-STORY-HEX##-LINE-###` 형식의 안정 ID를 사용한다. 384개 ID와 순서는 기계 대장에 전부 등록하지만, 원문 대조·문답·요구사항 검토를 실제로 시작한 효만 `docs/AI/Planning/스토리/<PLAN-ID>/README.md`를 연다. 따라서 안정 주소를 잃지 않으면서 빈 문서 384개의 중복 유지비를 피한다.

역경 스토리는 **괘 하나를 기획 정본 하나**로 관리한다. 괘 문서가 전체 Story Arc와 육효의 Story Beat, 필요한 주체·WI·H·Graph Map·배치 맵을 함께 선언하고, 각 효는 문서 안의 안정 절 앵커로 구분한다. 이 선언은 WI나 H 정의를 자동 생성하지 않으며, 이야기 승인과 개발 준비를 별도로 판정한다. H2 이상은 하위 H 조합 근거가 있어야 하고 개발 Goal 하나는 WI 하나만 소유한다. 기존 `PLAN-STORY-HEXnn-LINE-001..006` ID는 호환 식별자로 보존하되 별도 본문 정본을 계속 편집하지 않는다. 세부 계약은 [메인 스토리와 플레이 기능 결속 체계](메인스토리와플레이기능결속체계.md), 작성 형식은 [역경 괘·효사 기획서 템플릿](../ProjectOverview/templates/역경효사기획서템플릿.md)을 따른다.

실제 공부를 시작한 괘만 물리 문서를 연다. 괘 전체의 의미·캠페인 약속·시작과 완주 변화를 먼저 합의하고, 같은 문서 안에서 초효부터 상효까지 `지금·여기·나·너·이렇게`, 결과, H·WI 요구를 정밀화한다. 아직 다루지 않은 64괘·384효의 빈 문서를 미리 만들지 않는다.

## 현행 정본 경로와 기존 경로의 공존

현행 기획의 장기 표준 주소는 `docs/AI/Planning/<기획 분야>/<PLAN-ID>/README.md`다. 세부 규칙은 [현행 기획 정본 경로](../AI/Planning/README.md)를 따른다.

이 표준은 기존 문서를 일괄 이동하거나 과거 Q/D·문답 경로를 폐기하라는 뜻이 아니다. [기획 목차](../AI/PLANNING.md)가 현재 가리키는 기존 문서는 개별 이관이 끝날 때까지 정본으로 유지한다. 이관할 때는 현행 본문 하나만 새 주소에 두고, 기존 주소는 역사 원문 또는 호환 포인터로 보존하며 목차·역링크·판본/hash를 함께 검증한다. 같은 본문을 두 경로에서 병렬 편집하지 않는다.

## 기획 문서 필수 머리말

새 기획이나 의미 있는 개정에는 다음을 둔다.

```text
기획 ID
기획 분야
기획 판본
상태
상위 기획
관련 하위 기획
관련 결정
관련 WI·PlayableLoop
플레이 순서(메인 스토리와 연결될 때)
Graph Map 영향
다음 질문 또는 인계 상태
```

모든 항목을 억지로 채우지 않는다. 관련 WI나 Graph Map이 아직 없으면 `미등록`, `NoImpact`, `Unresolved`처럼 사실을 적는다.

핵심 진행·성장·광복기 기여를 다루는 새 기획이나 의미 있는 개정은 본문 또는 `문답 영향 묶음`에 **상위 목적 정렬**을 남긴다. `나의 막힘`, `나의 회복 행동과 대가`, `기여 자원`, `상대의 실제 필요`, `권위 결과`, `환류`, `직접 회복이 아닌 보조 층` 가운데 현재 확정된 것과 미정을 구분한다. 직접 회복을 다루지 않는 기획은 억지 연결 대신 보조 층 또는 사유 있는 해당 없음으로 기록하며, 이 사실만으로 기획 전체를 차단하지 않는다.

## 기획 스레드의 응답·기록 형식

기획 스레드의 일반 문답은 전역 결정 번호가 아니라 아래 식별자와 세 층을 차례로 표시한다. 첫째는 **게임 안의 플레이 상황**, 둘째는 그 게임 관계를 읽는 오행 메타데이터, 셋째는 Codex의 게임 기획 추천·이유·대가다. 현재 대화·문서 편집·저장소 작업·Codex 작업 상태를 `지금·여기·나·너·이렇게`에 대입하지 않는다.

```text
[기획 · {기획 분야} · {PLAN-* 기획 ID} · {기획 판본}]
플레이 순서: {메인 위치 / 필수·권장·선택·병행·조건부 귀환·자유 / 앞뒤 관계}

1. 지금·여기·나·너·이렇게
지금: 시간·절기·위기·진행 상태
여기: Area·Graph Map 노드·접근 가능한 공간
나: 실제 행위 주체·역량·소유·상태
너: 상대·사물·환경과 관측 가능한 상태
이렇게: 행동·수행 방법/WI·입력·대가·위험·대안·실패·회복 방식

2. 오행 관계
나의 괘: 이번 선택에서 주로 발휘하는 행위·작용·보조괘
너의 괘: 직접 대하는 대상괘
순환: 어떤 관계가 열리고 무엇이 아직 부족한지

3. 추천
추천: Codex가 권하는 선택 하나
이유: 현재 기획과의 연결
대가: 잃거나 미루는 것, 실패 가능성
확정: 이번 답변으로 확정된 한 가지
미정: 아직 선택하지 않은 것
다음 질문: 이어서 깊게 볼 질문 하나
```

다음 질문은 선택지만 단독으로 제시하지 않고, 아래의 **구체 질문 카드**를 먼저 보여 준다. 이 카드는 사용자가 이야기 선택과 함께 실제 제작 범위를 판단할 수 있게 하는 기획 미리보기이며, 구현 승인이나 Evidence 승격이 아니다.

```text
현재 효·장면: {정식 괘·효 이름과 현재 이야기 위치}
지금: {시간·절기·위기·진행 조건}
여기: {AreaSet·경로·장소와 현재 필요한 공간 범위}
나: {행위 주체와 시작 전 역량·권한·상태}
너: {직접 상대·사물·환경의 시작 전 상태}
이렇게: {사용자가 결정할 행동과 수행 품질·대가·실패·회복}

재사용 H1: {이미 존재하여 그대로 쓸 H1 안정 ID·의미, 없으면 없음}
신규 H1 필요: {새로 만들어야 할 H1과 필요한 이유, 없으면 없음}
상위 H 후보: {H2~H4 조립이 필요한지, 아직 후보면 후보라고 명시}
필요 WI: {재사용 WI·신규 WI 후보·각 WI가 맡는 직접 행위}
Graph Map 영향: {NoImpact / UpdateExisting / CreateSubgraph / CreateGraphMap과 이유}
배치 맵 영향: {NotApplicable / ReviewRequired / Required와 확인할 시야·통행·상대 배치}
구현 경계: {이번 문답은 기획만인지, 어떤 승인 뒤 Graph Map·개발로 내려가는지}

추천: {권하는 선택 하나}
이유: {이야기·플레이·기존 자산 재사용 관점}
대가: {미뤄지는 것·실패 가능성·추가 제작 부담}
다음 질문 하나: {사용자가 지금 확정할 한 가지}
```

H와 WI는 무조건 새로 만들 목록이 아니라 **기존 것 재사용 / 새로 필요 / 아직 후보**로 나눠 쓴다. 효 하나가 여러 WI를 요구할 때도 각 WI가 맡는 직접 행위를 분리하며, 아직 이야기 의미가 확정되지 않은 WI·H에는 안정 ID를 임의로 발급하지 않는다. 질문에 Graph Map이나 배치 맵 영향이 없으면 생략하지 말고 `NoImpact` 또는 `NotApplicable`과 그 이유를 적는다.

오행 관계에는 이번 질문과 직접 관련된 괘만 쓴다. 다섯 괘를 억지로 모두 채우거나 괘성을 능력치·권위 결과·Evidence로 해석하지 않는다. 사용자가 이야기 문답을 읽기 어렵지 않도록 괘 이름과 괘상은 한 번씩만 간결하게 표시한다.

`이렇게`에는 행동·방법·대가·대안을 기록하고, 실제 성공 여부는 결과 칸과 권위 증거에서 따로 판정한다.

메인 스토리와 연결되지 않은 독립 기획은 `플레이 순서: 자유`로 짧게 표시할 수 있다. 연결된 기획은 확정되지 않은 장 번호를 추정하지 않고 필수 선행·권장 순서·선택 분기·병행 가능·조건부 귀환을 구분한다. 순서 표시는 자동 수락이나 강제 이동을 승인하지 않는다.

여기서 `나`는 기본적으로 게임 안의 플레이어 또는 해당 장면의 관점 Actor이고, `너`는 플레이어가 대하는 NPC·사물·환경·조직이다. 문서 체계 자체를 논의한 직후라도 다음 기획 질문을 제시할 때는 현재 다루는 게임 장면으로 돌아가 이 다섯 칸과 오행을 작성한다. 운영·검증 결과는 세 층 바깥의 짧은 별도 문장으로만 보고한다.

- 기존 기획을 깊게 하는 답변은 같은 기획 ID의 판본만 올린다.
- 서로 독립적으로 검토해야 하는 플레이 약속이 생길 때만 새 `PLAN-*` ID를 만든다.
- 답변 본문과 질문은 해당 개별 기획 문서에 기록하고 `PLANNING.md`에는 현재 판본·상태·관계만 반영한다.
- 질문을 제시한 상태는 `Asked`, 사용자가 답한 범위만 `Confirmed` 또는 기획 상태에 맞는 승인 상태로 기록한다.
- 일반 기획 답변을 `D-###로 기록했다`고 보고하지 않는다. 둘 이상의 기획에 공통인 권위·안전·호환 규칙을 별도 결정으로 확정한 경우에만 관련 D를 함께 표시한다.
- 개발·Graph Map 결과는 완결 또는 차단된 최종 상태만 기획의 인계 상태로 받으며, 기획 답변 번호를 대신하지 않는다.

| `ApprovedPlanningBaseline` | 플레이어 약속과 주요 경계가 승인됨 |
| `ApprovedForHandoff` | 판본·해시·영향·제외 범위를 동결해 Graph Map 또는 개발 인계 가능 |
| `Blocked` | 기획 선택이나 필수 근거가 없어 다음 단계 중단 |
| `Superseded` | 새 판본이나 다른 기획이 대체함 |
| `Archived` | 더 이상 현행 기획에서 사용하지 않음 |

`ApprovedPlanningBaseline`은 코드 구현 승인이나 E 승격이 아니다. `ApprovedForHandoff`도 인계 가능 상태일 뿐 자동 실행 명령이 아니다.

## 언제 D 결정을 만드는가

다음 중 하나에 해당할 때만 새 D를 고려한다.

- 둘 이상의 기획이 함께 따라야 하는 장기 원칙
- 서버·Simulation·Unity 권위 경계
- 저장·공개·권리·안전·호환 규칙
- E/H/WI/Graph Map 같은 공통 판정 체계 변경
- 기존 결정을 명시적으로 대체해야 하는 정책

다음은 기획 문서만 개정한다.

- 한 장면의 등장인물·장소·사건 순서
- 선택 카드의 후보와 다음 질문
- 한 퀘스트의 대가·실패·회복·귀환
- 특정 자산 후보나 미확보 상태
- 아직 미정인 수치·대사·거리·연출
- Graph Map에 옮길 개별 노드·엣지 후보

기획 개정에서 여러 기획에 공통되는 새 원칙이 발견되면, 기획 본문을 먼저 확정한 뒤 필요한 원칙만 D로 요약하고 기획 ID·판본을 근거로 연결한다.

## 기획→Graph Map→개발

```text
기획 문답
  → 기획 문서 판본 갱신
  → 기획 목차 상태 갱신
  → ApprovedForHandoff 판본·해시 동결
  → Graph Map 레벨 1·2·3 반영
  → 개발 가능한 작은 slice만 개발 인계
  → 최종 결과를 기획 문서의 인계 상태에 반환
```

Graph Map 또는 개발의 중간 진행을 기획 문서에 누적하지 않는다. 기획에는 최종 반영·차단과 다음 질문만 돌아온다.

### 문답 영향 묶음의 연속 누적

확정된 답변 하나가 나올 때마다 기획 스레드는 해당 기획 판본 안에서 다음 `문답 영향 묶음`을 갱신한다. 별도 D나 새 WI를 자동 생성하지 않는다.

1. 게임 안의 `지금·여기·나·너·이렇게`, 결과·다음 선택
2. 관련된 나의 행위·작용·보조괘와 너의 대상괘
3. 상위 목적 정렬: 나의 막힘·회복 행동과 대가·기여 자원·상대 필요·권위 결과·환류·보조 층
4. 기존 WI·H·노드·엣지·기획 원문과 재사용 후보
5. Graph Map 레벨 1의 생성·변경·무영향 후보
6. 배치 맵 레벨 2의 시야·통행·접근·간격·경계·상태 표현 후보
7. 레벨 3에서 조사할 코드·컴포넌트와 실제 미결속
8. 직접권·1-hop·인과가 확인된 2-hop 영향과 전파 중단점
9. 미정 수치·자산·권위·실행 증거와 검증 상한

묶음 상태는 `AccumulateOnly`, `ReadyForGraphMap`, `GraphMapIntegrated`, `ReadyForDevelopment`, `FeedbackRequired`, `NoImpact`로 구분한다. 답변이 확정됐더라도 핵심 관계나 실패·회복·귀환이 부족하거나 핵심 진행으로 삼은 항목의 상위 목적 정렬이 미정이면 `AccumulateOnly`다. 보조 층으로 명시한 항목은 목적 사슬이 없다는 이유만으로 차단하지 않는다. 기획 판본·hash·영향·제외 범위가 동결되면 Graph Map 담당에게 `ReadyForGraphMap`으로 알리고, 기획 스레드는 중간 결과를 기다리지 않고 다음 문답을 이어간다.

Graph Map이 레벨 1·2·3과 배치 맵 영향을 `Integrated` 또는 `NoImpact`로 반환하고 독립적인 작은 slice가 닫힌 경우에만 기존 개발 인계 원장에 `ReadyForDevelopment` 후보를 만든다. 이는 개발 스레드에 읽을 일이 생겼다는 뜻이지 Goal·WI 활성화, 코드 변경, Unity 실행, Scene 저장 또는 Evidence 승격을 자동 승인한다는 뜻이 아니다. 개발은 현재 소유권·작업 명세·정확 쓰기 경로·검증 상한을 확인한 뒤 명시적으로 수용한다.

## 기존 D 기록 이관 원칙

기존 D 항목은 다음처럼 처리한다.

1. 삭제·재번호화하지 않는다.
2. 현재 기획에 필요한 항목은 기획 문서의 `관련 결정`에서 참조한다.
3. 세부 기획 내용은 기획 문서가 소유하도록 다음 판본에서 정리한다.
4. D 원문은 당시 이력이며 최신 기획 본문으로 사용하지 않는다.
5. 기존 D와 현행 기획이 다르면 대체 관계 또는 현행 기획 판본을 명시하고 조용히 덮지 않는다.
6. 이미 D로 잘못 기록된 개별 기획 답변은 항목을 삭제하지 않고 `CompatibilityPointerOnly`로 표시한 뒤 현행 `PLAN-*` 문서와 판본을 가리킨다.
7. 이관된 D의 세부 문구를 후속 기획 답변으로 계속 갱신하지 않는다.

## 기존 기획의 이름과 내용 이관

- 오래된 기획 문서와 Q/D 이력은 삭제하지 않고 역사 원문으로 보존한다.
- 현행 기획은 플레이 의미가 드러나는 새 표시 이름을 사용할 수 있지만 안정 `PLAN-*` ID와 이전 이름·원문 경로를 함께 남긴다.
- 같은 기획을 현재 구조로 다시 서술한 것은 새 기획으로 복제하지 않고 판본을 올린다.
- 통합 문서는 원문별로 `ReusedAsIs`, `ReframedForCurrentStructure`, `PartiallySuperseded`, `ReferenceOnly`, `ConflictRequiresQuestion`, `NonPlanningExcluded`, `EvidenceMissing` 가운데 현재 처분을 명시한다.
- 이름 변경만으로 과거 선택을 승인·폐기하거나 Graph Map·WI·개발 입력으로 자동 승격하지 않는다.
- `PLANNING.md`는 현행 이름과 문서를 가리키고, 역사 원문은 현행 문서의 계보·대체표에서 역조회한다.
