# Graph Map 기획 인계 순환 체계

## 목적

기획 스레드는 플레이어 약속과 선택을 계속 심화하고, Graph Map 작업은 승인된 기획 판본을 레벨 1·2·3의 구조로 옮겨 검증한다. 두 작업을 분리하되 파일 판본과 반환 결과로 이어서, 기획이 쌓일수록 Graph Map이 갱신되고 Graph Map에서 발견한 공백이 다음 기획 질문으로 돌아오게 한다.

이 체계는 Graph Map을 새 상태 권위나 월드맵으로 만들지 않는다. Graph Map은 실제 E5 배치 전에 기획 관계·공간 제약·코드 결속을 함께 검토하는 도구다. Unity Scene, Prefab 적용, 실제 입력·보행·Game View와 E 승격은 별도 승인과 증거가 필요하다.

계획·기획 인계·개발 인계 관리자는 `GraphMapTooling.ps1`의 저장소 경로 보호·JSON/해시·중복·결정적 출력 경계를 공유한다. 관리자는 고유 오류 접두사와 업무 검증만 소유하며 공통 파일 안전 규칙을 복제하지 않는다.

## 한 줄 흐름

```text
단일 질문 심화
  → 승인된 기획 판본과 SHA-256 동결
  → Graph Map 영향 판정·인계 등록
  → 기존 맵 대조와 레벨 1·2·3 반영
  → 구조·참조·신선도 검증
  → Integrated / Blocked / NoImpact 최종 반환
  → 다음 기획 질문 또는 개발 인계
```

## 소유권

| 역할 | 소유하는 것 | 하지 않는 것 |
| --- | --- | --- |
| 기획 스레드 | 지금·여기·나·너·이렇게, 결과·다음 선택, 승인 판본, Graph Map 영향과 제외 범위, 인계 요청 | Graph Map JSON·생성물·검사 도구 수정, Unity 구현, 중간 실행 대기 |
| Graph Map 작업 | 기존 맵 대조, 레벨 1·2·3 구조화, 하위 맵·포트·connector·overlay 갱신, 기계 검증, 최종 반환 | 누락된 플레이 선택·대가·실패·회복을 임의 창작, Scene/Prefab 적용, E 자동 승격 |
| 개발 통합 | Graph Map 결과를 작업 명세·Logic/Presentation·실제 E5 실행 범위와 연결 | Graph Map의 계획 관계를 운영·Simulation 사실로 간주 |
| 월드·공간·배치 | 승인된 실제 실행 범위의 Scene·Prefab·입력·Game View 검증 | 기획 또는 Graph Map 계획만으로 월드 적용 주장 |

기획 스레드는 인계한 뒤 Graph Map 작업의 중간 단계를 기다리지 않는다. 다른 기획을 이어가며, Graph Map 작업이 `Integrated`, `Blocked`, `NoImpact` 가운데 하나로 끝났을 때 결과를 인수한다. 같은 Graph Map 파일을 여러 작업이 동시에 수정할 때는 Graph Map 담당이 쓰기 소유를 직렬화한다.

## 연속 문답에서 자동으로 이어지는 범위

기획 문답의 `자동`은 확정 답변을 잊지 않고 다음 인계 후보에 누적하고, 관문이 충족되면 담당 스레드에 판본화된 읽기 요청을 보내는 데까지다. Graph Map 수정, 배치 맵 좌표 결정, 개발 수용, 코드 작성과 Unity 실행은 자동 범위가 아니다.

```text
Confirmed 답변
  → 같은 PLAN 판본의 문답 영향 묶음 갱신
  → AccumulateOnly | ReadyForGraphMap | NoImpact
  → Graph Map 담당의 기존 ID·레벨 1·2·3 대조
  → 배치 맵 영향 Update | Create | NotApplicable | Blocked
  → Integrated | Blocked | NoImpact 반환
  → 닫힌 작은 slice만 ReadyForDevelopment 후보
  → 개발 담당의 명시적 수용 또는 차단
```

같은 기획의 연속 답변은 마지막 승인 판본에서 합성한다. 답변마다 Graph Map 인계 행이나 개발 작업을 하나씩 만들지 않으며, 기존 인계가 진행 중일 때 의미가 바뀌면 다음 판본 또는 `FeedbackRequired`로 분리한다. 서로 다른 기획의 독립 묶음은 각각 관문을 통과할 수 있고, 하나가 차단됐다는 이유로 다른 기획 문답과 인계를 멈추지 않는다.

배치 맵 영향은 Graph Map 레벨 2와 함께 판정하지만 산출물은 분리한다. `여기`·`너`·`이렇게`가 H 수량, 상대 위치, 시야 순서, 통행, 접근, 경계 또는 상태별 외형을 바꾸면 배치 맵 후보를 누적한다. 정확 수치·지형·자산 근거가 없으면 상대 관계와 미정을 남기고 좌표나 Prefab을 추정하지 않는다.

## 기획 판본의 필수 인계 정보

승인된 기획 문서는 다음 항목을 사람에게 읽히는 형태로 가진다. 인계 원장은 문서 본문을 복제하지 않고 절·앵커와 SHA-256으로 참조한다.

1. 기획 판본 코드와 승인 상태
2. 원문 문서 경로와 SHA-256
3. 관련 결정 ID와 기존 WI ID
4. `지금·여기·나·너·이렇게→결과→다음 선택` 일곱 칸
5. 상위 목적 정렬: 나의 막힘·회복 행동과 대가·기여 자원·상대 필요·권위 결과·환류·보조 층
6. Graph Map 영향: `NoImpact`, `UpdateExisting`, `CreateSubgraph`, `CreateGraphMap`
7. 질문 영향권: 직접 노드·엣지, 명시 엣지로 연결된 1-hop 인접 노드, 인과가 확인된 2-hop 파급, 상위 H 파생 후보, 전파 중단·미확정 경계
8. 레벨 1에 필요한 플레이 관계
9. 레벨 2에 필요한 배치 제약, 기존 배치 규칙 참조와 미정 수치
10. 레벨 3에서 조사할 코드·컴포넌트 역할
11. 바꾸지 않을 권위·Scene·규칙과 검증 상한

핵심 칸이나 플레이어 대가·실패·회복·귀환, 핵심 진행의 상위 목적 정렬이 미정이라면 Graph Map 작업은 그 의미를 채우지 않는다. 구조화 가능한 부분만 반영하고 질문이 필요한 항목을 `Blocked` 또는 미연결 반환으로 남긴다. 보조 층은 직접 회복 엣지를 만들지 않는다는 경계만 보존하고 독립적인 관찰·표현 관계로 반영할 수 있다.

질문 영향권은 기본적으로 0-hop 직접권, 1-hop 인접권, 인과가 명시된 2-hop 파급권까지만 인계한다. Graph Map 담당은 실제 안정 엣지로 도달할 수 있는지 대조하고, 권위·Area 독립·connector·용량·판본 경계에서 전파를 멈춘다. 2-hop 밖의 중요한 영향은 원 질문을 확대하지 않고 출발 노드·엣지를 참조하는 후속 질문 판본으로 기획에 반환한다. H2 이상은 하위 H와 엣지 변화에서 파생해 재산정하며 질문 답변만으로 직접 승격하지 않는다.

## Graph Map과 별도 배치 맵

Graph Map과 배치 맵은 **논리적으로 연결하되 산출물과 책임을 분리**한다. 기존 배치 계획 엔진·배치 구조·제약 체계 위에 `배치 맵`이라는 판본화된 사람용·기계용 계획 산출물을 두며, 같은 책임의 새 엔진이나 상태 권위를 만들지 않는다.

| 산출물 | 소유하는 내용 | 소유하지 않는 내용 |
| --- | --- | --- |
| Graph Map | 노드·엣지의 플레이 의미, WI, 발견·이동·작업·물류 관계, 필수 연결, 주변 파급, H1→H2 파생 조건 | 개별 Prefab 인스턴스의 좌표·회전·간격, 실제 Renderer·Collider |
| 배치 맵 | `placementInstanceId`, `hDefinitionRef`, 반복 수량, 상대 위치·회전·규모, 전경·중경·배경 역할, 출입·작업·관찰 기준점, 통행·가림·완충·겹침 제약, 자산 후보 | 새로운 플레이 의미·WI·권위 결과, 실제 Unity 배치 성공 |
| Unity 실제 적용 | 동결 배치 맵과 같은 상태 사본을 소비한 Prefab·Renderer·Collider·입력·통행·해제·재적용 | Graph Map·배치 맵을 몰래 재설계하거나 Simulation 결과 변경 |

같은 H1 정의는 배치 맵에서 여러 인스턴스로 반복할 수 있다. 예를 들어 `농업 생산구획` 하나를 정의한 뒤 밭 A·B·C가 서로 다른 `placementInstanceId`로 같은 `hDefinitionRef`를 참조한다. 이 반복으로 WI나 H 정의를 복제하지 않는다.

배치 맵의 연결은 대응 Graph Map 엣지의 안정 ID를 참조한다. 이동·작업·물류 의미를 별도 배치 엣지로 다시 정의하지 않으며, Graph Map 엣지가 바뀌면 영향받는 배치 인스턴스와 제약만 새 배치 맵 revision에서 재검토한다. 반대로 배치 검증에서 통행·가림·점유가 성립하지 않으면 Graph Map 의미를 임의 변경하지 않고 해당 제약과 질문 판본으로 반환한다.

실제 World 지형이 동결되기 전 배치 맵은 상대 좌표·간격·방향·수량 범위만 소유한다. 절대 World 좌표, Scene Transform, 실제 지지면·Collider·보행 성공은 E5 실행과 별도 증거가 있어야 한다. 기존 `immersive-world-layout.v1.json`과 배치 계획 자료는 통합·재사용 후보이며, 새 배치 맵을 만든다는 이유로 과거 판본이나 현행 Scene을 자동 변경하지 않는다.

### 배치 맵의 Synty 표현 조사 태그

공간·시설·식생·소품·Actor 표현이 필요한 배치 인스턴스는 Synty 조사를 배치 맵 준비 과정에 포함한다. Graph Map에는 `visualRequirementTags`로 필요한 역할·분위기·상태만 남기고, 팩·기능 분류·자산 계열·Prefab 후보는 배치 맵의 `assetSurvey`가 소유한다. 이렇게 해야 플레이 의미를 특정 공급자 자산명에 고정하지 않으면서도 보유 자산을 우선적으로 찾을 수 있다.

배치 인스턴스의 선택적 `assetSurvey`는 다음 메타데이터를 사용한다.

| 필드 | 의미 |
| --- | --- |
| `visualRequirementTags` | `생활 주택`, `수리 중`, `숲 완충`, `작업 소품`처럼 기획과 H가 요구하는 표현 역할 |
| `sourcePreferenceCodes` | `SyntyOwnedFirst`, `ProjectOwnedVariant`, `ExistingNonSynty`, `ProceduralFallback`의 허용·우선순위 |
| `syntyPackCodes` | 실제 보유가 확인된 후보 팩. 팩 이름만으로 채택하지 않음 |
| `functionalModuleCodes` | Synty 기능 대장의 기능군·세부 기능군 코드 |
| `assetFamilyIds` | 역할에 맞는 자산 계열 후보. 실제 Prefab과 구분 |
| `candidateRefs` | Prefab GUID·fingerprint가 확인된 주 후보·대체 후보·fallback |
| `surveyStateCode` | `Unsearched`, `InventoryMatched`, `VisualReviewed`, `StaticCompatible`, `UnityVerified`, `Blocked` |
| `modificationNeedCode` | `None`, `WrapperOnly`, `ProjectOwnedCopy`, `BlenderPlanRequired`, `Unknown` |
| `openGapCodes` | 실측·통행·지지·상태 변형·Rig·Collider·권리 등 아직 닫히지 않은 공백 |

태그는 검색과 후보 축소를 위한 메타데이터이며 자동 할당 점수나 Simulation 권위가 아니다. `InventoryMatched`는 이름·분류상 후보, `VisualReviewed`는 이미지·Preview 외형 확인, `StaticCompatible`은 Bounds·피벗·재질·상대 규모 같은 정적 조건 확인, `UnityVerified`는 승인된 동일 판본의 실제 Prefab 결속·활성 표현 검증을 뜻한다. 앞 단계가 뒤 단계를 대신하지 않는다.

Synty 원본은 수정하지 않는다. 원본으로 표현할 수 없으면 `ProjectOwnedCopy` 또는 `BlenderPlanRequired`로 계획을 분리하고, 가공 권리·정확 입력 자산·출력·검증이 승인되기 전에는 후보 상태를 넘지 않는다. 자산 후보가 없더라도 Graph Map의 플레이 관계를 삭제하지 않으며 `Blocked`와 필요한 표현 역할을 기획에 반환한다.

### 기획·Graph Map·배치 맵 삼중 균형

세 산출물의 균형은 문서 분량, 노드 수, 배치 인스턴스 수를 같게 맞추는 뜻이 아니다. **기획의 플레이 약속, Graph Map의 관계 구조, 배치 맵의 공간 판독이 같은 대상과 판본을 역추적할 수 있는 상태**를 뜻한다.

세 산출물에는 [WI 괘성 분류 체계의 산출물 괘상](WI괘성분류체계.md#기획graph-map배치-맵의-산출물-괘상)을 별도 메타데이터로 붙인다. 기획을 세우는 행위는 간괘(☶)지만 동결된 기획 결과물은 `artifactGwae: RI`·리괘(☲)로서 후속 작업이 읽을 의미와 질서를 밝힌다. Graph Map은 `artifactGwae: GAN`·간괘(☶), 배치 맵은 `artifactGwae: TAE`·태괘(☱)다. 이 표시는 탐색·비교·시각화를 돕지만 각 산출물의 책임이나 Evidence 판정을 대신하지 않는다.

이 괘상은 객체의 고정 본질이 아니라 관계 속 역할이다. `기획 RI → Graph Map GAN → 배치 맵 TAE`는 같은 플레이 약속이 의미·관계·공간 구도로 변환되는 주 흐름이고, 공간과 공간 사이의 이동·운송·관측·교환 데이터는 Graph Map 엣지나 오버레이에서 `relationGwae: GAM`·감괘(☵)로 표시할 수 있다. 같은 노드가 경계 구조에서는 간괘, 배치 인스턴스에서는 태괘, 이동 기록의 출발·도착 관계에서는 감괘에 참여해도 안정 ID와 권위 상태는 하나로 유지한다.

감괘 관계의 근거가 공공 데이터인지, 플레이 기록인지, Simulation 상태인지, 수동 기획인지 `dataSourceKind`로 별도 구분한다. 공공 데이터는 출처·기준 시각·단위·이용 조건을, 플레이 데이터는 Session·Actor·Revision·행위 기록을 잃지 않는다. 괘상은 이 계보를 대체하거나 서로 다른 출처를 하나의 권위로 합치지 않는다.

현재 기계 판독에서 `artifactGwae`는 기획 인계 원장에, `relationGwaeCode`와 `dataSourceKindCode`는 이를 채택한 배치 프로필에만 존재한다. 이 문서의 관계 해석을 모든 Graph Map·WI schema에 필수 필드가 이미 있는 것처럼 확대하지 않는다. 공통 schema가 실제로 필요해질 때는 소비자와 호환성을 따로 검토한다.

오행 상생 관점의 **설계 점검 순서**는 `목·JIN WI 가능성 → 화·RI 기획 → 토·GAN Graph Map → 금·TAE 배치 맵 → 수·GAM 근거·문맥 → 다음 목·JIN`으로 읽는다. Graph Map은 WI를 연결하지만 실행하지 않고, 배치 맵은 WI가 읽힐 공간을 준비하지만 실행 성공을 증명하지 않는다. 실제 Runtime의 시간순서는 `WI 실행 → 행위 기록·권위 상태·이동 데이터 → 후속 선택`일 수 있으며, 공공 데이터나 상태 사본은 E1·E4·E6 등 필요한 시점에 먼저 들어올 수도 있다. 따라서 오행 도식을 실행 스케줄러나 고정 단계로 해석하지 않는다. Graph Map 담당은 토 관점을 소유하되 앞뒤 책임을 대신 완성하지 않는다.

| 관점 | 반드시 답할 질문 | 대표 소유 정보 |
| --- | --- | --- |
| 기획 | 플레이어가 왜 이 장소에 오고 무엇을 보고 선택하며 어떤 결과와 다음 선택을 얻는가? | 지금·여기·나·너·이렇게, 선택·대가·실패·회복·귀환, WI와 H 필요성 |
| Graph Map | 그 경험을 성립시키는 대상과 관계가 무엇이며 어디까지 도달·전파되는가? | 안정 노드·엣지, 필수·선택 관계, 레이어, H1→H2 파생, 접근·이동·작업·물류 관계 |
| 배치 맵 | 같은 관계를 사람이 공간에서 어떻게 발견하고 통과하며 구분하는가? | H 배치 인스턴스, 상대 위치·방향·수량, 시야 순서, 기준점, 통행·가림·완충·겹침 제약, 자산 후보 |

삼중 균형은 다음 추적 규칙으로 판정한다.

1. 공간과 관계에 영향을 주는 승인 기획 판본은 `planningRef`와 SHA-256을 가진다.
2. 기획의 핵심 대상·선택·결과 중 관계로 표현할 항목은 하나 이상의 Graph Map 안정 노드 또는 엣지와 대응한다. 대응하지 않는 항목은 `PlanningOnly`와 사유를 남긴다.
3. 플레이어가 실제 공간에서 판독해야 하는 Graph Map 노드·엣지는 하나 이상의 배치 인스턴스·기준점·제약과 대응한다. 비시각·비공간 관계는 사유 있는 `PlacementNotApplicable`로 남긴다.
4. 배치 인스턴스는 반드시 H 정의와 Graph Map 노드·엣지 중 적어도 하나를 참조한다. 단순 장식은 `Decorative`로 분리하고 플레이 의미나 WI를 가장하지 않는다.
5. 기획 선택이 바뀌면 영향 Graph Map을, Graph Map 관계가 바뀌면 영향 배치 맵을 새 판본으로 재검토한다. 배치 검증이 실패해도 기획 의미나 Graph Map 관계를 조용히 바꾸지 않는다.
6. 한 산출물의 미정·차단·무효화 조건은 나머지 둘에서 사라지지 않는다. 서로 다른 상태를 평균내거나 보기 좋은 배치로 결손을 상쇄하지 않는다.
7. 공간 간 흐름을 감괘 관계로 표시할 때는 출발·도착 안정 ID와 `dataSourceKind`, 근거 revision·hash를 함께 남긴다.

다음 값은 기획·Graph Map·배치 맵 묶음의 **추적 준비 상태**로만 사용한다. Evidence, H 성립, WI 실행 상태와 별개의 축이다.

- `BalancedDraft`: 세 관점의 대응표는 있으나 수치·자산·관계 일부가 미정이다.
- `BalancedForE4`: 기획·Graph Map·배치 맵의 판본과 참조가 동결됐고 구조·신선도·규칙성 검사가 통과했다.
- `Blocked`: 필수 플레이 의미, 안정 관계, 배치 제약 중 하나가 누락·stale·충돌 상태다.

`BalancedDraft`는 계속 기획하고 조사할 수 있는 상태이지 E5 준비 완료가 아니다. `BalancedForE4`는 **E4 검토에 사용할 추적 묶음이 동결됐다는 뜻일 뿐 E4 자체를 통과했다는 상태가 아니다.** 실제 Prefab·Scene·Renderer·Collider·입력·Game View도 입증하지 않는다. 공간·배치 대상이 E5로 넘어가려면 같은 판본 묶음을 E4 Evidence가 실제 소비하고 별도 실제 적용 증거를 남긴다. 비공간·비시각 WI는 사유 있는 `PlacementNotApplicable`을 사용할 수 있다.

## Graph Map 영향 판정

| 판정 | 사용 조건 | 결과 |
| --- | --- | --- |
| `NoImpact` | 공간·관계·표현·코드 결속에 변화가 없는 수치·문구 정제 | 맵을 고치지 않고 근거와 이유만 반환 |
| `UpdateExisting` | 기존 노드·엣지·제약·결속의 의미나 상태를 보완 | 기존 안정 ID를 유지하고 판본을 올림 |
| `CreateSubgraph` | 기존 federation 안에서 독립 책임·규모·소유 경계가 새로 필요 | 하위 맵과 port/connector를 추가하고 전체 맵과 연결 |
| `CreateGraphMap` | 기존 맵과 플레이·공간 책임이 독립이고 연결은 외부 관문으로 충분 | 새 Graph Map을 만들고 명시적 connector만 둠 |

유사한 이름, 같은 Area, 같은 자산 팩만으로 새 노드나 관계를 추론하지 않는다. 기존 WI·결정·H·AreaSet·Graph의 안정 ID가 있으면 먼저 재사용한다.

## 레벨별 반영 책임

### 레벨 1 — 플레이 관계

- 노드: 발견·생산·입고·회복처럼 플레이어가 판독하는 역할과 선택 지점
- 엣지: 이동·발견·작업 인계·물류·외부 관문
- 각 노드의 일곱 칸, 관련 WI·결정, 실제 참조와 미해결 계획의 구분
- 핵심 진행의 나의 막힘·회복 행동·기여 자원·상대 필요·권위 결과·환류 연결과 직접 회복이 아닌 보조 층의 구분
- 필수·선택·분리·미정 연결과 귀환 가능성

레벨 1은 “무엇을 왜 이어서 플레이하고, 누구의 어떤 실제 변화가 다음 선택으로 돌아오는가”를 답한다. 좌표·간격·Prefab 이름을 플레이 의미 대신 쓰지 않으며, 회복이라는 이름만으로 근거 없는 엣지나 공통 수치를 만들지 않는다.

### 레벨 2 — 배치 제약

- 통행·접근·지지·차폐·간격·가시선·방향·용량·안전 경계
- 노드 내부와 노드 사이의 제약 소유
- 확정 수치, 연구 기준, 미정 수치의 구분
- 기존 배치·LH·월드맵 엔진에 맡길 집행 책임
- 기존 H5 배치 규칙의 판본·식별자와 `BoundToGraphConstraint | AvailableNotSelected | OutsideCurrentGraph` 구분

레벨 2는 “어떤 조건을 만족해야 자연스럽고 실행 가능한가”를 답한다. 기존 배치 규칙은 별도 결속 대장에서 원본 판본과 적용 제약을 추적하며, Graph Map이 새 수치 규칙이나 H 성립 판정을 만들지 않는다. 계획 제약 통과는 실제 Scene 통과가 아니다.

### 레벨 3 — 코드·컴포넌트 결속

- 관련 assembly, 파일 경로, 심볼, SHA-256
- 읽기·검사·조립·표현·Editor 전용 역할
- 레벨 1·2 대상 selector와 미결속 대상
- canonical Scene과 Runtime 증거 경계

레벨 3은 코드 본문을 복제하지 않고 “어디에서 무엇을 소비·검사하는가”만 연결한다. 파일 존재·hash 일치는 실제 배선·Play Mode·Game View를 증명하지 않는다.

## 기존 Graph Map을 통합하는 정규화 리팩토링

노드·엣지 의미를 정규화할 때 현행 Graph Map 옆에 같은 세계를 설명하는 새 체계를 병렬로 만들지 않는다. 기존 안정 식별자, 기획·결정·WI 근거, 실제 공간 참조, 배치 규칙 결속, 하위 맵·port·connector와 레벨 3 코드 결속을 단일 현행 Graph Map 안에서 보존·통합한다.

### 정규화 기준

- `지금·여기·나·너·이렇게→결과→다음 선택` 일곱 칸은 삭제하거나 축약하지 않는 기획 의미의 기준선이다. 정규화 저장에서는 공통 `지금·여기`를 하위 그래프 문맥으로, `나·너`를 Actor·대상 노드 참조로, `이렇게·결과·다음 선택`을 엣지 계약으로 분리할 수 있지만 사람용 생성 조회와 기획 인계에서는 각 플레이 관계의 일곱 칸을 다시 완전하게 조립해야 한다. `이렇게` 엣지는 시간·공간·Actor·대상과 현재 목적에서 가져온 행동·수행 방법·필요 조건을 추적하며, 대표 추천 하나를 유일한 전역 최적 경로로 만들지 않는다.
- 노드는 장소·Actor·세계 객체·자원·외부 관문처럼 여러 관계에서 다시 참조할 수 있는 명사형 안정 대상을 기본으로 한다.
- 엣지는 이동·관찰·작업·운반·목격·상태 전이·권한 부여처럼 대상 사이에서 일어나는 동사형 플레이 관계를 기본으로 한다.
- 사건·결과를 표현하던 기존 노드는 즉시 삭제하지 않는다. 먼저 대응 엣지의 `guardRefs`, `worldInteractionIds`, `inputRefs`, `effectRefs`, `observationRefs`, `failureReturnRef`로 의미를 옮기고, 기존 노드 ID는 호환 별칭 또는 읽기 전용 역사 참조로 남긴다.
- 실제 공간 노드와 플레이 사건을 한 노드에 합치지 않는다. 공간·Actor·객체 노드는 유지하고, 그곳에서 가능한 사건은 엣지와 상태 효과로 연결한다.
- 레벨 2 제약은 자연어를 새로 복제하지 않고 기존 배치 규칙·H 계층·형성 방식·안전 경계의 안정 ID를 재사용한다.
- 레벨 3은 정규화된 노드·엣지별로 권위 입력, 권위 결과, Unity 소비, 표현, 시험과 미결속 사유를 조회하되 기존 코드 결속 대장을 단일 기준으로 유지한다.

### 점진적 이관 상태

각 기존 요소는 다음 가운데 하나로 판정한다.

- `Retained`: 명사형 안정 대상으로 그대로 유지
- `Reclassified`: 안정 ID를 유지하고 노드·엣지 종류만 명확히 함
- `RelationExtracted`: 사건형 노드의 의미를 하나 이상의 엣지 계약으로 추출
- `CompatibilityAlias`: 새 관계를 가리키는 역사 호환 ID로만 유지
- `Blocked`: 원래 의미·권위 결과·귀환을 잃지 않고 옮길 근거가 부족함

`RelationExtracted`를 완료하려면 기존 기획 문맥·WI·결정·제약·코드 결속을 새 관계에서 모두 역추적할 수 있어야 한다. 생성 조회와 회귀 검사는 이전 전후의 도달 가능한 다음 선택, 필수·선택 연결, 실패·중단·귀환, 미결속 목록이 조용히 사라지지 않았는지 비교한다. 완전 이관 전에는 호환 별칭을 제거하지 않는다.

### 개발 부담을 줄이는 출력

Graph Map 담당은 개발 인계 때 전체 맵이 아니라 진입 노드와 종료 관문으로 닫힌 연결 부분 그래프를 추출한다. 이 묶음에는 대상 노드·엣지, 레벨 2 제약, 레벨 3 결속, 재사용 WI, 미결속 사유, 검증 상한이 함께 있어야 한다. 개발은 이 묶음 밖의 기획 의미를 다시 추론하지 않으며, 누락된 계약은 임의 구현하지 않고 가장 이른 기획·Graph Map 단계로 반환한다.

이 리팩토링은 기존 Graph Map 결과를 폐기하거나 실제 Unity Scene·Prefab·입력·E 성숙도로 자동 승격하는 작업이 아니다. 한 PlayableLoop 하위 그래프에서 의미 보존을 입증한 뒤 같은 방식으로 다음 하위 그래프에 적용한다.

첫 정규화 표본은 북부 생활권의 한스 농장 하위 그래프로 고정한다. 이 표본은 노드·엣지 표현과 기존 의미 보존 방식을 함께 설계·이해하기 위한 비교 대상이며, 표본 지정만으로 Graph Map JSON 마이그레이션·개발 인계·Unity 구현을 승인하지 않는다.

한스 표본의 첫 설계 규칙은 Actor 노드의 지속성 기준이다. 한스처럼 여러 사건에서 고유 정체·상태·관계·권한이 이어지고 다른 노드와 반복 연결되는 고유 NPC는 안정 Actor 노드로 둔다. 이름 없는 작업자·경비병·운송 인력처럼 해당 관계 안에서 역할만 필요한 집단은 개별 노드를 대량 생성하지 않고 엣지의 `actorRoleRef`로 참조한다. 이후 고유 상태나 장기 관계가 생기면 기존 역할 참조의 계보를 보존하며 Actor 노드로 승격할 수 있지만, 이름이 있다는 이유만으로 자동 승격하지 않는다.

## 인계 상태

```text
Draft
  → ApprovedForHandoff
  → AcceptedByGraphMap
  → Integrated | Blocked | NoImpact
  → Superseded
```

- `Draft`: 기획이 아직 바뀔 수 있어 Graph Map 쓰기를 시작하지 않는다.
- `ApprovedForHandoff`: 기획 판본·hash·범위가 동결됐다.
- `AcceptedByGraphMap`: 담당이 신선도와 쓰기 소유를 확인했다.
- `Integrated`: 요청한 레벨이 반영되고 검사·반환 근거가 있다.
- `Blocked`: 기존 판본 충돌, 누락된 플레이 결정, 실제 참조 공백 등으로 안전하게 반영할 수 없다.
- `NoImpact`: 검토 결과 Graph Map 변경이 필요하지 않다.
- `Superseded`: 새 기획 판본이 이전 인계를 대체한다.

중간 실패를 `Integrated`로 올리지 않는다. `Blocked`는 차단 항목, 가장 이른 책임 레벨, 기획 질문 여부를 함께 반환한다.

## 반환 형식

Graph Map 작업은 최종 반환에서 다음을 구분한다.

- 반영: 추가·수정·재사용한 레벨 1/2/3 식별자
- 목적 정렬: 핵심 진행의 목적 사슬을 연결한 노드·엣지와 보조 층으로 남긴 요소
- 미반영: 이유와 원문 위치
- 차단: 기획 선택 필요 / 기술 조사 필요 / 실제 E5 실행 필요
- 검증: Graph Map Check, 회귀시험, 범위 Fast
- 증거 상한: Scene·Prefab·입력·Game View·E 승격 여부
- 결과 판본: Graph Map revision·hash와 보고서

기획은 플레이어 선택이 필요한 차단만 다음 단일 질문으로 이어간다. 기술 공백은 개발 또는 전문 담당의 후속으로 보내며 같은 질문을 반복하지 않는다.

## 개발로 이어지는 다음 인계

Graph Map이 `Integrated`됐다고 전체 맵을 곧바로 개발하지 않는다. [Graph Map 개발 인계 체계](GraphMap개발인계체계.md)에 따라 한 PlayableLoop·대표 WI·검증 가능한 노드/엣지/제약 묶음을 작은 slice로 고르고, 기존 Goal·E7 작업 명세·work item 후보와 결속해 `ReadyForDevelopment`로 넘긴다. 개발이 판본·소유·정확 쓰기 경로·검증 상한을 확인하기 전에는 자동 활성화하지 않는다.
