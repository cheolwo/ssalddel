# E1~E7 수직 폐루프와 E8~E10 수평 증거 체계

## 목적

이 문서는 현재 증거 모델 `horizontal-dual-cycle-evidence.r3`의 기준이다. 준비된 주체 사이의 WI Goal 하나를 만드는 수직 성숙도와, 완성된 상호작용 또는 선택적 폐루프 묶음을 반복 안정화하고 영역으로 조립해 사람이 승인한 뒤 제한 운영하는 수평 성숙도를 분리한다. 수직·수평은 판정 주체의 관계이며, 어느 쪽도 논리만 한 방향으로 통과하는 절차가 아니다.

Unity·Unreal의 공식 시험·검증·제한 배포 관행과 각 단계의 직접 대응·부분 대응·Mirror 고유 확장은 [E1~E10 게임업계·엔진사 공식 자료 대응](../Reports/E1-E10-게임업계공식자료대응-2026-09-03.md)에서 구분한다. 외부 도구나 권장 방식의 존재는 현재 프로젝트의 실행 증거나 E 승격을 대신하지 않는다.

```text
한 WI Goal의 수직 완성
Logic:       E7 → ... → E1 영향 검토 / E1 → ... → E7 조립·검증
Presentation:E7 → ... → E1 영향 검토 / E1 → ... → E7 조립·검증
Integrated:  min(Logic, Presentation)

완성된 E7의 수평 안정과 영역 조립
E7 WI Goal 또는 선택적 PlayableLoop 묶음 → E8 개별 반복 안정
E8 결과 둘 이상 → E9 영역 조화·사람 승인 → E10 제한 운영
```

E8~E10은 E1~E7과 같은 수직 작업 명세를 계속 늘리는 단계가 아니다. 기존 PlayableLoop 결속 항목의 E8 판정 주체는 `PlayableUnitStabilityCampaign`, E9는 `AreaHarmonySet`, E10은 `LimitedOperationWindow`다. Loop 없는 신규 Goal도 E7에서 끝나며, E8이 필요하면 WI Goal을 대상으로 하는 별도 안정성 캠페인을 명시적으로 등록해야 한다. 현재 기존 캠페인 원장을 임의로 복제하거나 E7 완료만으로 E8을 만들지 않는다.

## Loop 없는 WI 작업 명세의 호환 검증

`manage-e7-vertical-work-order.ps1`는 기존 `playableUnitStableId` 결속과 신규 `interactionGoalStableId` 결속을 구분한다. 신규 결속에서는 주체 기반 원장의 실제 Goal·WI, 동일한 Ready 주체 목록, 승인 기획 판본·파일 hash·승인 근거, 등록 작업 명세와 전달 상한을 대조한다. 선택적 PlayableLoop가 없는 Goal에 가짜 Loop를 만들지 않는다. 선택적 Loop가 있으면 그 참조와 WI 포함 여부도 검사한다.

두 형식 모두 동일한 E7 v2 궤적·상향 검증·표현 준비·통합 관문 검사를 받는다. 양식 검증 통과는 단계 승격이 아니다. Loop 없는 표현 근거는 Goal 식별자에 결속하며, 기존 Loop의 단계 일치 검사를 완화하지 않는다. 회귀 검사는 [`e7-native-work-order.ps1`](../../eng/tests/e7-native-work-order.ps1)과 기존 [`e7-vertical-work-order.ps1`](../../eng/tests/e7-vertical-work-order.ps1)로 나눈다.

WI 실행 파이프라인은 세 번째 성숙도 축이 아니라 Logic과 Presentation을 같은 `WI·Command·WorldRevision`으로 결속하는 공통 관문이다.

| 단계 | 파이프라인 확인 |
| --- | --- |
| E1 | 결과·변화 의미·분야 성장 적용 여부 계약 |
| E2 | 신뢰 Adapter·권위 원장·표현 소비자 결속 |
| E3 | 멱등성, Save/Replay, LocalProcess·RemoteHost 동등성 |
| E4 | TriggerSource·Actor·대상·공간·프로필 확정 |
| E5 Logic | 권위 반영과 같은 계보의 행위 기록, 성장 적용 또는 사유 있는 `NotApplicable` |
| E5 Presentation | 같은 Revision의 상태 사본 또는 행위 원장을 읽는 표현 소비자 |
| E6 | 실패·후퇴·오래된 cursor·checkpoint 재조립과 설명 가능성 |
| E7 | 실제 입력부터 결과·귀환·Game View 피드백까지 같은 계보 |
| E8 | 원장·성장 hash와 trace digest 반복 동등성 |
| E9 | 여러 Core의 행위 계보·자원 인계·엔진 cursor 연속성·사람 평가 |

비권위 trace는 검증 설명 자료이며 Save/Replay canonical hash에 넣지 않는다. 파이프라인 관문 실패는 관련 궤적의 가장 이른 E를 다시 열고 통합 E는 계속 두 궤적 중 낮은 값으로 계산한다.

## E1~E7 — 한 WI Goal의 수직 완성

| 단계 | 판정 질문 | 대표 증거 |
| --- | --- | --- |
| E1 | 플레이어 약속과 권위 계약이 확정됐는가? | StableId, 입력·출력, 경계, 완료 조건 |
| E2 | 계약을 실행할 코드와 Adapter가 준비됐는가? | Core·서버·Unity 소비 계약 |
| E3 | 같은 선택이 결정적으로 저장·복원·재생되는가? | 자동 시험, Save/Replay hash |
| E4 | WI의 발생원·주체·대상·자원·시간과 필요한 H 문맥이 결속됐는가? | 실행 문맥, 예약, WI–H 결속 |
| E5 | 선택과 결과가 권위 세계에서 실제로 발현되는가? | Preview·Confirm, Task·Effect, 후속 WI |
| E6 | 실제 플레이 전에 의미·인과·배치·피드백·귀환 결함이 정제됐는가? | 정제 질문표, 필요한 현실 근거와 계보 |
| E7 | 사람이 저장 Scene에서 실제 입력으로 WI의 결과와 귀환 또는 다음 선택까지 끝낼 수 있는가? | Play Mode, Game View, Console, 성공·실패·회복·귀환 |

새 WI Goal은 주체 기반을 먼저 확립하고 논리와 표현 각각에서 E7 목표부터 E1까지 영향을 검토한 뒤 가장 낮은 미완료 의존성을 구현하고 E1에서 E7 방향으로 검증한다. 표현 E1~E4 계획은 논리 E5 전에 만들 수 있지만 실제 표현 E5 증거는 논리 E5 상태 사본 없이는 승격하지 않는다. 상향 과정에서 누락이 발견되면 같은 Goal과 작업 명세를 유지한 채 해당 궤적의 가장 이른 E를 다시 연다. 통합 단계는 항상 두 궤적 중 낮은 값이다. 여러 WI의 폐쇄성을 함께 검증해야 하는 Goal만 선택적 PlayableLoop 참조를 추가한다.

### 상위 E는 모든 하위 E를 누적 소비한다

E1은 해당 궤적의 기초 계약이다. E2 이상은 자기 단계의 새 증거만 추가하는 번호표가 아니라, **같은 후보·판본에서 모든 하위 E의 유효한 결과를 실제 입력으로 소비하고 그 위에 새 질문을 닫는 누적 관문**이다.

```text
E1 = 기초 계약
E2 = E1 + 실행 준비
E3 = E1~E2 + 결정성·자동 검증
E4 = E1~E3 + Actor·대상·시간·H·표현 문맥
E5 = E1~E4 + 권위 세계·실제 표현 결속
E6 = E1~E5 + 의미·인과·실패·회복·귀환 정제
E7 = E1~E6 + 실제 입력·화면·결과·귀환 완주
E8 = 동결된 E1~E7 묶음 + 반복·Save/Replay·Local/Remote 안정
E9 = 구성원 각각의 E1~E8 묶음 + 영역 간 조화·사람 승인
E10 = 승인된 E1~E9 묶음 + 제한 운영·rollback 관찰
```

성능·접근성·현지화·플랫폼 호환·보안/개인정보·관측·Migration/rollback·콘텐츠 권리는 새 E 번호가 아니라 필요한 폐루프에 붙는 교차 품질 프로필로 관리한다. 적용 대상은 E1에서 요구와 예산을 선언하고, 이후 단계가 해당 하위 증거를 누적 소비한다. 세부 성립 관문은 [E1 기획 근거 결속 체계](E1기획근거결속체계.md#업계-관행을-반영한-교차-품질-프로필)를 따른다.

### E3의 점과 E8의 선 — 기획·장면 관계를 읽는 보조 해석

기획과 장면을 함께 살필 때에는 E3와 E8의 관계를 다음과 같이 읽을 수 있다. 이 해석은 현행 E 판정 기준을 바꾸거나 E4~E7을 생략하기 위한 새 단계가 아니다.

- **E3의 점**: 한 행동·상태 변화·표현 조립 단위가 같은 입력과 판본에서 결정적으로 검증된 상태다. 아직 실제 장면 배치나 플레이 완주를 뜻하지 않는다.
- **E4~E6의 연결 준비**: 검증된 점에 Actor·대상·시간·H·Graph Map·자산 후보·배치 맵과 실제 세계 결속·정제 문맥을 더한다.
- **E7의 한 번 이어진 선**: 같은 `PlayableUnit` 안에서 진입·선택·행동·결과·실패/회복·귀환을 실제 입력과 화면으로 한 번 완주한다.
- **E8의 안정된 선**: E7에서 이어진 같은 선을 동일 후보 revision과 build hash로 반복하고 Save·Restore·Replay·재진입·Local/Remote 경계를 통과시켜, 우연히 한 번만 이어진 결과가 아님을 입증한다.
- **E9의 선 사이 조화**: 서로 다른 E8 `PlayableUnit`의 선 둘 이상을 같은 영역에서 함께 읽고 권위·자원·시간·공간·카메라·입력·피드백의 조화를 사람이 평가한다.

따라서 여러 흩어진 장면을 잇는다는 말은 **한 `PlayableUnit`의 장면 마디를 잇는 경우에는 E7에서 형성하고 E8에서 안정성을 입증한다**는 뜻이다. 서로 다른 `PlayableUnit`을 하나의 생활권이나 이야기 흐름으로 조화시키는 일은 E8에 합쳐 넣지 않고 E9가 소유한다. E3의 개별 시험 통과만으로 장면의 선이나 E8을 선언할 수 없으며, E8의 반복 성공으로 서로 다른 Core의 E9 조화를 대신할 수도 없다.

여기서 `소비`는 과거 문서나 시험 이름이 존재하는지만 확인하는 일이 아니다.

- 선행 증거의 Goal·WI·궤적·범위·revision·hash와 무효화 조건을 현재 후보에 연결한다.
- 선행 결과가 현재 코드·상태 사본·자산·배치·입력·실행 경로에서 실제로 사용되는지 확인한다.
- 논리와 표현, 서로 다른 하위 단계 사이의 충돌·누락·만료를 검사한다.
- 적용하지 않는 항목은 숨기지 않고 대상 범위와 사유가 있는 `NotApplicable`로 남긴다.
- 현재 단계의 EvidencePackage에는 소비한 하위 근거와 새로 추가한 증거를 구분해 기록한다.

누적 소비는 매 승격마다 모든 과거 시험을 무조건 처음부터 다시 실행한다는 뜻이 아니다. 같은 후보 revision과 hash에 묶였고 무효화 조건이 발생하지 않은 동결 증거는 재사용할 수 있다. 다만 계약·규칙·코드·자산·배치·입력·실행 환경 중 하나가 바뀌어 선행 근거의 적용 가능성이 달라지면, 영향을 받은 가장 이른 E부터 목표 단계까지 다시 소비·검증한다.

따라서 E6가 통과했어도 E2 Adapter가 현재 후보에서 빠졌다면 실제 성숙도는 E6가 아니다. E9의 사람 평가가 좋아도 구성원 하나의 E5 결속이 무효화되면 해당 AreaHarmonySet의 E9 근거도 함께 무효화된다. 상위 E는 하위 결손을 평균·다수결·보기 좋은 화면으로 상쇄할 수 없으며, 논리·표현 통합 E는 계속 두 궤적과 유효한 선행 근거 중 가장 낮은 단계로 판정한다.

### E1~E7과 오행 설계 순환의 관계

[WI 괘성 분류 체계의 오행 균형 순환](WI괘성분류체계.md#오행-균형-순환)은 WI·기획·Graph Map·배치 맵·데이터 사이의 설계 결손을 찾는 내부 관점이다. E1~E7의 판정 대상은 오행 자체가 아니라 **같은 주체·WI Goal의 계약·구현·결정성·문맥·권위 발현·정제·실제 입력과 귀환**이다. 오행 관점은 이 누적 증거에서 빠진 책임을 찾는 데 사용하며 새 단계·점수·실행 권위를 만들지 않는다. 다만 권위 상태 변화를 소유하거나 일으키는 역할 객체가 있는 WI는, E5에서 어떤 객체가 어떤 행위·작용·상태 전환을 실제로 발현해야 하는지 E1~E4에서 동결하기 위한 필수 추적 정보로 오행 분류를 사용한다.

E 단계와 오행을 고정된 일대일 대응으로 해석하지 않는다. 한 E 단계가 여러 오행 관점을 함께 소비할 수 있고, 같은 오행 관점도 E가 높아지면서 계획 근거에서 실제 실행 근거로 정밀해진다. 공간·시각 표현이 필요 없는 WI에는 Graph Map·배치 맵·자산을 강제하지 않고 기존 사유 있는 `NotApplicable`을 사용한다.

| Evidence | 오행 관점으로 추가 점검할 수 있는 것 |
| --- | --- |
| E1 | 어떤 WI 행동·상태 변화를 의도하는지와 실제 실행 Actor·직접 대상·영향 범위·회복 판정 대상을 계약한다. |
| E2 | 계약·Adapter·소비자가 기획 의미와 안정 대상·관계를 잃지 않고 연결되는지 확인한다. |
| E3 | 같은 입력·판본에서 대상별 개선·유지·손실, 기여 원인과 반복 방지가 결정적으로 저장·복원·재생되는지 확인한다. |
| E4 | Actor·대상·시간·필요한 H 문맥과 결과 피드백을 확인한다. 권위 전환을 소유하거나 일으키는 역할 객체는 역할·주행위·작용·시작/완료/효과를 오행 관계와 함께 동결하고, 공간·시각 WI일 때만 Graph Map 관계·배치 맵·자산 후보를 함께 확인한다. |
| E5 | 같은 판본의 역할 객체 행위 분류를 포함한 동결 E1~E4를 소비해 WI의 권위 상태 변화와 공간 표현이 같은 계보에서 실제로 발현되는지 확인한다. 분류가 누락·오래됨·불일치이면 E5를 차단하며, 이 결속만으로 회복 기여를 지급하지 않는다. |
| E6 | 실패·중단·상충 손실·회복·귀환과 기여 대상·범위를 정제하고, 선택된 경우에만 공공 데이터·플레이 기록의 출처와 적용 범위를 확인한다. |
| E7 | 사람이 실제 입력으로 WI를 수행하고 대상별 결과와 적격 회복 피드백을 읽으며, 귀환·종결 또는 다음 선택까지 폐루프를 확인한다. |

따라서 E7은 화면 한 번이 보였다는 뜻이 아니라, 필요한 계약과 실행 근거가 같은 주체·WI·Goal·Session·Revision에서 이어졌다는 최종 수직 근거다. 반대로 오행 표가 균형적으로 보이거나 WI가 완료됐더라도 E1~E7 증거와 기여 Profile이 없으면 성숙도나 회복을 자동으로 올리지 않는다. 오행은 결손을 찾는 내부 설계·조회 메타데이터이고, Evidence는 WI Goal과 선택적 PlayableLoop 묶음의 실제 성숙도를 판정하는 근거 체계다.

E7에서 생성된 행위 기록·상태 사본·이동·관측 결과는 다음 기획과 WI 후보로 환류할 수 있다. 다음 후보가 실제로 생겼을 때만 E1 계약부터 새로 누적 입증하며, 귀환이나 종결로 닫힌 폐루프에 후속 WI를 억지로 만들지 않는다. 이 환류는 새 E를 자동 승인하지 않는다.

### E4에서 E5로 넘기는 표현 준비 인계

기획 스레드는 승인된 플레이 의미와 함께 아래 Presentation E4 준비 묶음까지 작성할 수 있다. 이는 E4의 문맥·후보·배치 규칙을 개발이 다시 추측하지 않게 하는 인계이며, E2 구현·E3 시험 또는 실제 E4 통과를 대신하지 않는다. 권위 상태 변화를 소유하거나 일으키는 역할 객체가 있으면 E4 인계에는 역할 객체 종류·역할·행위·시작/완료 상태·효과와 오행 분류 원장 revision/hash도 포함한다. 실제 Prefab·Terrain·Renderer·Collider·입력과 권위 상태를 World에 결속하는 E5부터는 개발 통합 담당이 소유하고, 필요한 Editor·Game View 작업은 월드·공간·배치 담당과 조율한다. 따라서 기획은 E5 실행을 기다리지 않고 다음 문답을 이어가며 개발은 완결 또는 차단 결과만 기획에 반환한다.

공간·물체·소품·Actor·UI 시각 자료가 플레이어 판독에 필요한 WI는 E4에서 단순히 “자산이 필요하다”고 적는 데서 멈추지 않는다. 다음 `presentationE4Preparation`을 판본화해 E5가 새로 자산을 탐색하거나 임시 배치를 장기 계약으로 굳히지 않게 한다.

```text
플레이어가 읽을 순간
+ 필요한 H 역할·능력 또는 사유 있는 NotApplicable
+ 의미 기반 VisualKey
+ 주 자산 후보 / 대체 후보 / 대체 표현 fallback
+ 공간·배치 대상이면 동결된 배치 맵 ID·revision·hash
+ 배치 맵이 참조하는 Graph Map ID·revision·hash와 대상 노드·엣지
+ H 정의와 배치 인스턴스 ID·반복 수·상대 위치·방향·규모·시야 역할
+ 지지면·방향·접근·통행·가림·완충·겹침을 포함한 배치 제약
+ InteractionAnchor 의도
+ 후보 revision 또는 fingerprint
+ 배치 맵 규칙성 검사 결과와 무효화 조건
+ Ready / Conditional / Blocked와 열린 결함
        ↓
E5 실제 Prefab·대체 표현 선택과 World 배치·WI 발현
```

E4는 후보의 존재와 선택 기준, 대체 경로와 결함을 드러내는 단계다. 공간·배치가 필요한 WI는 **Graph Map의 의미 관계를 참조하는 배치 맵을 먼저 동결하고 규칙성 검사를 통과해야 한다.** 배치 맵은 H 정의 자체를 복제하지 않고, 같은 정의를 사용하는 개별 배치 인스턴스와 상대 구도·제약을 판본화한다. 최종 절대 좌표, 저장 Scene 배치, 활성 `Renderer`·`Collider`·`Bounds`, 실제 Preview·Confirm 결과는 E5 이후 증거다. 따라서 자산 조사나 배치 맵 문서만으로 E5를 선언할 수 없다. 반대로 비공간·비시각 WI는 사유 있는 `NotApplicable`을 기록하고 불필요한 H·Prefab·배치 맵을 만들지 않는다.

배치 맵 규칙성 검사는 최소한 참조 ID·판본·hash의 최신성, Graph Map 노드·엣지와 H 정의의 존재, 배치 인스턴스 ID의 유일성, 필수 기준점·접근·통행·지지·가림·완충·겹침 제약의 충족, 자산 후보 fingerprint와의 일치를 확인한다. 필수 입력이 없거나 오래됐거나 서로 충돌하면 `Blocked`로 두고 표현 E4를 다시 연다. 선택적 미관 문제는 `Warning`으로 남길 수 있지만 경고 자체가 E5 증거를 만들지는 않는다. 이 구조 검사는 실제 Unity 배치·Play Mode·Game View를 대신하지 않는다.

E5는 위 E4 인계만 단독으로 읽지 않고 대상 WI에 적용되는 E1~E4 논리·표현 근거를 같은 Goal·Session·객체·Revision으로 함께 소비한다. 역할 객체의 적용 가능한 행위 분류가 없거나 공식 WI의 `ActionCode`·시작/완료 상태·`EffectCode`와 다르면 E5를 차단한다. 정적 배경·장식·설명 전용 객체에는 가짜 행위를 만들지 않고 대상·도구·배경 문맥 또는 사유 있는 `NotApplicable`로 남긴다. 공간·배치 대상의 실제 배치는 동결된 같은 배치 맵을 소비해야 하며, 인스턴스·후보·제약을 바꾸려면 배치 맵의 새 revision을 만들고 표현 E4부터 다시 검증한다. 누락·만료·충돌을 임시 자산·좌표·기본값으로 덮지 않으며, 맥락이 맞지 않으면 [논리·표현 이중순환의 E5 맥락 소비 관문](플레이폐루프논리시각이중순환체계.md#e5는-e1e4-맥락을-소비하는-실제-결속-관문이다)에 따라 가장 이른 책임 E를 다시 연다.

## E8 — 개별 플레이 폐루프 안정

E8의 판정 주체는 E7을 통과한 `PlayableUnit` 하나에 대응하는 `PlayableUnitStabilityCampaign`이다. 같은 후보 revision과 build hash를 동결하고 우연한 1회 성공이 아닌 반복 가능성을 검증한다. 기획 관점에서는 E3의 검증된 행동·상태라는 점들이 E4~E7을 거쳐 하나의 플레이 폐루프 선으로 이어진 뒤, 그 선이 반복·저장·재진입·실행 위치 변화에도 끊어지지 않는지를 판정하는 단계로 읽는다. 이 보조 해석은 아래 기존 관문을 완화하거나 대체하지 않는다.

| E8 관문 | 최소 기준 |
| --- | --- |
| 논리 반복 | 같은 fixture·명령열을 최소 3회 실행해 canonical hash 일치 |
| 저장 경계 | Save·Restore·Replay 결과와 hash 일치 |
| 권위 위치 | LocalProcess·RemoteHost가 같은 Simulation Core 결과를 생성 |
| 표현 반복 | canonical `SimulationWorldShell`에서 실제 입력 완주 최소 2회 |
| 재진입 | 저장 뒤 Scene 재진입에서도 같은 상태와 다음 선택 식별 |
| 실행 건강성 | 차단 Console 오류 0건 |

Logic과 Presentation 중 하나라도 기준을 통과하지 못하면 E8 승격은 불가하다. 결함은 같은 `PlayableUnit` Goal의 가장 이른 E1~E7을 다시 열어 수정하며 후보 revision이 바뀌면 기존 반복 횟수와 승인을 재사용하지 않는다.

## E9 — 영역 폐루프 조화·사람 승인

E9의 판정 주체는 같은 업무 영역 또는 심리 영역에서 E8을 통과한 Core `PlayableUnit` 둘 이상을 묶은 `AreaHarmonySet`이다. 기존 Core 하나를 E9 형식에 맞추려고 억지로 쪼개지 않는다. 구성원·권위 revision·후보 build를 함께 동결하고 논리·표현 조화와 사람 수용성을 같은 단계에서 검증한다.

| E9 궤적 | 필수 조화 모듈 |
| --- | --- |
| 논리 | 권위 revision·실행 순서 교차, 자원·시간·결과 인계, 실패·회복·귀환, 관련 NPC 논리 연속성 |
| 표현 | H 공간 전환 판독, 카메라·입력 연속성, 상태·결과 피드백, 관련 NPC 행동 관찰 가능성 |

NPC 생활 연속성은 별도 성숙도 단계가 아니라 관련 E9 조화 모듈이다. NPC가 관련된 묶음에는 논리 연속성과 행동 관찰 가능성을 각각 검증하고, 관련 없는 묶음만 사유가 있는 `NotApplicable`을 사용할 수 있다.

E9는 자동 시험만으로 승격할 수 없다. 같은 후보를 사람이 서로 다른 대표 순서로 직접 플레이하고 논리 경험과 표현 경험을 따로 평가한다.

| E9 궤적 | 사람 평가 항목 |
| --- | --- |
| 논리 | 인과 일관성(`CausalCoherence`), 선택 결과(`ChoiceConsequence`), 진행 연속성(`ProgressionContinuity`) |
| 표현 | 판독 가능성(`Readability`), 피드백 명료성(`FeedbackClarity`), 전환 자연스러움(`TransitionNaturalness`) |

두 궤적과 별도로 다음 종합 수용성을 기록한다.

- 재미
- 몰입
- 완성도
- 폐루프 사이 전환의 자연스러움

현재 내부 후보 기준은 각 궤적 평가와 재미·몰입·완성도 모두 5점 만점에 4점 이상, 열린 `Blocking`·`Major` 발견 사항 0건, 동일 후보 revision과 build hash에 대한 사람의 명시적 승인이다. 발견 사항은 대상 궤적과 재개 주체를 기록하고 E9 조화 모듈 또는 관련 PlayableUnit의 가장 이른 E1~E8로 되돌려 고친다. 수정으로 후보 revision이 바뀌면 조화와 사람 승인을 재사용하지 않는다.

## E10 — 제한 운영 검증

E10의 첫 실행 프로필은 `WindowsX64 + LocalProcess`다. E9에서 사람이 승인한 불변 build를 정해진 관찰창 동안 사용하고 다음을 확인한다.

- 시작·완주·실패 회복
- Save·Restore·Replay 일치
- 크래시·예외·저장 손상 여부
- rollback 훈련
- 관찰창 종료 뒤 사람의 계속 운영 승인

`InternalPilot`은 최소 3일·완주 5회·시험자 1명, `ReleasePilot`은 최소 7일·완주 20회·시험자 3명·새 대상 플레이어 1명을 요구한다. 후보 revision이나 build hash가 바뀌면 진행 중 관찰창은 무효가 된다. Provider 호출, 운영 DB 쓰기, 결제·계약·일반 공개는 E10에 자동 포함되지 않으며 별도 권위 승인이 필요하다.

## G 관리 체계

| 관리 체계 | 주 구간 | 책임 |
| --- | --- | --- |
| G1 | E1→E6 | 세계 성립, WI·H·결정성·정제 관리 |
| G2 | E6→E7 | 실제 입력·카메라·피드백·Game View 관리 |
| G3 | E7→E8 | 한 PlayableUnit의 반복 결정성·저장·동등성·실제 입력 안정 관리 |
| G4 | E8→E9 | 둘 이상의 안정 Core 조화, 사람 평가, 발견 사항 재개와 후보 승인 관리 |
| G5 | E9→E10 | 불변 후보의 제한 운영과 관찰창 관리 |

G 작업이 끝났다는 사실은 해당 E 증거를 자동 승격하지 않는다. 변경 영향·Migration·호환·회귀 검토는 E9 단계가 아니라 모든 구간에 걸친 교차 책임으로 유지한다.

## 현재 적용 범위

모든 등록 `PlayableUnit`은 정확히 하나의 E8 안정성 캠페인을 가진다. E9 후보는 둘 이상의 독립 Core가 등록된 Nature·Farm·Hub에만 만들고, Core가 하나뿐인 Town·City는 새 독립 Core 플레이 약속이 생길 때까지 보류한다. 기존 Town·City Core를 캠페인 수를 맞추려고 분할하지 않는다. 활성 Goal, 현재 E, 차단과 다음 WI 같은 변동 상태는 [`CURRENT_WORK.md`](../AI/CURRENT_WORK.md)와 생성 상태판만 권위로 사용한다.
