# 플레이 폐루프 논리·표현·결과 순환 개발 방법론

## 목적

플레이 폐루프의 코드와 상태 전이가 동작한다는 사실과 플레이어가 화면에서 상황·대상·행동·결과를 이해한다는 사실을 분리해 검증한다. 이 문서는 다른 영역과 다른 `PlayableLoop`에도 그대로 적용하는 공통 개발 방법론이다. 하나의 `PlayableLoop`는 다음 두 성숙도 궤적을 함께 가진다.

| 궤적 | 한국어 의미 | 주 검증 질문 |
| --- | --- | --- |
| `Logic` | 논리 성숙도 | 같은 입력이 같은 권위 상태·저장·재생 결과를 만드는가? |
| `Presentation` | 표현 성숙도 | 플레이어가 설명 없이 대상·행동·대가·결과·다음 선택을 읽을 수 있는가? |

통합 성숙도는 두 궤적 중 낮은 E 단계다.

`통합성숙도 = min(논리성숙도, 표현성숙도)`

논리 E7·표현 E5인 폐루프는 E7 완료가 아니라 통합 E5다. 이 규칙은 구현량을 낮게 평가하려는 장치가 아니라, 논리 증거와 플레이 증거를 서로 대신 쓰지 않기 위한 경계다.

이 문서에서 `Presentation`의 한국어 이름은 **표현**이다. 기존 문서와 파일명에 남은 `시각`은 같은 궤적을 가리키는 호환 용어이며, 표현은 화면뿐 아니라 입력 피드백·음향·카메라·공간 식별 가능성을 포함한다.

## 한 루프에 적용하는 다섯 단계

Codex는 새 기능 목록이 아니라 다음 순서로 `PlayableLoop` 하나를 닫는다.

1. **폐루프 정의**: 상황·욕구·선택·대가·성공·실패·회복·귀환을 하나의 플레이어 약속으로 고정한다.
2. **논리 순환**: 승인된 작업 목록에서 실제 선행 의존성과 쓰기 소유를 구분하고 권위 상태·결정성·저장·재생·Local/Hosted 동등성을 조립한다. 독립 WI·하위 작업은 병행하며 전역 단일 WI WIP를 요구하지 않는다.
3. **표현 순환**: E1~E4에서 요구·공간·표현 후보를 설계하고, 논리 E5의 결정적 상태 사본이 준비되면 E5~E7 표현 증거를 H 문맥·배치·자산·카메라·입력·피드백에 결속한다.
4. **결과·귀환 관문**: 논리 결과와 표현 결과가 같은 revision을 설명하고 플레이어가 회복·귀환 또는 달라진 다음 선택에 도달하는지 확인한다.
5. **피드백 재개**: 실패 원인을 가장 이른 책임 궤적과 E 단계에 귀속하고 같은 Goal 안에서 필요한 단계만 다시 연다.

표현 E1~E4의 요구와 공간 조건은 논리 구현 전에 설계할 수 있다. 그러나 실제 표현 조립은 논리 E5 상태 사본이 준비된 뒤 시작하며 Unity가 빠진 권위 상태를 임의로 만들어 메우지 않는다.

## 네 관점과 소유 결과

| 관점 | 질문 | 반드시 남길 결과 |
| --- | --- | --- |
| 폐루프 | 플레이어가 왜 시작하고 무엇을 선택하며 어디로 돌아오는가? | `playerPromise`, 진입·성공·실패·회복·귀환 상태 |
| 논리 | 같은 명령·시간·seed가 같은 세계 결과를 만드는가? | 권위 상태, Revision, Task·Effect, Save/Replay hash, Local/Hosted 증거 |
| 표현 | 플레이어가 설명 없이 대상·행동·대가·변화·다음 선택을 읽는가? | H 결속, 표현 준비 자료, 실제 입력, Play Mode·Game View 증거 |
| 결과 | 논리와 표현이 같은 사실을 가리키며 다시 선택 가능한가? | 통합 E, 닫힘 상태, 열린 피드백, 다음 인계 |

`결과`는 세 번째 성숙도 궤적이 아니다. 논리와 표현의 동일 revision 인계 및 귀환을 확인하는 **통합 관문**이다. 따라서 별도 `Result` E를 만들지 않고 기존 `Logic`, `Presentation`, `Integrated` 증거와 폐루프 닫힘 상태를 사용한다.

## 기존 체계와의 관계

이중 순환은 기존 체계를 대체하지 않는다.

| 기존 체계 | 유지되는 책임 |
| --- | --- |
| E1~E7 | 한 PlayableUnit의 계약부터 실제 플레이까지의 수직 증거 깊이 |
| H1~H5 | 상호작용 공간부터 세계 배치까지의 의미 계층 |
| WI | 한 의도와 하나의 주요 권위 결과를 가진 실행 단위 |
| G | 계획·조정·검증을 관리하는 운영 체계 |
| WI 음양 사분면 | 발산·수렴 목적과 플레이어·NPC 수행 주체 분류 |
| PlayableLoop | 여러 WI의 성공·실패·회복·귀환을 닫는 플레이 약속 |
| EvidencePackage | 시험·실행·화면·Hosted·운영 증거의 범위와 무효화 조건 |

`Logic`과 `Presentation`은 개발·검증 궤적이다. WI의 양·음과 플레이어·NPC 사분면은 게임 안 행동의 의미 분류이므로 서로 섞지 않는다.

## 궤적별 E 판정

같은 E 번호라도 증거의 질문은 다르다.

| E | 논리 궤적 | 표현 궤적 |
| --- | --- | --- |
| E1 | 명령·상태·오류 계약 | 플레이어가 보아야 할 정보 계약 |
| E2 | 규칙·비용·차단·반환 | 상태 투영·자산 조회·View 연결·표현 수명·도구 코드 준비 |
| E3 | 결정적 Core와 단위 시험 | 표현 상태·중복/과거 판본·조립/해제·도구 오류/보존 자동시험 |
| E4 | H 문맥·Actor·권위 결속 | 플레이어 판독 순간·VisualKey·주/대체/fallback 자산 후보·배치/InteractionAnchor 의도·E5 준비 상태 결속 |
| E5 | 실제 Fixture 발현·저장·재생 | E4 표현 준비 인계를 실제 Prefab 또는 대체 표현·배치 객체·활성 Renderer/Collider/Bounds에 결속 |
| E6 | Local/Hosted Adapter와 설명 가능한 조회·실패/회복·최신성 정제 | 배치 통제, Synty 조립, HUD·음향·상태 차이 및 필요한 현실 문맥 정제 |
| E7 | 실제 입력 명령열과 결과 동등성 | PlayMode·Game View에서 상황→행동→결과→다음 선택 식별 |
| E8 | 한 PlayableUnit의 반복 결정성·Save/Replay·Local/Remote 동등성 | 같은 PlayableUnit의 실제 입력 반복·Save 재진입·Console 건강성 |
| E9 | 둘 이상의 안정 Core 사이 권위·자원·시간·실패·NPC 조화와 사람의 인과·선택 결과 평가 | 공간 전환·카메라·입력·피드백·NPC 관찰 조화와 사람의 판독·전환 평가 |
| E10 | 두 궤적을 다시 늘리지 않고 승인된 불변 후보를 제한 운영 관찰창에서 통합 판정 | 두 궤적을 다시 늘리지 않고 승인된 불변 후보를 제한 운영 관찰창에서 통합 판정 |

모든 E2 이상은 현재 단계만 독립 판정하지 않고 [상위 E의 하위 E 누적 소비 원칙](E1-E7수직폐루프와E8-E10수평증거체계.md#evidence-cumulative-consumption)을 따른다. 즉 E4는 E1~E3, E7은 E1~E6, E8은 동결된 E1~E7 묶음을 소비한다. 유효한 동결 증거는 재사용할 수 있지만 선행 근거가 변경·누락·만료되면 가장 이른 E부터 다시 닫으며, 상위 단계의 화면·사람 평가·운영 결과로 하위 결손을 상쇄하지 않는다.

표현 E1~E4 계획은 논리 E5 전에 진행할 수 있다. 표현 E5 이상 증거는 최소한 논리 E5의 결정적 상태 사본이 준비된 뒤 승격한다. Unity가 표현을 먼저 임의 계산해 논리 상태를 대신 만들 수는 없다.

### E5는 E1~E4 맥락을 소비하는 실제 결속 관문이다

E5는 E4에서 고른 Prefab을 빈 장소에 놓는 단순 배치 단계가 아니다. 대상 WI에 적용되는 **E1~E4의 논리·표현 근거를 같은 Goal·WI·Session·객체·권위 Revision으로 다시 모아**, 그 맥락에 맞는 자산·위치·상태·상호작용 연결인지 판정하는 통합 관문이다. 적용 가능한 선행 근거 하나라도 누락·만료·충돌하면 임의 기본값이나 보기 좋은 대체 자산으로 메우지 않고 해당 결속을 차단한다.

| 소비할 선행 맥락 | E5에서 확인할 내용 |
| --- | --- |
| E1 계약 | 명령·상태·오류와 플레이어에게 보여야 할 정보가 실제 대상의 역할·표시 상태와 일치하는가 |
| E2 준비 | 규칙·비용·차단·반환, 상태 투영·자산 조회·표현 수명과 소유 경계가 실제 연결 경로에 존재하는가 |
| E3 검증 | 결정적 Core와 표현 조립·해제·중복/과거 판본 거부 시험이 이번 후보·판본·소비자에 유효한가 |
| E4 문맥 | 발생원·Actor·대상·자원·시간·H/Graph Map 관계, 판독 순간·VisualKey·후보 fingerprint·fallback·InteractionAnchor가 추적되는가. 권위 전환을 소유하거나 일으키는 역할 객체라면 종류·역할·행위·시작/완료 상태·효과와 오행 분류 revision/hash가 공식 WI와 일치하는가. 공간·배치 대상이면 동결된 배치 맵의 ID·revision·hash, Graph Map 참조, H 배치 인스턴스와 상대 구도·제약, 규칙성 검사 결과까지 일치하는가 |

E5 작업 명세와 EvidencePackage에는 새 성숙도 축이나 별도 권위 원장을 만들지 않고, 위 근거의 참조·판본·hash, 적용 여부 또는 사유 있는 `NotApplicable`, 실제로 소비한 후보·배치 규칙과 관측 결과를 남긴다. 역할 객체 행위 분류는 모든 세계 객체를 후보로 보되 권위 전환을 소유하거나 일으킬 때만 필수다. 정적 배경·장식·설명 전용 객체에는 가짜 행위를 만들지 않는다. 적용 가능한 분류의 누락·오래됨·불일치는 E5를 차단하지만, 분류가 존재한다는 사실만으로 E5가 성립하지 않는다. 공간 대상은 Graph Map 레벨 1의 플레이·접근·복귀 관계와 레벨 2의 의미 제약을 참조해 만든 **동결 배치 맵**을 E4 필수 인계로 소비한다. 배치 맵은 H 배치 인스턴스·반복·상대 위치/방향/규모·시야 역할과 자산·거리·지지·경계·통행·가림·완충·겹침 제약을 소유한다. 카메라·가시성·주변 기능과의 간섭도 해당 WI 판독에 영향을 주는 범위만 확인하며, 전체 월드나 모든 주변 기능의 완성을 개별 E5의 선행 조건으로 만들지는 않는다.

E5에서 후보가 역할과 맞지 않거나 위치·크기·접근·상태 표현이 맥락과 어긋남을 발견하면 좌표만 조정해 통과시키지 않는다. 원인이 후보·VisualKey·배치 인스턴스·상대 구도·제약이면 배치 맵 revision과 표현 E4, Actor·대상·시간·H 결속이면 논리 E4, 상태·규칙·계약이면 해당 E1~E3의 가장 이른 책임을 다시 열어 판본을 갱신한 뒤 E5를 재시도한다. 이 왕복은 E5를 느슨하게 만드는 예외가 아니라 잘못된 배치를 장기 계약으로 굳히지 않는 정식 절차다.

## E6 준비·입증의 공식 주력 절차 — D446·D447

E6까지의 준비와 입증은 **지금·여기·나·너·이렇게를 중심으로 기획·그래프 맵·자산/패턴·배치 규칙·실제 연결·플레이 전 정제와 필요한 현실 근거를 왕복하는 절차**를 주력으로 사용한다. E5에서 실제 성립을 확인하고 E6에서 의미·인과·표현·권위 인계·최신성 결함을 정제한다. 새 E 단계·도구 구현·게임의 집중하기 효과를 추가하는 결정이 아니다. [그래프 맵 기획 연계 문서](../AI/그래프맵-기획서연결-제안-2026-08-31.md)는 두 상세 수준과 사례를 설명하고, 공식 절차와 E 판정 경계는 이 절을 단일 기준으로 삼는다.

D447은 D446의 **공식 절차 적용 범위를 E5에서 E6까지 확장**한다. 기존 E5 관문은 중간 입증 지점으로 유지하고 E7의 전체 실제 플레이 검증은 다음 별도 범위로 남긴다. 이전 `e5-focused-workflow` 링크는 호환용으로 보존하며, 과거 D446 원문·인수와 실제 E 증거를 소급 변경하지 않는다. 개별 작업의 승인 상한·명세는 별도로 확인하므로 절차 확장만으로 모든 E5 작업이 즉시 E6 실행 권한을 얻지는 않는다.

### 적용 단위와 시작 조건

- 승인된 주제 기획·WI·필수 연구·작업 명세에서 **작게 입증할 WI/객체와 상황 하나**를 고른다. 전체 월드맵, 전체 자산 할당이나 모든 문답 정리가 끝나기를 기다리지 않는다. 독립 작업의 병행과 기존 소유권 조율은 유지한다.
- 원문·판본·현재 Logic/Presentation E·목표 상한·필수 의존성·미정을 먼저 읽는다. 이 절의 채택만으로 과거 제안의 수치·미답변·특정 후보를 확정하거나 중지된 실행을 재개하지 않는다.
- 공간 관계가 있는 WI는 같은 그래프의 **레벨 1(플레이·공간 관계)**과 **레벨 2(해당 관계의 구체 자산·배치 제약)**를 연결한다. 두 레벨은 H1/H2나 E1/E2가 아니며 기획의 행동 인과관계와 공간의 통행 엣지를 혼동하지 않는다.
- 비공간·비시각 WI는 적용 가능한 조건·객체·WI 연결만 남기고 공간/자산 항목은 사유 있는 `NotApplicable`로 처리한다. 작은 관계표로 충분하면 별도 그래프 UI나 새 노드·H·클래스·DB를 만들지 않는다.

아래는 새 성숙도 단계가 아니라 같은 작업에서 필요한 만큼 왕복하는 활동이다. 코드·시험 준비와 자산 조사는 병행할 수 있으며, 필수 의존성이 없는 활동을 일률적으로 직렬화하지 않는다.

배치 구조·제약은 기획 의도를 표현하고, 배치 엔진은 승인된 그래프 맵과 실제 지형·자산 입력으로 후보·검사 결과를 계산한다. LH 등 표현 소비자는 같은 권위 상태에 그 결과를 연결한다. **그래프·배치 엔진·Unity 어느 쪽도 누락된 Simulation 상태나 실행 성공을 대신 확정하지 않는다.**

검토할 때에는 선택한 WI/노드/엣지의 의도·후보·규칙·근거·결손을 함께 읽는다. 레벨 2의 필수 실패·입력 부족은 레벨 1의 관련 플레이에도 요약한다. 한 번의 보완은 확인한 원인과 영향 범위에 한정하고, 같은 실패를 같은 방식으로 반복하기 전에 새 근거·안전한 대안·차단을 기록한다. 필수 미정은 해당 연결만 보류하고 독립적으로 가능한 준비는 이어간다.

### E5 중간 입증은 유지한다

- E1의 계약, E2의 코드 준비, E3의 실제 자동시험, E4의 후보·문맥 결속, E5의 실제 발현은 앞 표의 기존 정의대로 판정한다. 문서 항목 수·그래프 정밀도·자산 할당·규칙 검사 통과로 E를 자동 증가시키지 않는다.
- 표현 E5에는 논리 E5의 결정적 상태 사본과 같은 Session/객체/판본의 실제 표현 결속이 필요하다. 권위 변화 WI의 행위 기록 또는 같은 판본 상태 읽기를 기존 엔진 상호작용 관문으로 확인하고, 같은 WI 판본의 역할 객체·행위·오행 분류를 함께 대조한다. 적용·해제 소유와 필요한 연결/보존 근거도 기존 기능 모듈에 따라 남긴다. 모든 시각 대상에 불필요한 Collider나 새 명령을 만들지는 않는다.
- 확인할 항목이 화면에서만 판별되면 필요한 실제 Play Mode·Game View 증거를 별도 승인·점유 범위에서 확보한다. 실행하지 못했으면 그 항목은 미검증이다. 반대로 모든 E5 작업에 E7의 전체 플레이 완주·전수 캡처를 일괄 선행시키지 않는다.
- 개별 승인이 E5까지만인 작업은 그 범위의 판정과 남은 문제를 인계한다. E6가 결속된 작업은 E5 기준선과 증거를 보존한 뒤 정제로 이어간다. 이미 확인된 필수 통행·입력·결과·상태/소유 결손을 E6로 미뤄 E5를 통과시키지 않는다.
- 부분 WI/객체의 E5 근거는 그 범위만 입증한다. 폐루프 필수 WI·연결이 남으면 전체 E5나 `PlayClosed`를 선언하지 않는다. 통합 E는 계속 `min(Logic, Presentation)`이며 E5 상한을 실제 성취값으로 기록하지 않는다.

### E6 정제와 공공·현실 자료를 연결한다

E6는 자료를 많이 모으는 단계나 미관만 다듬는 단계가 아니다. [현행 E6 정의](../../eng/execution-ledgers/evidence-stages.json)와 [E6 AreaSet 정제 기준](H5세계배치와선택형E6결속.md)에 따라 E5에서 발현한 WI/폐루프를 실제 플레이 전에 설명 가능하게 정제한다. 정제 질문은 **지금(시간·상태·최신성), 여기(존재 이유·배치·접근), 나/너(Actor·물건·역할), 이렇게/결과/다음 선택(시작·변화·피드백·회복·귀환)**에서 찾고 같은 그래프의 해당 노드/엣지·규칙과 근거를 연결한다. 새 레벨 3이나 새 H 계층은 만들지 않는다.

| 현실 자료 확인 | 공식 절차에서 남길 근거와 경계 |
| --- | --- |
| 필요성·기존 자료 | 어떤 WI·정제 질문을 설명할 자료인지 먼저 정하고 기존 승인 자료/저장 기록을 재사용한다. 자료가 필요하지 않은 기능에 공공데이터나 GIS를 일괄 필수화하지 않는다. |
| 의미와 품질 | 원천 식별자·출처, 대상 품목/시설·지역·기간/절기 대응, 단위/통화·정밀도, 관측/수집/검토 시각, 판본/hash, 이용조건·해석 한계를 연결한다. 이름·Prefab 외형·수집일만으로 동일 대상이나 최신 자료로 판정하지 않는다. |
| 수집·축적 | 별도 자료 조사 요청/범위가 결속되면 [기존 ASP.NET Core·Docker MySQL 조사 파이프라인](게임자료조사전문운영.md)을 따른다. 실제 수신·저장·독립 재조회와 검토를 구분하며, 이번 절차 개정 자체를 새 공급원 호출·DB 실행 지시로 해석하지 않는다. |
| 게임 소비 | [현실 자료 내부 판단·간접 표현 기준](E6현실자료내부판단과간접표현.md)에 따라 승인된 자료 사본과 해석 규칙을 연결한다. 세션에서는 시작 시 동결한 사본을 읽고 Tick/Unity 조회마다 Provider를 호출하거나 새 관측으로 실행 중 세션을 바꾸지 않는다. 의미 신호는 제안이며 기존 Simulation 규칙 없이 생산량·가격·성공·사건·H5 위치를 바꾸지 않는다. |
| 플레이어 표시·공백 | 기본은 승인된 게임 현상 표현, 출처·원문은 사용자가 선택한 상세 보기다. 원자료를 항상 띄우거나 열람을 게임 진행 조건으로 삼지 않는다. 자료 없음·낡음·대응/이용조건 미확인을 현재 값이나 가짜 자료로 메우지 않고 해당 상태와 영향 범위를 남긴다. |

조사·정제 질문 준비는 E5 이전에도 가능하지만 E6 합격 증거는 **현재 유효한 E5 기준선과 적용된 정제 결과**를 요구한다. 선택하지 않은 GIS의 `NotApplied` 자체는 E6 실패가 아니다. 필수로 선택한 현실 근거가 없으면 그 결속/정제 목표를 미완료로 남기되 기존 E5의 유효한 공간·권위 증거까지 폐기하지 않는다. DB 기록 존재나 자료 매칭만으로 게임의 의미·인과·표현 정제를 통과시키지 않는다.

### E6 종료와 E7 인계 경계

- 한 WI/노드의 정제는 작은 진척으로 반환할 수 있다. 다만 AreaSet E6 합격을 주장할 때에는 기존 프로필의 필수 H3 질문과 교차 H3 인과·이동 폐루프까지 확인한다. 부분 검토를 전체 AreaSet 합격으로 바꾸거나 무관한 모든 영역의 완성을 추가 선행시키지 않는다.
- 정제 전후의 대상·상태·자산/그래프/규칙·자료 판본과 검증 조건을 남긴다. 구조/코드 검사, 자동시험, 실제 공간/화면 비교, 청취는 각각 구분한다. 필요한 관측이 없으면 문서의 체크만으로 통과시키지 않는다.
- Graph·H·WI·질문표·근거 사본·생성기 등 해당 기준선이 바뀌면 영향받는 정제 결과를 재검토한다. `Current / Stale` 등 기존 상태를 사용하고 hash만 교체해 합격을 유지하지 않는다. 보완이 E5 배치·계약·권위에 영향을 주면 가장 이른 E를 다시 열어 회귀한다.
- 종료 인계는 **E5 성립 근거 / E6 정제 결과 / 현실 근거의 사용·미사용·결손 / 남은 결함·담당 / E7에서 확인할 항목**을 분리한다. 논리·표현·통합 E는 실제 증거로 각각 판정하며 E6 상한을 완료값으로 올리지 않는다.
- E6까지의 절차 완료는 E7 실제 플레이 완료나 `PlayClosed`가 아니다. E7의 전체 입력·성공/실패 회복·귀환 검증은 별도 승인·명세·실행 범위로 인계하고 자동 속행하지 않는다. 기존 E7 작업 명세의 영향 검토는 유지한다.

기획은 맥락·선택·규칙과 자료 사용 목적의 의미를, 개발은 기존 작업 명세·구현·검증·통합을 소유한다. 공간 담당은 자산·형상·배치·필요 화면, 애니메이션 담당은 Rig/Clip·동작·접촉, 자료 조사 담당은 지정된 출처·자료 품질·수집/축적 근거를 맡아 개발에 반환한다. 기존 명세·정제 질문표·모듈·`openFeedbackItems`·EvidencePackage를 재사용하며 새 대장이나 별도 승격기를 만들지 않는다. 실제 World/Scene·Save·가공·외부 효과·Editor 실행은 각각의 승인과 보호 경계를 계속 요구한다.

## 표현 검증 모듈 관문

### 전체 배치 기준과 개별 E5 성립의 책임 분리 (D-390)

E5는 배치만의 단계가 아니라 **권위 상태와 세계 표현이 같은 대상·판본에서 성립하는 단계**다. 전체 공간 기획의 제약을 소비하되, 모든 주변 기능·경관·영역 조화의 완성을 개별 E5 선행 조건으로 요구하지 않는다. [D390 적용 계획](../AI/E5개별성립과전체배치책임분리-2026-08-31.md)은 이 기준의 기술 반영 범위다.

| 책임 범위 | 남길 내용 | 개별 E5와의 관계 |
| --- | --- | --- |
| 전체 배치 기준 | 승인된 영역 역할·위치 기준·공간 예약·접근/통행·공유 자원·카메라/표현 제약의 원문 참조와 판본 | 해당 기능에 영향을 주는 제약을 소비한다. 전체 세계를 새로 완성하거나 조사할 필요는 없다. |
| 개별 실제 성립 단위 | 기존 Goal 안의 대상 WI·객체, 상태 공급, 후보, 입력/결과 연결, 적용·해제 소유, 필수 의존성과 검증 범위 | 작은 단위로 구현·검증하되 결과는 해당 범위의 증거다. 한 대상 성공을 전체 폐루프 E5로 확대하지 않는다. |
| 여러 기능의 조화 | 함께 배치했을 때의 동선·경관·카메라·입력·자원 간섭과 미해결 사항 | 조사는 앞 단계부터 가능하다. 정식 E9 판정은 기존 E8 Core 둘 이상과 AreaHarmonySet 관문을 따른다. |

**작게 나누는 것은 작업·증거 범위를 나누는 것이지 새로운 E5 하위 단계나 성숙도 축을 만드는 것이 아니다.** 기존 작업 명세·`workItems`·모듈 연결·`openFeedbackItems`·EvidencePackage를 사용하고 통합 E의 최솟값 규칙을 유지한다. 폐루프의 필수 WI·결과 연결이 남았으면 전체 폐루프 E5를 선언하지 않는다.

#### 차단을 판정하는 기준

- 현재 대상의 권위 상태, 같은 Session/판본, 필수 자산/컴포넌트, 지지·접근·통행, 입력·결과, 소유권이 빠지거나 충돌하면 해당 실제 연결은 차단한다. 미관측은 확인 완료가 아니다.
- 다른 시설의 장식·무관한 기능·향후 영역 조화가 미완성이어도 현재 대상에 영향이 없다는 범위·근거가 있으면 그 작업의 선행 의존성으로 추가하지 않는다. 다음 담당과 후속 검토 위치는 기록한다.
- 이미 발견된 통로 차단·카메라 가림·상태/자원 간섭처럼 현재 기능을 깨는 문제는 ‘E9 조화’로 미뤄 통과시키지 않는다. 가장 이른 실제 원인 E에 반환한다.
- 영향 여부를 모르면 미관측 조건으로 남긴다. 막연한 ‘전체 맵 미완성’을 구체적인 조사 대상·담당·의존성으로 좁히며, 그 조사와 무관한 승인 작업은 계속한다.
- 공유 기준이 바뀌면 소비 대상·판본·무효화 조건으로 영향받는 증거만 재검토한다. 단순 미감 변경을 이유로 관계없는 논리 증거까지 폐기하지 않는다.

#### 진행·인계 방식

완료한 준비·조립·연결·시험은 기존 참조로 보존하고, 남은 결손과 그 결손이 막는 작업을 따로 표시한다. 이 목록은 새 숫자 단계나 완료율이 아니다. 필수 연결이 남았으면 E는 그대로 두되 모든 작업을 정지시키지는 않는다.

E4 후보·도구·격리 준비는 논리 E5 전에 진행할 수 있다. 실제 표현 E5 판정에는 기존처럼 논리 E5 사본과 필요한 실제 적용 근거를 요구한다. E6 품질 정제·E7 실제 플레이·E8 반복 안정·E9 조화 판정을 앞 단계에 일괄 요구하거나 뒤 단계로 필수 E5 결손을 넘기지 않는다.

계획은 기존 승인된 전체 배치 기준을 참조하고, 개발은 그 안의 작은 실제 성립 단위를 선택·결속한다. 공간·애니메이션 담당은 해당 단위의 전문 결과를 개발에 반환한다. 같은 Scene/공유 계약의 쓰기는 단일 소유로 조율하며, 부분 결과를 먼저 통합해도 기존 중지·권한·승인 경계는 유지한다.

### 단계별 최소 구현 책임 (D-386)

E 번호의 판정 의미는 [현행 단계 원장](../../eng/execution-ledgers/evidence-stages.json)을 따른다. E2는 코드 준비, E3은 자동시험 통과다. 표현 언어·자산 후보만 나열했던 이전 E2/E3 설명은 제작의 관심사를 나열한 것이며 코드·시험 완료 근거가 아니다. 과거 E 증거를 자동 변환하거나 승격하지 않는다.

| E | 최소 책임 | 기록/재사용 |
| --- | --- | --- |
| E1 | 플레이어가 읽을 상태·오류·행동·귀환 계약 | 승인 기획·표현 요구 |
| E2 | 상태 투영·자산 선택·View 수명·도구 코드 | 실제 구현 참조, 기존 비교기·Adapter 우선 |
| E3 | 결정적 표현·중복·과거 판본·실패/해제 시험 | 시험 참조와 판본에 결속한 결과 |
| E4 | 자산 대조·필요 가공·Rig/Clip·배치 준비 | `presentationE4Preparation`·Required 연구·후보 fingerprint |
| E5 | 같은 권위 상태와 실제 World 표현 연결 | 활성 Renderer·필요 Collider·Bounds·행위/상태 읽기 |
| E6 | 공간·동작·상태 판독·음향 정제 | 기능별 모듈과 동일 조건 비교 |
| E7 | 실제 입력·결과·회복·귀환 | Play Mode·Game View·Console·재진입 |

모듈은 책임 단위이지 E별 새 클래스/프로젝트가 아니다. E1 계약, E3 시험, E7 실제 검증에 불필요한 런타임 구현을 만들지 않는다. 모델링·리깅·Clip 보완은 E4 후보 준비에 포함하고 실제 적용/품질은 E5/E6에서 확인한다. 도구 코드·자동시험은 E2/E3 지원 증거로 재사용하되 대상 자산의 적합성을 대신하지 않는다.

기존 대장의 v2는 E1~E3 공통 모듈과 `outputs`, `implementationRefs`, `testRefs`를 추가한다. `repo:`는 Hongdal 상대 파일, `unity:`는 별도 Unity 프로젝트 상대 파일이다. 관리기에 `-UnityProjectRoot`를 주면 외부 참조도 대조하며, 미제공은 외부 파일 검증 완료가 아니다. 관리기는 경로·메타데이터·증거 결속만 검사하며 Unity를 실행하지 않는다.

작업 명세의 선택적 `presentationModuleBindings`는 필요한 모듈별 `Unverified/Blocked/Passed/NotApplicable`, 이유, 구현/시험 참조, 후보 판본, 기존 EvidencePackage ID를 연결한다. 확장 없는 과거 명세는 Unverified로 표시하고 현재 E를 보존한다. 연결을 사용하는 명세는 기능 프로필의 모든 적용 모듈을 명시하며 비적용 사유를 생략할 수 없다. `Passed`는 Current/Passed Presentation 증거의 대상·모듈·E·판본과 파일 hash가 일치해야 하며 구현/시험 참조도 해당 hash 근거에 포함되어야 한다. E3는 자동시험, E7은 UnityPlayMode와 GameView 종류의 증거를 함께 요구한다. 증거 등록값 대조는 실제 실행이나 사람 품질 승인 자체를 대신하지 않는다.

첫 Farm 연결은 WI-FARM-04의 읽기 전용 상태 준비 범위이며 전체 Farm 폐루프 통과가 아니다. 실제 Snapshot 공급·Preview/Confirm·Scene 연결이 없으면 E5 미연결로 유지한다. 도구는 소수 표본의 정상 표시·자세 변화·오류/보존부터 검사하고 첫 실패 뒤 대량 촬영을 중단한다. 실패는 발견 E와 원인 E를 분리해 기존 피드백으로 반환한다.

### 기존 E4~E7 기능 검증

표현 궤적은 담당자가 매번 임의 검사 목록을 만드는 대신 [표현 검증 모듈 대장](../../eng/execution-ledgers/playable-loop-presentation-validation-modules.json)을 입력으로 사용한다. 모든 `PlayableUnit`에는 공통 모듈을 적용하고, 건물·지면·울타리·Actor·실내·작업 구역·카메라 가림처럼 실제로 사용하는 기능만 조건 모듈로 더한다. 현재 선택 결과는 [생성 상태판](../AI/generated/playable-loop-presentation-validation.md)에서 확인한다.

| 단계 | 공통 관문 | 실패 시 기본 재개 |
| --- | --- | --- |
| E4 | 권위 상태 사본·H 기준점 또는 NotApplicable·VisualKey·자산 후보 묶음·fallback을 결속한다. 공간·배치 대상은 동결 배치 맵의 판본/hash·Graph Map 참조·H 인스턴스·상대 구도/제약·규칙성 검사·E5 준비 상태를 필수로 결속 | 표현 E4, 상태·H 계약이 없으면 논리 E4 |
| E5 | E4 인계 후보와 같은 동결 배치 맵을 실제 Prefab 또는 대체 표현, World 배치와 활성 `Renderer`·`Collider`·`Bounds`에 결속 | 표현 E5, 배치 맵이 없거나 stale/불일치이면 표현 E4 |
| E6 | Player 대비 크기·간격과 상태별 표현 차이 | 표현 E6 |
| E7 | 저장 Scene·실제 카메라·입력·결과·귀환 | 표현 E7, 권위 결과가 다르면 원인 논리 E |

조건 모듈은 기능 프로필로 선택한다. 예를 들어 `GroundSurface`를 선언한 폐루프는 `surface-clearance`, `Building`은 `building-foundation-entry`, `FenceChain`은 `fence-continuity-entry-gap`을 통과해야 한다. 공간·배치 대상은 조건 모듈보다 먼저 공통 배치 맵 인계 검사를 통과한다. `Blocking` 실패는 해당 표현 E의 승격을 막고 `Warning`은 위험을 기록할 뿐 증거를 승격하지 않는다. 자동 배치 맵·Bounds 검사를 통과했다는 사실은 실제 카메라와 Game View 판독을 대신하지 않으며, 수동 화면 증거 역시 자동 사전 검사를 생략할 근거가 아니다.

대장과 선택 결과는 다음 명령으로 검증한다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File eng/execution-ledgers/manage-playable-loop-presentation-validation.ps1 -Mode Validate
```

검증 모듈은 표현 결과만 읽고 Simulation 권위 상태를 변경하지 않는다. 실패 결과는 `openFeedbackItems`의 원인·대상·재개 E를 정하는 입력이며 새로운 E·G·H 계층이나 세 번째 성숙도 궤적이 아니다.

## 엔진 상호작용 통합 관문

논리와 표현 사이의 실제 인계는 [플레이 폐루프 엔진 상호작용 검증 체계](플레이폐루프엔진상호작용검증체계.md)를 따른다. `WI Preview → Confirm → Simulation Authority → LH·Sky·실내외 배치 → 화면 결과·귀환`을 같은 `PlayableLoopStableId`, WI, Command와 Revision으로 추적한다.

이 관문은 `Logic`·`Presentation`에 이은 세 번째 E 궤적이 아니다. 두 궤적의 결과가 같은 명령과 권위 판본을 설명하는지 검사하는 `Integrated` 증거다. 표현 엔진은 권위 Revision을 변경할 수 없고, 이미 준비된 엔진 결과는 재실행 대신 `Reused`로 판정한다. 자동 추적 통과는 실제 Play Mode·Game View를 대신하지 않는다.

## 반복 규칙

1. E7 플레이 약속에서 E1 계약까지 하향 검토한다.
2. 가장 낮은 미완료 논리 의존성을 구현하고 E1부터 상향 조립한다.
3. 논리 E5 상태 사본이 준비되면 표현 궤적을 조립한다.
4. 실제 입력과 Game View에서 대상·행동·결과·다음 선택을 확인한다.
5. 실패 원인을 가장 이른 책임 단계와 궤적에 연결한다.
6. 해당 단계만 다시 열고 같은 `PlayableLoop` 안에서 재조립한다.
7. 두 궤적이 목표 단계에 도달하고 열린 피드백이 없을 때만 폐루프를 닫는다.

E7 이후에도 왕복 원리는 사라지지 않는다.

1. E8은 E7을 통과한 PlayableUnit 하나의 반복 안정 목표에서 필요한 논리·표현 증거를 하향 검토한다.
2. 같은 frozen revision과 build에서 논리 반복·Save/Replay·Local/Remote와 표현 실제 입력·Save 재진입을 검증한다.
3. E8 실패는 같은 PlayableUnit의 가장 이른 E1~E7을 다시 연다.
4. E9는 E8을 통과한 Core 둘 이상을 AreaHarmonySet으로 묶고 필요한 조화 모듈까지 하향 검토한다.
5. 같은 후보에서 논리·표현 조화와 사람의 인과·선택 결과·판독·피드백·전환 평가를 함께 통과시킨다.
6. 수정으로 후보 revision이 바뀌면 관련 E8 안정성과 E9 조화·사람 승인을 다시 연다.
7. E10은 새 논리·표현 궤적이 아니라 E9에서 승인한 불변 후보의 제한 운영 통합 관문이다.

표현 실패가 항상 표현 코드 문제인 것은 아니다. 화면에 통나무가 없는 이유가 권위 상태에 지면 통나무가 없기 때문이라면 논리 E1~E5를 다시 연다. 상태는 있으나 너무 작거나 잘못된 장소에 보인다면 표현 E4~E6을 다시 연다.

| 규칙 결과가 다르거나 비결정적이다 | 논리 E2~E3 | 같은 입력·seed·시간에서 상태 또는 hash가 달라짐 |
| Actor·WI·H·시간 결속이 없다 | 논리 E4 | 상태는 정의됐지만 세계 문맥에서 실행할 수 없음 |
| Fixture·저장·재생에 결과가 남지 않는다 | 논리 E5 | 권위 결과가 실제 상태 사본으로 발현되지 않음 |
| 상태는 있으나 자산·위치·크기·카메라가 부적절하다 | 표현 E4~E6 | 상태 사본은 정확하지만 플레이어가 대상을 읽지 못함 |
| 입력·피드백·결과·귀환을 실제로 완주할 수 없다 | 표현 E7, 필요하면 원인 논리 E | 실제 조작 실패를 먼저 기록하고 원인이 권위 계약이면 논리로 이동 |
| 관련 E9 조화 묶음의 NPC가 결과 뒤 다음 욕구·목표로 돌아가지 않는다 | E9 조건 모듈 | 생활세계 상태와 관찰 가능한 행동 중 빠진 책임을 분리하고 관련 E1~E8을 다시 연다. |

재개는 이전 증거를 삭제하는 일이 아니다. 변경이 `invalidationTriggers`를 건드린 증거만 `Stale` 또는 재검증 대상으로 만들고, 영향받지 않은 궤적의 증거는 보존한다.

자산 후보 조사와 공간 대상의 배치 맵 동결·규칙성 검사는 E4의 준비 책임이다. 후보나 배치 맵이 존재한다는 사실만으로 World 발현을 주장하지 않으며, E5는 E4에서 남긴 후보 revision·fingerprint와 같은 배치 맵 revision/hash를 소비했는지 확인한다. E5에서 후보·배치 인스턴스·상대 구도·제약을 바꾸거나 새로운 H 제약이 발견되면 표현 E4를 다시 열어 배치 맵과 인계 자료부터 개정한다.

## 피드백 귀속

`openFeedbackItems`는 다음 정보를 가진다.

| 항목 | 의미 |
| --- | --- |
| `feedbackId` | 피드백 고유 식별자 |
| `reasonCode` | 읽기 실패·실행 경험 실패 등 원인 |
| `detectedAtStage` | 문제가 발견된 E 단계 |
| `targetTrackCode` | 다시 열 논리 또는 표현 궤적 |
| `reopenStage` | 가장 이른 수정 책임 단계 |
| `targetRefs` | WI·H·표현 객체 등 수정 후보 |
| `statusCode` | 열린 상태 또는 해소 상태 |

화면이 부족하다는 이유로 이미 통과한 논리 저장·재생 증거를 지우지 않는다. 반대로 기존 논리 E7을 보존한다는 이유로 표현 실패를 닫지도 않는다.

## 완료 규칙

| 폐루프 상태 | 최소 조건 |
| --- | --- |
| `Open` | 한 궤적이라도 목표 미달이거나 열린 피드백 존재 |
| `CoreClosed` | Core 목표와 결정적 반환 상태 충족 |
| `PlayClosed` | 논리·표현 모두 E7 이상, 실제 플레이 귀환, 열린 피드백 없음 |
| `WorldClosed` | 과거 `legacy-change-adaptive.r10` 판본의 호환 값. 현재 새 PlayableUnit은 `PlayClosed` E7까지만 사용 |
| `ExtendedClosed` | 선택 확장 목표와 반환 상태까지 닫힘 |

`PlayClosed`는 컴파일·단위 시험만으로 만들지 않는다. 실제 입력, 저장된 Scene 배선, PlayMode와 Game View 증거가 필요하다. 음향이나 미세 미감처럼 장치·사람 수용이 필요한 항목은 범위와 제외를 증거 묶음에 명시한다.

## EvidencePackage 사용

증거 묶음은 `evidenceTrackCode`를 가진다.

- `Logic`: 계약·자동 시험·Save/Replay·Hosted 동등성
- `Presentation`: Unity EditMode·PlayMode·Game View·청음
- `Integrated`: 두 궤적의 동일 revision 인계 자체를 검증한 경우

한 증거 묶음이 여러 폐루프를 참조할 수 있지만 각 폐루프의 단계를 자동 승격하지 않는다. 예를 들어 같은 PlayMode 실행에서 작업대가 보였더라도 건설 중과 운영 중의 차이가 읽히지 않으면 작업대 표현은 E6에 머문다.

## 결과·귀환 관문

통합 결과는 다음 네 결과가 모두 연결됐을 때만 통과한다.

| 결과 종류 | 확인 내용 |
| --- | --- |
| 권위 결과 | Simulation 상태·Revision·Task·Effect가 승인된 규칙대로 남는다. |
| 표현 결과 | Unity가 같은 상태 사본을 읽어 대상·원인·변화를 식별 가능하게 표현한다. |
| 폐루프 결과 | 성공뿐 아니라 실패·중단·회복 뒤에도 귀환 또는 다음 선택이 열린다. |
| 개발 결과 | EvidencePackage에 범위·제외·revision·무효화 조건을 남기고 현재 E와 차단을 인계한다. |

통합 관문은 두 궤적의 동일 revision 인계, 실제 입력 명령열, 결과 상태 재조회와 반환 상태를 함께 본다. 수치가 맞지만 화면에서 원인을 알 수 없거나 화면은 좋아졌지만 저장 후 결과가 사라지면 통과하지 않는다.

## Codex 착수와 종료 인계

### 착수 입력

1. 활성 `PlayableUnit` Goal과 플레이어 약속을 확인한다.
2. `activeMaturityTrackCode`와 두 궤적의 현재·목표 E를 확인한다.
3. 열린 피드백과 실제 선행 의존성으로 승인된 WI·하위 작업의 좁은 성립 단위를 고른다. 다른 독립 작업의 활성 여부나 개수만으로 차단하지 않는다.
4. E7↔E1 작업 명세에서 권위·H·저장·표현·검증 영향을 확인한다.
5. 기존 EvidencePackage의 제외와 무효화 조건을 확인한다.

작업 시작 문장은 다음 형식을 사용한다.

> `[loopStableId]`에서 `[Logic 또는 Presentation]`의 `[현재 E]→[목표 E]`를 위해 `[WI 또는 표현 책임 하나]`를 처리하고 `[귀환 상태]`까지 검증한다.

### 종료 출력

- 변경한 궤적과 실제 도달 E
- 권위 결과와 표현 결과가 참조한 revision
- 통과한 증거와 명시적으로 실행하지 않은 검증
- 열린 피드백의 원인·재개 궤적·E 단계·대상
- 다음 작업에 넘길 상태 사본·H 능력·WI·EvidencePackage
- Goal 닫힘 여부와 다음 Goal을 자동 활성화하지 않았다는 사실

Codex는 구현량이나 파일 수를 완료 기준으로 사용하지 않는다. 하나의 WI 또는 표현 책임을 끝낸 뒤 같은 폐루프의 결과·귀환 관문을 다시 판정한다.

## Nature 첫 적용 결과

2026-08-26의 첫 적용은 canonical `SimulationWorldShell`과 `area-set:sim:pyeongchang:nature-home.v1`에서 수행했다.

| 폐루프 | 논리 | 표현 | 통합 | 판정 |
| --- | --- | --- | --- | --- |
| 도끼·벌목·오두막 기초 | E6 | E6 | E6 | 명시적 장착 추가 뒤 실제 입력 재검증 필요 |
| 황혼 위협 대응·귀환 | E7 | E7 | E7 | `PlayClosed` |
| 보관·수면·Day2 반환 | E7 | E6 | E6 | 시각 상태 차이 보완 필요 |

첫 논리 재개 항목이었던 `WI-NATURE-18 벌목 통나무 줍기`는 r5부터 벌목 결과를 지면 통나무 상태로 남기고 플레이어가 별도 획득하도록 분리되었다. 이후 `WI-ACTOR-02` 명시적 장착이 추가되어 도끼·벌목·오두막 폐루프는 논리·표현 E6에서 현재 명령열을 다시 검증한다. Unity는 상태 사본을 표현할 뿐 수량·용량·성공 여부를 계산하지 않는다.

첫 표현 재개 항목은 Nature의 잘못된 공간 원점, Cube 오두막, 월드 통나무 부재, 작은 Skeleton, 큰 진단 HUD였다. Nature H 기준점과 Synty 시각 자료 묶음으로 정제한 뒤 오두막·벌목과 황혼 루프는 닫았다. 보관·수면·새벽과 작업대는 기능 실행을 확인했지만 상태별 공간 변화가 충분하지 않아 E6에 남겼다.

## Codex Goal 적용

장기 Goal은 `PlayableUnit` 하나만 소유한다. WI WIP의 고정 상한은 두지 않고 [Goal 운영 체계](CodexPlayableLoopGoal운영체계.md)의 `workItems`로 여러 WI와 비중첩 하위 작업의 담당·경로·실제 의존성을 관리한다. `activeMaturityTrackCode` 등 기존 대표 표시는 전체 실행 작업 목록이나 전역 잠금이 아니다.

- 논리 궤적에서 새 권위 상태가 필요하면 한 WI를 구현한다.
- 표현 궤적에서는 같은 WI의 상태 사본과 H 문맥만 읽는다.
- 표현 검증에서 계약 누락이 발견되면 Goal을 교체하지 않고 같은 폐루프의 논리 궤적을 다시 연다.
- 현재 Goal이 두 궤적 E7과 열린 피드백 없음에 도달하면 `Completed`로 바꾸고 다음 Goal을 자동 활성화하지 않는다.

## 금지 경계

- Unity 시각 객체를 Simulation 권위 상태로 사용하지 않는다.
- 화면이 예뻐졌다는 이유로 Save/Replay·Hosted 동등성을 생략하지 않는다.
- 단위 시험이 통과했다는 이유로 Game View 식별 가능성을 통과 처리하지 않는다.
- Synty Prefab 이름이나 장면 좌표를 H 의미 계약으로 간주하지 않는다.
- 큰 진단 HUD 문장을 실제 공간 표현의 대체물로 사용하지 않는다.
- 한 표현 실패를 이유로 관련 없는 폐루프나 다른 스레드 변경을 함께 되돌리지 않는다.
