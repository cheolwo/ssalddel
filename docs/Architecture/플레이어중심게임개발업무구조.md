# 플레이어 중심 게임 개발 업무 구조

## 목적

Ssalddel의 게임 작업은 기술 계층이나 자산 목록이 아니라 **플레이어가 세계 안에서 무엇을 보고, 왜 선택하고, 무엇을 모아 어떻게 조립하며, 결과로 다음 선택이 어떻게 달라지는가**에서 시작한다.

플레이어 중심은 상태 권위를 플레이어 또는 Unity `GameObject`에 준다는 뜻이 아니다. 플레이어는 의도를 선택하고, Simulation Core는 비용·조건·시간·결과와 공간 성장을 판정하며, Unity는 그 선택과 결과를 이해하고 조작할 수 있게 표현한다.

```text
개발 관점의 중심 = 플레이어의 선택과 체감
상태 판정의 중심 = Simulation Core의 권위 상태
공간 분류의 중심 = H1~H5 의미 계층과 형성 계보
완료 판정의 중심 = E1~E7 수직 폐루프와 E8~E10 수평 증거
```

기계 판독 기준은 [`player-centered-development-flow.json`](../../eng/execution-ledgers/player-centered-development-flow.json)이다.

## 여러 영역의 선택형 플레이와 개발을 함께 진행한다 (D416)

Nature·Farm·Town·Hub·City는 플레이어가 관심과 실제 조건에 따라 발견하고 활동을 선택할 수 있는 공간이다. 현재 문답에서 숲 가장자리와 농장을 구체화했다는 이유로 그 경로를 유일한 시작이나 모든 개발의 필수 선행으로 두지 않는다. [다영역 선택형 플레이와 병행 개발](../AI/다영역-선택형플레이와병행개발-2026-08-31.md)에 영역별 기존 기획·대표 경험·공통 모듈·첫 개발 인계 범위를 연결한다.

넓게 설계하되 구현은 기존 승인/Required Accepted 연구·명세·소유 경로가 준비된 작은 기능들을 비중첩으로 병행한다. 기획은 분야를 바꾸어 핵심 질문 하나씩 심화하고, 개발은 다른 분야의 미정 때문에 독립 작업을 멈추지 않는다. 여러 작업의 활성 수 자체를 상한이나 차단으로 삼지 않으며 공유 코드·계약·Editor는 소유와 단독 점유를 조율한다. 아직 구체화되지 않은 Town 양조나 City 업무를 문서 방향만으로 구현 완료·E 승격으로 올리지 않는다.

독립 영역 개발은 장기적인 한 세계의 조화를 포기하는 뜻이 아니다. 개별 WI의 선택→입력→결과→귀환과 영역 간 실제 이동/전이·공통 상태의 일관성은 별도 증거로 연결한다. 실제 운영 마트/도시 업무의 코드 재사용·게임 체험과 실제 주문/재고/배차/결제 효과는 구분하고 운영 권한·동의·실행 경계를 유지한다. 전 세계 겨울 폐지, 중지된 야간/r129 포괄 재개나 운영 서버 변경은 이 방향에 포함하지 않는다.

## 시점의 스케일로 직접 탐험과 운영을 연결한다 (D417·D418)

첫 플레이는 1인칭 직접 탐험을 권장하고, 운영할 일이 늘면 현장 전술 3인칭과 광역 전략 시점을 활용한다. [시점 역할과 WI 스케일 기획](../AI/탐험과운영-시점역할과현실업무연결-2026-08-31.md)이 상세 방향·기존 D134/D162/Q183~190/D237/D273과의 관계·코드 차이·미정을 소유한다. 현재 탐험3P는 D162와 일치하고 D417 최초1P는 후속 변경 방향이다. 첫 시점은 첫 지역을 강제하지 않으며 허용된 수동 전환과 전투 참여 잠금은 유지한다.

WI는 기존 고유 식별자를 유지한 채 **시점 공통·시점 특화·특정 시점 전용**을 구분한다. 공통과 특화는 함께 성립할 수 있으므로 허용 범위와 편의/입력을 별도로 기록한다. 시점별 전용은 승인된 이유와 전환/복귀 조건이 필요하며 미구현을 기획상 금지로 바꾸지 않는다. 지금·여기·나·너·이렇게의 같은 문맥에서 보는 범위·조작 단위를 설명하는 것이지, 새 여섯 번째 필수 조건 축이나 H 포함·권한·E 성숙도와 같은 스케일이 아니다.

시점별 판독·입력·자산/상태 연결과 실제 근거는 기존 WI/작업 명세의 표현 준비에 대응시킨다. 각 시점의 기능을 독립적으로 발전시키되 전환 시 같은 Session/Actor/진행 작업·입력 소유를 연결한다. 기존 E 판정은 유지하고 한 시점의 성공을 모든 시점 성공으로 확대하지 않는다. 발전 군집은 필수 선행/대안/병행을 구분하며 1P→전술→광역의 강제 해금이나 별도 경험치 체계를 만들지 않는다.

자동 전투와 탐색·이동·전리품/귀환까지의 자동사냥은 구별한다. 게임뿐 아니라 글로벌 현실 업무 보조의 장기 방향을 포함하지만 실제 인증·권한·동의·원장/실행 경계는 별도다. 게임의 자동 행동이나 넓은 카메라가 실제 업무 권한·발주/결제 실행을 만들지 않는다. 구체 코드·UI·명세/검증은 개발 담당에 인계하고 이 기획만으로 실제 화면/운영 연결을 완료했다고 하지 않는다.

### 원하는 작업에서 반복 집중으로 효율을 높인다 (D419~D421)

1인칭의 가까운 관찰·직접 입력을 살린 타이밍 수행은 [선택형 집중 기획](../AI/1인칭-선택형집중타이밍-기획보완-2026-08-31.md)을 단일 기준으로 삼는다. 원하는 작업에서 플레이어가 ‘집중해서 하기’를 선택한 경우에만 도전을 제시한다. 1인칭 진입이나 일반 작업 시작만으로 자동 표시하지 않으며 다른 시점의 기존 기능을 일괄 금지하지 않는다.

집중을 선택한 작업에서는 도끼질 같은 유효한 반복 동작에서 계속 도전하고, 미스해도 이후 동작의 기회를 닫지 않는다. 가능하면 매 동작을 선호하며 ‘세 번 중 한 번’은 고정 간격이 아니다. 성공은 실질적인 작업 진척/더 빠른 완료에 기여한다. Q398/D366의 기본 작업 추가 손실 없음·추가 명상 성장 방향을 보존하고, 정확 간격·효율 계산/상한·성장 배분·소모 변화는 후속으로 정한다. ‘작업당 한 번’은 미채택 추천이지 과거 확정 규칙이 아니다.

지금 진행 중인 반복 동작, 여기의 접근 조건, 나의 집중 선택, 너의 현재 작업 상태, 이렇게의 입력을 같은 WI의 결과·다음 동작에 연결한다. 정당한 새 시도와 동일 판정의 재전송을 구별하며 화면 반복/애니메이션 가속만으로 작업 진척·성장을 만들지 않는다. 구현은 기존 판정·작업/행위 기록·표현 준비를 재사용해 개발에 인계하고 새 집중 엔진/중복 WI·E축을 만들지 않는다.

## 시간·공간·플레이어·대상으로 WI를 설명한다 (D391)

기획 문답과 기존 기획의 재정리는 **시간, 공간, 나(플레이어), 대상**의 네 관점에서 시작한다. 네 관점은 행동이 놓이는 문맥이며, WI는 그 문맥 속 행위와 관계를 설명한다. 결과와 다음 선택까지 기존 플레이 폐루프로 연결한다. E/G/H를 대체하는 새 단계·점수·성숙도나 네 종류의 WI를 만드는 것이 아니다.

| 관점 | 기록할 내용 | 기존 연결과 주의 |
| --- | --- | --- |
| 시간 | 계절·절기와 지역 문맥, 가능한 때, 시작·진행·완료 조건, 경과·반복, 중단·재개, 기한과 결과가 지속되는 기간 | 절기는 활동을 계획하는 공통 시간 문맥이다(D399). 해당 규칙의 권위 시간·Task·판본을 참조한다. 현실 시간, 게임 일, 초, Tick, 표현 시간을 같은 단위로 추정하지 않는다. 미정 수치를 채워 넣지 않는다. |
| 공간 | 행동 가능한 위치와 범위, 접근·통행·거리, 지지·차폐·주변 조건, 진입과 귀환 | H1 역할과 H2/H3/AreaSet 포함 관계를 참조한다. 비공간 행동은 사유 있는 해당 없음으로 남기고 UI·소품마다 새 H1을 만들지 않는다. |
| 나 — 플레이어 | 욕구·목표, 알고 있는 정보와 모르는 정보, 능력·도구·자원, 권한, 선택·대가·위험, 직접 수행 또는 위임 | 플레이어의 선택과 실제 실행 Actor를 구분한다. NPC 위임은 플레이어의 순간이동·자동 성공이 아니며 기존 권한·명령 계약을 따른다. |
| 대상 — 상대·사물·환경 | 대상 식별과 현재 상태, 행동 가능한 성질, 필요한 도구·입력, 반응과 변화; 상대라면 의도·수요·관계·동의·거절 조건 | 한 WI에 여러 대상이 참여할 수 있다. 상대의 숨은 정보를 플레이어에게 자동 공개하지 않는다. 사물·환경에 인격이나 동의를 억지로 부여하지 않는다. |

이 체계에서 `너`와 `상대`는 사람만이 아니라 NPC·몬스터·집단, 사물·자원·시설, 환경·공간·생태를 포함하는 상호작용 대상이다. 다만 대상 종류별 상태 소유자는 다르며 사물·환경을 사람처럼 의인화하지 않는다. [게임 기획 통합 기준의 상위 목적](게임기획통합기준.md#나와-상대의-오행-순환이-회복을-높인다)에 따라 나와 대상의 필요한 오행 관계가 실제 WI 결과와 회복·귀환으로 이어질 때 관련 회복이 높아질 수 있다. 회복역량은 별도 근거가 있는 능력·여지이며 좋은 결과에 자동으로 따라 오르지 않는다. 이는 모든 대상에 같은 회복 수치를 추가하거나 광복기를 자동 확정하는 규칙이 아니다.

한 행동에 위임·간접 피해·공동체 효과가 있으면 `나`라는 말 하나로 모두 묶지 않는다. 관점 플레이어, 실제 실행 Actor, 직접 대상, 간접 영향 범위와 회복 판정 대상을 구분해 적는다. 예를 들어 플레이어가 NPC에게 도로 수리를 위임했다면 플레이어는 선택·권한의 주체이고 NPC는 실행 Actor이며 도로는 직접 대상, 통행자와 물류권은 영향 범위다. 수리 완료가 플레이어의 직접 노동이나 모든 주민의 개인 회복으로 자동 치환되지는 않는다. 세부 기여 관문은 [통합 기준의 행위자·대상·영향 범위](게임기획통합기준.md#한-결과의-행위자대상영향-범위를-분리한다)를 따른다.

핵심 플레이로 발전시키는 WI는 `나의 막힘`, `나의 회복 행동`, `상대에게 건넬 수 있는 기여 자원`, `상대의 실제 필요`, `권위 있는 상태 차이`, `환류`를 같은 기획 판본에서 추적한다. 이 연결을 아직 설명하지 못한 장면은 삭제하지 않고 관찰·분위기·정보 제공 같은 보조 층으로 남길 수 있지만, 핵심 진행이나 회복 기여로 자동 계산하지 않는다.

공간은 **어디서 어떤 배치 조건으로** 행동하는지, 환경 대상은 **무엇을 관찰하거나 바꾸는지**를 설명한다. 예를 들어 모닥불의 위치·벽 차폐는 공간 조건이고, 불의 연료·점화 상태는 대상 상태다. 동일 사실을 두 원장에 복제하지 않고 같은 원문·상태를 서로 참조한다.

WI 연결은 다음 순서로 정리한다.

1. 네 관점의 현재 조건, 나의 막힘과 상대의 관측 가능한 필요를 적는다.
2. 그 조건에서 가능한 회복 행동·선택을 기존 WI/보편 행위와 대응시킨다. 실제 WI ID가 없으면 후보 또는 미연결로 남긴다.
3. 비용·시간·대상 상태가 어떻게 바뀌는지, 무엇을 기여 자원으로 얻게 되는지와 거부·실패·중단 때 보존되거나 잃는 것을 기존 결정으로 설명한다. 직접 대상과 간접 영향 범위의 `개선 / 유지 / 손실 / 미확인`을 따로 적는다.
4. 권위 결과와 그 결과를 보여주는 표현·소리·UI를 구분한다. 화면을 열거나 자료를 읽는 행위 자체를 자동으로 권위 변화 WI로 등록하지 않는다.
5. 상대의 실제 필요에 기여 자원이 어떻게 적용됐고 어느 상태가 달라졌는지 확인한다. 적격 Profile과 권위 결과가 없으면 회복 기여로 승격하지 않는다.
6. 변화한 시간·공간·플레이어·대상 상태가 나와 공동체에 돌려주는 회복·귀환·다음 선택을 잇는다. 고정된 지역 이동이나 유일한 진행 순서를 강제하지 않는다.

| 쉬운 말 | 기존 관점 | 기획에서 묻는 것 |
| --- | --- | --- |
| 지금 | 시간성 | 어느 계절·절기에 놓여 있는가? 그 시기와 지역에서 무엇을 준비할 때인가? 현재 진행 상태와 기다림·중단 뒤에는 무엇이 달라지는가? |
| 여기 | 공간성 | 어떤 장소·범위·관계에 있는가? 어디까지 접근하고 무엇을 지지·차폐하며 어떻게 돌아오는가? |
| 나 | 플레이어 | 나는 무엇을 원하고 알고 있으며, 어떤 능력·자원·도구·권한으로 선택하는가? |
| 너 | 대상 | 내가 대하는 NPC·몬스터·약초·사물·환경은 무엇이며, 어떤 상태·성질·필요·반응을 가지는가? |
| 이렇게 | 행동·수행 방법 | 무엇을 어떻게 하는가? 어떤 입력·도구·자원·대가·위험·대안이 있는가? |

기획 문장의 기본형은 **“지금, 여기서, 나는 너를 대하며 이렇게 한다. 그 결과 상황이 달라지고 다음 선택이 열린다.”**다. 이것은 의무 행동 순서나 고정 시나리오가 아니라 기존 기획을 읽는 공통 문장 틀이다.

- ‘지금’은 계절·절기를 바탕으로 현재를 읽고 시작 전 조건·경과·기한·중단/재개·결과 지속도 함께 설명한다(D399). 절기와 개별 작업 진행률을 같은 것으로 보거나 현실 시계와 게임 권위 시간을 같다고 가정하지 않는다.
- ‘여기’는 플레이어 발밑 좌표에 한정하지 않고 실제로 선택·위임하는 장소와 대상 사이의 관계를 포함한다. 원격 접근 허용 여부는 기존 규칙을 따른다.
- ‘너’는 대상의 호칭이다. NPC의 주체성·거절 가능성을 없애거나 약초·환경을 의인화하는 새 규칙이 아니다. 자기 대상 행동은 ‘나 자신’으로 설명하고 가짜 외부 대상을 만들지 않는다.
- ‘이렇게’는 WI/행동과 수행 방법을 설명한다. 하지 않기·관찰·보류·위임·후퇴도 기록할 수 있다. 단순 화면 열기·읽기는 그 자체로 새 권위 변화 WI가 아니며, 등록된 WI와 보편 행위 후보를 구분한다.
- 기존 일곱 칸의 읽기 제목을 `지금(시간) / 여기(공간) / 나(플레이어) / 너(대상) / 이렇게(선택·WI) / 결과 / 다음 선택`으로 대응시킨다. 새 원장·검색 체계·상태 권위는 만들지 않는다.

#### 효·캠페인 진행 조건으로 읽는 법

효 또는 캠페인의 다음 사건을 여는 조건도 같은 다섯 칸으로 작성한다. 다섯 칸은 새 권위 체계가 아니라 사람이 읽는 기획 원문이며, 개발 인계에서는 기존 상태 사본·WI·공간 ID를 검사하는 조건으로 투영한다.

| 기획 조건 | 진행 관문에서 확인하는 것 | 개발 인계 표현 |
| --- | --- | --- |
| 지금 | 현재 괘·효, 절기·WorldTick 구간, 사건 완료 시점, 대기 시간·기한·재개 가능 시점 | 시간·진행 상태 조건 |
| 여기 | AreaSet, Graph Map 노드·엣지, H1~H4, 접근·귀환·통행·상호작용 범위 | 공간 조건과 발동 접점 |
| 나 | 이안 또는 실제 행위 주체의 생존·회복·위협·역량·권한·장착·소유 인벤토리 | 행위 주체 상태 조건 |
| 너 | NPC·몬스터·시설·작물·마차·창고 등 직접 대상의 존재·관계·손상·필요·보유 재고·수락 가능 상태 | 대상 상태 조건 |
| 이렇게 | 요구 WI, 행동 종류·횟수·정밀도·성공률, 행동 순서, 관찰·위임·직접 조작, 실제 ActionRecord, 비용 지불·도구 사용·중단·회복 방법 | 행동·상호작용·숙련 조건 |

`결과`는 위 조건을 만족한 뒤 현재 효가 실제로 무엇을 완료했는지, `다음 선택`은 어떤 효·캠페인·자유 생활이 열리는지를 기록한다. 모든 칸을 억지로 필수화하지 않고 `Required / AnyOf / Optional / NotApplicable(사유)`을 구분한다.

- 현실 시계가 아니라 Simulation의 절기·WorldTick·캠페인 상태를 `지금`의 권위로 사용한다.
- 플레이어 소유·장착·개인 인벤토리는 `나`, NPC·마차·창고·시설이 보유한 재고는 `너`에 기록한다.
- `여기`가 필수라면 AreaSet과 눈에 보이는 H1의 이중 결속을 기본으로 하며, H2~H4는 조합·지역 조건이 실제로 필요할 때만 추가한다.
- 단순 버튼 입력이나 Collider 진입은 `이렇게`의 완료가 아니다. 실제 WI·ActionRecord와 권위 상태 변화가 요구된 경우 이를 확인해야 한다.
- `이렇게`는 필요하면 `유효 수행 횟수 / 수행 품질 / 대상 범위 / 상황 난도 / 결과`로 정량화한다. 도끼를 50번 휘두른 사실과 나무의 유효 타격점에 정밀하게 맞힌 사실, 몬스터 50마리를 실제로 처치한 사실은 서로 다른 지표다.
- 횟수·품질 조건은 `StoryRequired / ReadinessRecommended / OptionalMastery`로 구분한다. 이야기의 인과에 필요한 최소 행동만 필수로 두고, 권장 숙련은 다음 효의 예상 난이도·도움·경고에 사용하며, 반복 숙련은 선택 보상이나 우회 해금에 사용한다.
- 예상 성장은 `유효 행동 × 기본 성장량 × 품질·난도 보정`의 범위로 계산하되, 같은 낮은 위험 행동의 무한 반복은 중복 판정·구간 상한·체감 보정으로 통제한다. 정확 수식과 수치는 분야별 성장 기획이 소유한다.
- 플레이 경로가 다를 수 있으므로 다음 효의 플레이어 수준은 단일 고정 레벨보다 `최소 / 예상 / 숙련` 구간으로 예측한다. 실제 진입 판정은 저장된 권위 값을 사용하고 예상 구간 자체를 권위 상태로 쓰지 않는다.
- 조건 미충족은 곧바로 실패가 아니다. 현재 효의 자유 생활·이동을 유지하고 부족한 `지금·여기·나·너·이렇게`를 사용자에게 보여 준다. 이미 진행 중인 시간 압박과 위협은 별도 규칙에 따라 계속될 수 있다.
- 기획에서 정한 다섯 조건은 개발 인계 때 `StoryStateGate / WorldStateGate / SpatialActivationTrigger / ActionRecordGate`로 투영할 수 있지만, 이 이름 자체로 새 코드·원장·Scene을 자동 생성하지 않는다.

### 공통 기획에서 공간 특화 절차를 조건부로 연다

기획은 먼저 지금·여기·나·너·이렇게와 결과·다음 선택, 주체·대상, 행동 전후의 상태와 플레이어가 읽을 피드백을 확정한다. 이 공통 기획은 좌표·Prefab·Blender 가공 방법을 미리 요구하지 않는다. 승인된 의미를 분야별로 판정한 뒤 **위치·거리·통행·시야·배치가 선택이나 결과에 영향을 주는 경우에만** 공간 특화 절차를 연다.

공간 영향은 다음 가운데 하나라도 해당할 때 `Required`다.

- 위치가 달라지면 선택 가능 여부나 결과가 달라진다.
- 출입구·길·경계·시야·접근·복귀 조건이 플레이에 필요하다.
- H1/H2 조합, 반복 인스턴스 또는 주변과의 이격이 필요하다.
- 후보 자산의 크기·높이·지지면·충돌이 행동 판정에 영향을 준다.
- 행동 전후 상태가 공간의 외형 변화로 판독되어야 한다.

공간 특화 흐름은 `승인 기획 판본 → Graph Map → 별도 배치 맵 → Synty 후보 → 필요한 경우에만 Blender 보완 → Unity 실제 결속`이다. [Graph Map 기획 인계 순환 체계](GraphMap기획인계순환체계.md)가 레벨 1 플레이 관계, 레벨 2 의미 제약, 레벨 3 코드·컴포넌트 결속과 별도 배치 맵의 책임을 소유한다. Graph Map 레벨 2는 지켜야 할 관계·제약을, 배치 맵은 특정 AreaSet에 적용한 H 인스턴스·상대 위치·방향·수량·시야·통로를 소유한다. Blender는 기존 Prefab과 Unity 조립만으로 필요한 상태 변화가 읽히지 않을 때만 프로젝트 소유 파생형을 준비하며 Synty 원본을 수정하지 않는다.

한 번의 기본 작업 단위는 `AreaSet 하나 + 대표 WI 하나 + 필요한 최소 H1/H2 묶음`이다. 자산 후보·Blender 결과·준비 배치는 Presentation E4 준비이며, 같은 기획·Graph Map·배치 맵·자산 판본을 실제 World·입력·WI 결과와 결속하기 전에는 E5가 아니다. 의미가 틀리면 기획, 관계가 틀리면 Graph Map, 간격·겹침·높이가 틀리면 배치 맵, 외형 판독이 틀리면 자산/Blender, 실제 입력·상태가 틀리면 Unity 또는 더 이른 논리 E로 반환한다.

단순 수치·대화·정책·목록·저장처럼 공간과 무관한 기획은 사유 있는 `NotApplicable`로 이 절차를 생략하고 필요한 논리·데이터·UI·Audio·서사 책임만 따른다. Graph Map·배치 맵·Blender를 모든 WI의 의무 통과 단계로 만들지 않는다.

#### 다섯 조건을 모델링·배치 표현 요구 카드로 내린다

공간 특화 절차가 `Required`인 효·WI는 승인된 `지금·여기·나·너·이렇게 → 결과·다음 선택`을 **표현 요구 카드** 한 장으로 투영한다. 이 카드는 새 자산 대장이나 상태 권위가 아니라, 기획·Graph Map·배치 맵·자산 후보·Unity가 같은 변화와 같은 H를 가리키는지 확인하는 인계 표지다.

| 기획 조건 | 모델링·배치에서 고정할 항목 |
| --- | --- |
| 지금 | 활성 절기·시간대·효 단계와 필요한 전·중·후 상태 변형, 상태가 나타나고 사라지는 시점 |
| 여기 | AreaSet, H1~H4 안정 ID, 배치 맵 인스턴스, 지지면·경계·통로·시야·이격·접근 면 |
| 나 | 행위 주체 모델, 장비·손 소켓·도달 범위·카메라 판독 방향. 실제 Rig·동작 전이는 E6 책임으로 분리 |
| 너 | 직접 대상의 모델 정체성, 손상·미관리·작업 중·완료 같은 필요한 상태 변형과 보존할 기능 |
| 이렇게 | `InteractionAnchor`, 접촉점·도구 접근 방향·작업 영역·상태 교체 신호와 수행 품질을 화면에서 읽을 단서 |
| 결과·다음 선택 | 완료 상태의 가시적 차이, 다음 상호작용 접점·귀환 동선·fallback 표현 |

표현 요구 카드에는 최소한 `ModelIdentity`, `RequiredStateVariants`, `StateTransitionEvidence`, `Scale/Pivot/Bounds`, `ColliderIntent`, `InteractionAnchor`, `PlacementSurface`, `Clearance/Sightline`, `Fallback`, 원천 후보와 파생형의 `revision/fingerprint`를 둔다. 정확 좌표나 Blender 제작법을 기획이 미리 결정하지는 않으며, 배치 맵과 자산 검토가 각자의 책임 안에서 채운다.

기존 Synty Prefab·Blender `.blend`·PNG·H 안정 ID·배치 시안은 삭제하거나 일괄 개명하지 않는다. 먼저 `ExistingCandidate` 또는 `LegacyCandidate`로 연결하고, 재사용 가능 여부를 판정한다. 새 파생 모델이 필요하면 원본을 수정하지 않고 원천 GUID·파생 이유·상태 변형·판본을 연결한다. 기존 후보가 현재 요구를 만족하지 못해도 이력에서 제거하지 않고 `SupersededForThisRequirement` 또는 열린 결함으로 남긴다.

결속 순서는 다음과 같다.

```text
승인된 효·WI의 다섯 조건
→ 표현 요구 카드
→ 기존 H·Synty·Blender 후보 대조
→ 상태 변형 결손 판정
→ Graph Map 의미 관계 + 배치 맵 실제 상대 배치
→ Presentation E4 후보 동결
→ E5 실제 Unity Prefab·World·Renderer·Collider·Bounds·WI 결속
→ 동작이 필요한 경우에만 E6 Rig·Animation·전이·중단·귀환 검증
```

Graph Map은 노드·엣지와 H의 의미·가능/불가능 관계를, 배치 맵은 특정 AreaSet에서의 인스턴스 위치·방향·수량·간격을, Blender는 필요한 외형·상태 파생 후보를, Unity E5는 실제 World 결속을 소유한다. 모델 이미지나 `.blend`가 준비된 사실만으로 배치 완료 또는 E5로 보지 않는다.

### 첫 인과 기록에서 기존 문답의 플레이 흐름을 이어간다 (D408)

사용자는 발견하며 알아가는 구도를 첫 인과 사례로 남기고 기존 Q/의미 후속을 지금·여기·나·너·이렇게와 결과·다음 선택으로 다시 정리하기를 원한다. 승인 의미와 첫 사례는 [첫 플레이 체감 문답의 인과 기록 01](PlayableLoops/PlanningSessions/첫플레이체감/first-play-experience.inquiry.r1.md#인과-기록-01--발견하며-알아가는-구도-d408)이 소유한다.

‘첫’은 함께 문서화한 첫 기록을 뜻하며 게임의 고정 시작 절기·좌표·튜토리얼 순서가 아니다. **단서를 판독함 → 관심에 따른 선택·행동 → 달라진 상황/정보 → 다음 선택**에서 가지를 이어 가고, 행동하지 않기·중단·돌아가기와 기존 선택권을 보존한다. 관찰로 더 알아보는 경험과 권위 지식/지도 해금·보상은 구별한다.

[전체 기획 이관](../AI/전체기획-네관점순환이관-2026-08-31.md)의 기존 단일 관계 입력·생성 조회를 재사용한다. 여러 질문이 한 WI/흐름을 설명할 수 있으며 Q 번호를 필수 선행 순서로 바꾸지 않는다. 이미 답한 조건·선택·대가·결과는 해당 원문을 연결하고, 새 의미가 필요한 부분만 문답한다. 기획 사례·원문 대조·코드·자산·실제 Unity 증거를 분리하고 부분 정리를 전체 이관/구현 완료로 보고하지 않는다. 기획은 의미를, 개발은 구조적 연결·검증과 상태 동기화를 맡는다.

### 절기를 공통 시간 문맥으로 사용한다 (D399)

문답의 ‘지금’은 단지 ‘작물이 막 성숙했다’ 같은 대상 상태에 그치지 않는다. **어느 계절·절기이며 무엇을 준비하고 선택할 시기인지**를 먼저 생각하고, 여기에 하루 중 때·날씨·작업 경과·기한을 필요한 만큼 결합한다. 사용자가 예로 든 하지·추분은 절기 문맥의 예이며 해당 절기에 특정 작물·상품이 반드시 대응한다는 결정은 아니다.

- **Farm:** 절기·지역·작물/작형을 함께 보고 파종·관리·수확을 계획한다. D400에 따라 적기를 조금 놓쳐도 위험을 감수한 파종 시도를 허용하고, 재배 중 비닐하우스 같은 시설로 조건을 보완해 수확할 기회를 열어 둔다. 시설 설치 자체가 즉시 성숙·수확 성공이나 모든 작물의 계절 무관 재배를 보장하지 않는다. 보호 범위·비용·효과·손실 회복은 개별 규칙을 정한다.
- **Nature(야생):** D400은 계절에 따라 만나는 몬스터의 종류와 같은 종류의 속성도 달라질 수 있게 한다. 기존 Q161/163/164의 종족 기본값·지역/계절/날씨/사건·관찰 지식 경계를 재사용한다. 출현 후보 변화와 기존 개체의 속성 변화는 구분하며, 절기 경계에서 모든 개체를 즉시 교체하거나 숨은 속성을 자동 공개하는 규칙을 뜻하지 않는다. Nature의 기존 의미와 공간 ID는 보존한다.
- **City:** 계절에 따른 상품 관심·수요 변화를 구매·판매 판단에 연결한다. 기존 Q258/259의 수요·공급·거리·위험과 예상 범위/신뢰도를 유지하며 절기별 확정 이익을 만들지 않는다.
- **Hub:** 관련 상품의 준비·입고 예정·실제 입고·출고를 구분해 절기와 함께 읽는다. 계절 수요만으로 재고·주문·입출고 완료를 생성하지 않는다. City와 Hub는 별개 영역이고 Farm→Hub→City를 필수 진행 순서로 만들지 않는다.
- **공통 책임:** 게임 달력/규칙은 Simulation, Sky는 해당 문맥의 낮밤·빛·날씨 표현, 달력·경제/현장 화면은 플레이어의 판독을 맡는다. 절기는 모든 실시간 작업을 대체하는 새 Tick 단위가 아니다. 기존 시간 계약·Save·성장 규칙은 별도 구현 결속 없이 바꾸지 않는다.
- **한국 24절기와 자료(D403):** 기획의 명칭·순서는 한국에서 쓰는 24절기를 기준으로 한다. 농수산물의 제철·파종/수확·어획/출하·월별 추천 자료는 기간 의미와 지역·품종/어종·방식을 구분하여 조사한다. [조사와 기획 연결 계획](../AI/24절기-제철자료-조사와기획연결-2026-08-31.md)에 따라 기존 자료조사 체계의 구조화 파일로 작은 표본부터 정리하며 원천 사실→검토한 절기 대응→게임 해석을 분리한다.
- **시간을 공간에서 읽는다(D405):** 산·나무·숲의 계절별 색감으로 ‘지금’을 ‘여기’에서도 알아볼 수 있게 한다. 기존 월드맵/지도구성·배치·LH와 Unity 표현, Sky의 협력은 [계절 경관 책임](지도구성과세계자산배치분리.md#절기별-산숲-표현과-세-공간-엔진의-협력--d405)을 따른다. 색감 변화는 새 산/나무 발생이나 수확·통행 규칙 변경이 아니며 수종·지역 차이와 기존 WI 대상의 판독성을 보존한다.
- **미정과 후속:** 게임 내 절기 길이, 현실 달력 동기화, 지역/기후 대응, 작물·상품별 수치와 예고 방식은 별도 검토한다. D403은 제한된 공식 자료 조사·정리를 허용한 것이며 운영 DB/Provider 실행·대량수집이나 현실 재배 일정의 게임 규칙 자동 적용 승인은 아니다.

기존 Q089·Q252·Q258·Q259·Q261·Q265와의 관계, 사용자 원문 요지와 다음 단일 질문은 [절기 기반 시간 문답](PlayableLoops/PlanningSessions/시간절기/seasonal-time-context.inquiry.r1.md)에 둔다. 이 방향은 앞선 수확 여유 질문의 답변을 대신하지 않는다.

### 같은 기획을 문서·코드·자산·Unity·결과로 왕복한다 (D395)

‘지금·여기·나·너·이렇게’를 문서의 말로만 남기지 않고, **같은 WI와 기획 판본**이 코드·자산 후보·실제 표현·검증 결과까지 이어지게 한다. 별도 제작 단계나 중복 관리 대장을 추가하지 않고 기존 Logic/Presentation E, 작업 명세와 문답·공간 색인을 재사용한다.

| 과정 | 같은 기획에서 연결할 산출물 | 담당·기존 책임 |
| --- | --- | --- |
| 문서로 정립 | 지금/여기/나/너의 조건, 이렇게(선택·WI), 대가·거부/실패·결과·다음 선택, 원문·미정 | 기획. 기존 문답·주제 기획·E1 계약과 연결 |
| 코드로 정립 | 기존 상태·명령·조회·Task·시간·권한 계약과 실제 코드 경로, 논리 결과를 표현이 읽는 연결, 시험 | 개발. 각 궤적의 E2/E3 및 기존 실행 결속 책임을 유지 |
| 보유 자산·Prefab 조사 | 어떤 조건·대상·상태 차이를 무엇으로 보여줄지, 후보 GUID·판본·외형/크기·필요한 Collider/Anchor·Actor라면 Rig/Clip, 재사용/보완/미검사 | 개발 조율→공간·애니 전문. E2 가벼운 목록 확인과 Presentation E4 적합성 준비 재사용 |
| Unity에서 검증 | 승인된 같은 상태와 후보를 연결하고 준비·적용·해제·재적용, 입력·결과 판독과 필요한 실제 화면을 확인 | 개발 통합, 공간이 View 캡처. E5 연결·E6 정제·E7 실제 플레이의 서로 다른 관문 유지 |
| 결과로 다시 문서화 | 계획한 조건과 관측 조건, 실제 결과, 검증 종류·판본·근거, 남은 결함·책임·다음 선택을 기존 보고/명세/색인에 환류 | 전문→개발 검토·통합→기획. 해당 책임의 가장 이른 미완료 지점으로 돌아감 |

이 표는 한 번만 순서대로 지나가는 절차가 아니다. 자산 적합성은 코드 작성 전에도 확인하고 독립된 준비는 병행한다. 상태 공급 결손은 코드/계약으로, 외형·접촉·통행 결함은 표현 연구/조립으로, 선택·대가의 모순은 기획으로 돌려보낸다. 같은 실패를 같은 입력으로 반복하지 않고 새 근거와 변경점을 남긴다.

한 번의 인계에서 같은 `질문/의미 ID → 기획 판본 → WI/대상 → H/후보 → 코드/시험 → Unity 근거 → 결과/다음 선택`을 찾아갈 수 있게 한다. 항목이 해당 없거나 아직 없다면 사유·미연결을 명시하고 가짜 ID·상태·이미지로 채우지 않는다. 코드 경로와 시험 수만으로 실제 입력 성공을 대체하지 않으며, 자산 미리보기·격리 조립·실제 Game View의 근거 종류도 구분한다.

결과 보고도 같은 말로 읽는다. **어떤 지금·여기·나·너에서 이렇게 했고, 무엇이 실제로 달라졌으며, 다음에 무엇을 할 수 있는가**를 계획과 비교한다. 시간 관측은 직접 참여·기다림·병행 가능 구간·중단점을 구분하며 병행 시간을 중복 합산하거나 새 소요 시간 규칙으로 확정하지 않는다.

기존 전체 기획 이관(D392)은 계속 우선한다. 우선 이 구조의 연결과 누락을 정리하고, 개별 실제 구현·Unity 검증은 해당 주제의 기존 승인·필수 연구·작업 명세·정확 경로와 대상이 준비된 범위부터 개발이 배분한다. 모든 문서/이미지를 완성해야 한 WI도 검증할 수 있다는 전역 선행 조건은 만들지 않는다. 반대로 이 절만으로 모든 기능의 실제 실행·Scene 수리·가공을 일괄 재개하지 않는다.

기획은 기준·선택·결과 해석을, 개발은 코드·시험·명세/색인 연결과 최종 통합을, 공간은 배치·View 근거를, 애니메이션은 동작·Rig·접촉 근거를 소유한다. 필요 근거가 달라지는 개별 작업에서는 기존 소유권과 Editor 단독 점유를 먼저 조율한다. 원본/미소유 변경·승인hash·실행 권위·E 상한과 기존 중지 경계를 유지한다.

### E6까지의 주력 정밀화 절차 — D446·D447

지금·여기·나·너·이렇게로 정리한 WI를 E6까지 준비·입증할 때는 [E6 준비·입증의 공식 주력 절차](플레이폐루프논리시각이중순환체계.md#e6-focused-workflow)를 따른다. 작은 플레이 맥락을 그래프 맵의 레벨 1 관계와 레벨 2 자산·배치 규칙, 코드/시험·E5 실제 연결, E6 플레이 전 정제와 필요한 공공·현실 근거에 이어 검토하고 결과를 같은 기획에 환류한다. 공간·자료와 무관한 항목은 사유를 남겨 제외하고, 전체 맵 완성이나 모든 자료 수집을 개별 WI의 선행 조건으로 만들지 않는다.

승인된 기획 판본이 Graph Map에 영향을 주면 [Graph Map 기획 인계 순환 체계](GraphMap기획인계순환체계.md)로 넘긴다. 기획은 일곱 칸과 플레이어 약속·결정·WI·변경 의도까지만 소유하며, Graph Map 담당이 기존 안정 ID를 대조해 레벨 1 플레이 관계·레벨 2 배치 제약·레벨 3 코드 결속을 반영하고 최종 상태를 반환한다. 기획 스레드는 중간 구현을 기다리지 않고 다음 단일 질문을 이어가며, 반환된 플레이 선택 차단만 다음 질문으로 삼는다.

공식 절차는 D447에서 E6까지 확장했다. E5 성립과 E6 정제의 실제 증거는 분리하며 문서·그래프 검사·DB 자료 존재만으로 합격을 선언하지 않는다. 개별 승인·명세 상한과 중지 경계는 그대로 확인하고 E7 실행으로 자동 확대하지 않는다. 상세 절차는 위 기준 문서에만 둔다.

### 기획 판단의 로컬 관계형 저장 — D439

지금·여기·나·너·이렇게와 결과·다음 선택을 정리한 문서에서 기존 WI 사용 판단·객체 참여·자산 역할을 명시하고 [기획 문서 → 로컬 관계형 DB 파이프라인](기획판본-서버반입파이프라인.md)으로 이어간다. Codex가 의미를 정리하고 기존 ASP.NET Core 저장 기능은 판본·관계를 검증하여 MySQL에 보존한다. 같은 로컬 환경에서 HTTP/API를 필수로 두지 않는다. 첫 구현은 기존 WI/객체 참여만 지원하며 미지원 관계·실제 저장 여부는 별도로 표시한다.

### 기존 기획의 재정리 원칙

- 승인된 답변·기획·연구·작업 명세를 조용히 재작성하지 않는다. 첫 정리는 원문 Q/의미 ID·경로·위치·판본을 가리키는 대응표이며, 승인 의미가 달라지는 변경은 별도 판본과 승인으로 처리한다.
- 각 내용은 기존 확정 / 미정 / 해석 제안 / 해당 없음 / 근거 미확인으로 구분한다. 공간 후보·구현 E·실제 캡처 여부는 결정 상태와 별도다. 빈 칸을 추정으로 채워 완성으로 표시하지 않는다.
- 기존 주제 기획의 필수 절, WI 계약, 문답 ID, H 고유 식별자와 검색 체계를 재사용한다. 모든 과거 문서에 새 필수 필드를 일괄 추가하거나 새 DB·중복 원장을 만들지 않는다.
- 우선 Farm 재배·집하, 약초 제작·재가열, 방문자 상호작용, 방위·후퇴, 거래·상환처럼 서로 다른 활동을 대응시켜 편중을 피한다. 일부 재정리 완료를 전체 문답 검토 완료라고 하지 않는다.
- 기획은 의미·미정·질문과 원문 재구성, 개발은 연결의 정확성·색인/도구·회귀·기술 통합, 전문 담당은 지정된 자산·공간·동작 근거를 맡는다. 새 문답은 누락된 관점 중 플레이어 선택에 영향을 주는 것부터 묻고 기술 구현 선택은 개발에 넘긴다.

적용 순서와 첫 대응 예시는 [시간·공간·플레이어·대상 WI 기획 정리](../AI/시간공간플레이어대상-WI기획정리-2026-08-31.md)를 따른다. 이 절이 공통 관점의 기준이며 개별 규칙은 해당 문답·기획 원문이 계속 소유한다.

### 문답의 발전 가능성을 군집·테크트리로 연결한다 (D402)

지금·여기·나·너·이렇게에서 드러난 발전 수단은 관련 기능 군집으로 조회하고, 실제 선행·선택 대안·병행 보완 관계를 구분한다. 세부 기준과 사용자 승인 원문은 [문답 기반 발전 군집과 테크트리](../AI/문답기반-발전군집과테크트리-2026-08-31.md)에 둔다. 기존 건물 테크트리·WI·지식/공간 참조를 재사용하며 모든 스펙트럼을 고정 선행 경로로 만들지 않는다.

플레이어에게 큰 발전 방향은 먼저 보여주고 구체 내용은 발견·학습에 따라 드러낸다. 화면 공개와 실제 학습·해금·사용, 개발 Evidence 단계는 별개다. 이 방향만으로 새 비용·자격·노드/원장·UI·Scene을 구현하거나 미발견 세부 정보를 모두 공개하지 않는다.

## 자리이타 — 나를 위한 활동이 타인의 이로움으로 이어지는 기획

플레이어가 자신의 생존·회복·성장을 위해 익힌 행동이, 필요한 상대를 만나면서 타인에게도 도움이 되는 방향으로 자연스럽게 확장되도록 기획한다(D-330). 자기 이익과 타인의 이익을 별도 강제 임무로 갈라 놓지 않는다.

- 첫 폐루프는 혼자서도 자기 문제를 해결하고 돌아올 수 있어야 한다. 이후 축적한 기술·물품·여유와 상대의 필요가 만날 때 공급·교류·협력의 선택이 열린다.
- 예: 나를 위한 약초차 준비 → 약초를 다루는 경험 → 포션 제작의 후속 발전 → 필요한 NPC나 공동체의 수요 발견 → 선택한 공급·협력. 이 예시는 고정 해금 순서나 강제 지역 이동 경로가 아니다.
- 타인을 돕는 일을 무상 기부로만 한정하지 않는다. 정당한 대가를 받는 거래도 자신과 상대에게 함께 이로울 수 있다. 수량·가격·보상·관계 변화는 해당 규칙에서 별도로 정한다.
- 플레이어의 물품을 자동 기부·납품하거나, 도움을 선택하지 않았다고 도덕 점수·내면 위협 페널티를 임의 부과하지 않는다. 단독 생존·탐험 선택과 기존 의무 수락 규칙은 유지한다.
- 플레이어가 실제로 도움을 주기로 선택했다면 누구의 어떤 필요가 충족됐는지 결과로 판독할 수 있게 설계한다. 단순 판매 횟수나 일률적 버프만으로 이 기획 의도를 대신하지 않는다.
- 후속 문답에서는 ‘자신에게 필요한 이유’, ‘다른 사람에게 도움이 될 수 있는 연결’, ‘자발적 선택과 대가’, ‘실제 상대의 변화’를 살핀다. 모든 WI에 타인 참여를 의무화하거나 새 E/WI 계층을 만들지는 않는다.

이는 게임 기획 방향이다. 도움에 따른 회복·위협·관계·경제 효과의 구체 판정과 수치를 자동 승인하지 않으며, 실제 결과는 기존 Simulation 권위와 증거 체계로 검증한다.

## 현실에 닿는 운영 경험 (D369)

사용자는 구매·물류 대행, 자원 공급, 제조와 상단 운영을 즐기며 현실과 연결되는 판단 경험이 남기를 원한다. 플레이 기획은 상대의 수요, 선택 가능한 조달/제조/위임, 자원·시간·비용·위험, 결과와 다음 선택 사이의 인과를 읽을 수 있게 한다. 세부 답변은 [생존경제 Q401](PlayableLoops/PlanningSessions/생존경제/survival-economy.inquiry.r1.md#q-401-현실에-닿는-운영-경험과-게임의-재미)이 소유한다.

현실성을 실제 업무의 모든 절차나 서류 작업을 반복시키는 것으로 해석하지 않는다. 기존 NPC 위임과 선택형 상세 정보를 유지하고 학습을 강제하지 않는다. 현실 자료·게임 해석·가상 규칙을 구분하며 현실 사업 성과나 능력 향상을 보장하지 않는다. 이 원칙은 새 보상·실패 페널티·실행 WI·E 승격을 자동 승인하지 않는다.

## 세 활동 경로는 역할이나 모드가 아니다

플레이어의 기회는 이해를 돕기 위해 `현장 원정(FieldExpedition)`, `영역 운영(AreaOperation)`, `영역 제조·건설(AreaManufacturing)`의 세 경로로 분류한다. 이 값은 플레이어 직업이나 영구 모드가 아니며 역할 전환 API도 만들지 않는다. 같은 플레이어가 상황에 따라 세 경로를 왕복한다.

| 활동 경로 | 플레이어가 하는 일 | 첫 Nature 기준선 |
| --- | --- | --- |
| 현장 원정 | 영역 밖의 자원·위협에 직접 개입하고 결과를 가지고 돌아온다. | 벌목, 황혼 조우, 승리·후퇴·패배 |
| 영역 운영 | 재고·위험·우선순위를 읽고 다음 행동을 고른다. | 거점 보관, 수면, 다음 확장 선택 |
| 영역 제조·건설 | H1 작업 장소에서 재료를 기능·건물·보급품으로 바꾼다. | 작업대 건설, `WI-NATURE-16` 현장 보급 제작 |

세 경로는 서로 결과를 공급하지만 강제 잠금 고리는 만들지 않는다. 현장 성과는 거점 제조의 재료가 되고 거점 제조는 다음 원정의 선택과 위험을 바꾼다. 다만 건물 발전이 늦어져도 기본 원정·후퇴·회복은 항상 가능해야 한다. 카드나 원격 목록은 우선순위와 상태를 보여줄 수 있지만 H1 제작·건설을 원격으로 대신 확정하지 않는다.

운영 서버에서 유래한 반복 업무 WI는 플레이어가 실무 단계마다 버튼을 눌러 완료하는 네 번째 활동 경로로 만들지 않는다. `NpcRoutine`에서는 NPC가 업무를 수행하고 플레이어는 자동화·우선순위·담당자·차단 해소를 선택한다. Farm처럼 직접 작업 자체가 플레이 경험인 WI는 `PlayerOrNpc`로 남긴다. 세부 기준은 [NPC 루틴 WI 통제 정책](NPC루틴WI통제정책.md)이 소유한다.

## 발산(陽)·수렴(陰)은 행동 목적의 순환이다

세 활동 경로 위에는 행위자 선택의 방향을 설명하는 `발산 흐름(陽)`과 `수렴 흐름(陰)`을 둔다. 이 값은 장소·직업·성별·선악·이익/불이익이 아니며 Player 또는 NPC가 수행하는 행동의 목적에 귀속된다. 같은 AreaSet 안에서도 두 흐름이 모두 존재할 수 있다. 사람이 읽는 `++`·`+-`·`-+`·`--` 표기는 [WI 음양·수행주체 사분면 체계](WI음양수행주체사분면체계.md)가 소유한다.

| 흐름 | 플레이어 관점 | 대표 행동 |
| --- | --- | --- |
| 발산 `Outward` | 세계의 위협과 기회에 직접 개입하고 결과를 가지고 돌아온다. | 탐사, 채집, 전투, 구조, 현장 위기 대응 |
| 수렴 `Inward` | 확보한 상태를 읽고 정책·우선순위·NPC 위임·회복을 결정한다. | 재고 검토, 업무 위임, 시설 우선순위, 휴식과 재정비 |
| 순환 연결부 `TransformationBridge` | 발산 성과와 수렴 계획을 재료·시설·보급품으로 변환한다. | 제조, 건설, 정비, 보급 준비 |

`FieldExpedition`은 주로 발산, `AreaOperation`은 주로 수렴이며 `AreaManufacturing`은 두 흐름 사이의 순환 연결부다. 이는 고정 일대일 매핑이 아니다. `ObserverOperation`과 `DirectAction`도 입력 강도는 다르지만 외부 위협에 대응한다는 목적에서는 같은 발산 흐름이다. Player가 정책과 위임을 정하는 선택과 NPC가 실제 작업하는 실행은 서로 다른 인스턴스 문맥이며 WI 발생원·실제 Actor·음양 목적을 각각 기록한다.

조화는 50:50 수치나 버프가 아니라 **발산 결과가 수렴 선택으로 인계되고, 수렴 결과가 다음 발산 선택을 실제로 바꾸는 폐루프**로 판정한다. 어느 한 흐름을 적게 이용했다고 불이익을 주거나 강제로 교대시키지 않는다. 카드에는 현재 선택과 인계 방향을 설명할 수 있지만 메이저 아르카나 방향·배율의 새 판정 근거로 사용하지 않는다.

첫 왕복 기준선은 `현장 승리의 재건 부품 → WI-NATURE-13 보관 → 운영 작업대 → WI-NATURE-16 직접 제작 또는 WI-NATURE-17 NPC 위임 제작 → 다음 WI-NATURE-06에서 꾸러미 선택 → 패배 시 소지 재료 한 단위 보호 → 귀환`이다. NPC가 없거나 정책이 꺼져도 직접 제작과 기본 원정은 계속 가능하다. 현재 재고는 별도 Lot 원장보다 아이템 스택이 먼저 존재하므로 r4는 결정적으로 정렬한 소지 재료 스택 하나를 보호한다. 진짜 다중 Lot이 도입되면 기존 결과를 바꾸지 않는 새 판본으로 확장한다.

## 주체가 폐루프보다 먼저다

플레이어 관점으로 기획하더라도 개발 단위는 먼저 주체를 확립한다. Actor와 직접 대상의 역할·권위·초기 상태 해석·저장 정체성이 준비된 뒤 두 주체 사이의 WI 하나를 Goal로 선택한다. 직접 결과를 먼저 닫고 주변 영향은 파생 작용으로 분리한다. 상세 관문은 [주체·상호작용 중심 개발 체계](주체상호작용중심개발체계.md)를 따른다.

아래 선택 흐름은 모든 WI가 별도 PlayableLoop 객체를 반드시 가져야 한다는 뜻이 아니다. 단일 WI의 결과와 귀환 또는 다음 선택이 자체적으로 닫히면 WI Goal만으로 E1~E7을 진행한다. 둘 이상의 WI를 성공·실패·회복·귀환의 반복 경험으로 함께 검증할 필요가 있을 때만 PlayableLoop를 선택적 묶음으로 연결한다.

## 플레이어 선택 폐루프

모든 의미 있는 게임 작업은 아래 흐름 중 자신이 담당하는 구간과 닫지 않는 구간을 적는다.

```text
상황을 본다
  → 욕구·목표를 이해한다
  → 가능한 선택과 대가·위험을 비교한다
  → 재료·도구·장소를 찾고 모은다
  → 배치·조합 결과를 Preview한다
  → 명시적으로 Confirm한다
  → 이동·작업·전투·시간을 통과한다
  → 세계와 공간의 권위 있는 결과를 확인한다
  → 회복·귀환 또는 달라진 다음 선택으로 이어진다
```

UI, 카드, 건물 Prefab, 자원 수치나 서버 API 하나만으로는 플레이 단위가 닫히지 않는다. 플레이어가 선택의 이유와 대가, 결과와 다음 가능성을 화면과 세계 안에서 이해할 수 있어야 한다.

## E1~E7 수직 폐루프와 E8~E10 수평 증거를 플레이어 관점에서 검토한다

E 단계 정의와 완료 관문은 바꾸지 않는다. 다만 모든 단계에서 최종적으로 어떤 플레이어 선택을 성립시키는지 추적한다.

| E | 기존 증거 책임 | 플레이어 중심 검토 질문 |
| --- | --- | --- |
| E1 | 목적·계약·StableId | 플레이어가 왜 이 행동을 하며 어떤 선택과 결과를 약속받는가? |
| E2 | 실행 가능한 Core·계약·Adapter | 플레이어 의도가 권위 경계로 들어가고 결과 상태 사본으로 돌아오는가? |
| E3 | 결정성·시험·Save/Replay | 같은 선택·비용·시간이 같은 결과로 재현되고 저장 뒤에도 이어지는가? |
| E4 | WI 실행 문맥 결속 | 선택한 행동의 허용 발생원·주체·대상·자료·자원·시간과 필요한 경우 H 공간 문맥이 결속됐는가? |
| E5 | WI 세계 발현 | 선택이 권위 전이·Task/Effect·결과·후속 선택을 가진 결정적 세계 변화로 실제 발현되는가? |
| E6 | 세계 정제·필요 근거 | WI 폐루프의 장소·원인·피드백·귀환이 이해되며 필요한 현실 문맥의 한계가 드러나는가? |
| E7 | 실제 플레이 실행 | 저장된 `SimulationWorldShell`에서 실제 입력으로 선택 폐루프를 끝낼 수 있는가? |
| E8 | 개별 폐루프 안정 | 같은 PlayableUnit이 반복 실행·저장 재진입·Local/Remote·실제 입력에서도 같은 결과와 다음 선택을 유지하는가? |
| E9 | 영역 조화·사람 승인 | 같은 영역의 안정된 Core 둘 이상이 조화를 이루고 사람이 대표 순서로 직접 플레이했을 때 재미·몰입·완성도가 승인 기준을 넘는가? |
| E10 | 제한 운영 검증 | 승인된 불변 후보가 관찰창 동안 안전하게 지속되고 사람이 계속 운영을 승인했는가? |

이 표는 `E1=기획`, `E7=플레이어`처럼 앞 단계를 플레이어와 무관한 기술 작업으로 두지 않기 위한 검토 렌즈다. E7 이전에 Game View 증거를 요구하거나 E1 문서만으로 플레이 가능성을 주장하는 규칙도 아니다.

## 보편 WI에서 구체 WI로 특화한다

여러 영역에서 반복되는 행위는 도구별 WI를 먼저 늘리지 않고, 행위자가 무엇을 바꾸는지에 따라 보편 WI 계약을 먼저 둔다. 구체 WI는 보편 계약의 권위 전이를 재사용하면서 장소·대상·비용·시간·피드백만 특화한다.

```text
WI-ACTOR-01 물품 획득
  ├─ WI-NATURE-05 벌목 도끼 확보
  ├─ 후속 삽 획득
  └─ 후속 곡괭이 획득

WI-ACTOR-02 장착 상태 변경
  ├─ MainHand 도끼 장착 → capability:woodcutting
  ├─ MainHand 삽 장착 → capability:terrain-grading
  └─ MainHand 곡괭이 장착 → capability:mining
```

`WI-ACTOR-01`은 세계에 놓인 고유 물품 인스턴스를 인벤토리로 이전한다. `WI-ACTOR-02`는 소유한 인스턴스의 `Equip`, `Unequip`, `Swap`을 처리한다. 획득만으로 도구 능력을 주지 않으며 능력은 장착 완료 상태에서 파생한다. 첫 슬롯은 `MainHand`, `OffHand`, `Head`, `Body`, `Legs`, `Feet`, `Back`, `Accessory`로 고정한다.

보편 WI가 공간 의미를 갖지 않으면 H 근거를 억지로 붙이지 않는다. 도끼가 실제 어디에 놓이고 얼마나 가까이 가야 하는지는 `WI-NATURE-05` 같은 특화 WI와 H 결속이 소유한다. 반대로 상태창을 여는 읽기 전용 입력은 세계 상태를 바꾸지 않으므로 WI가 아니다.

역할 카드 장착 `WI-WORLD-06`과 전투 편성은 같은 장착 어휘를 사용해도 물리 물품 인스턴스·슬롯 원장과 합치지 않는다. 공개 ID와 저장 의미를 유지한 채 공통 Preview·Confirm 리듬만 공유한다.

첫 구현 계보는 `simulation-save.v27`이 물품 인스턴스, 8개 슬롯, 장착 개정과 파생 능력을 저장한다. v1~v26의 기존 hash와 자동 장착 의미는 호환 경계로 보존한다. 지형 평탄화 `WI-WORLD-09`는 삽 획득·장착을 실제 `SimulationWorldShell` 입력으로 검증한 뒤 여는 후속 작업이며 이번 보편 장착 WI의 완료 증거에 포함하지 않는다. 당시 예약했던 `simulation-save.v28` 번호는 D-267에서 행위 원장·분야 Profile wrapper에 사용했으므로 지형 평탄화 저장은 다음 가용 판본을 사용한다.

## H1~H5와 플레이어 조립

플레이어는 공간 깊이 이름을 직접 만드는 것이 아니라 세계 안의 구체적인 재료와 행동을 선택한다.

| H | 플레이어 관계 | 권위 판정 |
| --- | --- | --- |
| H1 작업공간 | 오두막·작업대·밭·울타리처럼 직접 배치·복구·연결할 수 있다. | Preview·Confirm, 비용, 배치 규칙과 공간 인스턴스 계보를 검사한다. |
| H2 블록 | 원하는 생활핵·생산핵을 목표로 필요한 H1과 연결 방식을 선택한다. | 필요한 H1·연결구·용량·안전 조건이 모였는지 세계가 성장 판정한다. |
| H3 경관 | 여러 H2 사이의 채집·생산·위협·회복 폐루프를 반복하며 방향을 만든다. | 이동·반환·인과 폐루프가 유지되는지 세계가 성장 판정한다. |
| H4 AreaSet | 기존 지역 안을 변화시키고 다음 지역을 발견·이동한다. | 현재 단계에서는 플레이어가 지역 계약 자체를 임의 생성하지 않는다. |
| H5 세계 배치 | 영역 사이의 관계와 변화를 경험하고 선택한다. | 세계 배치·회랑·전이 계약은 작성·승격·호환 절차가 소유한다. |

따라서 플레이어는 H2·H3의 성장을 **의도하고 유도**할 수 있지만, H1 하나를 놓은 즉시 임의로 H3라고 이름 붙이지 않는다. LH가 준비한 `LhComposed`, 플레이어가 만든 `PlayerComposed`, 둘이 누적된 `HybridEvolving` 형성 방식도 H 깊이와 별도로 기록한다.

## 재료·조립·표현을 분리한다

“플레이어가 재료로 집을 만든다”는 한 문장 안에는 서로 다른 상태가 있다.

```text
세계 자원·Lot
  → 획득·운반·보관
  → 조립법과 필요 비용
  → 배치 후보와 Preview
  → Confirm·예약·Task·시간
  → H1 공간 인스턴스
  → H2/H3 성장 판정
  → Synty 자산을 사용한 Unity 표현
```

| 개념 | 의미 | 권위 |
| --- | --- | --- |
| 세계 자원·Lot | 나무·돌·작물처럼 획득·소비·이동하는 상태 | Simulation 재고·세계 상태 |
| 조립법·비용 | 어떤 자원·도구·시간·장소가 필요한지 정한 규칙 | Simulation 규칙·계약 |
| 배치 후보 | 현재 장소에서 가능한 형상·회전·연결의 미확정 결과 | Preview, 상태 변경 없음 |
| H1 공간 인스턴스 | Confirm과 작업 완료로 성립한 실제 작업공간 | Simulation 공간 상태·계보 |
| H2/H3 성장 | H1 집합과 폐루프가 상위 공간 조건을 충족한 결과 | Simulation·H 검증 규칙 |
| 시각 자산 | Synty Prefab·재질·애니메이션 등 보이는 표현 | Unity Presentation |

Synty Prefab을 Scene에 놓는 일은 자원을 소비하거나 H1을 성립시키지 않는다. 반대로 서버 상태에 H1이 생겼어도 플레이어가 필요한 재료, 진행 시간과 결과를 화면에서 이해하지 못하면 플레이 경험은 아직 닫히지 않았다.

## Operations·Simulation·Unity 책임

플레이어 관점에서 Operations는 실제 자료와 외부 효과의 사용 가능성, Simulation은 선택 조건·비용·시간·세계 결과, Unity는 발견·비교·조작·피드백, Integration은 Local·Hosted와 생산자·소비자 사이의 같은 의미를 묻는다. 세부 소유 범위와 브랜치·검증 routing은 [운영·Simulation·Unity 작업 흐름 분리](OperationsSimulationUnity작업흐름분리.md)가 소유한다.

Solo에서는 Unity 프로세스 안의 `LocalSimulationRuntime`, Hosted에서는 `Simulation.Server`가 같은 Simulation Core를 실행한다. 실행 위치가 달라져도 플레이어 선택의 계약과 결과 의미는 갈라지지 않는다. 이 문서는 그 선택을 검토하는 관점만 소유하며 기술 책임표를 중복 소유하지 않는다.

## 업무 순서

실제 작업 선택·E7→E1 분해·가장 낮은 미완료 의존성 구현·E1→E7 증거 갱신 순서는 [게임 개발 업무 순서 기준](게임개발업무순서기준.md)이 소유한다. E7 이후의 영역 조화·사람 플레이테스트·제한 운영은 [E1~E7 수직 폐루프와 E8~E10 수평 증거 체계](E1-E7수직폐루프와E8-E10수평증거체계.md)가 소유한다. 여러 WI의 시작·성공·실패·회복·귀환을 공식 판정 단위로 등록하고 실제 증거의 범위와 무효화 조건을 기록하는 형식은 [플레이 폐루프와 증거 묶음 개발 체계](플레이폐루프와증거묶음개발체계.md)가 소유한다.

## 완료 판정

다음 질문에 답하지 못하면 구현 파일이나 자산이 있어도 플레이어 중심 작업은 아직 닫히지 않았다.

- 플레이어가 현재 상황과 선택 이유를 알 수 있는가?
- 선택 후보 사이의 재료·비용·시간·위험 차이를 알 수 있는가?
- 필요한 것을 직접 찾고 모으고 운반하거나 배정할 수 있는가?
- Preview와 Confirm의 차이를 알 수 있는가?
- 행동 결과가 재고·공간·세계 상태에 권위 있게 남는가?
- H2·H3 성장이 단순 이름이 아니라 H1 집합과 플레이 폐루프로 판정되는가?
- 성공·실패·중단·회복의 피드백을 이해할 수 있는가?
- 결과가 귀환 또는 의미 있는 다음 선택을 여는가?
- Save/Replay와 Solo·Hosted에서 같은 선택 의미가 유지되는가?
- 주장한 E 단계의 실제 완료 관문을 별도로 통과했는가?

이 기준은 E·G·H·WI를 새 축으로 대체하지 않는다. 이미 있는 체계를 플레이어의 선택과 세계 변화로 끝까지 연결하기 위한 공통 업무 관점이다.
